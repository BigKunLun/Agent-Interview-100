中级 · Planning & Reasoning · 可交互讲解

先定计划，
再按变化改计划。

Plan-and-Solve 把“理解问题、制定计划、逐步执行”写进 Prompt；Plan-and-Execute 把规划和执行拆成两个角色。计划不可能一次做对，重规划负责在失败后只改该改的部分。

边界：PS / PS+ 是零样本 Prompting，不是 Agent 架构；重规划不是从头再来，而是保留已完成进度、最小修改剩余计划。原文基准数字为 text-davinci-003 口径，属原文版本、未联网核实。

一 · Plan-and-Solve

先理解，
再列计划，再执行。

PS 是 Wang et al.（2023，ACL）提出的零样本 Prompting 策略。它针对 Zero-shot CoT 的三类问题：遗漏步骤、计算错误、语义理解错误。

Zero-shot CoT 只加一句“Let's think step by step”，模型自由发挥，可能漏步骤、算错数，或者没真正理解题意。PS 把过程拆成两个明确阶段：先理解并制定计划，再按计划逐步求解。

Zero-shot CoT

  • Prompt 只要求逐步思考。
  • 可能遗漏关键步骤。
  • 可能出现计算错误。
  • 推理质量不稳定。

Plan-and-Solve

  • 先理解问题。
  • 明确要求制定计划。
  • 再按计划执行。
  • 把“计划”从推理链里显式拆出来。

PS 与 PS+ 的 Prompt 模板

PS 的基础模板只多两句：先理解问题并制定计划，再按计划逐步求解。PS+ 在此基础上加入三条更具体的指令。

原文 Prompt 模板

# 基础 PS Prompt
ps_prompt = """
{question}

Let's first understand the problem and devise a plan to solve it.
Then, let's carry out the plan and solve the problem step by step.
"""

# 增强版 PS+ Prompt
ps_plus_prompt = """
{question}

Let's first understand the problem, extract relevant variables
and their corresponding numerals, and devise a plan to solve it.
Then, let's carry out the plan, calculate intermediate results
(pay attention to correct numerical calculation and commonsense),
and solve the problem step by step.
"""

PS+ 的三条增强分别对应三类错误：提取变量，防止遗漏关键信息；计算中间结果，强制记录过程；注意数值计算和常识，减少计算错误。

二 · Plan-and-Execute

规划一个角色，
执行另一个角色。

PS 在 Agent 系统里演化为 Plan-and-Execute：Planner 生成全局计划，Executor 逐步执行；执行结果触发检查，需要时重规划。

执行循环

Planner 的输出是带工具和依赖的步骤列表。Executor 按顺序执行，每步拿到前序结果；一旦某步标记 needs_replan，Planner 带着已完成结果和失败原因重新生成剩余计划。

原文 run 方法节选

plan = await self.plan(task)

results = []
for i, step in enumerate(plan.steps):
    result = await self.execute_step(step, results)
    results.append(result)

    # 阶段 3：检查是否需要重规划
    if result.needs_replan:
        plan = await self.replan(task, plan, results, i)

return await self.synthesize(task, results)

原文把 Planner 和 Executor 拆成两个 LLM 引用：规划可以用更强的模型，执行可以用更便宜、更快的模型。这是异构配置，不是必须。

展开原文 PlanAndExecuteAgent 代码 
class PlanAndExecuteAgent:
    """Plan-and-Solve 在 Agent 系统中的扩展"""

    def __init__(self, planner_llm, executor_llm, tools):
        self.planner = planner_llm   # 规划用的 LLM（可用更强模型）
        self.executor = executor_llm  # 执行用的 LLM（可用更便宜模型）
        self.tools = tools

    async def run(self, task: str):
        # 阶段 1：规划
        plan = await self.plan(task)

        # 阶段 2：逐步执行
        results = []
        for i, step in enumerate(plan.steps):
            result = await self.execute_step(step, results)
            results.append(result)

            # 阶段 3：检查是否需要重规划
            if result.needs_replan:
                plan = await self.replan(task, plan, results, i)

        # 阶段 4：汇总
        return await self.synthesize(task, results)

    async def plan(self, task):
        prompt = f"""
        任务：{task}

        请制定一个详细的执行计划：
        1. 分析任务目标和约束
        2. 列出完成任务所需的步骤
        3. 标注每步需要的工具
        4. 标注步骤间的依赖关系

        输出格式：
        Step 1: [描述] | 工具: [工具名] | 依赖: []
        Step 2: [描述] | 工具: [工具名] | 依赖: [Step 1]
        """
        return await self.planner.invoke(prompt)

    async def execute_step(self, step, previous_results):
        prompt = f"""
        当前步骤：{step.description}
        可用工具：{step.tool}
        前序步骤结果：{previous_results}

        请执行这一步并返回结果。
        """
        return await self.executor.invoke(prompt)

与 ReAct 的对比

ReAct 与 Plan-and-Execute 的对比
维度ReActPlan-and-Execute
决策方式思考 → 行动 → 观察，循环推进。先定全局计划，再逐步执行。
全局视角弱，容易陷入局部循环。强，计划明确总步数和依赖。
灵活性高，每步都能根据结果调整。依赖重规划机制应对意外。
审核难在执行前审核整条路径。计划可以先被人类审核。

LangGraph 推荐的混合方案是：Plan-and-Execute 负责全局计划，每个子步骤用 ReAct 执行。这样既有全局规划，又保留局部灵活性。

三 · 动态重规划

失败不可怕，
从头再来才可怕。

静态计划无法应对工具失败、信息偏离和环境变化。重规划要回答三个问题：何时触发、怎么改、保留什么。

为什么需要重规划

原文例子：步骤 1 完成，步骤 2 因 API 超时失败，步骤 3 依赖步骤 2，无法执行。如果不重规划，Agent 要么卡死，要么跳过关键步骤。重规划后只替换步骤 2：改用备用数据源，步骤 3 和 4 保持不变。

五个触发条件

原文列出的五个重规划触发条件
条件含义
步骤执行失败当前步骤返回失败，后续步骤无法继续。
结果严重偏离预期deviation_score 超过阈值，说明执行方向可能错了。
新信息推翻前提执行中发现原计划依赖的假设不成立。
步数超过预期已执行步数超过预期步数的 1.5 倍，可能陷入循环。
用户干预用户主动要求修改目标或约束。
展开原文 ReplanTrigger 代码 
class ReplanTrigger:
    """检测何时需要重规划"""

    def should_replan(self, state) -> bool:
        # 触发条件 1：步骤执行失败
        if state.last_step_failed:
            return True

        # 触发条件 2：结果与预期严重偏离
        if state.deviation_score > self.threshold:
            return True

        # 触发条件 3：发现新信息改变了前提假设
        if state.assumptions_invalidated:
            return True

        # 触发条件 4：已执行步骤超过预期，可能陷入循环
        if state.steps_executed > state.expected_steps * 1.5:
            return True

        # 触发条件 5：用户干预请求修改目标
        if state.user_intervention:
            return True

        return False

三种重规划策略

反应式、周期性和 ALAS 事务性三种重规划策略
策略何时触发怎么做代价
反应式步骤失败时立即触发。保留已完成进度，重新规划剩余部分；递归执行，最多重试 3 次。失败前没有预警，重规划偏晚。
周期性每执行 N 步评估一次，不等失败。原文示例每 3 步检查进度是否符合预期，需要时调整计划。评估本身要花调用，N 太小会增加成本。
ALAS 事务性每个步骤作为原子事务。成功提交；验证失败回滚；异常回滚后重试，重试耗尽再重规划。需要状态快照和回滚机制。

反应式最简单，适合失败代价不高的任务；周期性适合长流程，能在失败前发现偏移；ALAS 适合有副作用的操作，例如写文件、发请求，失败必须能回滚。

DuSAR：全局子目标 + 局部经验

DuSAR 先按子目标做全局规划，再对每个子目标查经验库：有相似历史策略就复用，没有就探索新策略。执行结果改变上下文时，重新分解剩余子目标；每次结果都写回经验库。

原文把 DuSAR 和 ALAS 放在“长时域复杂任务”一类：一个负责经验积累，一个负责事务性保障。

五条设计原则

原文列出的五条重规划设计原则
原则做法
最小变更保留仍然有效的部分，只改必须改的步骤，避免全部推翻。
上下文传递把已完成结果和失败原因传给 Planner，不要从零开始。
防止无限循环设置最大重规划次数，例如 3 次；超过后报告失败。
失败记忆记住失败方案，避免重规划时再次生成同样的计划。
降级策略多次失败后简化目标、请求人类帮助，或接受部分完成。

实际系统中的闭环

Planner、Executor、Monitor、Replanner 四个组件的职责和去向
组件职责输出去向
Planner生成初始计划。交给 Executor。
Executor逐步执行计划，产生结果。结果交给 Monitor。
Monitor监控执行偏差，判断是否需要重规划。有偏差交给 Replanner；无偏差且未完成，回到 Executor；全部完成，输出结果。
Replanner根据失败原因和已完成结果生成新计划。新计划回灌 Executor。

常见误区 / 面试追问

四个误区，
四个追问。

前四条是误区，后四条是面试追问；答案都来自原文。

误区 1

“Plan-and-Solve 就是 Chain-of-Thought 的变体。”

PS 不只是让模型“逐步思考”，而是明确把过程分为“规划”和“执行”两个独立阶段。CoT 一次性生成推理链，PS 先生成计划再按计划执行。

误区 2

“计划一旦制定就不应该改变。”

好的 Plan-and-Execute 系统必须支持重规划。执行中可能遇到工具失败、信息不符合预期，需要动态调整计划。

误区 3

“每次失败都应该重规划。”

不是所有失败都需要重规划。瞬时错误（网络超时）重试就行；只有结构性问题，例如方案不可行、前提假设变化，才需要重规划。过于频繁的重规划浪费资源，还可能引入新问题。

误区 4

“重规划 = 重新从头开始规划。”

好的重规划是增量修改：保留已完成进度和仍然有效的步骤，只改必须改的部分。全部推翻重来是最后手段。

追问 1

“PS+ 为什么不需要 Few-shot 示例就能接近 Few-shot CoT？”

PS+ 的详细指令，包括提取变量、计算中间结果、注意计算正确性，本质上把 Few-shot 示例中隐含的推理策略显式化了。指令替代了示例的作用。

追问 2

“Planner 和 Executor 应该用同一个模型吗？”

不一定。常见做法是 Planner 用更强的模型保证计划质量，Executor 用更快更便宜的模型降低成本。原文举的例子是 Planner 用 Opus、Executor 用 Haiku；这种异构配置是生产中的常见实践。

追问 3

“如何防止重规划陷入循环？”

三层防御：记录失败的计划，新计划不能重复；设置最大重规划次数上限；每次重规划必须与前次不同，可以用 LLM 自评判断新计划是否实质性不同。

追问 4

“重规划的成本如何控制？”

只在必要时重规划，而不是每步都重规划；重规划只传摘要而非完整历史，控制 token 用量；Planner 可以用较小模型做快速重规划，只在关键决策点用大模型。

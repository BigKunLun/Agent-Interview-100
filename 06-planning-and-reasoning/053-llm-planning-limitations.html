中级 · Planning & Reasoning · 可交互讲解

LLM 会写计划，
不等于计划能做。

LLM 是候选计划生成器，不是可靠的验证器。约束满足、长程规划、世界模型和幻觉四类弱点，需要外部检查来补。

核心判断来自 Kambhampati（ASU，2024）：LLM 不能真正规划，但可以在规划中发挥建设性作用。原文 Blocksworld 数据：纯 LLM 可行率 30–40%，LLM-Modulo 可到 80%+；属原文版本、未联网核实。

    一 · 四项核心局限

    会生成步骤，
    不等于会做规划。

    原文把问题拆成四类，并补了一条“回溯能力缺失”。前四类决定了 LLM 单独规划为什么不可靠，第五条解释了推理模型带来的变化。

    LLM 作为规划器的五项局限、表现和原因
    局限表现原因
    约束满足弱安排 5 人会议，每人空闲时间不同；LLM 经常忽略部分约束。自回归逐 token 生成，无法全局优化多个相互制约的条件。
    长程规划退化10 步计划的可行率远低于 3 步计划。每一步的小错误会累积放大。
    世界模型缺失把积木 A 移到 B 上，可能忘记 A 下面原来还有积木会暴露出来。LLM 是语言模型，不是物理或逻辑模拟器。
    幻觉与虚构计划里引用不存在的 API、使用不可用的工具。LLM 优化语言流畅度，不是计划可行性。
    回溯能力缺失发现第 3 步需要第 1 步的不同输出时，无法改写第 1 步。单向生成，已写出的 token 进入 KV-cache 后不可修改。

    重要例外

    Reasoning Models（o1/o3、DeepSeek-R1、Claude extended thinking 等）通过 RL 训练出现功能性回溯：在思考链里说“wait, let me reconsider...”并重新走一条路径。本质仍是顺序生成，但语义层面已经能模拟回溯效果。更细的推理模型内容见本批 055 页。

    这五条不是“模型不够大”的问题。更大的模型可以改善，但自回归架构对约束满足和状态追踪的弱点不会自动消失。

    二 · 实证与缓解

    LLM 出候选，
    验证器把关。

    原文用 Blocksworld 对比了纯 LLM、LLM 自检和外部验证。结论很直接：LLM 单独规划远不如传统规划器，但加上外部验证能显著提升。

    注意 Self-Verify 只有约 55%：让 LLM 自己检查自己，能改善但不够。真正把可行率拉到 80% 以上的是外部验证器，它掌握 LLM 没有的约束和环境信息。

    缓解方案 1：LLM-Modulo

    LLM 只负责生成候选，正确性交给外部验证器。验证不通过就把具体错误回传，让 LLM 带着反馈重生成，最多尝试 5 次。

    1 · LLM 生成候选理解自然语言需求，产出计划草案。
    →
    2 · 外部验证器语法、约束、可执行性、模拟四层检查。
    →
    3 · 输出或反馈可行就输出；不可行把错误回传，回到第 1 步。

    不合格 → 反馈错误信息 → LLM 修正重生成（循环）

    验证器不是单一检查，而是多层：语法、约束、可执行性、模拟。领域不同，验证器来源也不同：代码用单元测试和类型检查，数学用符号计算，现实世界用模拟器，通用场景可以用另一个 LLM 交叉验证。

    展开原文 LLMModuloPlanner 完整代码与流程图源码 
    class LLMModuloPlanner:
    """LLM 生成 + 外部验证器检查"""

    async def plan(self, task, max_attempts=5):
        for attempt in range(max_attempts):
            # 1. LLM 生成候选计划
            candidate = await self.llm.generate_plan(
                task=task,
                feedback=self.previous_feedback if attempt > 0 else None
            )

            # 2. 外部验证器检查
            validation = await self.verify(candidate)

            if validation.is_valid:
                return candidate
            else:
                # 3. 将验证反馈回传给 LLM
                self.previous_feedback = validation.errors
                # "步骤 3 违反了约束 X：..."

        return None  # 所有尝试都失败

    async def verify(self, plan):
        """多层验证"""
        errors = []

        # 语法验证：步骤格式是否正确
        errors += self.syntax_check(plan)

        # 约束验证：是否满足所有约束
        errors += self.constraint_check(plan)

        # 可执行性验证：每个动作是否可执行
        errors += await self.executability_check(plan)

        # 模拟验证：在模拟环境中执行
        errors += await self.simulation_check(plan)

        return ValidationResult(is_valid=len(errors) == 0, errors=errors)

    缓解方案 2：混合规划架构

    让 LLM 做它擅长的部分，传统算法做确定性的部分。LLM 负责高层目标分解，调度、排列组合等结构化子问题交给经典规划器。

    原文 HybridPlanner 节选

    high_level_goals = await self.llm.decompose(task)

for goal in high_level_goals:
    if goal.is_structured:
        # 调度、排列组合等 → 用确定性算法
        goal.plan = self.classical_planner.solve(goal)
    else:
        # 创意、判断等 → 用 LLM
        goal.plan = await self.llm.plan_steps(goal)

return self.merge_plans(high_level_goals)

    缓解方案 3：Plan-Verify-Correct

    生成初版计划，让 LLM 按固定检查项审查：有没有漏步骤、顺序对不对、有没有不可执行步骤、是否满足约束。发现问题就修正，再进入下一轮。

    原文 PlanVerifyCorrect 节选

    plan = await self.generate_initial_plan(task)

for iteration in range(self.max_iterations):
    issues = await self.llm.verify_plan(plan=plan, prompt="""
        审查以下计划，检查：
        1. 是否有遗漏的步骤？
        2. 步骤顺序是否正确？
        3. 是否有不可执行的步骤？
        4. 是否满足所有约束？
        列出发现的问题。
    """)
    if not issues:
        break
    plan = await self.llm.correct_plan(plan=plan, issues=issues)

return plan

    这个方案仍然依赖 LLM 的检查能力，适合没有外部验证器、又需要快速迭代的场景。它比一次生成好，但不能替代真正掌握环境数据的验证器。

    缓解方案 4：分层规划降低复杂度

    抽象层、中间层和执行层各自负责的内容
    层级负责例子
    抽象层（LLM 擅长）高层目标和策略。先收集数据，再分析，最后生成报告。
    中间层（LLM + 约束）具体子任务与顺序。搜索竞品 A → 提取定价 → 搜索竞品 B → 提取定价。
    执行层（工具 / 代码）原子操作。调用 search_api('竞品A 定价')。

    每一层只处理 3–5 个步骤，控制在 LLM 的能力范围内。层数越多，跨层一致性越难保证，所以分层不是越细越好。

    三 · 关键研究

    四条结论，
    一条共同边界。

    这些结论来自原文列出的研究。它们共同指向一件事：LLM 的强项在理解和生成候选，弱项在精确状态追踪和约束验证。

    四项关键研究及其结论
    研究结论
    Kambhampati 2024LLM 不能规划，但能帮助规划。LLM-Modulo 让 LLM 做候选生成器，外部验证器保证正确性。
    Valmeekam et al. 2023Blocksworld 上 GPT-4 直接生成的计划只有约 35% 可行，远低于预期。
    DeepPlanning 2026隐含约束比显式约束更难被 LLM 发现。环境中没有明确写出来的限制，是 LLM 规划的最大盲区。
    PlanGenLLMs SurveyLLM 在需要精确状态追踪的规划任务上表现最差，在需要常识推理的规划任务上有独特优势。

    这解释了为什么“让模型再想一遍”不够：模型看不到日历、会议室、库存这些外部状态。它能把计划写得通顺，但无法确认计划真的可执行。

    常见误区 / 面试追问

    两个误区，
    两个追问。

    前两条是误区，后两条是面试追问；答案都来自原文。

    误区 1

    “用更大的模型就能解决规划问题。”

    规划能力的局限是自回归架构的根本问题，不是模型大小的问题。更大的模型可以改善，但无法根本解决约束满足和状态追踪的弱点。正确做法是用外部工具补偿结构性弱点。

    误区 2

    “LLM 不能规划 = LLM 在规划中没用。”

    恰恰相反。LLM 在规划中的角色是理解自然语言需求、生成候选方案、提供常识知识。它不擅长精确约束满足和状态追踪，这些交给传统算法或验证器。

    追问 1

    “如何判断一个规划任务是否适合 LLM？”

    看两个维度：约束的数量和复杂度，少约束适合 LLM，多约束需要验证器；步骤数，3–5 步 LLM 可以直接处理，10 步以上需要分层规划或外部辅助。

    追问 2

    “LLM-Modulo 的验证器从哪来？”

    取决于领域：代码规划用单元测试和类型检查；数学规划用符号计算验证；现实世界规划用模拟器；通用场景用另一个 LLM 做交叉验证，效果有限但成本低。

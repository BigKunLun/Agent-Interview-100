基础 · Planning & Reasoning · 可交互讲解

把大任务拆小，
但别拆得太碎。

任务分解把复杂目标拆成可执行的子任务。四种方法各有取舍：LLM 驱动灵活、程序化可靠、HTN 递归、ADaPT 只在失败时拆。真正难的是粒度。

关键权衡：太粗 LLM 一次做不完，太细协调开销压过收益。原文数据：ADaPT 在 ALFWorld、WebShop、TextCraft 上分别提升 28.3%、27%、33%，属原文版本、未联网核实，不是本页实测。

一 · 为什么拆，怎么拆

先看任务，
再选方法。

LLM 擅长聚焦、范围明确的任务；不擅长模糊、多步骤、长依赖链的复杂任务。分解的目的，是把后者变成前者。

“帮我做一份竞品分析报告”包含五类工作：确定竞品、收集资料、收集市场与定价、对比分析、生成报告。把它们拆开，每一步都能用一次模型调用或一次工具调用完成。

原文示例：从复杂任务到子任务

复杂任务："帮我做一份竞品分析报告"
  ↓ 分解
子任务 1: 确定要分析的竞品列表
子任务 2: 收集每个竞品的产品特性
子任务 3: 收集市场数据和定价信息
子任务 4: 对比分析优劣势
子任务 5: 生成报告和可视化图表

方法 1：LLM 驱动分解

用 Prompt 让 LLM 自行拆分，要求它输出带依赖关系和工具标注的 JSON。最灵活，适合未知或多变的任务；缺点是可能产生逻辑错误或遗漏步骤。

原文 Prompt 与输出示例

将以下任务分解为可独立执行的子任务列表。

要求：
1. 每个子任务足够小，可以用一次 LLM 调用或一次工具调用完成
2. 明确标注子任务间的依赖关系
3. 标注每个子任务需要的工具

输出 JSON 格式：
[
  {"id": 1, "task": "...", "depends_on": [], "tools": ["search"]},
  {"id": 2, "task": "...", "depends_on": [1], "tools": ["analyze"]}
]

示例输出：
{"id": 1, "task": "搜索竞品列表", "depends_on": [], "tools": ["web_search"]}
{"id": 2, "task": "收集竞品A的数据", "depends_on": [1], "tools": ["web_search"]}
{"id": 3, "task": "收集竞品B的数据", "depends_on": [1], "tools": ["web_search"]}
{"id": 4, "task": "对比分析", "depends_on": [2, 3], "tools": []}
{"id": 5, "task": "生成报告", "depends_on": [4], "tools": ["write_file"]}

注意 2 和 3 都只依赖 1，可以并行。分解结果不只是任务列表，还要带上依赖和工具，后续编排才有依据。

方法 2：程序化分解

用代码预定义拆分规则，确定、可靠，适合固定流程的业务逻辑。代价是不灵活，任务一变就要改代码。

原文示例：固定流水线

steps = [
    {"name": "data_collection", "agent": "researcher", "parallel": True},
    {"name": "data_analysis", "agent": "analyst", "parallel": False},
    {"name": "draft_writing", "agent": "writer", "parallel": False},
    {"name": "review", "agent": "reviewer", "parallel": False},
]

for step in self.steps:
    agent = self.get_agent(step["agent"])
    context[step["name"]] = await agent.execute(context)

这种写法把“做什么”固化在代码里，运行时不需要 LLM 参与规划。稳定，但遇到没预设过的任务就无能为力。

LLM 驱动

灵活，适合未知或多变任务；稳定性靠校验和重试兜底。

方法 2

程序化

可靠，适合成熟业务流程；任务变化需要改代码。

方法 3

HTN 层级分解

递归拆到“可直接执行”，适合复杂但有结构的任务。

方法 4

ADaPT 按需分解

先直接做，失败才拆；只在必要时付出分解成本。

二 · 递归与按需

拆到能执行，
或者拆到失败为止。

HTN 一路递归，直到每个子任务都能直接执行；ADaPT 反过来，先尝试直接执行，失败了才拆。两者都靠“是否可执行”决定何时停。

方法 3：层级分解（HTN）

HTN 递归拆分任务，直到每个子任务都是“原始任务”——可以用一次工具调用完成。原文实现用两个停止条件：任务已经被判断为原始任务，或者到达最大深度。

原文递归骨架

async def decompose(self, task, depth=0, max_depth=3):
    if depth >= max_depth:
        return [task]              # 达到最大深度，不再分解
    if await self.is_primitive(task):
        return [task]              # 已经可以直接执行
    subtasks = await self.llm_decompose(task)
    all_tasks = []
    for subtask in subtasks:
        all_tasks.extend(await self.decompose(subtask, depth + 1))
    return all_tasks

判断“是否原始任务”本身也调用 LLM：问它“这个任务能否用一次搜索、代码执行或 API 调用完成”。这个判断的质量直接决定递归会不会过早停止或拆得过深。

展开原文 HTN 完整代码 
class HierarchicalDecomposition:
    """递归分解：直到每个子任务可直接执行"""

    async def decompose(self, task, depth=0, max_depth=3):
        if depth >= max_depth:
            return [task]  # 达到最大深度，不再分解

        # 判断任务是否足够简单可以直接执行
        if await self.is_primitive(task):
            return [task]

        # 分解为子任务
        subtasks = await self.llm_decompose(task)

        # 递归分解每个子任务
        all_tasks = []
        for subtask in subtasks:
            decomposed = await self.decompose(subtask, depth + 1)
            all_tasks.extend(decomposed)

        return all_tasks

    async def is_primitive(self, task):
        """判断任务是否可以用一次工具调用完成"""
        response = await self.llm.invoke(
            f"这个任务能否用一次搜索/代码执行/API调用完成？"
            f"任务：{task}\n回答 yes 或 no"
        )
        return response.strip().lower() == "yes"

方法 4：自适应分解（ADaPT）

ADaPT（As-Needed Decomposition and Planning）先尝试直接执行。成功就返回；失败才分解，然后让每个子任务递归走同一流程，最后聚合子结果。

原文执行骨架

async def solve(self, task):
    result = await self.attempt(task)
    if result.success:
        return result
    subtasks = await self.decompose(task)
    results = []
    for subtask in subtasks:
        sub_result = await self.solve(subtask)   # 子任务递归
        results.append(sub_result)
    return self.aggregate(results)

“失败”不只看异常：输出质量不达标也算失败。原文的 attempt 会先校验结果，校验不过就返回 Failure("输出质量不达标")，再进入分解。

原文数据、未联网核实

ADaPT 在 ALFWorld 上提升 28.3%，WebShop 提升 27%，TextCraft 提升 33%；简短回答概括为 27–33%。这些数字来自原论文设置，不是本页实测，也不保证换任务后仍成立。

展开原文 ADaPT 完整代码与流程图源码 
class ADaPT:
    """As-Needed Decomposition and Planning with LLMs"""

    async def solve(self, task):
        # 先尝试直接执行
        result = await self.attempt(task)

        if result.success:
            return result
        else:
            # 执行失败 → 分解后重试
            subtasks = await self.decompose(task)
            results = []
            for subtask in subtasks:
                # 递归：每个子任务也先尝试直接执行
                sub_result = await self.solve(subtask)
                results.append(sub_result)
            return self.aggregate(results)

    async def attempt(self, task):
        """尝试直接用 LLM 执行任务"""
        try:
            result = await self.llm.invoke(task)
            if self.validate(result):
                return Success(result)
            else:
                return Failure("输出质量不达标")
        except Exception as e:
            return Failure(str(e))

三 · 表示、粒度与选型

拆完以后，
还要说清怎么连。

子任务可以表示成线性序列、DAG 或树。表示方式决定哪些步骤能并行；粒度则决定每一步值不值得单独调用。

三种子任务表示

线性序列、DAG 和树形层级三种子任务表示方式的对比
表示结构适合限制
线性序列任务按顺序排成一条链。步骤固定、无并行需求的流程。无法表达并行和复杂依赖。
DAG节点是任务，边是依赖；允许多个前驱。有并行机会、依赖关系明确的流程。要额外做拓扑排序和依赖管理。
树形层级任务递归包含子任务。层级清晰、需要逐层展开的目标。同一子任务被多个父任务复用时不好表达。

原文示例：同一组工作的三种写法

# 方式 1：线性序列（最简单）
linear = ["搜索", "分析", "写作", "审核"]

# 方式 2：DAG（有向无环图，支持并行）
dag = {
    "搜索A": {"depends_on": []},
    "搜索B": {"depends_on": []},       # 与搜索A并行
    "分析": {"depends_on": ["搜索A", "搜索B"]},
    "报告": {"depends_on": ["分析"]},
}

# 方式 3：树形层级
tree = {
    "竞品分析": {
        "数据收集": {
            "搜索竞品A": {},
            "搜索竞品B": {},
        },
        "分析对比": {},
        "生成报告": {},
    }
}

分解粒度的权衡

任务分解太粗、太细和适中的例子与结果
粒度原文例子结果
太粗“做一份完整的竞品分析报告”LLM 无法一次完成，输出质量差。
太细“搜索关键词”“提取第一条的标题”“提取第一条的内容”……可能出现 100 个微步骤，协调开销巨大。
适中“收集竞品 A 的核心产品特性和定价”一次搜索加一次分析可完成。

判断粒度的一个实用标准：这个子任务能不能用一次模型调用或一次工具调用完成。能，就停；不能，再拆。超过这个粒度继续拆，通常只是在增加协调成本。

方法选择指南

五种任务分解方法的适用场景、可靠性和灵活性
方法适用场景可靠性灵活性
LLM 驱动未知 / 多变的任务中最高
程序化固定流程的业务逻辑最高最低
层级（HTN）复杂但有结构的任务高中
ADaPT复杂度不确定的任务高高
TDAG多 Agent + 动态环境中高

最佳实践通常是混合：程序化定义主流程，LLM 处理需要判断力的子步骤。这样既有稳定骨架，又保留对未知情况的适应能力。

常见误区 / 面试追问

四个容易
被追问的点。

前两条是误区，后两条是面试追问；答案都来自原文。

误区 1

“LLM 分解总是最好的。”

LLM 分解灵活但不稳定，可能产生逻辑错误或遗漏关键步骤。对成熟的业务流程，程序化分解更可靠。最佳实践是混合：程序化定义主流程，LLM 处理需要判断力的子步骤。

误区 2

“分解越细越好。”

过度分解增加 LLM 调用次数和协调复杂度。研究指出，小模型加精细分解可能损失大模型整体推理产生的创造性洞见。找到合适的粒度才是关键。

追问 1

“如何验证分解结果的质量？”

检查三个方面：完整性，子任务是否覆盖原始目标的所有方面；独立性，子任务之间是否有不必要的耦合；可执行性，每个子任务是否足够具体、可以直接执行。

追问 2

“任务分解和 Agent 编排是什么关系？”

分解产生子任务图（DAG），编排决定执行策略（顺序、并行、条件）。分解是“做什么”，编排是“怎么做”。LangGraph 等框架把两者统一：分解结果直接映射为图的节点和边。

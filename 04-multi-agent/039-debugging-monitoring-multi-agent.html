高级 · Multi-Agent · 可交互讲解

问题出在 C，
根因可能在 A。

多 Agent 系统难调试，因为输出不确定、调用跨 Agent、依赖常是隐式的。核心方法是分布式追踪：用 Trace 记录一次完整请求，用 Span 记录每个 Agent、工具和 LLM 调用的耗时与输入输出。

关键边界：最终输出正确，不代表过程正确。Agent 可能靠错误路径碰巧得到正确结果；只有过程追踪才能看出工具选错、参数错误或 Handoff 丢字段。

    独特挑战

    不是一条链，
    是一张有环的图。

    单 Agent 往往是一条链；多 Agent 有分流、循环和失败重试，调试复杂度随之上升。

    展开原文 Mermaid 源码 
    flowchart TD
    IN["Input"] --> A["Agent A"]
    A --> T1["Tool 1"]
    T1 --> B["Agent B"]
    B --> T2["Tool 2"]
    A --> C["Agent C"]
    C -- "循环" --> A
    A --> D["Agent D"]
    C --> T3["Tool 3"]
    T3 -- "失败" --> R["重试"]
    R --> T3
    多 Agent 调试的五类独特挑战
    挑战说明
    非确定性同样的输入可能产生不同的执行路径
    跨 Agent 交互问题可能源于 Agent A 但表现在 Agent C
    隐式依赖Agent 间通过共享状态产生的隐式耦合
    延迟叠加多个 LLM 调用串联，延迟难以定位
    上下文丢失Handoff 过程中关键信息可能丢失

    核心方法

    Trace 装请求，
    Span 装步骤。

    Trace 记录一次完整请求，Span 嵌套成执行树。每个 Agent、工具和 LLM 调用都是一个 span，带耗时、token 和状态。

    展开原文 Mermaid 源码 
    flowchart TD
    T["Trace：用户询问订单退款<br/>总计 470ms · 1700 tokens · $0.012"]
    T --> S1["Span：Triage Agent<br/>120ms · 500 tokens"]
    T --> S2["Span：Refund Agent<br/>350ms · 1200 tokens"]
    S1 --> A1["LLM 推理（80ms）"]
    S1 --> A2["Handoff（10ms）"]
    S2 --> B1["LLM 推理（100ms）"]
    S2 --> B2["Tool：get_order_status（150ms）→ 成功"]
    S2 --> B3["Tool：process_refund（80ms）→ 成功"]
    S2 --> B4["LLM 生成回复（50ms）"]

    Trace 解决“一次请求发生了什么”，Span 解决“哪一步慢、错在哪”。两者一起用，才能把“C 表现异常”追到“A 传错了字段”。

    实现追踪

    OpenTelemetry
    或现成平台。

    行业正在收敛到 OpenTelemetry（OTEL）作为标准遥测协议；也可以直接用 Langfuse 等 LLM 可观测性平台。下面两段都来自原文。

    方式 1：OpenTelemetry · 原文代码

    from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider

tracer = trace.get_tracer("multi-agent-system")

async def agent_execute(agent_name, task):
    with tracer.start_as_current_span(f"agent.{agent_name}") as span:
        span.set_attribute("agent.name", agent_name)
        span.set_attribute("task", task)

        with tracer.start_as_current_span("llm.invoke") as llm_span:
            response = await llm.invoke(task)
            llm_span.set_attribute("tokens.input", response.input_tokens)
            llm_span.set_attribute("tokens.output", response.output_tokens)
            llm_span.set_attribute("model", response.model)

        for tool_call in response.tool_calls:
            with tracer.start_as_current_span(f"tool.{tool_call.name}") as tool_span:
                result = await execute_tool(tool_call)
                tool_span.set_attribute("tool.success", result.success)

        span.set_attribute("agent.status", "completed")
        return response

    方式 2：Langfuse · 原文代码

    展开 Langfuse 装饰器示例 
    from langfuse import Langfuse
from langfuse.decorators import observe

langfuse = Langfuse()

@observe(name="triage-agent")
async def triage_agent(user_message):
    response = await llm.invoke(user_message)

    if response.needs_handoff:
        with langfuse.span(name="handoff", metadata={"to": response.target_agent}):
            return await handoff(response.target_agent, response.context)

    return response

@observe(name="refund-agent")
async def refund_agent(context):
    order = await get_order(context["order_id"])
    refund = await process_refund(order)
    return refund

    OTEL 的好处是避免厂商锁定：同一套基础设施可以监控不同框架的 Agent。代价是属性命名要自己统一，否则跨 Agent 的查询仍然对不上。

    Handoff 成功率要单独看：它衡量“上下文有没有完整过去”，不是“目标 Agent 有没有回话”。这两个数混在一起，会掩盖交接丢字段的问题。

    调试工作流

    发现、定位、
    根因、验证。

    先从告警或异常 Trace 进入，再展开 Span 树定位，最后用原始输入重放验证修复。顺序不能倒。

    1. 问题发现告警触发：延迟飙升、错误率上升、成本异常。
    2. 问题定位查看 Trace 列表，筛选异常 Trace；展开 Span 树，定位到具体 Agent、工具或 LLM 调用。
    3. 根因分析检查该 Span 的输入、输出和 prompt；判断是 LLM 选错工具、参数错误，还是工具超时。
    4. 修复验证调整 prompt、工具描述或超时设置；在 Playground 用原始输入重放，确认修复后再部署。

    多 Agent 特有技巧

    断点、决策日志、
    回放。

    三个技巧分别补三类盲区：Handoff 时丢了什么、LLM 为什么选这个工具、线上问题能不能离线复现。

    class HandoffDebugger:
    def on_handoff(self, from_agent, to_agent, context):
        self.logger.info(
            f"Handoff: {from_agent} → {to_agent}",
            extra={
                "context_size": len(json.dumps(context)),
                "context_keys": list(context.keys()),
                "messages_count": len(context.get("messages", [])),
            }
        )

class DecisionLogger:
    def log_decision(self, agent_name, prompt, response, chosen_tool):
        self.store({
            "agent": agent_name,
            "input_summary": summarize(prompt),
            "tool_chosen": chosen_tool,
            "confidence": response.confidence,
            "alternatives_considered": response.alternatives,
        })

class TraceReplayer:
    def replay(self, trace_id):
        trace = self.load_trace(trace_id)
        for span in trace.spans:
            print(f"[{span.agent}] {span.operation}: {span.input[:100]}...")
            print(f"  → {span.output[:100]}...")
            print(f"  ⏱ {span.duration_ms}ms, 💰 {span.cost}")

    回放的价值在于把“偶发”变成“可重复”：保存完整 Trace 后，用同一输入离线重跑，才能确认修复不是又一次运气。

    2026 落地信号

    子 Agent 嵌套，
    不再全是黑箱。

    原文记录 Claude Agent SDK 在 2026-08 补了四类嵌套可观测性盲区。版本号只按原文，未联网核实。

    • 结构信息（TS v0.3.238）：task_started 新增 spawn_depth（嵌套层数）和 is_backgrounded（是否后台执行）。
    • 失败路径的显式终态（TS v0.3.238）：command_lifecycle 新增 refused 终态，跨会话 peer 消息被拒时明确上报，而不是静默无帧。
    • 节点内部的过程（Python v0.2.140）：forward_subagent_text 把子 Agent 的 text / thinking block 转发进主消息流。
    • 结构化错误（Python v0.2.140）：ResultError 取代裸 exit code，携带 subtype、errors、api_error_status、terminal_reason、session_id 等字段。

    原文说明：这是 SDK 层能力，不是 OTEL 标准扩展；接入统一可观测性设施仍需在导出时映射成 span attribute。它说明子 Agent 嵌套的可观测性正从“各家自己埋点”变成 SDK 默认提供。

    常见误区 / 面试追问

    两个误区，
    五个追问。

    前两条是误区，后五条是面试追问，其中三条是场景题；答案来自原文。

    误区 1

    “用 print / log 就够了。”

    多 Agent 系统的日志是分散的，无法从日志中重建 Agent 间的因果关系。需要结构化的 Trace + Span 来保留操作间的父子和时序关系。

    误区 2

    “只监控最终输出质量。”

    最终输出正确不代表过程正确。Agent 可能通过错误的推理路径得到了正确结果（运气好），这类问题只有通过过程追踪才能发现。

    追问 1

    OpenTelemetry 在 LLM 领域的角色是什么？

    OTEL 正在成为 Agent 遥测的标准协议。多个框架（Pydantic AI、smolagents、Strands Agents）已原生支持 OTEL 导出。这避免了厂商锁定，允许用同一套基础设施监控不同框架的 Agent。

    追问 2

    如何测试多 Agent 系统？

    因为输出非确定性，不能用精确匹配断言。推荐：用评分标准评估输出质量；用 LLM-as-Judge 自动评估；构建场景级集成测试而非单元测试；用 Trace 回放做回归测试。

    场景 1

    高峰期 P99 从 2 秒飙到 15 秒，单个 Agent 测试都正常，怎么定位？

    检查 Trace 中的跨 Agent 通信延迟，可能是消息队列或网络瓶颈；分析依赖关系，找串行化热点；检查数据库、向量库等共享资源在高峰期的表现；查看是否有 Agent 触发过多重试，重试风暴会指数级放大延迟；实施 Agent 级熔断，某个 Agent 慢时快速失败而非等待。

    场景 2

    出现“幽灵 Agent”，偶尔执行预期外的操作，怎么排查？

    立即启用全量 Trace 记录，捕获完整路径；检查 System Prompt 是否有模糊指令；分析 Agent 间消息传递，排查上下文污染或消息篡改；检查配置漂移，确认生产与开发的 Prompt 版本一致；实施 Agent 白名单，明确允许的操作范围，超出即告警。

    场景 3

    Agent A 传给 B 的数据偶尔丢字段，B 因此做错决策，怎么解决？

    在 Handoff 接口实施 Schema 验证；设计标准化 Handoff 协议，明确输入输出格式；在交接点记录日志，对比发送和接收的数据；加入数据补全机制，B 检测到缺失字段时主动向 A 请求；构建专门的 Handoff 场景测试集。

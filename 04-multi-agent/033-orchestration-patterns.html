中级 · Multi-Agent · 可交互讲解

先看依赖，
再选拓扑。

多 Agent 编排模式决定 Agent 之间的控制流和协作结构。三种核心模式：Pipeline 顺序链、Hub-Spoke 中心辐射、Hierarchical 层级树；Parallel 和 Maker-Checker 是两种常用补充。

编排模式不是 Agent 数量，而是控制流。选择取决于任务的依赖关系、并行度和控制粒度。生产系统通常组合多种模式，而不是只选一种。

    一、总览

    三种核心拓扑，
    三种控制流。

    Pipeline 是链，Hub-Spoke 是中心到多个专家，Hierarchical 是多层树。拓扑不同，失败方式、延迟和调试难度也不同。

    三种核心编排模式的拓扑、控制方式与适用场景
    模式拓扑控制方式适用场景主要代价
    Pipeline链：A → B → C固定顺序步骤固定、有先后依赖无法并行，一步失败全停
    Hub-Spoke中心辐射：协调器 → 多个专家集中分派与汇总一个任务需要多种专业能力协调器是单点瓶颈
    Hierarchical多层树：管理者 → 子管理者 → 执行者逐级分解与委派大型复杂项目、多层审批层级延迟与信息失真

    补充的 Parallel（扇出/扇入）解决“同一任务多角度并行”，Maker-Checker（生成-校验循环）解决“质量需要迭代把关”。它们经常嵌在三种核心模式内部使用。

    模式 1 · Pipeline

    一条链，
    上一个的输出是下一个的输入。

    每个 Agent 处理前一个 Agent 的输出，按预定顺序链式执行。简单、可预测，但任何一步都不能跳过。

    Pipeline 模式实现 · 原文代码

    # Pipeline 模式实现
class Pipeline:
    def __init__(self, agents: list):
        self.agents = agents  # 按执行顺序排列

    async def run(self, initial_input):
        result = initial_input
        for agent in self.agents:
            result = await agent.process(result)
        return result

# 使用示例：内容生产流水线
pipeline = Pipeline([
    ResearchAgent(),    # Step 1: 搜索资料
    OutlineAgent(),     # Step 2: 生成大纲
    WriterAgent(),      # Step 3: 撰写内容
    EditorAgent(),      # Step 4: 编辑润色
])
output = await pipeline.run("写一篇关于 AI Agent 的技术博客")

    适用场景：数据处理流水线、内容生产（研究→写作→审核）、ETL 工作流。

    优势：简单可预测、易于调试、每步结果可检查。

    劣势：无法并行、一步失败整个流水线停止、不适合需要迭代的任务。

    模式 2 · Hub-Spoke

    一个中心，
    把任务分给多个专家。

    协调器分析任务、分派给专家 Agent，再汇总结果。集中控制带来灵活分派，也让协调器成为单点瓶颈。

    Hub-Spoke 实现 · 原文代码

    class HubSpokeOrchestrator:
    def __init__(self, coordinator, specialists: dict):
        self.coordinator = coordinator
        self.specialists = specialists  # name → agent

    async def run(self, task):
        # 协调器分析任务，决定分派给哪些专家
        plan = await self.coordinator.plan(task)

        results = {}
        for subtask in plan.subtasks:
            agent = self.specialists[subtask.assigned_to]
            results[subtask.id] = await agent.execute(subtask)

        # 协调器汇总所有专家的结果
        return await self.coordinator.synthesize(results)

# Google ADK 风格：Coordinator + sub_agents
coordinator = LlmAgent(
    name="coordinator",
    instruction="你是项目经理，分析用户需求并分配给合适的专家",
    sub_agents=[researcher, coder, designer],
    # LLM 驱动的委派：基于专家描述自动选择
)

    适用场景：客服路由、任务分发、专家咨询系统。

    优势：集中控制、灵活分派、专家可独立扩展。

    劣势：协调器是单点瓶颈、协调器需要理解所有专家的能力。

    注意：原文代码里的循环是顺序 await；要真正并行，需要把专家调用并发执行。拓扑上它们是从中心分出的分支，执行上是否并行取决于实现。

    模式 3 · Hierarchical

    多层管理，
    逐级分解和委派。

    顶层管理者做战略分解，中层做战术分解，底层专家执行具体任务，结果再自底向上汇报。适合大型复杂项目。

    Hierarchical 实现 · 原文代码

    class HierarchicalOrchestrator:
    """多层级管理结构"""

    async def run(self, task):
        # 顶层：CEO Agent 做战略分解
        strategy = await self.ceo.decompose(task)

        # 中层：VP Agent 做战术分解
        for department_task in strategy.department_tasks:
            vp = self.get_vp(department_task.department)
            tactical_plan = await vp.plan(department_task)

            # 底层：专家 Agent 执行具体任务
            for work_item in tactical_plan.work_items:
                worker = self.get_worker(work_item.skill)
                await worker.execute(work_item)

        # 自底向上汇报
        return await self.ceo.synthesize_reports()

    补充模式

    并行与质量回路，
    常嵌在核心拓扑里。

    Parallel 负责扇出/扇入，Maker-Checker 负责生成-校验循环。它们不是第四、第五种“大拓扑”，更像可复用的局部结构。

    Parallel（扇出/扇入）

    # 多个 Agent 并行执行，结果汇聚
async def fan_out_fan_in(task, agents):
    # Fan-out：并行分发
    results = await asyncio.gather(
        *[agent.execute(task) for agent in agents]
    )
    # Fan-in：汇聚结果
    return aggregate(results)  # 投票、合并或 LLM 综合

    Maker-Checker（生成-校验循环）

    # 一个 Agent 生成，另一个 Agent 校验
async def maker_checker_loop(task, maker, checker, max_rounds=3):
    for round in range(max_rounds):
        output = await maker.generate(task)
        review = await checker.review(output)
        if review.approved:
            return output
        task = f"{task}\n\n上一轮反馈：{review.feedback}"
    return output  # 达到最大轮次

    模式选择

    按依赖、专业度、
    规模和质量要求选。

    先看步骤之间有没有先后依赖，再看是否需要多种专业能力、是否需要多层治理、是否能并行、是否需要质量回路。

    场景与推荐编排模式
    场景推荐模式原因
    步骤固定、有先后依赖Pipeline简单可预测
    一个任务需要多种专业能力Hub-Spoke灵活分派
    大型复杂项目、需要多层管理Hierarchical分层治理
    需要多角度分析同一问题Parallel速度 + 多样性
    需要质量保证和迭代改进Maker-Checker内置质量循环
    混合需求组合多种模式如 Hierarchical + Parallel

    这张表给的是起点，不是硬规则。真实系统常常在一种大拓扑里嵌套另一种：Hierarchical 的每一层内部可能是 Pipeline，Hub-Spoke 的某个专家分支可能是一个 Parallel 扇出。

    常见误区 / 面试追问

    四条，
    按原文顺序。

    前两条是误区，后两条是面试追问；答案都来自原文。

    误区 1

    “选一种模式就够了。”

    实际生产系统通常混合使用多种模式。例如 Hierarchical 的每一层内部可能是 Pipeline 或 Parallel。Strands Agents 就采用了 ReWOO 的规划纪律 + ReAct 的步内灵活性的混合方法。

    误区 2

    “Hub-Spoke 中协调器必须是 LLM。”

    协调器可以是确定性代码（基于规则路由），而非 LLM。OpenAI 建议：当需要可预测性和速度时，用代码编排而非 LLM 编排。

    追问 1

    如何在编排模式中加入 Human-in-the-Loop？

    多种模式都支持：Pipeline 中在关键步骤后插入人工审核节点；Hub-Spoke 中协调器可以将高风险任务路由给人类审批；Maker-Checker 中 Checker 可以是人类。

    追问 2

    编排模式如何影响测试策略？

    Pipeline 可以逐节点单元测试；Hub-Spoke 需要测试协调器的路由逻辑；Hierarchical 需要集成测试验证层间通信。因为 Agent 输出不确定性，建议用评分标准或 LLM-as-Judge 而非精确匹配断言。

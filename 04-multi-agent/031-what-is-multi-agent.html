基础 · Multi-Agent · 可交互讲解

一个人干不完，
再拆给一队人。

多 Agent 系统由多个 LLM 驱动的 Agent 协同解决复杂问题。每个 Agent 专注一个子任务，通过通信和协调完成单个 Agent 难以胜任的工作。核心优势是专精化、并行、上下文分散和模块化；代价是通信开销、不可预测和调试复杂度。

关键边界：多 Agent 不是默认更优。简单任务拆成多 Agent，通信成本可能超过收益。本页的选型分数是固定教学权重，不是实测结论，也不调用任何 Agent。

      定义

      分而治之，
      每个 Agent 只管一段。

      多 Agent 系统由多个各自拥有 LLM 的 Agent 组成。协调器拆任务，专精 Agent 各带小工具集和独立上下文，最后汇总。

      复杂任务→协调器 Agent · 分配任务 / 汇总结果
      搜索 Agent · 工具：搜索 / 专精：检索
      分析 Agent · 工具：SQL / 专精：数据
      写作 Agent · 工具：无 / 专精：文案
      ↓汇总结果

      核心思想是分而治之：复杂任务拆成子任务，每个子任务由专精 Agent 处理。协调器负责拆解和汇总，专精 Agent 不承担全局协调。

      单 Agent 的局限

      一个上下文，
      装不下所有角色。

      长指令、多工具、互相冲突的角色要求，都会让单 Agent 的选择质量下降。

      single_agent_problems = {
    "上下文过载": "50+ 工具定义 + 复杂指令 = 上下文窗口被占满",
    "角色冲突": "同时要求严谨分析和创意写作，风格矛盾",
    "工具选择困难": "工具越多，选错工具的概率越高",
    "单点故障": "一个 Agent 出错，整个任务失败",
    "不可并行": "所有步骤必须顺序执行",
}

      当前 LLM 面对超长、多目标的 prompt 时表现不佳，也不擅长从大量工具中挑对工具。把任务拆给多个专精 Agent，是应对这两个限制的自然方案。

      核心优势

      专精、并行、上下文、
      模块化，再加准确率。

      六个优势里，前四个是架构带来的直接收益；后两个依赖具体任务和研究结论，引用时要带来源。

      1. 任务专精化

      每个 Agent 有明确角色和有限工具集。模型也可以按任务选：研究用性价比高的模型，编码用最强模型。

      agents = {
    "researcher": {
        "system_prompt": "你是研究分析师，专注于收集和验证信息",
        "tools": ["web_search", "arxiv_search"],
        "model": "claude-sonnet",
    },
    "coder": {
        "system_prompt": "你是高级软件工程师，专注于编写代码",
        "tools": ["code_executor", "file_write"],
        "model": "claude-opus",
    },
    "reviewer": {
        "system_prompt": "你是代码审查专家，专注于发现 bug 和改进",
        "tools": ["code_analyzer"],
        "model": "claude-sonnet",
    },
}

      2. 并行处理

      多个 Agent 同时工作，总时间取最长的那一个。原文引用研究称，动态多 Agent 框架相比传统顺序系统，执行时间可减少 33%——原文引用、未联网核实。

      async def parallel_research(topic):
    results = await asyncio.gather(
        researcher_agent.search_papers(topic),
        market_agent.analyze_market(topic),
        tech_agent.review_implementations(topic),
    )
    return coordinator.synthesize(results)

      3. 更好的上下文管理

      单 Agent 处理长文档时容易丢上下文。多 Agent 中每个 Agent 只处理自己那部分，通过通信维持整体一致性，等效于扩展了上下文窗口。

      4. 模块化与可维护性

      old_analyzer = AnalyzerAgent(model="gpt-4")
new_analyzer = AnalyzerAgent(model="claude-opus")  # 零影响替换

team.add_agent(TranslationAgent())  # 不修改现有代码

      单个 Agent 可以独立开发、测试和替换。升级分析能力只换分析 Agent；增加翻译能力只加一个 Agent。

      5. 准确率提升

      原文提到 Producer-Reflector 双 Agent 架构在代码生成任务中大幅提升准确率；Meta 分析显示 MAS（如 Captain Agent）在编程、数据分析和科学推理任务中，准确率和成本效率均优于单 LLM。这些是原文引用，未联网核实。

      6. 降低人工监督成本

      原文引用 2024 年对 128 家企业的研究：使用多 Agent AI 的企业在验证和纠正输出上花费的时间减少 61.2%，每年可节省约 194 万美元人力成本。该数字为原文引用，未联网核实，不能直接套到其他组织。

      代价

      多出来的 Agent，
      都要说话、都要调试。

      多 Agent 的收益不是免费的。五项代价里，通信和 token 冗余最先出现，调试难度随 Agent 数量上升。

      多 Agent 系统的五项主要代价
      挑战说明
      通信开销Agent 间信息共享可能引入延迟和冲突
      不可预测性多 Agent 交互可能产生意外行为
      调试困难问题追踪需要跨 Agent 跟踪
      架构复杂度需要设计通信协议、协调机制、错误处理
      Token 浪费Agent 间重复传递信息导致 token 冗余，原文研究显示 53–86%

      Token 冗余的三个常见解法：共享记忆池（黑板模式）、消息摘要（传摘要而不是原始内容）、Instruction-Tool Retrieval（每步只加载必要信息）。

      何时选择

      先单 Agent，
      遇到瓶颈再拆。

      原文的判断清单很直接：简单线性、工具少于 10 个、不需要并行、快速原型，先选单 Agent；多技能、可并行、要审查、要模块化、工具超过 20 个，再考虑多 Agent。

      decision_guide = {
    "选择单 Agent": [
        "任务简单、线性",
        "工具少于 10 个",
        "不需要并行处理",
        "快速原型验证",
    ],
    "选择多 Agent": [
        "任务需要多种专业技能",
        "子任务可以并行执行",
        "需要 checker/reviewer 验证质量",
        "系统需要模块化扩展",
        "工具数量超过 20 个",
    ],
}

      这不是硬阈值，而是优先级：先看有没有专精或审查需求，再看能不能并行，最后看工具规模和模块化。工具数量只是信号之一，不是唯一理由。

      常见误区 / 面试追问

      四个问题，
      别为拆而拆。

      前两个是误区，后两个是追问。

      误区 1

      “多 Agent 总是优于单 Agent。”

      对于简单任务，多 Agent 的通信开销可能超过收益。不要为了用多 Agent 而用多 Agent。从单 Agent 开始，遇到明确瓶颈时再拆分。

      误区 2

      “每个 Agent 必须用不同的 LLM。”

      Agent 的差异化来自 System Prompt、工具集和角色定义。同一个模型配不同 prompt 就是不同的 Agent，不一定要换模型。

      追问 1

      多 Agent 系统的 token 冗余问题如何解决？

      原文研究显示重复率可达 53–86%。解法包括共享记忆池（黑板模式）、消息摘要（传摘要而非原文）、Instruction-Tool Retrieval（每步只加载必要信息）。

      追问 2

      如何定义 multi-agent？两个 LLM 调用就算吗？

      不算。真正的多 Agent 系统需要 Agent 间有自主决策和交互能力，而不是简单的顺序调用链。关键特征是 Agent 能基于其他 Agent 的输出自主调整行为。

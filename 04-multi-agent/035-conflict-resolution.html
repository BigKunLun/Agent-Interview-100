中级 · Multi-Agent · 可交互讲解

意见不一致时，
让规则说话。

多个 Agent 得出不同结论，或者抢同一个资源，就需要冲突解决机制。常见做法有三类：投票表决、多轮共识、指定仲裁者。它们解决“听谁的”，但不自动保证“谁是对的”。

关键边界：投票和共识只能聚合立场，不能修正共同错误。如果多数 Agent 基于同一份错误数据推理，多数决会放大错误；共识轮次过多还可能让 Agent 互相迎合。

冲突类型

先分清
在吵什么。

冲突不只有“结论不同”。资源、优先级、方案和事实都可能冲突；不同类型对应不同解法。

多 Agent 冲突的五种类型与例子
冲突类型例子
结论冲突Agent A 说“买入”，Agent B 说“卖出”
资源冲突两个 Agent 同时要修改同一数据库记录
优先级冲突安全 Agent 说“阻止”，效率 Agent 说“放行”
方案冲突Agent 对解决同一问题提出不同方案
事实冲突Agent 引用了互相矛盾的数据源

投票和共识主要处理结论、方案和优先级冲突；资源冲突更适合用锁、版本号或任务拆分解决；事实冲突要先回到数据源核对，不能靠投票决定哪个事实为真。

机制 1

投票：把立场
变成可数的票。

最直观的冲突解决方式。二元决策用多数决，专业度不均等用加权，高风险操作用一票否决。

二元、加权与排序投票 · 原文代码

class VotingResolver:
    """投票式冲突解决"""

    async def resolve_binary(self, agents, question) -> str:
        """二元投票：是/否"""
        votes = await asyncio.gather(
            *[agent.vote(question) for agent in agents]
        )
        yes_count = sum(1 for v in votes if v == "yes")
        return "yes" if yes_count > len(agents) / 2 else "no"

    async def resolve_weighted(self, agents, question) -> str:
        """加权投票：按 Agent 专业度加权"""
        weighted_votes = {}
        for agent in agents:
            vote = await agent.vote(question)
            weight = agent.expertise_score
            weighted_votes[vote] = weighted_votes.get(vote, 0) + weight
        return max(weighted_votes, key=weighted_votes.get)

    async def resolve_ranked(self, agents, options) -> str:
        """排序投票：Agent 提交偏好排序"""
        rankings = await asyncio.gather(
            *[agent.rank(options) for agent in agents]
        )
        # Borda 计分法：排名越高得分越多
        scores = {opt: 0 for opt in options}
        for ranking in rankings:
            for i, opt in enumerate(ranking):
                scores[opt] += len(options) - i
        return max(scores, key=scores.get)
四种投票方式及适用场景
投票类型适用场景示例
多数决二元决策“是否发布该版本？”
加权投票专业度不均等安全专家在安全问题上权重更高
排序投票多选一从 5 个方案中选择最优

投票的边界很清楚：它只汇总已有立场。票数再多，也不能把一个错误事实变正确；所以高风险场景通常还要加人工审批或安全否决。

机制 2

共识：多轮辩论，
阈值逐步放宽。

Agent 每轮提出或修改立场，系统计算一致率；达到阈值就合并，达不到就阈值乘 0.95 进入下一轮，超过最大轮次则降级。

多轮共识协议 · 原文代码

class ConsensusProtocol:
    """多轮共识协议"""

    def __init__(self, agents, max_rounds=5, threshold=0.8):
        self.agents = agents
        self.max_rounds = max_rounds
        self.threshold = threshold  # 80% 一致才算共识

    async def reach_consensus(self, topic):
        proposals = {}
        for round_num in range(self.max_rounds):
            for agent in self.agents:
                context = {
                    "topic": topic,
                    "round": round_num,
                    "other_proposals": {
                        a.id: p for a, p in proposals.items() if a != agent
                    }
                }
                proposals[agent] = await agent.propose(context)

            agreement_rate = self.calculate_agreement(proposals)
            if agreement_rate >= self.threshold:
                return self.merge_proposals(proposals)

            # 动态调整阈值（任务越紧急，越容易通过）
            self.threshold *= 0.95

        # 达到最大轮次仍未共识 → 降级到投票或人工裁决
        return await self.fallback_to_voting(proposals)

    def calculate_agreement(self, proposals):
        conclusions = [p["conclusion"] for p in proposals.values()]
        most_common = max(set(conclusions), key=conclusions.count)
        return conclusions.count(most_common) / len(conclusions)

关键设计点有三条：动态共识阈值（按紧急度和轮次调整）、最大轮次限制（防止无限辩论）、降级机制（失败后切投票或人工裁决）。

阈值逐轮放宽是一把双刃剑：它能避免僵局，但也意味着“越拖越容易通过”。上线前要明确阈值下限，不能让它无限乘 0.95。

机制 3

中介仲裁：
把最终裁决权交给一个人。

指定一个权威 Agent 或人类，分析各方推理后给出最终裁决。它适合高风险、需要解释理由的冲突。

仲裁者 · 原文代码

class MediatorResolver:
    def __init__(self, mediator_agent):
        self.mediator = mediator_agent  # 仲裁者

    async def resolve(self, conflicting_outputs: dict):
        """仲裁者分析冲突并做出裁决"""
        prompt = f"""
        以下是不同 Agent 对同一问题的分析结果，它们存在冲突：

        {self._format_conflicts(conflicting_outputs)}

        请分析每个 Agent 的推理过程，指出各自的优缺点，
        然后给出你的最终裁决和理由。
        """
        decision = await self.mediator.generate(prompt)
        return decision

仲裁者的权力边界要预先写清：能裁决什么、不能裁决什么、是否必须给出理由、人类是否保留最终否决权。否则“仲裁”只是把单点故障换了个名字。

防止趋同效应

辩论越多，
不一定越对。

LLM Agent 容易迎合对方观点，而不是坚持自己正确的判断。这叫趋同效应（Sycophancy），会让共识看起来很好，实际质量下降。

CONSENSAGENT 的抗趋同做法 · 原文代码

class AntiSycophancyProtocol:
    async def debate(self, agents, topic):
        for round in range(self.max_rounds):
            for agent in agents:
                # 强制要求 Agent 先独立推理，再考虑他人观点
                response = await agent.generate(f"""
                第一步：独立分析（忽略其他 Agent 的观点）
                {topic}

                第二步：考虑其他观点后，明确说明你是否改变立场
                如果改变，解释具体哪个论据说服了你
                如果不改变，解释为什么你认为自己的分析更正确

                其他 Agent 的观点：{other_views}
                """)

做法是强制“先独立推理，再看别人”。改立场可以，但必须指出是哪个论据说服的；不改也要给出理由。这样把“迎合”变成可检查的记录。

资源冲突

抢同一把锁时，
先避免，再加锁。

资源冲突不只是“谁先拿”，还包括拿到后怎么写。按代价从低到高分三层：避免冲突、加锁、合并。

写冲突处理的三层做法、代价与适用场景
层次做法代价与适用
避免冲突任务拆分时文件集不重叠无等待、无死锁，首选
加锁文件锁 / 版本号 / 分布式锁有等待和死锁风险
合并三方合并、测试兜底冲突已经发生，只能补救

避免为什么最好：不需要锁服务，不会死锁，也不会有 Agent 排队等锁时白白消耗时间。任务拆分阶段就让每个 Agent 写不同的文件；需要新建文件的场景天然不冲突，各写各的文件，最后统一汇总。只有无法拆开时才退到加锁。

展开资源抢占与排队的最小示例 
class ResourceConflictResolver:
    """处理多个 Agent 竞争同一资源的冲突"""

    def __init__(self):
        self.locks = {}  # 资源锁

    async def request_resource(self, agent_id, resource_id):
        if resource_id in self.locks:
            holder = self.locks[resource_id]
            if self.priority(agent_id) > self.priority(holder):
                # 高优先级 Agent 可以抢占
                await self.preempt(holder, resource_id)
                self.locks[resource_id] = agent_id
                return True
            else:
                # 排队等待
                await self.wait_queue(resource_id, agent_id)
                return False
        else:
            self.locks[resource_id] = agent_id
            return True

锁粒度：默认文件级。目录级适合批量操作，例如整体替换一个包；行级锁实现复杂、收益低，一般不做。关键原则是缩小临界区，而不是放大粒度。模型调用、计算、内容生成都放在锁外，只在写盘的那一瞬间持锁。

文件级锁：模型调用在锁外 · 原文代码

from pathlib import Path
from filelock import FileLock, Timeout


class FileWriter:
    """文件级锁：模型调用在锁外，只在写入瞬间加锁"""

    def __init__(self, root: str, lock_timeout: float = 5.0):
        self.root = Path(root)
        self.lock_timeout = lock_timeout

    async def write(self, rel_path: str, producer):
        path = self.root / rel_path
        content = await producer(path)          # 生成内容，不持锁

        lock = FileLock(str(path) + ".lock", timeout=self.lock_timeout)
        try:
            with lock:                          # 只包住写盘
                path.parent.mkdir(parents=True, exist_ok=True)
                path.write_text(content, encoding="utf-8")
        except Timeout:
            raise RuntimeError(f"{rel_path} 被占用，稍后重试或换文件")
        return path

乐观并发：读版本，写时比对

读的时候记下版本号，写的时候带上版本号比对。版本没变就写入并递增，变了就失败，调用方重新读取再试。适合读多写少的场景，不需要提前加锁。

展开 VersionedStore 原文代码 
class VersionConflict(Exception):
    pass


class VersionedStore:
    """CAS：dict 模拟，生产用 Redis WATCH 或数据库行版本号"""

    def __init__(self):
        self._data = {}                         # key -> (value, version)

    def read(self, key):
        value, version = self._data.get(key, (None, 0))
        return value, version

    def compare_and_set(self, key, expected_version, new_value) -> int:
        _, current = self._data.get(key, (None, 0))
        if current != expected_version:
            raise VersionConflict(f"{key} 版本已变为 {current}")
        self._data[key] = (new_value, current + 1)
        return current + 1

    async def update(self, key, mutate, max_retries=3):
        for _ in range(max_retries):
            value, version = self.read(key)
            try:
                return self.compare_and_set(key, version, mutate(value))
            except VersionConflict:
                continue                        # 重新读取后再试
        raise VersionConflict(f"{key} 连续 {max_retries} 次冲突")

死锁预防与 fencing token

需要多把锁时，全局按路径字典序获取；拿不到锁就超时释放已持有的锁。顺序一致就不会形成环路，超时保证不会永久阻塞。

fencing token 解决租约过期的残留写入：锁服务每次授予锁时发一个单调递增的编号，写请求必须带上编号，存储端拒绝比已记录编号更小的写入。

展开 OrderedLocks 与 FencedStore 原文代码 
class OrderedLocks:
    """按字典序批量加锁，失败时释放已持有的锁"""

    def __init__(self, root: str, timeout: float = 5.0):
        self.root = Path(root)
        self.timeout = timeout

    async def acquire_all(self, rel_paths):
        handles = []
        try:
            for rel in sorted(set(rel_paths)):  # 全局锁顺序：字典序
                lock = FileLock(str(self.root / rel) + ".lock",
                                timeout=self.timeout)
                lock.acquire()
                handles.append(lock)
            return handles
        except Timeout:
            for handle in handles:              # 失败则回滚已持有的锁
                handle.release()
            raise


class FencingLockService:
    """分布式锁服务：每次授予返回单调递增 token"""

    def __init__(self):
        self._counter = 0

    def grant(self, resource: str) -> int:
        self._counter += 1
        return self._counter


class FencedStore:
    """存储端拒绝旧 token，防止过期持有者覆盖新写入"""

    def __init__(self):
        self._last_token = {}
        self._data = {}

    def write(self, resource: str, token: int, value):
        if token <= self._last_token.get(resource, 0):
            raise PermissionError(f"token {token} 已过期，拒绝写入")
        self._last_token[resource] = token      # 生产环境需原子完成
        self._data[resource] = value

生产实现里，token 比较和写入要在同一个原子操作里完成（Redis Lua 脚本或数据库条件更新），否则检查和写入之间仍有竞态。合并是最后手段：不同文件直接合；同一文件用三方合并；语义冲突只能靠构建和测试发现。

安全性提升

共识能挡住
一部分攻击。

单个 Agent 被注入攻击后，其他 Agent 可以通过投票或共识否决异常行为。原文给出了一组对比数字。

常见误区 / 面试追问

五个容易
答偏的点。

前两条是误区，后三条是面试追问；答案来自原文。

误区 1

“多数投票总是对的。”

如果大多数 Agent 都基于同一个错误数据源推理，多数投票会放大错误。级联幻觉（一个 Agent 的错误输出导致其他 Agent 连锁出错）是多 Agent 系统中的重要风险。

误区 2

“共识轮次越多越好。”

过多辩论增加延迟和成本。更重要的是，LLM 的趋同效应意味着更多轮次不一定提高质量——Agent 可能只是学会了迎合对方。要设置合理的最大轮次和降级机制。

追问 1

拜占庭容错在 LLM 多 Agent 中有用吗？

有用。当一个 Agent 被 Prompt Injection 操控产生恶意输出时，它实际上就是一个“拜占庭节点”。BFT 共识机制可以在部分 Agent 被攻陷的情况下维持系统正确性。

追问 2

如何检测冲突而不只是解决冲突？

实现冲突检测器：比较各 Agent 输出的语义相似度，低于阈值时触发冲突解决流程。结构化输出（如 JSON）可以做字段级别的差异比较。

追问 3

多个 Agent 写同一工作区，只加文件锁够吗？

不够。文件锁只防同时写，防不了租约过期后旧持有者继续写，这时需要 fencing token，让存储层拒绝旧编号的写入。另外锁的临界区要尽量小，模型调用和计算都放在锁外。能从任务拆分上避免文件重叠，就不要用锁。

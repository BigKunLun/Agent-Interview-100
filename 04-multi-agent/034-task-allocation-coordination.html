中级 · Multi-Agent · 可交互讲解

把大任务拆开，
再交对人。

任务分配与协调要连续解决四个问题：把复杂任务拆成子任务，把子任务交给合适的 Agent，按依赖关系协调执行，最后合并结果。集中式规划和动态分配解决的是同一组问题，区别在于“什么时候做决定”。

关键边界：集中式规划在开工前一次性排好全部子任务，动态分配在依赖满足时逐个决定。前者计划清晰，后者更适应运行时的负载和表现变化；两者都必须处理依赖、失败和结果聚合。

      策略 1

      集中式规划，
      分散执行。

      中央规划器负责全局分解和分配，再把同一批无依赖的子任务并行发出去。控制权集中，执行权分散。

      中央规划器 · 原文代码

      class CentralPlanner:
    """中央规划器负责全局任务分解和分配"""

    def __init__(self, agents: dict[str, Agent]):
        self.agents = agents

    async def plan_and_execute(self, task: str):
        subtasks = await self.decompose(task)
        assignments = self.assign(subtasks)

        results = {}
        for batch in self.topological_sort(assignments):
            # 同一批次的任务无依赖，可并行
            batch_results = await asyncio.gather(
                *[self.agents[a.agent_id].execute(a.subtask, results)
                  for a in batch]
            )
            results.update(zip([a.subtask.id for a in batch], batch_results))

        return results

    def assign(self, subtasks):
        """基于 Agent 能力描述的自动匹配"""
        assignments = []
        for subtask in subtasks:
            best_agent = max(
                self.agents.values(),
                key=lambda a: self.capability_match(a, subtask)
            )
            assignments.append(Assignment(subtask, best_agent.id))
        return assignments

      这段代码的关键在 topological_sort 之后的分批：同一批任务放进 asyncio.gather，才是真正的并行；不同批次之间按依赖串行。

      策略 2

      让 LLM 当
      协调器。

      把任务和所有 Agent 的能力描述一起交给 LLM，由它输出“谁做什么、依赖哪一步”的计划，再解析执行。

      LLM 协调器 · 原文代码

      class LLMCoordinator:
    async def coordinate(self, task, agents):
        agent_descriptions = "\n".join([
            f"- {a.name}: {a.description}, 擅长: {a.capabilities}"
            for a in agents
        ])

        plan = await self.llm.generate(f"""
        任务: {task}

        可用 Agent:
        {agent_descriptions}

        请分解任务并分配给合适的 Agent。
        输出格式:
        1. [Agent名] → 子任务描述 (依赖: 无/步骤N)
        2. ...
        """)

        return self.parse_and_execute(plan)

      原文结论

      原文引用研究称：Planner 方法（先生成完整计划再执行）在处理并发操作时优于 Orchestrator 方法（逐步决策），因为 Planner 能更好地识别可并行的子任务。这是原文引用的结论，不是本页实测。

      策略 3

      角色写清楚，
      再谈能力匹配。

      每个 Agent 声明角色、能力和约束，路由器按语义相似度匹配子任务。约束和能力同样重要：能做什么、不能做什么都要写。

      CAMEL 风格的角色分配 · 原文代码

      class RoleBasedAllocation:
    def __init__(self):
        self.agents = {
            "researcher": Agent(
                role="研究分析师",
                capabilities=["web_search", "paper_analysis", "data_collection"],
                constraints=["只能读取数据，不能修改"],
            ),
            "developer": Agent(
                role="软件工程师",
                capabilities=["code_generation", "debugging", "testing"],
                constraints=["只能修改 src/ 目录下的文件"],
            ),
            "reviewer": Agent(
                role="质量审核员",
                capabilities=["code_review", "fact_checking"],
                constraints=["不能直接修改代码，只能提出建议"],
            ),
        }

    def match(self, subtask: str) -> str:
        """基于语义匹配找到最合适的 Agent"""
        subtask_embedding = embed(subtask)
        scores = {
            name: cosine_similarity(subtask_embedding, embed(a.capabilities))
            for name, a in self.agents.items()
        }
        return max(scores, key=scores.get)

      能力描述只说明“会什么”，约束说明“允许做什么”。只做前者，容易出现越权修改；两者都写，才能把角色边界落到路由层。

      策略 4

      动态分配：
      把运行时状态算进分数。

      静态分配假设能力和环境不变；DRAMA 方法用能力、历史表现、当前负载和空闲程度四项加权，在选择时动态算分。

      动态分配与亲和度更新 · 原文代码

      class DynamicAllocator:
    """基于亲和度的事件驱动动态分配"""

    def __init__(self, agents):
        self.agents = agents
        self.affinity_scores = {}  # (agent, task_type) → 历史成功率

    async def allocate(self, subtask):
        candidates = []
        for agent in self.agents:
            score = self.compute_score(agent, subtask)
            candidates.append((agent, score))
        best = max(candidates, key=lambda x: x[1])
        return best[0]

    def compute_score(self, agent, subtask):
        return (
            0.4 * self.capability_match(agent, subtask) +
            0.3 * self.affinity_scores.get((agent.id, subtask.type), 0.5) +
            0.2 * (1 - agent.current_load / agent.max_load) +
            0.1 * self.recency_bonus(agent)
        )

    def update_affinity(self, agent_id, task_type, success: bool):
        key = (agent_id, task_type)
        old = self.affinity_scores.get(key, 0.5)
        self.affinity_scores[key] = old * 0.8 + (1.0 if success else 0.0) * 0.2

      四项权重加起来等于 1，每项都在 0–1 之间，所以总分也在 0–1 之间。动态分配的代价是每次决策都要现算，而且历史分数可能让某个 Agent 长期被偏爱，需要额外设计探索机制。

      协调的关键挑战

      依赖、冗余、
      失败。

      分配只是开始。任务图要能表达依赖，传递要控制冗余，执行要能超时降级，这三件事决定系统能不能稳定收口。

      1. 依赖管理

      2. Token 冗余控制

      原文引用研究称多 Agent 框架中 token 重复率达 53%–86%（原文数据，未联网核实）。常见做法是交接时传摘要，而不是把完整输出反复转述。

      def compress_for_handoff(agent_output: str, max_tokens: int = 500):

        return summarize(agent_output, max_tokens=max_tokens)
    return agent_output

      3. 失败处理

      class ResilientCoordinator:
    async def execute_with_fallback(self, subtask, primary_agent, backup_agent):
        try:
            return await asyncio.wait_for(
                primary_agent.execute(subtask),
                timeout=30
            )
        except (TimeoutError, AgentError):
            return await backup_agent.execute(subtask)

      超时和 Agent 错误降级到备选 Agent；如果备选也失败，还要有上层兜底。降级不是静默重试，结果里应该记录“用了哪个备选”。

      任务分配与协调的五条设计原则
      原则说明
      明确角色边界每个 Agent 有清晰的能力和约束定义
      从小开始先 3–5 个 Agent，验证后再扩展
      匹配通信模式简单链用 Pipeline，复杂协调用 Hierarchical
      健壮的错误处理断路器、重试、降级回退
      可观测性追踪每个 Agent 的输入 / 输出 / 耗时

      常见误区 / 面试追问

      四个容易
      答偏的点。

      前两条是误区，后两条是面试追问；答案来自原文。

      误区 1

      “Agent 越多越好。”

      每增加一个 Agent 都增加通信开销和协调复杂度。最佳实践是从一个 Agent 开始，遇到明确瓶颈才拆分。原文建议初始阶段限制在 3–5 个 Agent。

      误区 2

      “用 LLM 做所有协调决策。”

      LLM 协调灵活但慢且贵。确定性的任务路由用代码规则更可靠。混合方式最佳：简单路由用代码，复杂判断用 LLM。

      追问 1

      如何处理 Agent 间的目标冲突？

      明确优先级规则（如安全 > 效率 > 成本）；引入仲裁 Agent 或投票机制；把冲突升级给人类决策者。系统性的冲突解决机制见第 035 题。

      追问 2

      分布式 Agent 系统如何保证一致性？

      非关键系统接受最终一致即可。关键操作（如金融交易）使用事务性协调：先锁定资源，再执行操作，最后确认或回滚。

基础 · Memory & State · 可交互讲解

LLM 不记事，
记忆是工程层。

短期记忆是当前会话的对话历史，长期记忆是外部存储里、需要检索才能使用的知识，工作记忆是当前这一步真正放进上下文窗口的全部信息。三者配合，Agent 才显得“记得住”。

关键边界：LLM 本身无状态。每次 API 调用相互独立，模型不会自动记住上一轮。所有跨轮、跨会话的记忆，都由应用代码负责存储、检索并重新放进 Prompt。

    记忆的本质

    模型没有记忆，
    应用才有。

    这是理解三类记忆的前提：LLM 每次调用都从零开始，记忆是应用在请求之外维护、再拼回请求里的数据。

    核心事实

    LLM 本身是无状态的。每次 API 调用都是独立的——模型不会“记住”之前的调用。

    产品层面的“记忆”（如 ChatGPT 记住你的名字）是在 LLM 之上工程化实现的记忆层，不是模型的固有能力。构建 Agent 时，你需要自己实现这个记忆层。

    LLM 与应用代码在记忆中的分工
    角色本次请求内负责请求之外负责
    LLM读取本次上下文，生成回答不保存任何状态
    应用代码组装 Prompt、调用模型保存对话、检索长期记忆、决定哪些内容进入下一次请求

    所以“记忆”不是一个模型开关，而是一套数据流：应用把历史、检索结果和工具输出拼成上下文，模型只对这一次拼接出来的内容做推理。

    短期记忆 · STM

    当前会话的
    对话历史。

    短期记忆就是本次会话累积的 messages。它直接可用，不需要检索；会话结束或窗口溢出，它就消失。

    短期记忆 = 上下文窗口中的对话历史 · 原文代码

    conversation_history = [
    {"role": "user", "content": "帮我查一下订单 #12345"},
    {"role": "assistant", "content": "订单 #12345 已发货，预计明天到达"},
    {"role": "user", "content": "物流单号是多少？"},
    # Agent 可以回答，因为"订单 #12345"在短期记忆中
]

# LLM 调用时，完整对话历史作为输入
response = llm.invoke(messages=conversation_history)
    短期记忆的五个特征
    维度短期记忆
    存储位置LLM 的上下文窗口（Context Window）
    生命周期当前会话
    容量限制受上下文窗口大小限制（原文示例：4K–200K tokens）
    访问方式直接可用，无需检索
    丢失时机会话结束、上下文窗口溢出

    注意“直接可用”的含义：它已经在本轮请求的 messages 里，不需要额外查询。一旦会话关闭，这份列表只存在于你的应用侧；模型侧不会保留。

    长期记忆 · LTM

    外部存储加检索，
    跨会话保留。

    长期记忆不在模型里，而在向量数据库、关系数据库或其他外部系统中。要用的时候，先检索，再把结果放进当前窗口。

    长期记忆 = 外部存储 + 检索 · 原文代码

    class LongTermMemory:
    def __init__(self, vector_db, relational_db):
        self.vector_db = vector_db      # 语义检索
        self.relational_db = relational_db  # 结构化查询

    def store(self, memory: dict):
        """存储记忆到外部系统"""
        # 向量化存储（用于语义检索）
        embedding = embed(memory["content"])
        self.vector_db.upsert(
            id=memory["id"],
            vector=embedding,
            metadata=memory["metadata"]
        )
        # 结构化存储（用于精确查询）
        self.relational_db.insert(memory)

    def retrieve(self, query: str, top_k: int = 5) -> list:
        """基于语义相似度检索相关记忆"""
        query_embedding = embed(query)
        results = self.vector_db.search(query_embedding, top_k=top_k)
        return results

    长期记忆的三个认知子类型（LangMem 框架）

    语义记忆、情景记忆、程序记忆的定义、示例、存储与检索方式
    子类型定义示例存储检索
    语义记忆（Semantic）事实和知识——Agent 知道的东西用户偏好、产品知识、规则向量数据库 Collection 或结构化 Profile按语义相似度搜索
    情景记忆（Episodic）经历和事件——Agent 做过的事成功解决问题的完整交互记录带上下文的完整交互日志按情境相似度检索（类似 few-shot）
    程序记忆（Procedural）技能和流程——Agent 知道怎么做System Prompt 中的规则和步骤Prompt 模板、规则引擎通常固定加载，不动态检索

    三种子类型可以同时存在：语义记忆回答“用户喜欢什么”，情景记忆回答“上次类似问题怎么解决”，程序记忆回答“这类任务按什么步骤做”。

    工作记忆 · Working Memory

    当前这一步，
    能想到的全部信息。

    工作记忆不是另一块存储，它就是当前上下文窗口的内容总和：System Prompt、对话历史、检索到的长期记忆、工具结果。

    工作记忆 = 当前上下文窗口中的所有信息 · 原文代码

    working_memory = {
    "system_prompt": "你是客服助手...",           # 程序记忆
    "user_profile": "用户偏好：简洁回答",          # 从长期记忆检索
    "relevant_docs": ["退款政策: ...", "退货流程: ..."],  # RAG 检索
    "conversation": [...],                        # 短期记忆
    "tool_results": {"order_status": "shipped"},  # 工具调用结果
}

# 所有这些组合起来 = Agent 当前"能想到"的全部信息
context_window = format_for_llm(working_memory)
response = llm.invoke(context_window)

    操作系统类比

    上下文窗口（工作记忆）≈ RAM：当前运行的程序可直接访问，容量有限。

    长期记忆（外部存储）≈ 硬盘：大容量，但需要读取操作才能进入内存。

    记忆管理

    固化、遗忘、
    按需加载。

    记忆不是只进不出。应用要决定哪些短期记忆值得固化、哪些长期记忆该衰减删除、当前问题又该加载哪些条目。

    固化 consolidate

    给短期记忆打重要性分数，超过阈值的写入长期记忆。

    遗忘 forget

    按时间衰减降低相关性；低访问次数且低相关性的条目删除。

    加载 load

    按当前查询检索 top_k 条长期记忆，放进工作记忆。

    记忆在 STM 和 LTM 之间的流转 · 原文代码

    class MemoryManager:
    """记忆在 STM 和 LTM 之间的流转"""

    def consolidate(self, short_term_memory):
        """将重要的短期记忆转化为长期记忆"""
        for memory in short_term_memory:
            importance = self.score_importance(memory)
            if importance > self.threshold:
                self.long_term.store(memory)

    def forget(self, long_term_memory):
        """遗忘机制：清除低价值的长期记忆"""
        for memory in long_term_memory:
            # 时间衰减：越老的记忆权重越低
            memory.relevance *= 0.95
            # 频率加权：经常被访问的记忆保留
            if memory.access_count < 2 and memory.relevance < 0.1:
                self.long_term.delete(memory.id)

    def load_to_working(self, query):
        """将相关长期记忆加载到工作记忆"""
        relevant = self.long_term.retrieve(query, top_k=5)
        self.working_memory.update(relevant)

    代码里的 0.95 衰减系数、访问次数 2、相关性阈值 0.1 和 top_k=5 都是原文示例参数，不是通用最佳值；真实系统要按业务调整。

    研究进展 · AgeMem

    把记忆操作
    变成工具。

    2026 年 1 月提出的 AgeMem 框架，让 Agent 在任务执行中自己决定何时存储、检索、更新、摘要或丢弃信息。

    和固定流水线里的 consolidate/forget 不同，AgeMem 把“什么时候动记忆”也交给 Agent 决策：记忆操作被暴露成一组工具，Agent 根据当前任务自主调用。

    AgeMem：记忆操作即工具 · 原文代码

    memory_tools = [
    {"name": "memory_store", "description": "存储重要信息到长期记忆"},
    {"name": "memory_retrieve", "description": "从长期记忆中检索相关信息"},
    {"name": "memory_update", "description": "更新已有的记忆条目"},
    {"name": "memory_summarize", "description": "将多条记忆合并为摘要"},
    {"name": "memory_forget", "description": "删除不再需要的记忆"},
]
# Agent 在任务执行中自主调用这些工具管理记忆

    这仍然是工程层实现：工具由应用暴露，真正的存储由应用执行。区别在于“记忆管理策略”从固定代码变成了 Agent 的运行时决策。

    官方原语 · Anthropic Memory Tool

    memory_20250818：
    文件接口式的官方记忆。

    Anthropic 在 2025-08 通过 Claude Developer Platform 推出 Memory Tool，把记忆做成 client/server 模式的工具原语。

    服务端只暴露文件接口（list/read/create/update/delete），由客户端持久化到任意存储后端（本地 FS、S3、SQLite、Redis 等），Claude 在 agentic loop 中按需调用。

    声明并调用 Memory Tool · 原文代码

    import anthropic

client = anthropic.Anthropic()

# 1) 声明 Memory Tool（type 字段是 server-managed 标识，与 web_search 同范式）
memory_tool = {
    "type": "memory_20250818",
    "name": "memory",                       # 工具固定名
}

# 2) 调用 Claude，启用 context-management beta 与 memory beta
response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=2048,
    tools=[memory_tool],
    extra_headers={"anthropic-beta": "context-management-2025-06-27"},
    messages=[
        {"role": "user", "content": "总结一下我上次说的项目偏好"}
    ],
)

# 3) Claude 会返回 tool_use 形如：
#    {"type": "tool_use", "name": "memory",
#     "input": {"command": "view", "path": "/memories"}}
#    客户端在本地文件系统/数据库里实现 view/create/str_replace/insert/delete/rename
#    把结果作为 tool_result 回灌，Claude 在下一轮继续 read/write

# 4) 与上下文编辑（context_editing）配合：当工具结果累计接近上限，
#    自动清掉旧的 tool_result block，但保留写入 memory 文件的那一份
#    → 实现"长寿命 agent + 紧凑 context window"

    关键特性

    客户端持有数据所有权：服务器不存任何记忆内容，便于满足 GDPR/合规。

    与 context editing 协同：旧的 tool_result 会被服务端策略性清理，但 memory 文件保留。

    跨会话共享：把同一份 memory 文件挂到多个 Claude 会话/Agent，实现团队级或个人长期画像。

    比向量数据库更简单：路径 + 文本读写，模型自己决定存什么，不依赖额外的 embedding 服务。

    原文称这是目前 LLM 厂商提供的最完整的“官方记忆原语”，与 Anthropic Skills、Structured Outputs 一起构成 2025-2026 Claude Platform 的三大新原语。

    注意：本页只展示原文代码，不调用 Anthropic API，也不读写任何真实记忆文件。

    三种记忆的关系

    位置、容量、
    持久性都不同。

    短期记忆和工作记忆都在上下文窗口内，但内容范围不同；长期记忆在窗口外，容量近乎无限，但每次使用都要检索。

    短期记忆、工作记忆、长期记忆在位置、容量、持久性、访问速度和内容上的对比
    维度短期记忆工作记忆长期记忆
    位置上下文窗口上下文窗口外部存储
    容量受窗口限制受窗口限制近乎无限
    持久性会话级请求级永久
    访问速度即时即时需检索
    内容对话历史STM + 检索的 LTM所有历史知识

    一句话区分：短期记忆是“聊过什么”，工作记忆是“这一次请求里有什么”，长期记忆是“存在外面、需要去取什么”。

    常见误区 / 面试追问

    五个容易
    被追问的点。

    前两条是误区，后三条是面试追问；答案都来自原文。

    误区 1

    “上下文窗口越大，就不需要长期记忆了。”

    即使 200K token 的窗口，也无法存储数月的用户交互历史。更重要的是，窗口越大成本越高，且 LLM 在超长上下文中的注意力会分散（“lost in the middle” 问题）。

    误区 2

    “短期记忆和工作记忆是一回事。”

    短期记忆是对话历史的累积；工作记忆是当前步骤可用的全部信息（包括从长期记忆检索的内容）。工作记忆 = 短期记忆 + 检索的长期记忆 + System Prompt + 工具结果。

    追问 1

    如何决定什么信息值得存入长期记忆？

    用重要性评分：（1）用户明确要求记住的信息（高优先级）；（2）影响未来决策的事实（如用户偏好）；（3）成功解决问题的范例（情景记忆）。避免存储临时性信息和中间推理步骤。

    追问 2

    MemGPT 的核心思想是什么？

    将上下文窗口视为有限的“内存”资源，实现类似操作系统虚拟内存的层级管理。Agent 可以在核心记忆（RAM/上下文窗口）和归档记忆（磁盘/外部存储）之间主动移动数据，创造“无限记忆”的体验。

    追问 3

    “LLM 无状态”这个前提会一直成立吗？

    不一定。它描述的是当前主流架构，不是理论必然。Metis 这类记忆基础模型把记忆状态放进模型内部，通过 memory attention 访问历史压缩信息，更新只需一次前向传播、不需要梯度，推理时权重冻结而记忆状态自主演化——这时“无状态”就不再成立了。面试时的稳妥答法：说清楚这是当前工程现实和它成立的原因（每次 API 调用独立、KV cache 不跨请求保留），再指出已有把记忆内化进底座的研究方向。

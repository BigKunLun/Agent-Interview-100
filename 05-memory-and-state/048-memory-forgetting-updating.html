高级 · Memory & State · 可交互讲解

忘不掉旧偏好，
就会一直推荐错。

记忆系统不仅要能记住，还要能忘记和更新。时间衰减、频率淘汰、容量限制、TTL 解决“什么时候删”；冲突检测与四态更新解决“新旧矛盾听谁的”。

关键边界：TTL 配了不等于记忆真的消失。过期要在读路径上过滤，不能只靠后台清扫；否则两次清扫之间的过期记忆仍会被检索，访问续期还可能把它“复活”。

为什么遗忘

全留着，
检索就会被旧信息污染。

第 1 天“用户喜欢 React”，第 30 天“开始学 Vue”，第 90 天“现在全部用 Vue”。三条都留着，查询“推荐前端框架”会检索到两条指向 React 的旧信息，Agent 可能推荐错。

问题不在存储容量，而在检索质量。LLM 无法仅凭内容判断哪条检索结果最新，它会把所有记忆同等对待。没有遗忘机制，存储会膨胀、检索噪声增加、过时信息误导决策。

遗忘策略

四种删法，
各有各的坑。

时间衰减按年龄降权；频率淘汰清理长期没人访问的记忆；容量限制在满时淘汰最低价值；TTL 靠过期时间，但工程上最容易踩坑。

1. 时间衰减

原文用 Ebbinghaus 遗忘曲线：R = e^(-t/S)，其中稳定性 S = 1.0 + access_count × 0.5。访问越多，记忆越稳定；强度低于 0.05 时归档或删除。

2. 基于检索频率的淘汰

存在超过 30 天且从未被检索 → 价值低；最近 30 天未访问且总访问少于 3 次 → 淘汰。

3. 容量限制淘汰

达到上限时，淘汰价值最低的记忆。原文的价值函数：0.4 × access_count / max_access + 0.3 × strength + 0.3 × confidence。

4. TTL 的实现陷阱

TTL 通常由后台清扫任务周期性删除，两次清扫之间存在窗口期：已过期的记忆仍然躺在库里，检索照样能命中。更糟的是，很多实现带 refresh_ttl（访问即续期），一次检索命中就把本该死掉的行“复活”。

LangGraph 在 checkpoint v4.2.0（2026-08）给 TTLConfig 加了 omit_expired（默认 False）：查询层直接过滤过期行，并阻止 refresh_ttl 给已过期的行续命。结论：遗忘要在读路径上生效，不能只挂在写路径和后台清扫上。

查看 TTLConfig 的原文代码 
from langgraph.store.base import TTLConfig

ttl_config = TTLConfig(
    default_ttl=60,        # 分钟
    refresh_on_read=True,
    omit_expired=True,     # v4.2.0 新增，默认 False

更新策略

新事实来了，
旧事实怎么办？

先检索相似记忆（阈值约 0.85），没有就存；有相似就让 LLM 判四态：UPDATE / CONTRADICT 失效旧存新，SUPPLEMENT 共存，DUPLICATE 忽略。

UPDATE新信息是旧记忆的更新版本，例如偏好变化 → 旧记忆失效，存新事实
CONTRADICT新信息与旧记忆矛盾 → 旧记忆失效，存新事实
SUPPLEMENT新信息是补充，两者可以共存 → 新旧都保留
DUPLICATE新信息是重复 → NOOP，忽略

知识图谱里的更新不是删除，而是时间失效：找到当前有效的旧事实，把它的 valid_to 设为现在；再创建 valid_from=now、valid_to=None 的新事实。历史保留，支持时间旅行查询。

查看四态冲突检测的原文代码 
class ConflictAwareUpdater:
    """检测新旧信息冲突并智能更新"""

    async def process_new_fact(self, user_id, new_fact):
        similar = await self.retrieve_similar(
            user_id, new_fact, threshold=0.85)

        if not similar:
            await self.store(user_id, new_fact)
            return "STORE"

        decision = await self.llm.invoke(f"""
        已有记忆: {similar[0]['content']}
        新信息: {new_fact}
        判断关系：
        - UPDATE: 新信息是更新版本
        - CONTRADICT: 两者矛盾，需要替换
        - SUPPLEMENT: 新信息是补充，两者共存
        - DUPLICATE: 新信息是重复，忽略
        """)

        if decision in ["UPDATE", "CONTRADICT"]:
            await self.invalidate(similar[0])
            await self.store(user_id, new_fact)
            return decision
        elif decision == "SUPPLEMENT":
            await self.store(user_id, new_fact)
            return "SUPPLEMENT"
        else:
            return "NOOP"
查看知识图谱时间失效的原文代码 
class TemporalFactUpdate:
    async def update_fact(self, subject, predicate, new_object):
        old_fact = await self.graph.find(
            subject=subject, predicate=predicate,
            valid_to=None  # 当前有效
        )
        if old_fact:
            old_fact.valid_to = datetime.now()  # 失效，不删除
            await self.graph.update(old_fact)

        await self.graph.add(
            subject=subject, predicate=predicate, object=new_object,
            valid_from=datetime.now(), valid_to=None
        )

前沿研究

存之前先问：
这条值不值得记？

A-MAC（自适应记忆准入控制）把记忆存储视为结构化决策问题，从五个维度评估价值：未来效用、事实置信度、语义新颖性、时间新近性、内容类型先验。

原文称实验表明：基于效用的删除策略比朴素策略（FIFO / 随机）性能提升 10%。A-MAC 的“事实置信度”维度还能拦住幻觉信息：存入前先评估可靠性，低于阈值就不存。

原文只给出五个维度和加权求和的框架；本页后续演示里的权重、分值和阈值是固定教学假设，不是论文参数。

评估维度

记得准，
不等于记得对。

MemoryAgentBench 评四个能力：准确检索、测试时学习、长程理解、选择性遗忘。MemTrapBench 又补了一个维度：记忆本身没错，仍可能把推理带偏。

MemoryAgentBench 的四个能力

  • Accurate Retrieval：能否准确检索出相关记忆？
  • Test-Time Learning：能否从交互中学习新知识？
  • Long-Range Understanding：能否在长时间跨度中保持理解？
  • Selective Forgetting：能否智能地遗忘过时信息？

MemTrapBench：记忆诱发的认知陷阱

记忆内容本身没有任何问题，既被忠实记录、也与当前问题语义相关，但进入上下文后仍扭曲了模型的推理过程或信念状态。它分两类：Reasoning Fixation（推理固着，旧解法被复用到表面相似、实质不同的新问题上）和 Belief 类（信念扭曲，曾经成立的判断被当作无需校验的“已知前提”）。

遗忘机制与 MemTrapBench 解决的是两类不同失效
视角解决什么失效长什么样对策
前文的遗忘 / 更新机制记错、记多、记旧检索到过时或错误的记忆衰减、淘汰、冲突覆盖、准入控制
MemTrapBench 揭示的记对了仍有害检索到正确且相关的记忆，推理照样跑偏不在写入侧，得在使用侧

两者正交而非替代：遗忘做得越干净，剩下的记忆越“可信”，被无条件采信的风险反而越高。工程含义：记忆质量不能只用“检索准确率”单指标验收——一条记忆该不该留（写入侧）和它进入上下文后会不会被误用（使用侧）要分别评估。

实际影响

遗忘不是清理，
是可靠性的一部分。

原文的三条结论：效用删除比朴素策略性能提升 10%；无差别存储会导致错误传播和长期性能退化；幻觉信息一旦存入，会在后续交互中反复出现。

常见误区 / 面试追问

六个问题，
从容量问到 GDPR。

前两个是误区，后四个是追问。TTL 和失效/删除的区别是高频考点。

误区 01

“只要存储空间够大，就不需要遗忘”

记忆系统的问题不是存储容量，而是检索质量。过时和错误的记忆会污染检索结果，导致 Agent 做出错误决策。“智能遗忘是可靠记忆的前提条件”。

误区 02

“删除旧记忆就是遗忘”

更好的做法是“失效”而非“删除”：标记旧事实为过期但保留历史，支持时间旅行查询。知识图谱的 valid_from / valid_to 模型是最佳实践。

追问 03

如何防止幻觉信息被存入记忆？

A-MAC 的“事实置信度”维度正是解决这个问题：存入前评估信息可靠性。还可以对 LLM 提取的事实做交叉验证；设置置信度阈值，低于阈值的信息不存储。

追问 04

给记忆加了 TTL，是不是就实现遗忘了？

不够。TTL 一般靠后台清扫兑现，清扫周期之间过期记忆仍会被检索到；如果还开了“访问即续期”，一次命中就把它续活，等于永不过期。正确做法是让过期在读路径生效：查询时直接过滤过期行，并禁止续期作用于已过期数据。LangGraph checkpoint v4.2.0 的 TTLConfig.omit_expired 就是这个语义，默认关闭，需要显式开。

追问 05

把该遗忘的都遗忘干净了，记忆系统是不是就没问题了？

不是。遗忘机制解决“记错 / 记多 / 记旧”，判据是存取正确率。MemTrapBench 度量的是另一类失效：记忆被忠实记录、且与当前问题语义相关，仍可能扭曲推理或信念。Reasoning Fixation 是沿用旧解法解表面相似的新问题，Belief 类是曾经成立的判断被当作无需校验的前提。两者正交，验收不能只看检索准确率。

追问 06

记忆遗忘和 GDPR 的“被遗忘权”有什么关系？

GDPR 要求系统能完全删除用户数据。Agent 记忆系统必须支持彻底的物理删除，不只是逻辑失效，包括向量存储、知识图谱和所有备份中的数据。

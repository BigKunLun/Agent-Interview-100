中级 · Memory & State · 可交互讲解

Agent 忘了刚才，
就谈不上下一步。

状态管理决定 Agent 在任意时刻知道什么、做过什么、下一步该做什么。主流做法是共享状态图 + Reducer + Checkpoint：节点读写全局状态，Reducer 合并更新，每个执行步骤自动落快照。

关键边界：状态必须可序列化、可恢复、可审计。Checkpoint 保存的是“当时的状态”，恢复时只能回到快照点，不能凭空跳到任务末尾。

为什么需要

没有状态，
多步任务走不下去。

无状态 Agent 每次调用都是独立的：工具结果丢失，无法基于前序结果决策；中断后无法恢复，长任务不可靠。

无状态与有状态 Agent 的对比
维度无状态 Agent有状态 Agent
多步任务每次 LLM 调用独立，难以继续状态跨步骤持久化，支持复杂工作流
中断恢复中断即丢失，长任务不可靠可暂停、可恢复，支持 Human-in-the-Loop
调试审计看不到中间状态状态可检查，支持调试和审计

模式 1

共享状态图：
Reducer 决定怎么合并。

LangGraph 的状态是流经每个节点的共享内存对象。节点读取状态、返回局部更新，框架用 Reducer 把更新合并回全局状态。

状态 Schema 用 TypedDict 定义。字段的更新方式由 Annotated 上的 Reducer 决定：operator.add 表示追加或累加，不写 Reducer 则直接替换。原文称这套 State + Reducer + Checkpoint 组合已成为业界主流，被 Klarna、Replit 等企业用于生产。

三种常见的 Reducer 行为
写法行为示例
Annotated[list, operator.add]追加：新消息加到列表末尾messages
Annotated[int, operator.add]累加：数字相加revision_count
str（无 Reducer）替换：新值直接覆盖旧值draft / status
查看共享状态图的原文代码 
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START
import operator

class AgentState(TypedDict):
    messages: Annotated[list, operator.add]   # 追加
    research_data: str                       # 替换
    draft: str
    revision_count: int
    status: str

def research_node(state: AgentState) -> dict:
    query = state["messages"][-1]["content"]
    data = search(query)
    return {"research_data": data, "status": "research_complete"}

def write_node(state: AgentState) -> dict:
    draft = generate(state["research_data"])
    return {
        "draft": draft,
        "revision_count": state["revision_count"] + 1,
        "status": "draft_complete"
    }

def should_revise(state: AgentState) -> str:
    if state["revision_count"] >= 3:
        return "end"
    if quality_score(state["draft"]) < 0.8:
        return "revise"
    return "end"

graph = StateGraph(AgentState)
graph.add_node("research", research_node)
graph.add_node("write", write_node)
graph.add_edge(START, "research")
graph.add_edge("research", "write")
graph.add_conditional_edges("write", should_revise)

模式 2

Checkpointing：
把“当时”存下来。

每个执行步骤后自动保存状态快照。服务重启、人工审批后继续、时间旅行调试，都从检查点恢复。

  • 2 小时的 Agent 任务中途 Pod 重启 → 从检查点恢复，不用从头跑。
  • Human-in-the-Loop：暂停等待审批 → 审批后从暂停点继续。
  • 时间旅行调试：回到第 N 步，查看当时的完整状态。
查看 SqliteSaver 的原文代码与使用注意 
from langgraph.checkpoint.sqlite import SqliteSaver

# SqliteSaver.from_conn_string 是 context manager，
# 必须用 with ... as 形式打开；
# 直接赋值会得到未进入的 contextmanager 对象，运行时报错。
with SqliteSaver.from_conn_string("./agent_state.db") as checkpointer:
    app = graph.compile(checkpointer=checkpointer)

    config = {"configurable": {"thread_id": "user_123_session_1"}}
    result = app.invoke({"messages": [user_msg]}, config)

    # 从上次暂停处继续
    result = app.invoke(None, config)

长进程服务可以用 AsyncSqliteSaver / PostgresSaver 的 async with 形式，也可以手动调用 .setup() + .close()，但 with 是官方推荐写法。

模式 3

事件溯源：
存变更，不存结果。

事件溯源记录所有状态变更事件，当前状态由事件推导。好处是完整回放和审计；代价是事件日志会持续增长。

查看事件溯源的原文代码 
class EventSourcedState:
    """记录所有状态变更事件，支持回放"""

    def __init__(self):
        self.events = []          # 事件日志
        self.current_state = {}   # 当前状态（由事件推导）

    def apply_event(self, event: dict):
        self.events.append({
            **event,
            "timestamp": datetime.now(),
            "sequence": len(self.events)
        })
        self.current_state = self.rebuild()

    def rebuild(self, up_to: int = None):
        """从事件日志重建状态"""
        state = {}
        events = self.events[:up_to] if up_to else self.events
        for event in events:
            if event["type"] == "tool_result":
                state[event["tool"]] = event["result"]
            elif event["type"] == "decision":
                state["last_decision"] = event["decision"]
            elif event["type"] == "handoff":
                state["current_agent"] = event["to_agent"]
        return state

    def replay_to(self, step: int):
        """回放到特定步骤（时间旅行调试）"""
        return self.rebuild(up_to=step)

模式 4

有限状态机：
状态和事件都写死。

FSM 用明确的状态和转移规则管理流程。任何不在转移表里的事件都会被拒绝，适合线性或规则清晰的流程。

原文 AgentFSM 的状态转移表
当前状态事件 → 目标状态
idlereceive_task → planning
planningplan_ready → executing；plan_failed → error
executingstep_done → executing；all_done → reviewing；error → error
reviewingapproved → complete；rejected → executing
errorretry → planning；abort → idle
completereset → idle
查看 AgentFSM 的原文代码 
class AgentFSM:
    """用 FSM 管理 Agent 流程状态"""

    TRANSITIONS = {
        "idle":       {"receive_task": "planning"},
        "planning":   {"plan_ready": "executing",
                       "plan_failed": "error"},
        "executing":  {"step_done": "executing",
                       "all_done": "reviewing",
                       "error": "error"},
        "reviewing":  {"approved": "complete",
                       "rejected": "executing"},
        "error":      {"retry": "planning", "abort": "idle"},
        "complete":   {"reset": "idle"},
    }

    def __init__(self):
        self.state = "idle"
        self.history = []

    def transition(self, event: str):
        allowed = self.TRANSITIONS.get(self.state, {})
        if event not in allowed:
            raise InvalidTransition(
                f"Cannot {event} from {self.state}")
        old_state = self.state
        self.state = allowed[event]
        self.history.append((old_state, event, self.state))

模式 5

Human-in-the-Loop：
在节点里中断。

LangGraph 的 interrupt 在敏感操作前暂停，把动作和理由交给人。审批后从暂停点继续，而不是重跑整个任务。

查看 interrupt 的原文代码 
from langgraph.types import interrupt

def sensitive_action_node(state):
    """需要人工审批的敏感操作"""
    action = plan_action(state)

    approval = interrupt({
        "action": action,
        "reason": "此操作将修改生产数据库",
        "options": ["approve", "reject", "modify"]
    })

    if approval["decision"] == "approve":
        return execute(action)
    elif approval["decision"] == "modify":
        return execute(approval["modified_action"])
    else:
        return {"status": "rejected"}

模式 6

外置状态 + 环境审计：
谁能写状态？

LongHorizon-Harness（2026-08）换了一个维度：状态只接受环境已验证的事实，模型自我判断不算数。Manager 派发，Executor 零上下文执行，Auditor 只读核验。

Manager
维护任务状态
派发 →
Executor
零上下文执行，做完即弃
任务状态
唯一跨子任务载体
← 验证通过才写回
Auditor
只读核验环境
任务状态
据状态派发 →
Manager
下一个子任务

状态只接受环境已验证的事实：文件确实存在、测试确实通过，不是模型说“我做完了”。

对比常见做法：单个 Agent 在膨胀的上下文里自我评估“我刚才做成了吗”，一次误判会留在上下文里，后续每一步都在错误结论上继续推理。外置状态 + 独立审计切断这条链路：Executor 上下文每次归零，错误无处驻留；状态里的每条事实都被环境验证过。

原文论文数据：WeaveBench 51.8% → 80.7%，OSWorld 2.0 2.8% → 8.3%，增益可迁移到 Claude Opus 4.7。以上为原文版本数据，本页未联网核实。

设计要点：状态是唯一的跨步骤载体，子任务之间不共享上下文，只共享状态；写状态需要凭据，来源必须是环境的可观测结果；审计只读，避免 Auditor 自己成为新的错误来源。

设计原则

状态不是越多越好，
是越可用越好。

五条原则：可序列化、幂等、最小化、版本管理、显式 Reducer。再附一张场景到模式的选型表。

常见误区 / 面试追问

四个问题，
从全局变量问到性能。

前两个是误区，后两个是追问。回答时先给结论，再讲机制和代价。

误区 01

“全局变量就是状态管理”

Agent 的状态需要持久化、可恢复、可审计。全局变量在 Pod 重启后丢失、无法调试、不支持并发。需要 Checkpointer 或事件溯源等正式机制。

误区 02

“状态越详细越好”

状态越大，序列化和反序列化越慢，Checkpoint 占用越多存储。只保留决策所需的最小信息集。中间推理过程应该在 Trace 中记录，而不是塞进状态。

追问 03

LangGraph 的 Reducer 和 Redux 的 Reducer 有什么关系？

概念相同：都是纯函数，接收当前状态和更新，返回新状态。LangGraph 用 Python 的 Annotated 类型标注来声明 Reducer 规则，例如 operator.add 表示追加。

追问 04

Checkpointing 对性能的影响？

每个 super-step 后保存检查点会增加延迟。优化方案：使用异步写入；只在关键步骤做 Checkpoint；用 Redis 替代 SQLite 做高性能 Checkpoint。

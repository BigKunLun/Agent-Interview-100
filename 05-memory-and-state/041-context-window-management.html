基础 · Memory & State · 可交互讲解

窗口是固定的，
对话不是。

上下文窗口是 LLM 的工作记忆：System Prompt、对话历史、检索内容和工具结果都要挤进同一个固定 token 空间。对话越长，越需要主动管理，否则成本、延迟和“中间丢失”会一起找上门。

关键边界：生产实践通常把输入控制在窗口的 75% 以内，给输出留 25%。压缩之外还要保留锚点：原始需求、约束、已确认决策和关键标识永远不进入摘要器。

基础策略

先试零成本的，
再考虑调模型。

截断、滑动窗口、观察掩码都不需要额外 LLM 调用。原文特别指出：掩码在总效率上往往不逊于摘要。

截断与滑动窗口

截断从最旧的消息开始丢，直到装进预算；改进版会区分必须保留和可选内容。滑动窗口只保留最近 N 轮，零成本、token 用量可预测，但会丢掉所有旧上下文。

查看截断与滑动窗口的原文代码 
def truncate_messages(messages, max_tokens):
    """保留最新消息，截断最旧的"""
    total = 0
    kept = []
    for msg in reversed(messages):
        msg_tokens = count_tokens(msg)
        if total + msg_tokens > max_tokens:
            break
        kept.insert(0, msg)
        total += msg_tokens
    return kept


def sliding_window(messages, window_size=10):
    """只保留最近 N 轮对话"""
    system_messages = [m for m in messages if m["role"] == "system"]
    conversation = [m for m in messages if m["role"] != "system"]
    # 每轮 = user + assistant
    return system_messages + conversation[-window_size * 2:]

观察掩码（Observation Masking）

旧工具结果和长回复不再保留原文，而是替换成占位符。模型知道“这里曾经有内容”，需要时再重新查询。原文的研究结论是：掩码在总效率（性能 / 成本比）上与 LLM 摘要相当，甚至更优。

查看观察掩码的原文代码 
def observation_masking(messages, window=5):
    """用占位符替代旧的工具结果和长回复"""
    result = []
    for i, msg in enumerate(messages):
        if i < len(messages) - window:
            if msg["role"] == "tool" or len(msg["content"]) > 500:
                result.append({
                    "role": msg["role"],
                    "content": "[内容已省略——如需详情请重新查询]"
                })
            else:
                result.append(msg)
        else:
            result.append(msg)  # 最近 N 条保持原样
    return result

进阶策略

摘要不是万能，
结构化也不是白拿。

LLM 摘要保留语义，但要额外调用；分层压缩让越旧的信息越激进；结构化提取信息密度最高，却依赖模型判断。

原文的上下文策略对比
策略成本信息保留实现复杂度适用场景
截断零低极简短对话、快速原型
滑动窗口零低极简简单聊天
观察掩码零中简单工具密集型 Agent
LLM 摘要高（原文经验估算 +7%）高中长对话助手
分层压缩中高中长时运行的 Agent
结构化提取中最高高客服 / 销售场景
ACON（指引 + 蒸馏）自适应高高生产级长视野 Agent

成本与复杂度评级来自原文，未联网核实

三种进阶策略的取舍

  • LLM 摘要：保留语义完整性，但每次压缩都要一次模型调用，可能丢失细节。原文建议只保留核心意图、重要决定、关键数字和待解决问题。
  • 分层压缩：最近 5 轮保留原文，5–20 轮前压缩为摘要，20 轮以前只保留关键事实。越旧越激进。
  • 结构化提取：提取 CONTEXT / ENTITIES / DECISIONS / PENDING / USER_PREFERENCES 等字段。信息密度最高，但提取质量依赖模型，可能漏掉隐式信息。
查看分层压缩与结构化提取的原文示意代码 
class HierarchicalCompression:
    """越旧的信息压缩越激进"""

    def compress(self, messages):
        total = len(messages)
        result = []
        for i, msg in enumerate(messages):
            age = total - i
            if age <= 5:
                result.append(msg)              # 最近 5 轮：原文
            elif age <= 20:
                if i % 4 == 0:                  # 5-20 轮前：摘要
                    batch = messages[i:i+4]
                    result.append(self.summarize_batch(batch))
            else:
                pass  # 20 轮以前：只保留关键事实
        return result


class StructuredExtractor:
    """从对话中提取结构化信息"""

    def extract(self, conversation):
        prompt = f"""
        从以下对话中提取关键信息，以结构化格式输出：
        {conversation}
        输出格式：
        CONTEXT: 当前在做什么
        ENTITIES: 提到的关键实体
        DECISIONS: 已做出的决定
        PENDING: 待解决的问题
        USER_PREFERENCES: 用户表达的偏好
        """
        return llm.invoke(prompt)

生产实践

触发式压缩，
组合优于单一。

原文推荐把上下文控制在窗口 75% 以内，按阈值触发压缩。ACON 的两个机制常被误传成“40%/60%/95% 三阈值”，原文明确说那不是事实。

ACON：指引优化 + 小模型蒸馏

ACON 原论文（arXiv:2510.00615）由两个核心机制构成：第一，把“该压缩什么、保留什么”写成一段可优化的自然语言指引，通过对比成功与失败轨迹不断 refine；第二，把大模型生成的高质量压缩样本蒸馏到小模型，作为生产环境的廉价 compressor。

原文特别提醒

ACON 并不是按 40% / 60% / 95% 三阈值切换。原文称这是常见误传，不要在面试中引用。具体数字以论文为准。

混合策略：最近原文 + 中期摘要 + 远期结构化

生产级管理器通常按顺序拼上下文：System Prompt 必留；最近 N 轮保留原文；预算还有余量时，用向量检索补相关历史；更早的对话用摘要兜底。原文的示例把 max_context 设为窗口的 75%，预留 25% 给输出。

查看生产级上下文管理器的原文代码 
class ProductionContextManager:
    """组合多种策略的生产级上下文管理"""

    def __init__(self, config):
        self.max_context = config.max_tokens * 0.75  # 预留 25% 给输出
        self.buffer_size = config.buffer_turns
        self.vector_store = config.vector_store

    def build_context(self, current_query, full_history):
        context = []
        budget = self.max_context

        # 1. System Prompt（必须保留）
        context.append(self.system_prompt)
        budget -= count_tokens(self.system_prompt)

        # 2. 最近 N 轮原文（高保真）
        recent = full_history[-self.buffer_size * 2:]
        context.extend(recent)
        budget -= count_tokens(recent)

        # 3. 语义检索相关历史（按需补充）
        if budget > 1000:
            relevant = self.vector_store.search(current_query, top_k=3)
            for doc in relevant:
                if count_tokens(doc) < budget:
                    context.insert(1, {"role": "system",
                                      "content": f"相关历史：{doc}"})
                    budget -= count_tokens(doc)

        # 4. 旧对话摘要（兜底）
        if len(full_history) > self.buffer_size * 2:
            old = full_history[:-self.buffer_size * 2]
            summary = self.summarize(old)
            context.insert(1, {"role": "system",
                              "content": f"历史摘要：{summary}"})
        return context

“中间丢失”效应

开头（高）中间（容易被忽略）结尾（高）

实践建议：最重要的指令放开头（System Prompt），当前用户消息放结尾，中间放参考资料和历史上下文。

原文的四条关键洞察

简单未必差：掩码和截断把成本减半，可靠性往往优于摘要。摘要≠万能：通用摘要捕获“发生了什么”，但丢失“进展到哪了”。场景决定策略：工具密集型用掩码，对话密集型用摘要。组合优于单一：最佳实践是最近原文 + 中期摘要 + 远期结构化提取。

锚点保留

有些话，
一句都不能丢。

摘要是有损压缩。丢一句寒暄没关系，丢掉“不能删除线上数据”就可能让整个任务跑偏。锚点要独立存储，不进入摘要器。

永远不压缩的五类信息

  • 用户最初的需求原文，不是转述
  • 明确的约束和禁止项，例如“不要改数据库 schema”“输出必须是 JSON”
  • 已经确认的决策，例如“用方案 B，不用方案 A”
  • 当前子目标，随进度更新，但始终显式存在
  • 关键标识：文件路径、订单号、变量名、接口名

实现上，锚点用独立的结构化字段保存，不混进摘要文本。拼上下文时把它渲染成单独的 system 区块，放在历史摘要之后、最近消息之前。锚点要小，只放不可丢的事实；长文档仍走摘要或检索。

from dataclasses import dataclass, field


@dataclass
class AnchorState:
    """任务锚点：独立持久化，任何压缩策略都不得修改它"""

    original_request: str
    constraints: list[str] = field(default_factory=list)
    decisions: list[str] = field(default_factory=list)
    current_subgoal: str = ""
    identifiers: dict[str, str] = field(default_factory=dict)

    def render(self) -> str:
        parts = [
            f"原始需求：{self.original_request}",
            f"当前子目标：{self.current_subgoal}",
        ]
        if self.constraints:
            parts.append("约束与禁止项：\n" + "\n".join(
                f"- {c}" for c in self.constraints))
        if self.decisions:
            parts.append("已确认决策：\n" + "\n".join(
                f"- {d}" for d in self.decisions))
        if self.identifiers:
            pairs = "；".join(f"{k}={v}" for k, v in self.identifiers.items())
            parts.append(f"关键标识：{pairs}")
        return "\n".join(parts)


class ContextAssembler:
    """锚点单独成块，放在历史摘要之后、最近消息之前"""

    def __init__(self, max_tokens: int):
        self.max_tokens = max_tokens

    def build(self, system_prompt, anchors, history_summary,
              recent_messages):
        head = [{"role": "system", "content": system_prompt}]
        if history_summary:
            head.append({"role": "system",
                         "content": f"历史摘要：\n{history_summary}"})
        head.append({
            "role": "system",
            "content": f"任务锚点（不可违背）：\n{anchors.render()}",
        })

        # 预算不够时从最旧的最近消息开始丢；锚点区块永不裁剪
        recent = list(recent_messages)
        while count_tokens(head + recent) > self.max_tokens and recent:
            recent.pop(0)
        return head + recent

摘要补救

摘要压坏了，
怎么发现、怎么补？

自由文本摘要是黑盒：漏了关键决策也看不出来。原文从三处下手：强制结构化、摘要里留指针、压缩后做一致性检查。

三个补救动作

  1. 强制结构化输出：摘要必须回答固定字段——目标、已完成、未完成、关键决策、关键数据、待确认。字段缺失比文字啰嗦更容易被发现。
  2. 摘要里留指针：提到文件、工具调用、外部单据时保留归档 id。原文不删除，只是移出上下文；需要细节时按 id 回查。压缩的是对话，不是知识。
  3. 压缩后做一致性检查：只给模型看压缩后的上下文，让它复述当前目标和约束，再和锚点比对。对不上说明这次压缩压坏了关键信息，应回退或重新压缩。

from pydantic import BaseModel, Field


class StructuredSummary(BaseModel):
    goal: str
    done: list[str] = Field(default_factory=list)
    pending: list[str] = Field(default_factory=list)
    decisions: list[str] = Field(default_factory=list)
    key_data: list[str] = Field(default_factory=list)
    open_questions: list[str] = Field(default_factory=list)
    refs: list[str] = Field(default_factory=list)  # 原文归档 id


class SummaryCompressor:
    def __init__(self, llm, archive):
        self.llm = llm
        self.archive = archive  # put(messages) -> id, get(id) -> messages

    async def compress(self, messages):
        archive_id = await self.archive.put(messages)  # 原文先归档
        prompt = f"""把以下对话压缩为 JSON 摘要。
只能使用对话中出现的信息；拿不准的内容放进 open_questions。
对话：
{messages}
"""
        raw = await self.llm.invoke(prompt, response_format="json")
        summary = StructuredSummary.model_validate_json(raw)
        summary.refs.append(archive_id)
        return summary

    async def check(self, summary, anchors) -> bool:
        """压缩后复述目标与约束，对不上说明压坏了"""
        answer = await self.llm.invoke(f"""只根据下面的摘要回答：
1. 当前任务目标是什么？
2. 有哪些不能违反的约束和已确认的决策？
摘要：
{summary.model_dump_json()}
""")
        verdict = await self.llm.invoke(f"""锚点：
{anchors.render()}

复述：
{answer}

复述与锚点是否一致？只回答 yes 或 no。
""")
        return verdict.strip().lower().startswith("yes")

跨块关联

靠结构，
不靠模型的记忆。

按时间切摘要，会把同一个子任务的信息切散。解法是给结构：消息带 turn_id 和 subtask_id，摘要按子任务聚合，任务状态表全量保留。

  • 每条消息带 turn_id 和 subtask_id，摘要按子任务聚合，而不是按固定时间窗切。
  • 维护任务状态表：子任务 → 状态 → 产出 → 依赖。这张表全量保留、永不压缩，跨块的因果关系都挂在它上面。
  • 需要历史细节时，用当前 query 检索历史消息：关键词和向量混合召回，取 top-k 拼回上下文。

纯向量检索对编号类信息不敏感：订单号 A123 和 A124 在向量空间里往往非常接近，通常要靠关键词精确匹配才能可靠区分。所以混合检索里两路都要留。

class TaskStateTable:
    """任务状态表：全量注入、永不压缩"""

    def __init__(self):
        self.nodes: dict[str, SubtaskNode] = {}

    def ready(self) -> list[SubtaskNode]:
        """依赖已全部完成、自己还没开始的子任务"""
        return [
            n for n in self.nodes.values()
            if n.status == TaskStatus.TODO
            and all(d in self.nodes
                    and self.nodes[d].status == TaskStatus.DONE
                    for d in n.depends_on)
        ]

    def messages_of(self, subtask_id, history):
        """按子任务聚合消息，而不是按时间窗切"""
        return [m for m in history
                if m.get("subtask_id") == subtask_id]


class HybridHistorySearch:
    """关键词 + 向量混合召回：编号靠关键词，语义靠向量"""

    def search(self, query: str, top_k: int = 5):
        kw = self.keyword_index.search(query, top_k)
        vec = self.vector_index.search(query, top_k)
        return self._rrf_merge(kw, vec)[:top_k]

    def _rrf_merge(self, *ranked_lists):
        """Reciprocal Rank Fusion：按名次融合"""
        scores = {}
        docs = {}
        for ranked in ranked_lists:
            for rank, doc in enumerate(ranked, start=1):
                doc_id = doc["id"]
                scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (60 + rank)
                docs[doc_id] = doc
        return [docs[i] for i in sorted(
            scores, key=lambda i: scores[i], reverse=True)]

常见误区 / 面试追问

八个问题，
分清成本和效果。

前三个是误区，后五个是追问。回答时先给结论，再讲成本和适用条件。

误区 01

“上下文窗口越大越好 / 越大就不需要压缩”

更大的窗口意味着更高成本、更大延迟和更严重的“中间丢失”。即使 200K 窗口，长对话仍会导致成本线性增长和注意力质量下降。压缩不仅省钱，还能提高模型注意力的质量。

误区 02

“只要不超过上下文限制就没问题”

即使不超限，上下文中的噪声也会降低准确率，也就是“上下文腐化”。精简、高相关性的上下文优于冗长的完整历史。

误区 03

“LLM 摘要是最佳策略”

研究表明简单的观察掩码在总效率上不逊于 LLM 摘要。摘要额外消耗约 7%+ 成本（原文经验估算值，实际因场景而异），且不总能保留正确信息。应按场景选择，而不是默认最复杂的方案。

追问 04

摘要压缩的成本问题怎么解决？

每次摘要需要一次额外 LLM 调用，可能占总成本的 7%+。优化：只在 token 超阈值时触发摘要；用小模型做摘要；用观察掩码替代 LLM 摘要。

追问 05

如何评估压缩策略的质量？

两个维度：信息保留率，即压缩后 Agent 能否正确回答依赖历史信息的问题；成本效率，即总 token 消耗，包含压缩调用本身的开销。原文提到 LoCoBench-Agent 是专门评估长上下文压缩的基准。

追问 06

增量摘要 vs 全量重新摘要？

增量摘要每次只处理新消息，更快更便宜，但可能累积误差；全量重新摘要更准确但成本高。实践中用增量摘要 + 定期全量校正的混合方式。

追问 07

Claude 的 Server-Side Compaction 是什么？

原文称 Anthropic 在 Claude Sonnet 4.6+ / Opus 4.6+ 上提供服务端自动压缩（context editing / compaction）：对话接近上限时，由服务端策略性删除或折叠旧的 tool_result 与思考块。早期 Sonnet 4 / Opus 4 不带这套原语，需要客户端自己实现。它和 Memory Tool（memory_20250818）配合时，被压缩掉的内容可以先落盘再检索回来。

追问 08

锚点保留和摘要是什么关系？

互补，不是替代。摘要压缩历史对话，锚点保存不可丢的事实，单独存储、不经过摘要器。每次拼上下文时锚点作为独立 system 区块全量注入。锚点要小，只放需求、约束、决策、子目标和关键标识；长文档仍走摘要或检索。

中级 · Memory & State · 可交互讲解

记忆放哪里，
决定它能回答什么。

Agent 长期记忆有三类存储介质：向量擅长语义相似度，结构化存储擅长精确字段查询，知识图谱擅长关系推理与时间推理。生产系统通常走混合架构，而不是三选一。

关键边界：向量检索不是“理解”，只能找语义相近的内容；图谱也不是把所有信息都存成三元组，只存实体、关系和关键事实。

三种介质

同样是“记住”，
查法完全不同。

向量存高维浮点，查语义相似度；结构化存表 / 键值 / 文档，查精确字段；知识图谱存节点、边和属性，查多跳关系和时间有效性。

三种长期记忆存储介质的核心区别
介质数据结构查询能力典型场景
向量高维浮点向量语义相似度对话历史、文档检索
结构化（SQL / NoSQL）表 / 键值 / 文档精确字段查询用户画像、偏好、配置
知识图谱节点 + 边 + 属性多跳推理 + 时间推理实体关系、事实追踪

向量记忆

意思相近，
就能找出来。

文本编码成向量，按余弦相似度找最近邻。不需要预定义 Schema，语义理解强；但相似不等于理解，也不支持关系和时间推理。

优势
  • 语义理解：按含义匹配，不靠关键词
  • 灵活：不需要预定义 Schema
  • HNSW 索引在百万级数据上仍保持毫秒级检索（原文表述）
劣势
  • 语义相近但含义不同的内容可能被错误检索
  • 不支持关系推理：“A 的上级是 B，B 的上级是谁？”
  • 不支持时间推理：“上周和这周的偏好有什么变化？”
查看向量记忆的原文代码 
class VectorMemory:
    def store(self, text: str):
        embedding = embed_model.encode(text)  # 文本 → 向量
        self.index.add(embedding, metadata={"text": text})

    def retrieve(self, query: str, top_k=5):
        query_vec = embed_model.encode(query)
        results = self.index.search(query_vec, top_k)
        return results

memory.store("用户是 Python 开发者，偏好 FastAPI")
memory.store("上次讨论了数据库优化，使用了 PostgreSQL")
results = memory.retrieve("推荐一个 Web 框架")

结构化记忆

字段对得上，
就别绕语义。

用户画像、偏好、配置这类键值化数据，用 PostgreSQL、DynamoDB 或 Redis 直接查字段，延迟低、一致性强、容易审计和迁移。

优势
  • 精确查询：按字段名直接获取
  • 强一致性：ACID 事务支持
  • 低延迟：主键查询毫秒级
  • 易审计、易迁移
劣势
  • 不支持模糊匹配：“偏好类似 FastAPI 的框架”无法直接用 SQL 表达
  • Schema 演化成本高
  • 不擅长关系推理
查看结构化记忆的原文代码 
class StructuredMemory:
    """适合用户画像、偏好等键值化数据"""

    def __init__(self, db):
        self.db = db  # PostgreSQL / DynamoDB / Redis

    def update_profile(self, user_id, updates: dict):
        self.db.upsert("user_profile", user_id, updates)

    def get_profile(self, user_id):
        return self.db.get("user_profile", user_id)

    def query_by_attribute(self, attr, value):
        return self.db.query(
            f"SELECT * FROM users WHERE {attr} = ?", value)

知识图谱记忆

谁和谁有关，
什么时候变的。

向量记忆能记住“张三在公司 A 工作”和“张三跳槽到公司 B”，但没法判断哪条最新。知识图谱用带时间有效性的边，直接找到当前有效的关系。

张三 --[works_at, 2024-01 ~ 2025-05]--> 公司 A 张三 --[works_at, 2025-06 ~ now]--> 公司 B 查询“张三现在在哪？” → 公司 B

Graphiti 的混合检索架构

用户交互
→
LLM 提取实体与关系
知识图谱：节点 / 边 / 双时间线
→
图遍历语义向量BM25 关键词
RRF 融合排序
→
注入 LLM 上下文

Graphiti 用双时间线：时间线 T 是事件实际发生的时间，时间线 T' 是数据被系统记录的时间。每条事实还带 valid_from / valid_to，支持“张三 2024 年 6 月在哪工作”和“我们什么时候得知张三跳槽”两类查询。多个 Agent 共享同一张图时，任何一个 Agent 的更新都对其他 Agent 可见；写入前先找冲突事实，把旧事实标记失效，再写新事实。

延迟提醒：原文实测 Graphiti 检索阶段不调用 LLM，但中位数延迟 2–3 秒，受图查询深度和 Neo4j 网络开销影响，并非常被引用的“300ms”。生产需要做延迟测试并设置 SLA。以上为原文版本数据，本页未联网核实。

先看查询，

混合架构

对话历史进向量库；抽取实体和关系进图库；用户属性进结构化库。查询时三路检索再合并。Mem0 的混合方案就是向量做语义记忆、图数据库做关系追踪，统一 API 对上层透明。

查看 HybridMemory 的原文代码 
class HybridMemory:
    def __init__(self):
        self.vector_store = ChromaDB()       # 语义检索
        self.knowledge_graph = Neo4j()       # 关系推理
        self.profile_store = PostgreSQL()    # 结构化属性

    async def store(self, interaction):
        # 1. 对话历史 → 向量存储
        self.vector_store.add(interaction["text"])

        # 2. 提取实体和关系 → 知识图谱
        entities = extract_entities(interaction["text"])
        for entity in entities:
            self.knowledge_graph.upsert(entity)

        # 3. 用户属性 → 结构化存储
        profile_updates = extract_profile(interaction["text"])
        self.profile_store.update(interaction["user_id"], profile_updates)

    async def retrieve(self, query, user_id):
        semantic_results = self.vector_store.search(query, top_k=5)
        entities = extract_entities(query)
        graph_results = self.knowledge_graph.query(entities)
        profile = self.profile_store.get(user_id)
        return merge(semantic_results, graph_results, profile)

框架横评

四个框架，
四种记忆抽象。

原文把 2026 年称为“Agent Memory 元年”。Mem0、Zep、LangMem、Letta 的差异，本质是“记忆是什么”的抽象不同。

原文的四大 Agent Memory 框架对比
框架出身核心思路记忆底座
Mem0独立记忆层产品LLM 抽取原子事实 → 混合存储向量库 + 图数据库
ZepGraphiti 作者团队时序知识图谱（双时间线）Neo4j + 混合检索（Graphiti 引擎）
LangMemLangChain 官方LangGraph 之上的记忆原语可插拔 Store（后端无关）
Letta基于 MemGPT 研究类 OS 的分页式自管理记忆块存储（core）+ 向量（archival）

一句话区分

  • Mem0：把记忆抽象成原子事实，粒度最细，接入最快。
  • Zep：把记忆抽象成带时间戳的图结构，最强于关系推理和时间推理。
  • LangMem：借鉴认知科学的三分类（semantic / episodic / procedural），不同类型走不同写入和检索策略。
  • Letta：把记忆抽象成计算机内存层级，Agent 通过 function call 自己翻页（page in / out）。

更新与检索的机制差异

四个框架的冲突处理与检索方式
框架更新机制检索方式
Mem0LLM 判定新事实与旧事实关系，四态 ADD / UPDATE / DELETE / NOOP向量相似度 + 图遍历，返回扁平事实列表
Zep双时间线：旧边自动失效，新边生效，保留全部历史向量 + BM25 + 图遍历，RRF 融合
LangMem开发者在 graph 节点定义更新逻辑可插拔 Store，策略由开发者定
LettaAgent 调用 replace 工具改写 core memory，需 guardrail 兜底core memory 常驻，需要时 Agent 主动检索 archival

最重要的范式差异：Mem0 / Zep / LangMem 是系统在用户无感的情况下自动管理记忆，更像数据库；Letta 走 Agent 自主管理路线，记忆操作本身是 Agent 可调用的工具，更像大脑。

自研 vs 框架

自研与使用框架的取舍
维度用框架自研
冷启动速度几行代码接入，立即可用从头实现抽取 / 冲突 / 检索

定制灵活性受框架抽象约束记忆类型、更新策略完全可控

常见误区 / 面试追问

八个问题，
从“一把梭”到一致性。

前四个是误区，后四个是追问。回答时先讲介质边界，再讲混合与一致性。

误区 01

“向量数据库能解决所有记忆需求”

向量检索基于相似度，不是真正的理解。它无法回答“A 和 B 是什么关系？”或“这个信息是什么时候变的？”等需要结构化推理的问题。

误区 02

“知识图谱太复杂，不值得用”

对于简单应用确实如此。但当 Agent 需要追踪实体关系、处理矛盾信息或做时间推理时，知识图谱的价值会迅速超过构建成本。Graphiti 等框架已大幅降低门槛。

误区 03

“知识图谱就是把所有信息都存成三元组”

不是所有信息都适合图谱。对话历史、非结构化文档适合向量；用户属性配置适合结构化；图谱只存实体、关系和关键事实。混合架构是最佳实践。

误区 04

“构建知识图谱必须预定义完整 Schema”

Graphiti 等现代框架支持 learned ontology：从数据中自动学习 Schema，同时支持预定义的 prescribed ontology 约束关键关系。

追问 05

向量检索返回语义相似但实际无关的内容怎么办？

两层解决：加 Reranker 对检索结果做精排；结合结构化元数据过滤（按用户 ID、时间范围、类别筛选后再做语义检索）。

追问 06

混合架构的一致性如何保证？

同一条信息在向量存储和图谱中需要同步更新。实践中用事务性写入或最终一致性。删除尤其要注意：向量存储和图谱里都要清理。

追问 07

图谱记忆的实体提取准确率不够怎么办？

三层保障：用专门的 NER 模型做初步提取；LLM 做上下文理解和关系推理；对关键事实做人工审核或交叉验证。

追问 08

图谱和 RAG 的关系是什么？

GraphRAG 是两者的结合：用知识图谱增强 RAG 检索。传统 RAG 只做文档级语义检索，GraphRAG 可以在检索后利用图结构做关系推理和多跳问答。

中级 · Memory & State · 可交互讲解

下周回来，
它还记得你。

持久化记忆让 Agent 跨会话保留知识。核心是双层存储：短期记忆留在上下文窗口，长期记忆落到外部存储。向量库管语义检索，结构化库管精确字段，图库管实体关系。

关键边界：LLM 本身无状态，产品里的“记忆”完全是工程实现。不是所有对话都值得记住，写入、去重、衰减、整合缺一不可。

为什么需要

没有记忆，
每次都是陌生人。

会话 1 用户说“我是 Python 开发者”，会话 2 问“推荐个框架”。没有持久化记忆，Agent 可能推荐 Java 框架；有了记忆，它检索到偏好后推荐 FastAPI 或 Django。

LLM 本身是无状态的。上下文窗口里的历史只在当前会话有效，会话结束就消失。持久化记忆把值得保留的信息写到外部存储，下次会话再检索回上下文。

提取去重衰减整合

原文把生命周期拆成四步：从对话中提取值得记忆的事实；检查是否已有类似记忆，有则更新、无则新增；按时间衰减旧记忆的权重；定期合并碎片化的记忆。

架构

双引擎，
三套存储。

持久化记忆 = Agent 挂双引擎（提取落库 + 检索回灌），底层是向量、关系、图三套持久层。每套存储擅长的问题不同。

实现方式

从向量库，
到记忆编排层。

原文给了三层实现：直接用向量数据库；用 LangGraph + MongoDB 的跨线程 Store；用 Mem0 这类记忆编排层，自动处理提取、存储、检索和去重。

方式 1：向量数据库

把每条记忆编码成向量，写入集合；检索时用 query 向量找最近邻，并按 user_id 过滤，保证用户间隔离。

查看 VectorMemory 的原文代码 
import chromadb
from sentence_transformers import SentenceTransformer

class VectorMemory:
    def __init__(self):
        self.client = chromadb.PersistentClient(path="./memory_db")
        self.collection = self.client.get_or_create_collection("agent_memory")
        self.encoder = SentenceTransformer("all-MiniLM-L6-v2")

    def store(self, user_id: str, content: str, metadata: dict = None):
        embedding = self.encoder.encode(content).tolist()
        self.collection.add(
            ids=[f"{user_id}_{uuid4()}"],
            embeddings=[embedding],
            documents=[content],
            metadatas=[{"user_id": user_id, "timestamp": now(),
                        **(metadata or {})}]
        )

    def retrieve(self, user_id: str, query: str, top_k: int = 5):
        results = self.collection.query(
            query_embeddings=[self.encoder.encode(query).tolist()],
            n_results=top_k,
            where={"user_id": user_id}
        )
        return results["documents"][0]

方式 2：LangGraph + MongoDB

LangGraph 的跨线程 Store 以 (memories, user_id) 为命名空间，节点里先检索、把记忆拼进 system 上下文，再把新事实 put 回去。

查看 LangGraph + MongoDB 的原文代码

方式 3：Mem0 记忆编排层

Mem0 自动处理提取、存储、检索和去重。用户说“最近开始学习 Go 语言”，它会判断这是新信息还是对旧信息的更新。

生命周期管理

写入容易，
维护才难。

提取、去重、衰减、整合四步组成一个循环。原文的时间衰减规则是：每天乘 0.99；相关度低于 0.05 且访问次数少于 2 次时删除。

查看 MemoryLifecycle 的原文代码 
class MemoryLifecycle:
    """记忆的完整生命周期"""

    async def process_interaction(self, user_id, conversation):
        # 1. 提取：从对话中提取值得记忆的信息
        facts = await self.extract(conversation)

        # 2. 去重：检查是否已有类似记忆
        for fact in facts:
            existing = self.retrieve_similar(user_id, fact, threshold=0.9)
            if existing:
                await self.update(existing.id, fact)   # 更新而非重复
            else:
                await self.store(user_id, fact)

        # 3. 衰减：降低旧记忆的权重
        await self.decay_old_memories(user_id)

        # 4. 整合：定期合并碎片化的记忆
        if self.should_consolidate(user_id):
            await self.consolidate(user_id)

    async def decay_old_memories(self, user_id):
        memories = self.get_all(user_id)
        for mem in memories:
            age_days = (now() - mem.created_at).days
            mem.relevance *= 0.99 ** age_days  # 每天衰减 1%
            if mem.relevance < 0.05 and mem.access_count < 2:
                await self.delete(mem.id)

注意：衰减是乘在相关度上的指数项，不是线性减法。年龄越大，衰减越快；访问次数高、相关度高的记忆能撑更久。

用户偏好学习

从记住事实，
到了解一个人。

偏好常常是隐式的、会随时间漂移的。原文给出三条前沿路径：PAMU 感知偏好变化、动态画像做结构化聚合、Memory-R1 用强化学习学记忆操作。

偏好分三类

  • 显式：“请用中文回复”“代码示例用 Python”，用户直接说出，一次提取即可。
  • 隐式：“用户总追问技术细节 → 偏好深度分析”，需要从行为归纳。
  • 演化中：“三个月前用 React，最近开始学 Vue”，需要持续追踪。

PAMU：短期波动 + 长期趋势

PAMU（Preference-Aware Memory Update）用滑动窗口平均捕捉短期波动，用指数移动平均（EMA）捕捉长期趋势，再融合两路信号检测偏好漂移。原文示例的融合公式是 0.6 × EMA + 0.4 × 滑动窗口平均，EMA 平滑因子 alpha=0.3。衰减只回答“要不要遗忘”（见 048），PAMU 还要回答“偏好是不是变了、要不要主动适配”。

动态用户画像

偏好项是零散的，动态画像把它们聚合成持续演进的结构化档案：技术水平、偏好语言、沟通风格、领域专长。字段初始为 unknown，随交互逐步具化。关键纪律是“有证据才更新”，不能靠模型臆测填充。

Memory-R1：把记忆操作当动作空间

Memory-R1 的四个记忆动作
动作含义作用
ADD新增记忆写入新事实 / 偏好
UPDATE修改已有记忆偏好变化时覆盖旧值
DELETE删除记忆清除过时或错误信息
NOOP不操作当前事件不值得改动记忆库

原文称 Memory-R1 仅用 152 条训练样本，就在多个长期记忆基准上超越 Mem0 等强基线。NOOP 尤其关键：它避免 Agent 对无信息量的对话强行写入噪声。

这在思路上和 103 Agentic-RL / GRPO 一致：记忆管理的下一站，可能不是更复杂的启发式规则，而是用 RL 让 Agent 自己学会“记什么、改什么、忘什么”。

检索优化

写入容易，
检索才是胜负手。

Mem0 论文和 MemMachine 的消融实验都表明：检索阶段的优化（+4.2%）远比摄入阶段（+0.8%）影响大。原文给了四个方向。

1. 多因子打分

Stanford 的 Generative Agents 用三因子加权：score = α_recency × recency + α_importance × importance + α_relevance × relevance。其中 recency = 0.995 ** hours_since_last_access，importance 由 LLM 打 1–10 分再归一化，relevance 是余弦相似度。论文中三个 α 都取 1。

2. 多信号融合

Mem0 2025 的算法并行跑语义检索、BM25 关键词、实体匹配，再加权融合。原文数据：LoCoMo 92.5 / LongMemEval 94.4，平均每次检索不到 7K token；对比 full-context 方法要 25K+ tokens。

3. 两阶段检索

Query → Embedding → 向量 Top-50 → Reranker Top-5 → 注入上下文。向量召回宽，cross-encoder 精排准但只能跑 50–100 条候选。原文给出的生产管线延迟约 25–30ms；Mem0 实测全开 keyword + rerank + filter 约 0.41s。

4. Query 改写 / 检索 Agent

HyDE 让模型先生成假想答案，再用假想答案的向量检索，解决 query 太短、太抽象的问题。但 HyDE、BM25 hybrid、chunk rerank 都是单查询策略，解决不了依赖链。MemMachine 的解法是加一层 LLM 路由器，把查询分成 direct / decompose / iterative 三种策略。

以上性能数字均按原文版本呈现，本页未联网核实，也不代表当前产品实测。

原文给出的检索组合建议
场景推荐组合
轻量场景（<10 万条记忆、单用户）向量检索 + 三因子打分 + 时间衰减
生产场景（多用户、跨会话）多信号融合（vector + BM25 + entity）+ reranker
复杂推理（多跳、依赖链）上面的组合 + Retrieval Agent（query 路由 + decomposition）

安全与选型

记忆是资产，
也是攻击面。

MEXTRA 攻击可以通过 prompt injection 提取存储的记忆；恶意用户也能注入虚假信息。记忆必须被当作“可被操纵的不可信数据”。

  • 数据泄露：MEXTRA 攻击可通过 prompt injection 提取存储的记忆。
  • 记忆污染：恶意用户可注入虚假信息到 Agent 记忆中。
  • 隐私合规：GDPR 要求支持记忆的完全删除。
  • 防护：PII 脱敏、输入验证、完全删除（right to be forgotten）、用户间访问隔离。

常见误区 / 面试追问

六个问题，
从存储问到安全。

前两个是误区，后四个是追问。回答时先给判断，再解释机制。

误区 01

“向量数据库是唯一选择”

Google 的 Always On Memory Agent 用 SQLite + LLM 驱动的整合替代了向量数据库。向量检索适合语义查找，但结构化查询和关系推理需要其他存储方案。最佳实践是混合使用。

误区 02

“所有对话都应该存入记忆”

选择性存储是关键。寒暄、重复提问、中间推理步骤不值得持久化。只存储影响未来交互的信息：用户偏好、关键决定、重要事实。

追问 03

如何处理记忆冲突？

当新信息与旧记忆矛盾时，例如用户改了偏好，应该用新信息更新旧记忆，而不是让两者并存。Mem0 通过检索相似记忆 + LLM 判断是否为更新来自动处理。

追问 04

记忆安全的最大风险是什么？

MEXTRA 攻击证明存储的记忆可被 prompt injection 提取。防护需要：记忆内容脱敏、访问控制、输入验证，以及把记忆视为“可被操纵的不可信数据”。

追问 05

Memory Retrieval 怎么优化？纯向量检索为什么不够？

纯向量有三个硬伤：没有时间维度，昨天和半年前的记忆同等对待；没有重要性维度，“刷牙”和“我离婚了”被同等检索；ANN 召回有 false positive，会污染上下文。工业界标准方案是三因子打分 + 多信号融合 + 两阶段 rerank。原文称 Mem0 用这套方案在 LongMemEval 拿到 94.4，平均每次检索约 7K token，比 full-context 省 90%+。

追问 06

HyDE 等查询改写为什么不够用？

HyDE、BM25 hybrid、chunk rerank 都是单查询策略，只在原查询的一次表达上做文章。很多记忆问题是依赖链：要回答“我上次提到的那个客户的预算多少”，得先定位“上次提到的客户是谁”再查预算。MemMachine 的解法是 Retrieval Agent，把查询分成 direct / decompose / iterative，复杂查询走分解或链式查询；原文称 HotpotQA hard 上能到 93.2%（原文数据，未联网核实）。

先让用户看到第一个字，

Agent 多步工作流经常超过 15 秒，而用户在 3 秒后就开始流失（原文引 Nielsen Norman Group）。延迟优化分两条线：Streaming 降低“感知延迟”，缓存、并行、批处理降低“真实延迟”。原文称多层缓存可实现 27–73% 的延迟降低，APC 平均减少 27.28% 延迟和 50.31% 成本。

关键边界：本页的请求、耗时、缓存命中率和吞吐量都是固定教学数据，不冒充真实压测。27–73%、23×、27.28% 等数字按原文标注，未联网核实。

延迟构成

先拆开，
再谈优化。

原文给了一次 Agent 请求的典型拆分：总计约 5800ms，其中两轮 LLM 推理占大头，工具调用 1000ms。优化目标分两条：减少真实延迟，减少感知延迟。

环节原文典型耗时优化方向

两个目标

减少真实延迟：缓存、模型路由、并行化、批处理。减少感知延迟：Streaming，让用户立即看到输出开始。原文提醒：用户在 3 秒后开始流失（Nielsen Norman Group 研究，按原文引用），而多步 Agent 经常超过 15 秒。

Streaming

先给第一个字，
别让人干等。

Streaming 用 SSE 把 Token 逐个推给客户端。总生成时间不变，但 TTFT 变成用户真正感知到的等待。原文给的目标是 TTFT < 500ms。

@app.post("/chat")
async def chat_stream(request: ChatRequest):
    """SSE 流式响应"""

    async def generate():
        async for event in agent.stream(request.message):
            if event.type == "thinking":
                yield f"data: {json.dumps({'type': 'thinking', 'content': event.text})}\n\n"
            elif event.type == "token":
                yield f"data: {json.dumps({'type': 'token', 'content': event.text})}\n\n"
            elif event.type == "tool_call":
                yield f"data: {json.dumps({'type': 'tool', 'name': event.tool_name, 'status': 'calling'})}\n\n"
            elif event.type == "done":
                yield f"data: {json.dumps({'type': 'done'})}\n\n"

    return StreamingResponse(
        generate(),
        media_type="text/event-stream",
    )

关键指标是 TTFT（Time to First Token）：用户看到第一个字的时间。原文目标 TTFT < 500ms；整体延迟可能不变，但用户体验显著改善。上面代码只作阅读展示，本页不执行，也不启动任何服务。

常见踩坑

SSE 被 NGINX 缓冲，加 X-Accel-Buffering: no；原生 EventSource 只支持 GET，可用 @microsoft/fetch-event-source；Token 逐个渲染会导致页面卡顿，按 30–60ms 批量更新一次。

SSE vs WebSocket

单向用 SSE，
双向才上 WebSocket。

LLM 生成文本本质是“逐 token 单向输出”，SSE 的单向特性刚好匹配。需要双向音频、协作编辑或二进制流时，才用 WebSocket。

通信方向单向（服务器 → 客户端）双向（客户端 ↔ 服务器）
协议基础HTTP（text/event-stream）TCP 升级协议
自动重连原生支持需自行实现
断点续传Last-Event-ID 原生支持需自定义
消息格式文本文本 + 二进制
实现复杂度低中高（连接管理、心跳）

场景推荐理由

原文还解释了 MCP 的选择：MCP 传输层用 Streamable HTTP（HTTP POST + 可选 SSE 流式响应），而不是 WebSocket。原因是 MCP 通信以请求-响应为主，不需要全双工；HTTP+SSE 更简单、更容易穿透企业防火墙。原文提到社区已有讨论考虑增加 WebSocket 传输支持。

断线重连

协议层重连不够，
事件要能补发。

SSE 的 Last-Event-ID 只解决协议层重连。服务端不留事件、连接一断 run 就停，重连也接不上。恢复需要两个前提：事件有稳定序号，run 不依赖连接存活。

每个事件带 run_id、单调递增的 seq 和时间戳。SSE 的 id 字段携带 seq；服务端按它补发。原文固定的事件类型：

run.startedtext.deltatool_call.startedargs.deltatool_call.endedtool.resultrun.finishedrun.error

run 与连接解耦

  • LLM 调用和工具执行在服务端后台跑，连接只是订阅者。
  • 断网、刷新不影响 run 继续；重连是接着收，不是重新做。
  • 断线不能重跑：重跑再付一次 token 成本，还会重复副作用，比如邮件发两次。

事件缓冲与兜底

  • 每个 run 的事件按 run_id 写入 Redis Stream 或带持久化的环形缓冲。
  • 客户端带 run_id、last_seq 重连，服务端补发 seq > last_seq 的事件；先订阅再补发，避免中间丢事件。
  • 缓冲过期时返回 run 状态快照（当前步骤、已生成文本、工具状态），从快照 seq 往后推；宁可丢中间过程，也不能卡死。
  • 客户端按 seq 丢弃重复或更旧的事件，渲染保持幂等。

工具执行中重连

前端只显示工具状态，不重放中间输出。重连后查状态：running 继续等，done 补结果。工具长输出同样按 seq 进缓冲。

三个坑

  • args.delta 是 JSON 片段：前端自己拼会在半个 JSON 上解析失败，后端拼完整再推结构化事件。
  • 长连接会被中间设备掐断：每 30 秒发一次注释心跳（原文称经验值）。
  • 同一 run 必须由一处分配 seq：否则多实例序号乱；用 sticky 路由固定实例，或收敛到统一事件服务。

@dataclass
class RunEvent:
    run_id: str
    seq: int
    type: str
    data: dict
    ts: float = field(default_factory=time.time)

    def to_sse(self) -> str:
        payload = json.dumps(
            {"type": self.type, "data": self.data, "ts": self.ts},
            ensure_ascii=False,
        )
        return f"id: {self.seq}\nevent: {self.type}\ndata: {payload}\n\n"

class RunEventBuffer:
    """单 run 的事件缓冲：分配 seq、按 seq 补发、订阅新事件"""

    async def append(self, run_id: str, type_: str, data: dict) -> RunEvent:
        self._seq[run_id] += 1
        event = RunEvent(run_id, self._seq[run_id], type_, data)
        self._events[run_id].append(event)
        for q in list(self._subs[run_id]):
            q.put_nowait(event)
        return event

    def replay(self, run_id: str, last_seq: int) -> list[RunEvent] | None:
        """补发 seq > last_seq 的事件；缓冲不连续时返回 None"""
        buf = self._events.get(run_id)
        if not buf or buf[0].seq > last_seq + 1:
            return None
        return [e for e in buf if e.seq > last_seq]

@app.get("/runs/{run_id}/events")
async def stream_run_events(run_id: str, last_event_id: str | None = Header(None, alias="Last-Event-ID")):
    last_seq = int(last_event_id or 0)
    q = buffer.subscribe(run_id)        # 先订阅，再补发
    async def gen():
        try:
            history = buffer.replay(run_id, last_seq)
            if history is None:
                state, snap_seq = await run_store.load(run_id)
                snap = buffer.snapshot(run_id, state, snap_seq)
                yield snap.to_sse()
                if state.get("status") in ("finished", "failed"):
                    return
                sent = snap.seq
            else:
                for event in history:
                    yield event.to_sse()
                    if event.type in {"run.finished", "run.error"}:
                        return
                sent = history[-1].seq if history else last_seq
            while True:
                try:
                    event = await asyncio.wait_for(q.get(), timeout=30)
                except asyncio.TimeoutError:
                    yield ": keep-alive\n\n"
                    continue
                if event.seq > sent:
                    yield event.to_sse()
                    sent = event.seq
                if event.type in {"run.finished", "run.error"}:
                    return
        finally:
            buffer.unsubscribe(run_id, q)
    return StreamingResponse(gen(), media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})

多层缓存

从语义缓存，
到规划缓存。

原文把缓存分四层：KV Cache、Prompt Cache、Semantic Cache、Agentic Plan Cache。查询逐层兜底：语义缓存毫秒级，规划缓存跳过规划，都 miss 才落到 LLM。

Layer 1 · KV Cache

2–5×

推理层，框架内置；缓存 attention 的 Key-Value 矩阵，避免重复计算。长文本生成时原文称速度提升 2–5x。注意占用 GPU 显存，需要合理的驱逐策略。

Layer 2 · Prompt Cache

最高 ~85%

提供商层；缓存静态 Prompt 前缀的处理结果。原文称延迟最高可降低约 85%，成本降低 90%（Anthropic），具体取决于命中率和复用程度。静态内容放 Prompt 开头。

Layer 3 · Semantic Cache

毫秒级

应用层；对语义相似的查询返回缓存结果，Redis + 向量相似度搜索。适合 FAQ、重复查询、热门问题。相似度阈值太低会返回不准确的缓存。

Layer 4 · Agentic Plan Cache

-27.28%

Agent 专用（NeurIPS 2025）；缓存规划模板，新任务复用。原文称平均减少 27.28% 延迟和 50.31% 成本。传统缓存不适合 Agent，因为输出依赖环境；APC 缓存结构化规划而非具体输出。

批处理

静态、连续、
还是 Batch API。

批处理的目标是提高 GPU 利用率。原文对比三种策略：Static Batching、Continuous Batching、Batch API。它们适合的负载不同。

Static Batching

原理：收集固定数量的请求后一起处理。

优势：实现简单。

劣势：等待时间长，短请求被长请求拖慢。

Continuous Batching

原理：动态添加/移除请求，不等待批次填满；完成的请求立即释放资源，新请求立即注入计算流。

优势：吞吐量最高可提升约 23 倍（原文注明来自 vLLM 早期论文，实际取决于负载模式），延迟更低。

实现：vLLM、TGI、Triton Inference Server。

Batch API

原理：非实时任务提交批量请求。

优势：OpenAI Batch API 50% 折扣（原文示例）。

适用：评估、数据处理、报告生成。

延迟：24 小时内完成（非实时）。

原文的适用建议：实时交互用 Continuous Batching（vLLM）；离线任务用 Batch API；评估管道用 Batch API + 并行化。批处理提升的是吞吐，不是单个用户的等待时间；两者不要混为一谈。

并行化

独立调用同时跑，
有依赖的还得等。

原文给了两种并行：独立工具调用并行执行；推测性执行，在 Agent 思考时预先执行最可能的下一步。两者都能压缩真实延迟，但都有前提。

async def parallel_tool_calls(self, tools_to_call):
    """独立工具调用并行执行"""
    independent = self.find_independent(tools_to_call)
    dependent = self.find_dependent(tools_to_call)

    results = await asyncio.gather(*[
        self.call_tool(tool) for tool in independent
    ])

    for tool in dependent:
        result = await self.call_tool(tool)
        results.append(result)

    return results
    # 效果：3 个独立工具调用从 3s 降到 1s

推测性执行则是在 Agent 思考时，预先执行最可能的工具调用：先预测 likely tools，再 prefetch；如果预测正确，工具结果已经准备好。原文没有给命中率数字，只给了思路。

边界

并行化要先识别依赖图；有依赖的工具不能并发。推测性执行可能浪费算力和成本，也可能触发不必要的副作用，所以只适合可安全预取、无副作用的工具。原文没有承诺每个系统都能把 3s 降到 1s。

常见误区 / 面试追问

Streaming 不降总延迟，
缓存也不是越久越好。

原文列了 2 条误区和 8 条追问，其中 3 条是生产场景排障。高频点：感知延迟 vs 真实延迟、缓存 TTL、P99 飙升、长尾工具、长上下文、SSE 选型与重连。

误区 1

“Streaming 能减少总延迟。”

Streaming 不减少总延迟（总 Token 生成时间不变），它减少的是“感知延迟”——用户几百毫秒就看到第一个字开始输出，心理等待感大大降低。真正减少总延迟需要缓存、模型路由和并行化。

误区 2

“缓存会导致回答过时。”

设置合理的 TTL 和缓存失效策略即可。FAQ 类缓存可以设 24 小时，实时数据相关的查询不应缓存。语义缓存的相似度阈值也需要调优——太低会返回不相关的缓存结果。

追问 1

如何衡量延迟优化的效果？

四个关键指标：(1) TTFT（Time to First Token，感知延迟）；(2) P50/P95/P99 延迟（不同百分位的总延迟）；(3) 吞吐量（QPS，每秒处理的请求数）；(4) 缓存命中率（命中率越高，平均延迟越低）。

追问 2

Agent 多步执行的延迟如何优化？

(1) 规划缓存（APC）跳过规划阶段；(2) 并行工具调用（独立工具同时执行）；(3) 推测性执行（预取可能的工具结果）；(4) 分步 Streaming（每步结果实时推送）；(5) 早停（发现足够信息就提前结束）。

场景 1

P99 从 2 秒突然飙升到 12 秒，如何快速定位根因？

定位路径：(1) 检查 Trace，找出延迟增加发生在哪个环节（LLM 调用、工具执行、网络传输）；(2) 检查模型提供商状态，是否有服务降级或限流；(3) 检查缓存命中率是否下降，缓存失效可能导致大量请求走 LLM；(4) 检查工具服务延迟。快速止损：启用模型降级到更快模型、增加 KV Cache 容量、临时降低并发限制。

场景 2

一个工具每次调用要 3 秒，整体延迟怎么优化？

(1) 分析该工具是否可以优化或换用更快的替代方案；(2) 实施工具结果缓存，如果相同参数频繁调用；(3) 并行化，如果工作流中有其他独立工具，让它们并行执行；(4) 异步化，让工具在后台执行，先返回部分结果；(5) 预计算，如果可以预测用户可能需要的数据，提前加载到缓存。

场景 3

长上下文让延迟从 2 秒涨到 8 秒以上，怎么优化？

(1) 检查是否真的需要完整上下文，用 RAG 检索替代全文；(2) 优化 Prompt 结构，静态内容使用 Prompt Cache；(3) 使用支持长上下文的模型和框架；(4) 分块处理，将长任务拆分为多个短任务；(5) 考虑模型降级，对长上下文场景，专门的长上下文模型可能更经济。

追问 3

SSE 和 WebSocket 在 AI 应用中如何选型？

核心看通信方向：LLM 流式输出是单向的（服务器→客户端），用 SSE 就够了，且更简单、原生支持重连。需要双向通信（语音对话、协作编辑）或二进制传输（音频/视频流）时才用 WebSocket。原文称 ChatGPT、Claude 等都使用 SSE。

追问 4

MCP 为什么用 SSE 而不用 WebSocket？

MCP 通信模型是 JSON-RPC 请求-响应式，不需要全双工。HTTP+SSE 更简单、更容易部署、更容易穿透企业防火墙。原文提到社区已有讨论考虑增加 WebSocket 传输支持。

追问 5

SSE 原生支持断线重连，为什么还要自己做事件缓冲？

原生支持的只是协议层：浏览器会自动重连，并把最后收到的 id 通过 Last-Event-ID 带上。服务端要认这个 id、保留对应事件、按序补发，重连才有内容可接。如果 run 随连接结束、事件不落缓冲，重连只能重新开始或拿到空白流。重连也不等于重跑：LLM 和工具在服务端继续执行，客户端只是重新订阅。

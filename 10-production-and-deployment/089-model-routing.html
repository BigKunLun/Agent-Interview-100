别让所有请求，
都用最贵的模型。

模型路由在运行时按请求的复杂度、类型、延迟要求和成本约束，动态选择最合适的 LLM。简单问答用 GPT-4o-mini（原文示例 $0.15/M token），复杂推理用 GPT-4o（$2.50/M），极难问题用 o3（$10/M）。ICLR 2025 的 RouteLLM 证明：用 26% 的 GPT-4 调用可保住 95% 的 GPT-4 质量，成本削减约 85%。

关键边界：本页的请求、路由结果和成本对比是固定教学数据；模型价格与能力只按原文示例，不更新现价。RouteLLM 的 26% / 95% / 85% 按原文标注，未联网核实。

为什么需要路由

一个模型，
照顾不了所有请求。

原文把问题拆得很直接：全用最强模型，简单任务浪费；全用最便宜模型，复杂任务质量差；手动选，不可扩展。路由的目标是“刚好够用”。

全用最强模型

成本高，简单任务浪费。原文举例：GPT-4o 为 $2.50/M token，o3 为 $10/M token。

全用最便宜模型

复杂任务质量差。翻译、分类可能够用，多步推理和代码生成未必。

手动选择

不可扩展，需要领域知识；流量一大，人工判断跟不上。

智能路由

自动判断复杂度，路由到“刚好够用”的模型，平衡质量、成本和延迟。原文给的总体结果是 85% 成本削减 + 95% 质量保持。

原文版本、未联网核实

85% 成本削减、95% 质量保持来自原文对 RouteLLM（ICLR 2025）的转述；具体数字取决于流量分布、模型组合和评估集，不是每个系统都能复现。本页不把它写成当前事实。

四种路由策略

规则、分类器、
语义、级联。

原文列了四种策略：基于规则、分类器路由、语义路由、级联路由。它们可以组合使用，不是互斥的。

1. 基于规则

做法：关键词、输入长度、任务类别匹配。翻译走小模型，代码生成走中端，复杂推理走强模型。

优势：简单、快速、可预测。

劣势：规则维护成本高，无法处理边界情况。

2. 分类器路由

做法：训练小模型判断“这个请求需要强模型吗”。RouteLLM 用矩阵分解路由器，阈值 0.7。

优势：能处理规则覆盖不到的复杂度信号。

代价：需要偏好数据和训练；阈值要用业务数据校准。

3. 语义路由

做法：把查询和模型擅长领域都转成向量，找余弦相似度最高的模型。原文举例：代码、创意、推理、通用四类模型画像。

优势：不依赖关键词，能匹配语义相近的任务。

代价：需要维护模型画像和向量索引；相似不等于质量最优。

4. 级联路由

做法：先用小模型尝试，置信度 ≥ 0.8 就返回；不足再升级到强模型。

优势：确保质量下限。

代价：升级时成本翻倍（两次调用）；原文示例称只有约 20% 请求需要升级。

class RuleBasedRouter:
    """基于预定义规则路由"""

    def route(self, query):
        # 按任务类型
        if query.task_type == "translation":
            return "gpt-4o-mini"      # 翻译用小模型即可
        if query.task_type == "code_generation":
            return "claude-sonnet-4-5"  # 代码生成用中端模型
        if query.task_type == "complex_reasoning":
            return "o3"               # 复杂推理用最强模型

        # 按输入长度
        if len(query.text) < 100:
            return "gpt-4o-mini"      # 短查询用小模型
        elif len(query.text) < 2000:
            return "gpt-4o"
        else:
            return "claude-sonnet-4-5"  # 长文本用大上下文模型

class CascadeRouter:
    """先用小模型尝试，不确定时升级"""

    async def route_with_cascade(self, query):
        response = await self.call("gpt-4o-mini", query)
        if response.confidence > 0.8:
            return response  # 小模型够用
        response = await self.call("gpt-4o", query)
        return response

怎么选

有明确任务类型和长度信号，先用规则路由；有偏好数据、需要更细的复杂度判断，用分类器；任务类型跨领域、需要按语义匹配，用语义路由；最看重质量下限、能接受偶发双调用，用级联。生产系统通常规则 + 分类器 + 级联组合。

路由决策流

简单、中等、复杂，
各走各的路。

原文的流程图把请求分成三档：简单走小模型，中等走中端，复杂走强模型；小模型置信度不足时级联升级。

多维度路由决策

不只看质量，
还看成本、延迟、隐私。

原文的多维路由器给候选模型打分，默认权重是质量 0.4、成本 0.3、延迟 0.2、隐私 0.1，另外还要看可用性。

维度默认权重（原文示例）看什么
质量0.4模型在该类型任务上的预期表现
成本0.3每个 token 的价格
延迟0.2模型的响应时间
隐私0.1是否需要本地部署（敏感数据）
可用性—模型的当前健康状态

权重不是固定的。面向用户的实时问答更看重延迟，离线批处理更看重成本，涉及敏感数据时隐私维度会直接变成硬约束，而不是 0.1 的软权重。

RouteLLM 数字

26%、95%、85%，
分别是什么。

原文引用 RouteLLM（ICLR 2025）的三个核心数字。它们描述的是一个特定设置下的整体结果，不是每个请求的固定比例。

GPT-4 调用比例26%仅用 26% 的 GPT-4 调用

原文补充

原文还写了数据增强后的结果：95% 质量、仅 14% 强模型调用、成本削减 75–85%。这组数字和 26% 是不同设置，不能混着引用。分类器路由的推理时间原文称小于 10ms，成本几乎为零。

这三个数字回答的是“整体上能省多少、质量掉多少”，不是“每个请求该用哪个模型”。具体到单个请求，路由可能选小模型、中端模型，甚至比基线更贵的强模型。下面的成本对比会展示这种差异。

常见误区 / 面试追问

路由器不贵，
两个模型也不够。

原文列了 2 条误区和 2 条追问。核心是：路由开销很小；生产通常要 3–5 个模型；评估看质量保持率和成本削减率；路由是结构性需求。

误区 1

“路由器本身的开销会抵消收益。”

分类器路由（如 RouteLLM 的矩阵分解模型）推理时间 < 10ms，成本几乎为零。相比于将简单请求从 $2.50/M 路由到 $0.15/M 的节省，路由器开销微不足道。

误区 2

“两个模型就够了（强+弱）。”

实际生产系统通常需要 3–5 个模型：最轻量（FAQ/简单任务）→ 中端（一般任务）→ 高端（复杂推理）→ 特化模型（代码/数学/创意）。原文称 37% 的企业在 2026 年使用 5+ 个模型，该调查数字按原文时点，未联网核实。

追问 1

如何评估路由器的效果？

两个核心指标：(1) 质量保持率——路由后的整体质量 vs 全部使用强模型的质量（原文目标 > 95%）；(2) 成本削减率——路由后的总成本 vs 全部使用强模型的成本（原文目标 > 50%）。同时监控各模型的实际调用比例和各自的质量指标。

追问 2

更强的模型会不会让路由不再需要？

不会。即使最强的模型变得很便宜，不同模型在不同任务上仍有各自优势（速度、专业性、上下文长度）。而且新的强模型出来后，旧的模型变成“弱模型”，路由的价值持续存在。原文判断这是一个结构性需求。

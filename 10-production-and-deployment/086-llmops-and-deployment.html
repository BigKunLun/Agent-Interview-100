LLMOps 是面向 LLM 应用的运维体系：以使用模型为核心，主要成本从训练 GPU 转向运行时推理 API，迭代周期从周/月级缩到小时/天级。生产级 Agent 通常分五层部署：接入、编排、模型网关、数据与工具、可观测性。

关键边界：本页的请求、Trace、耗时、Token 和成本都是固定教学数据，不连接真实云服务或模型 API。成本数字仅用于演示，原文示例、未更新现价；缓存降本 90% 等结论按原文标注。

LLMOps vs MLOps

一个训练模型，
一个使用模型。

原文用十个维度对比 MLOps 与 LLMOps。核心差异是：MLOps 以训练模型为核心，LLMOps 以使用模型为核心；主要成本从训练 GPU 转到运行时推理 API。

维度MLOpsLLMOps
核心模型自训练模型预训练 LLM（API）
数据类型结构化数据非结构化文本
主要产物模型文件、特征Prompt、向量索引
迭代周期周/月级小时/天级
主要成本训练（GPU 时间）推理（API 调用）
评估方式AUC/F1/MSELLM Judge/人工

原文判断

LLMOps 不替代 MLOps，而是在其基础上扩展。企业通常需要两者协同工作：推荐系统、风控模型仍然需要 MLOps；LLM 应用需要 LLMOps 管 Prompt、RAG、评估和运行时成本。

LLMOps 核心组件

六个组件，
各管一段。

原文列了六个核心组件，并分别给了 MLOps 类比。它们不是六个独立工具，而是一条从 Prompt 到监控的链路。

Prompt 管理

LangSmith · Humanloop · PromptLayer

内容：Prompt 版本控制、A/B 测试、模板管理。

类比：MLOps 中的特征工程。

模型网关

LiteLLM · Portkey · Kong AI Gateway

内容：API 路由、负载均衡、故障转移、成本控制。

类比：MLOps 中的模型服务器。

RAG 基础设施

Pinecone · Weaviate · Chroma

内容：向量数据库、文档处理、索引更新。

类比：MLOps 中的特征存储。

评估管道

DeepEval · Ragas · Braintrust

内容：自动化评估、回归测试、LLM Judge。

类比：MLOps 中的模型验证。

可观测性

Langfuse · LangSmith · Arize Phoenix

内容：Trace/Span 追踪、成本监控、质量监控。

类比：MLOps 中的模型监控。

安全护栏

Guardrails AI · NeMo Guardrails

内容：输入/输出过滤、PII 检测、内容安全。

类比：MLOps 中的数据验证，但范围更广。

企业协同

MLOps 和 LLMOps，
不是二选一。

原文用保险行业举例：定价、欺诈检测、客户分群归 MLOps；智能客服、保单解释、理赔报告归 LLMOps。两者共享 CI/CD、监控基础设施和数据治理。

MLOps 管理

  • 定价模型：结构化数据 → 风险评分
  • 欺诈检测模型：交易数据 → 欺诈概率

  • 智能客服：用户问题 → 自然语言回答

部署策略

按规模选形态，
先 Serverless 再 K8s。

原文按用户规模给三档部署：早期/MVP 用 Serverless，中期用容器，大规模上 Kubernetes。用户数是原文示例阈值，固定教学数据。

早期 / MVP< 1000 用户（原文示例）
Serverless（Cloud Run / Lambda）；按用量付费，无需管理服务器。注意冷启动延迟 + 执行时间限制。
中期 / 增长1K–100K 用户（原文示例）
容器化（ECS / Cloud Run 持续运行）；自动扩缩容 + 健康检查；引入 Redis 缓存和 CDN。
大规模100K+ 用户（原文示例）
Kubernetes 集群；多区域部署 + 全球负载均衡；自建模型服务（vLLM）降低成本。

四件共同要事

  • 密钥管理：Vault / AWS Secrets Manager；不要把密钥写进代码或 Git。
  • 网络隔离：Agent 不直接访问公网；出口走白名单或代理。
  • CI/CD：代码和 Prompt 都走管道，避免 Prompt 改动绕过评审。
  • 可观测性：从 Day 1 接入 Trace，不要等出事再补。

常见误区 / 面试追问

不是加个 Prompt 管理，
也不是直接调 API。

原文列了 4 条误区和 4 条追问。高频点包括：LLMOps 与 MLOps 的关系、模型网关的必要性、Agent 部署的特殊性、小团队怎么起步。

误区 1

“LLMOps 就是 MLOps 加个 Prompt 管理。”

LLMOps 引入了全新的挑战维度：非确定性输出评估、Prompt Injection 安全、运行时成本控制、向量数据库管理等。这些不是简单地在 MLOps 上“加功能”，而是需要不同的思维方式和工具链。

误区 2

“用了 LLM API 就不需要 MLOps 了。”

大多数企业的 AI 系统同时包含传统 ML 模型和 LLM 应用。推荐系统、风控模型仍然需要 MLOps。LLMOps 和 MLOps 是互补关系，不是替代关系。

误区 3

“直接在应用代码里调 LLM API 就行。”

生产系统需要模型网关层来处理故障转移、限流、成本控制和缓存。直接调 API 会导致：单点故障、无法切换模型、成本失控、无法追踪。原文称 LiteLLM 或 Portkey 可以一行代码解决这些问题。

误区 4

“Agent 系统和普通 Web 服务部署一样。”

Agent 有独特的部署挑战：(1) 长时间运行（一次任务可能执行数分钟）；(2) 状态管理（多步执行需要检查点）；(3) 高内存需求（上下文窗口占用大量内存）；(4) 不确定的成本（每次请求的 Token 消耗不同）。

追问 1

LLMOps 的最大挑战是什么？

原文的答案是评估。传统 ML 有明确的量化指标（准确率、F1），但 LLM 输出的质量是主观且多维度的。如何自动化、可靠地评估 LLM 输出质量是 LLMOps 的核心难题，也是 LLM-as-Judge 等技术兴起的原因。

追问 2

小团队如何起步 LLMOps？

原文的最小可行方案：(1) Prompt 用 Git 版本管理；(2) 用 Langfuse（免费开源）记录所有请求和成本；(3) 维护 50 条 Golden Dataset 做回归测试；(4) 用 LiteLLM 统一多模型 API。原文称这四步一周内可以搭好。

追问 3

如何处理 Agent 的长时间运行任务？

(1) 异步执行：接收请求后立即返回任务 ID，客户端轮询或 WebSocket 推送结果；(2) 检查点机制：每步保存状态，支持断点恢复；(3) 超时保护：设置最大执行时间和最大步数；(4) 流式输出：中间结果实时推送给用户。

追问 4

选择框架还是自研？

原文的参考原则：如果需求匹配框架能力的 80%+，用框架（LangGraph）；如果需要深度定制或框架是瓶颈，自研核心 Agent 循环但复用社区工具（LiteLLM、Langfuse）。原文还强调：框架选择比模型选择更重要。

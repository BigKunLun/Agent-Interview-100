它没报错，
但答案已经错了。

Agent 的失败常常不是崩溃，而是质量退化：HTTP 200、输出看起来合理，实际不准确或不安全。所以要三层一起看：结构化日志记内容，分布式追踪记路径，指标加告警盯趋势。

关键边界：本页的请求日志、Trace、质量分和告警都是固定教学数据，不连接任何观测平台，也不读取真实日志。告警阈值按原文示例；真实系统要按自己的基线设定。

为什么不够

传统监控看服务，
Agent 还要看语义。

HTTP 200、CPU、内存、错误率能说明服务活着，但说明不了回答对不对、安不安全、贵不贵。

核心区别：Agent 的“失败”通常不是崩溃，而是质量退化。API 返回 200，输出看似合理，但实际不准确或不安全。这种“静默失败”只有通过语义级别的监控才能发现。

“存储很便宜，事故中缺少数据很贵”——宁可多记少用。原文举例：S3 存储约 $0.023/GB/月，一天 10 万请求的完整日志约 1–5GB。价格按原文示例，未联网更新。

三层架构

日志记内容，
Trace 记路径，指标盯趋势。

原文的三层可观测性：Layer 1 结构化日志，Layer 2 分布式追踪，Layer 3 指标加智能告警。三层不是替代关系。

Layer 1 · 结构化日志记内容：输入 / 输出、工具调用、Token 与成本、护栏触发。回答“这个请求到底说了什么”。
↓ 同一 request_id 串起来
Layer 2 · 分布式追踪记路径：Trace / Span 树，每步推理、工具调用、LLM 交互。回答“为什么慢、错在哪一步”。
↓ 聚合成趋势
Layer 3 · 指标 + 告警盯趋势：质量、性能、成本、安全，偏离基线自动告警。回答“现在整体是否健康”。

# Layer 1: 结构化日志
class AgentLogger:
    """Agent 专用的结构化日志"""

    def log_request(self, request_id, data):
        """记录完整的请求-响应对"""
        log_entry = {
            "request_id": request_id,
            "timestamp": datetime.utcnow().isoformat(),
            "user_id": data["user_id"],

            # 输入
            "input": data["user_message"],
            "system_prompt_version": data["prompt_version"],

            # 模型信息
            "model": data["model"],
            "model_version": data["model_version"],
            "temperature": data["temperature"],

            # 输出
            "output": data["response"],
            "tool_calls": data.get("tool_calls", []),

            # 资源消耗
            "input_tokens": data["usage"]["input_tokens"],
            "output_tokens": data["usage"]["output_tokens"],
            "cost_usd": data["cost"],
            "latency_ms": data["latency_ms"],
            "ttft_ms": data.get("ttft_ms"),

            # 安全
            "guardrail_triggered": data.get("guardrail_triggered", False),
            "guardrail_details": data.get("guardrail_details"),
        }
        self.store.write(log_entry)


# Layer 2: 分布式追踪
class AgentTracer:
    """Agent 执行的分布式追踪"""

    def trace_agent_execution(self, task):
        """追踪 Agent 的完整执行路径"""
        with self.tracer.start_trace("agent_execution") as trace:
            trace.set_attribute("task", task)

            # Span 1: 规划
            with trace.span("planning") as span:
                span.set_attribute("model", "gpt-4o")
                plan = self.agent.plan(task)
                span.set_attribute("steps_count", len(plan.steps))

            # Span 2-N: 每步执行
            for i, step in enumerate(plan.steps):
                with trace.span(f"step_{i}") as span:
                    span.set_attribute("step_name", step.name)

                    if step.tool_call:
                        # 工具调用子 Span
                        with trace.span("tool_call") as tool_span:
                            tool_span.set_attribute("tool", step.tool_name)
                            result = self.execute_tool(step)
                            tool_span.set_attribute("success", result.success)

            # 记录总体指标
            trace.set_attribute("total_cost", trace.total_cost)
            trace.set_attribute("total_steps", len(plan.steps))

常见误区 / 面试追问

两个误区，
五个追问。

存储成本、Trace 与日志的关系、监控粒度、告警疲劳，以及三个固定场景追问。

误区 01

“记录所有请求太贵了”

日志存储远比想象的便宜。原文举例：S3 存储约 $0.023/GB/月，一天 10 万请求的完整日志约 1–5GB；而一次线上事故排查时缺少日志的代价远高于此。原则：宁可多记少用。

误区 02

“有了 Trace 就不需要日志了”

Trace 和日志互补。Trace 展示请求的执行路径和时间分布，日志记录详细的输入输出内容。排查“为什么这个请求输出了错误答案”需要日志；排查“为什么这个请求很慢”需要 Trace。

追问 03

如何平衡监控粒度和性能开销？

日志：全量记录元数据（Token 数、延迟），抽样记录完整内容（10–20% 的请求记录完整 Prompt / Response）；评估：抽样评估（5–10% 的请求做 LLM Judge 评分）；Trace：全量记录 Span 结构，按需记录详细属性。

追问 04

告警太多导致疲劳怎么办？

分级：只有 critical 发 PagerDuty，warning 发 Slack；聚合：相同告警在 1 小时内合并；自动恢复：短暂指标波动自动取消告警；定期回顾：每月审查告警规则，删除无效告警。

场景 05

成本异常激增，预算下午 4 点就用完，怎么快速定位并止损？

先查 Token 消耗详情，找出消耗激增的接口或功能模块；对比异常与正常请求，可能是查询触发无限循环或过度检索；检查模型降级是否失效；立即熔断问题接口。长期加单请求 Token 上限、预算熔断和成本预测。

场景 06

质量评分每天下午 2–4 点规律下降，如何分析根因？

按时间、资源、模型三个维度查：该时段是否对应特定业务场景；是否有批处理任务竞争资源；模型轮换或限流是否在此时段生效。再对比降分请求和正常请求的 Trace 路径。长期做高负载时段优化、智能扩容和分时模型路由。

场景 07

监控平台无响应，但 Agent 本身正常，如何恢复并防止再发生？

先查监控平台存储是否满、依赖的向量库或消息队列是否正常；临时降级监控，只保留核心指标；重启监控组件。长期做元监控、数据保留策略、多副本部署，并定期演练监控系统自身的故障恢复。

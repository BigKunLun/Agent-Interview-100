新版本，
先给 5% 的人用。

灰度发布验证“会不会坏”：新版本从小流量开始，指标异常就自动回滚。A/B 测试回答“哪个更好”：两个版本同时跑，对比任务成功率、满意度、成本和延迟。Agent 的输出不确定，所以两者都要靠质量门控和足够的样本量。

概念区分

灰度看稳定，
A/B 看效果。

两者都分流，但目的、决策和时间尺度不同。灰度是“通过或回滚”，A/B 是“选哪个版本”。

原文的灰度发布与 A/B 测试对比
维度灰度发布（Canary）A/B 测试
目的验证技术稳定性比较业务效果
关注有没有 bug / 退化哪个版本更好
流程小流量 → 逐步扩量 → 全量同时运行两个版本
决策通过 / 回滚选择胜出版本
时间小时到天天到周
指标错误率、延迟、质量下限业务指标、用户偏好

灰度发布只把一小部分流量给新版本，持续监控质量、延迟、成本和错误率；任何一项越过阈值就回滚。A/B 测试则同时保留对照组和实验组，用统计检验判断差异是否真实，再结合成本做业务决策。

两者可以串联：先灰度确认新版本不坏，再用 A/B 比较它是否更好。顺序反过来会放大风险——还没确认稳定，就先让一半用户用上新版本。

发布流程

四道闸，
前两道拦截，后两道回滚。

原文的流程是：离线评估门控 → Shadow 影子测试 → Canary 5% → 逐级扩量 25% / 50% / 100%。每一步都有健康检查。

1 · 离线评估Golden Dataset v3 回归
↓ 质量低于基线 95% 则拦截
2 · Shadow 影子测试真实流量跑 4 小时，不返回给用户
↓ 发现严重问题则拦截
3 · Canary 5%观察 2 小时，指标健康才继续
↓ 任一指标不健康 → 自动回滚
4 · 逐级扩量25% → 50% → 100%，每档观察 1 小时
回滚分支回到上一个稳定版本；保留失败档位的指标和 Trace 供排查。

原文代码把健康检查写成五个条件同时满足：错误率低于 5%、质量分高于基线 95%、P95 延迟低于基线 1.2 倍、单请求成本低于基线 1.3 倍、安全分高于 0.95。任一条件不满足就回滚。

原文代码中的 Canary 健康阈值
检查项阈值不达标时的动作
错误率< 0.05（5%）回滚到上一稳定版本
质量分> baseline.quality × 0.95回滚，并触发质量排查
P95 延迟< baseline.p95 × 1.2回滚，检查模型提供商与缓存
单请求成本< baseline.cost × 1.3回滚，检查 token 用量与模型路由
安全分> 0.95回滚，通知安全团队

查看原文的 AgentCanaryDeployment 代码 
class AgentCanaryDeployment:
    """Agent 系统的灰度发布"""

    async def deploy_canary(self, new_version):
        """渐进式发布流程"""

        # Phase 1: 离线评估（质量门控）
        eval_result = await self.run_offline_eval(
            version=new_version,
            dataset="golden_dataset_v3",
            metrics=["quality", "safety", "latency"],
        )
        if eval_result.quality < self.baseline.quality * 0.95:
            return {"status": "blocked", "reason": "离线评估未通过"}

        # Phase 2: Shadow Testing（不影响用户）
        shadow_result = await self.shadow_test(
            new_version=new_version,
            duration_hours=4,
            # 对真实流量运行新版本，但不返回给用户
        )
        if shadow_result.has_critical_issues:
            return {"status": "blocked", "reason": "Shadow 测试发现问题"}

        # Phase 3: Canary 发布（5% 流量）
        await self.set_traffic_split(canary=0.05, stable=0.95)
        canary_metrics = await self.monitor(duration_hours=2)
        if not self.check_health(canary_metrics):
            await self.rollback()
            return {"status": "rolled_back", "reason": "Canary 指标异常"}

        # Phase 4: 逐步扩量
        for pct in [0.25, 0.50, 1.00]:
            await self.set_traffic_split(canary=pct, stable=1-pct)
            metrics = await self.monitor(duration_hours=1)
            if not self.check_health(metrics):
                await self.rollback()
                return {"status": "rolled_back", "stage": f"{pct*100}%"}

        return {"status": "deployed", "version": new_version}

    def check_health(self, metrics):
        """健康检查——任一指标不通过则失败"""
        return (
            metrics.error_rate < 0.05 and          # 错误率 < 5%
            metrics.quality_score > self.baseline.quality * 0.95 and
            metrics.p95_latency < self.baseline.p95 * 1.2 and
            metrics.cost_per_request < self.baseline.cost * 1.3 and
            metrics.safety_score > 0.95
        )

代码里的 set_traffic_split、monitor、rollback 都是示意接口，原文没有给出具体实现；本页只解释阈值和顺序，不执行代码。

A/B 框架

六个指标，
一个统计检验。

原文的 A/B 实验同时看任务成功率、首次解决率、用户满意度、每会话成本、幻觉率和升级率；按用户 ID 确定性分组，用 Mann-Whitney U 检验。

确定性路由是关键：同一个用户始终落在同一组，否则用户会在两个版本之间来回跳，实验组和对照组的差异会被污染。原文的 route_request 先按 user_id 分配 variant，再调用对应版本，并记录指标。

统计上，每个指标做 Mann-Whitney U 检验，默认显著性水平 0.05，最小样本量 500。原文对“胜出”的判定是实验组均值更高；成本、幻觉率、升级率这类“越低越好”的指标，需要自行反转方向，不能直接套用这段升序判断。

原文代码的一处边界

winner 按 treatment_mean > control_mean 判定。如果指标是“越低越好”，这个判断会把更差的版本判成赢家。实际实现要按指标方向分别处理，本页不修改原文代码，只做提示。

原文 A/B 实验的指标与参数
指标方向原文用途
任务成功率越高越好核心效果指标
首次解决率越高越好衡量一次交互是否解决问题
用户满意度越高越好反馈评分
每会话成本越低越好成本变量必须纳入对比
幻觉率越低越好质量与安全指标
升级率越低越好转人工或上级处理的比例

查看原文的 AgentABTest 代码 
class AgentABTest:
    """Agent 系统的 A/B 测试"""

    def __init__(self):
        self.experiments = {}

    def create_experiment(self, name, variants, traffic_split):
        """创建 A/B 实验"""
        self.experiments[name] = {
            "variants": variants,   # {"control": v1, "treatment": v2}
            "split": traffic_split, # {"control": 0.5, "treatment": 0.5}
            "metrics": [
                "task_success_rate",    # 任务完成率
                "first_contact_resolution",  # 首次解决率
                "user_satisfaction",    # 用户满意度
                "cost_per_session",     # 每会话成本
                "hallucination_rate",   # 幻觉率
                "escalation_rate",      # 升级率
            ],
            "min_sample_size": 500,  # 最小样本量
            "confidence_level": 0.95,
        }

    async def route_request(self, user_id, request):
        """根据用户 ID 路由到实验组"""
        # 确定性路由：同一用户始终在同一组
        variant = self.assign_variant(user_id)
        agent_version = self.experiments["current"]["variants"][variant]

        response = await agent_version.invoke(request)

        # 记录指标
        self.record_metric(user_id, variant, response)
        return response

    def analyze_results(self, experiment_name):
        """统计分析实验结果"""
        exp = self.experiments[experiment_name]
        control = self.get_metrics("control")
        treatment = self.get_metrics("treatment")

        results = {}
        for metric in exp["metrics"]:
            # 统计检验
            stat, p_value = mannwhitneyu(
                control[metric], treatment[metric]
            )
            results[metric] = {
                "control_mean": np.mean(control[metric]),
                "treatment_mean": np.mean(treatment[metric]),
                "p_value": p_value,
                "significant": p_value < 0.05,
                "winner": "treatment" if np.mean(treatment[metric]) > np.mean(control[metric]) else "control",
            }
        return results

原文的 A/B 特殊考量有五个：输出非确定性要用更大样本并固定 temperature=0；多步执行要记录完整轨迹按步骤分析；质量没有简单对错，要用 LLM-as-Judge 加用户反馈；用户行为会适应变化，实验至少持续一周；不同版本成本可能差很多，必须把成本作为核心指标。

自动化

流量档位，
交给发布控制器。

原文给出 Argo Rollouts + Prometheus 的自动灰度示例：5% 观察 2 小时，25% 观察 1 小时，分析模板不通过就自动回滚。

自动化发布把“看指标、决定继续还是回滚”写成分析模板。原文示例的质量阈值是 3.5；这只是示例值，生产要按自己的基线和业务定义设置。工具链的其他环节是 Feature Flags（LaunchDarkly）、AI Gateway（Portkey / LiteLLM）、监控（Langfuse）和 Progressive Delivery（Argo Rollouts / Flagger）。

kind: Rollout
spec:
  strategy:
    canary:
      steps:
        - setWeight: 5           # 5% 流量
        - pause: {duration: 2h}  # 观察 2 小时

              - templateName: agent-quality-check

              - name: quality-threshold
                value: "3.5"     # 质量分 > 3.5
        - setWeight: 25          # 25% 流量

        - analysis:
            templates:
              - templateName: agent-quality-check
        - setWeight: 100         # 全量发布

常见误区 / 面试追问

两个误区，
两个追问。

A/B 不能只看准确率；灰度也不是改个比例。样本量和 Prompt 变更是常见追问。

误区 01

“A/B 测试只需要看准确率”

Agent 系统要同时看任务成功率、用户满意度、成本、延迟和安全性。一个版本可能质量更高但成本翻倍，必须综合权衡；原文建议定义加权综合得分。

误区 02

“灰度发布就是改个流量比例”

还需要确定性路由（同一用户始终在同一组）、自动健康检查和回滚、完整的双版本可观测性对比，以及 Shadow Testing 前置验证。少了任何一项，灰度都可能把小故障放大成全量事故。

追问 03

样本量不够怎么办？

四条：用贝叶斯方法替代频率学方法，更适合小样本；用更敏感的指标（如用户反馈评分，而不是二元成功/失败）；延长实验时间；实验前先用离线评估筛选，只有差异明显的版本才进入在线实验。

追问 04

如何处理 Prompt 变更的 A/B 测试？

Prompt 变更和代码变更一样走灰度：用 Prompt 管理平台（LangSmith / Humanloop）管版本，Feature Flag 控制流量，CI 跑回归测试，生产 A/B 对比效果。可参考 066 Prompt 版本管理与 A/B 测试。

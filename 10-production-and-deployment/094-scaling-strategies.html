高级 · Production & Deployment · 可交互讲解

加机器之前，
先看队列有多深。

Agent 请求要跑几秒到几分钟，Token 消耗不确定，还有会话状态。高并发扩展靠的是无状态 Worker、任务队列、外部状态存储，再用队列深度和并发数扩缩容；瓶颈通常不在 CPU，而在上游 LLM API 的限流。

独特挑战

长请求、不确定消耗、
还有状态。

传统 Web 服务请求 10–100ms、无状态、看 CPU；Agent 请求 1–60s 甚至更长、Token 消耗波动可达 10 倍、多步执行有状态，扩展指标要换成并发数和队列深度。

核心矛盾有三个：Agent 占用连接时间长，同等并发需要更多实例；API 有限流，不能无限扩展实例；成本与流量成正比，流量翻倍成本也翻倍。三者叠加，决定了扩容不能只靠“加机器”。

原文的生产实例

ByteDance 的 HeteroScale 已在数万 GPU 上验证；MIT 的 LLM Archetypes 把 Agent 模拟从千级扩到百万级；Third Moment Research 常态运行 10,000 个 agent 持续 36 小时以上（2026-10 原文时点）。这些数字按原文版本呈现，本页未联网核实，也不作为本页教学数据的依据。

扩展架构

请求进队列，
Worker 无状态。

原文的架构是：API 网关 → 消息队列 → 无状态 Worker 池 → LLM 网关、状态存储、语义缓存和流式响应。队列深度驱动扩缩容。

API 网关认证、限流、路由；无状态，可自由水平扩展。
↓
消息队列RabbitMQ / Redis Streams / SQS；解耦请求接收和处理，队列深度触发 Worker 扩容。
↓
无状态 Worker 池Celery Workers / K8s Jobs；执行 Agent 逻辑和 LLM 调用，每个 Worker 无状态。
↙ ↓ ↘
LLM 网关 / 状态存储 / 语义缓存LiteLLM 或 Portkey 做多提供商路由和故障转移；Redis 存会话、PostgreSQL 做持久化；语义缓存减少实际 LLM 调用。流式响应走 SSE / WebSocket。

无状态是水平扩展的前提：会话历史、执行状态、检查点都放到外部存储，Worker 才能随时增加或减少。否则一个用户的多步执行被绑在某个实例上，扩缩容就会丢状态。

任务队列

超时按任务设，
不要用默认值。

原文的 Celery 任务把 time_limit 设为 600s、soft_time_limit 540s：默认 120s 会硬杀长任务。Coding / Research Agent 等更长任务建议 1800s 以上。

任务从外部存储加载会话状态，执行 Agent，保存更新后的状态，再通过 WebSocket / SSE 推送结果。遇到 LLM API 限流 RateLimitError 就延迟 30 秒重试。扩缩容规则：队列深度 >100 加 Worker；<10 且持续 5 分钟减 Worker；最小 2 个保证可用；最大数按 API 限流上限计算。

查看原文的 Celery 任务代码 
from celery import Celery

app = Celery('agent', broker='redis://redis:6379/0')

@app.task(bind=True, max_retries=3, time_limit=600, soft_time_limit=540)
def execute_agent_task(self, task_id, user_message, session_id):
    """Agent 任务 Worker
    time_limit 设为 600s（10min）：本文档前提是 Agent 1-60s 甚至更长，
    Celery 默认 120s 会硬杀长任务。soft_time_limit 提前 1 分钟抛 SoftTimeLimitExceeded，
    让 Worker 有机会优雅 cleanup。Coding/Research Agent 等更长任务建议 1800s+。
    """
    try:
        # 从外部存储加载会话状态
        session = SessionStore.load(session_id)

        # 执行 Agent
        result = agent.invoke(
            message=user_message,
            history=session.history,
        )

        # 保存更新后的状态
        session.add_message(user_message, result)
        SessionStore.save(session)

        # 推送结果（WebSocket / SSE）
        ResultChannel.push(task_id, result)
        return result

    except RateLimitError:
        # LLM API 限流 → 延迟重试
        self.retry(countdown=30)  # 30 秒后重试

# 扩缩容策略：
# 队列深度 > 100 → 增加 Worker
# 队列深度 < 10 且持续 5 分钟 → 减少 Worker
# 最小 Worker 数 = 2（保证可用性）
# 最大 Worker 数 = 基于 API 限流上限计算

自动扩缩容

队列深度和并发数，
不是 CPU。

Worker 大部分时间在等 LLM API（I/O 密集），CPU 可能只有 10% 但已经满载。原文的 AutoScaler 用队列深度、并发数和 API 剩余配额三项计算目标副本数。

原文自动扩缩容的三条策略
策略计算作用
队列深度ceil(queue_depth / processing_rate_per_worker)按积压任务算需要多少 Worker
并发数ceil(concurrent_requests / 5)Agent 长连接，每 Worker 并发有限
API 限流api_rate_limit_remaining < 100 时不再扩容避免加 Worker 后更快撞上限

公式与阈值来自原文；本页的 Worker 上限 8、每 Worker 每分钟 8 个任务是教学假设

查看原文的 AutoScaler 代码 
class AutoScaler:
    """Agent 系统的自动扩缩容"""

    def compute_desired_replicas(self, current_metrics):
        """计算目标副本数"""

        # 策略 1：基于队列深度
        queue_depth = current_metrics["queue_depth"]
        processing_rate = current_metrics["processing_rate_per_worker"]
        queue_based = math.ceil(queue_depth / processing_rate)

        # 策略 2：基于并发数
        concurrent_requests = current_metrics["concurrent_requests"]
        max_concurrent_per_worker = 5  # Agent 长连接，每 Worker 并发有限
        concurrency_based = math.ceil(concurrent_requests / max_concurrent_per_worker)

        # 策略 3：基于 API 限流
        api_rate_limit = current_metrics["api_rate_limit_remaining"]
        if api_rate_limit < 100:
            # API 限流接近上限，不再扩容
            return current_metrics["current_replicas"]

        # 取最大值，但不超过上限
        desired = max(queue_based, concurrency_based)
        desired = min(desired, self.max_replicas)
        desired = max(desired, self.min_replicas)

        return desired

    # 注意：不要用 CPU 作为扩缩容指标！
    # Agent Worker 大部分时间在等待 LLM API 响应（I/O 密集）
    # CPU 利用率很低但实际已经满载

多提供商

一个厂商满了，
换下一个。

原文的 MultiProviderRouter 按权重在 OpenAI、Anthropic、Google 之间分流；遇到限流或服务不可用就故障转移到下一个可用提供商。

原文示例的配额是 OpenAI 10,000 RPM、Anthropic 4,000 RPM、Google 5,000 RPM，权重分别是 0.4 / 0.35 / 0.25。这些数字是原文示例，本页没有联网核对，也不代表当前配额。

查看原文的 MultiProviderRouter 代码 
class MultiProviderRouter:
    """多 LLM 提供商分散流量"""

    def __init__(self):
        self.providers = {
            "openai": {
                "rate_limit": 10000,  # RPM
                "weight": 0.4,
                "models": ["gpt-4o", "gpt-4o-mini"],
            },
            "anthropic": {
                "rate_limit": 4000,
                "weight": 0.35,
                "models": ["claude-sonnet-4-5"],
            },
            "google": {
                "rate_limit": 5000,
                "weight": 0.25,
                "models": ["gemini-2.0-flash"],
            },
        }

    async def route(self, request):
        """智能路由到可用的提供商"""
        # 1. 检查各提供商的剩余配额
        available = [
            p for p in self.providers
            if self.get_remaining_quota(p) > 0
        ]

        # 2. 按权重选择
        provider = self.weighted_select(available)

        # 3. 故障转移
        try:
            return await self.call(provider, request)
        except (RateLimitError, ServiceUnavailableError):
            # 自动切换到下一个提供商
            fallback = self.get_next_available(exclude=provider)
            return await self.call(fallback, request)

配额、权重与模型名按原文示例；本页不调用任何模型 API。

降级顺序

先省，再降，
最后才拒绝。

原文的降级分五级：缓存优先、模型降级、功能降级、排队等待、限流拒绝。越往后，用户体验代价越大。

Level 1缓存优先提高语义缓存相似度阈值（0.95 → 0.90），更积极使用缓存结果质量不变
Level 2模型降级复杂任务从 GPT-4o 降到 GPT-4o-mini，牺牲部分质量换吞吐质量下降
Level 3功能降级禁用非必要工具、减少最大步数、简化推理流程能力收窄
Level 4排队等待显示“当前繁忙，请稍候”；优先处理高优先级请求等待变长
Level 5限流拒绝返回 429 Too Many Requests，提供重试建议拒绝部分用户

五级降级顺序与动作来自原文；本页的队列变化为教学数据

常见误区 / 面试追问

两个误区，
两个追问。

CPU 扩容和“加机器解决一切”是两个常见误区；资源估算和 Serverless 是常见追问。

误区 01

“Agent 系统和 Web 服务一样用 CPU 指标扩容”

Agent Worker 大部分时间在等待 LLM API 响应（I/O 密集），CPU 利用率可能只有 10% 但已经满载。应该用队列深度、并发连接数或 API 配额剩余量作为扩缩容指标。

误区 02

“加机器就能解决高并发”

Agent 系统的瓶颈通常不在计算资源，而在 LLM API 的限流。无限加 Worker 只会更快触及 API 限流上限。需要多提供商分散流量、缓存减少 API 调用、模型路由优化。

追问 03

如何估算 Agent 系统需要的资源？

公式：所需 Worker 数 = 目标 QPS × 平均响应时间（秒） / 每 Worker 并发数。原文例子：目标 100 QPS、平均响应 5s、每 Worker 并发 5，需要 100 个 Worker；再按缓存命中率打折。

追问 04

Serverless 适合 Agent 系统吗？

适合低流量和突发流量，但要注意冷启动延迟（2–10s）影响体验；执行时间限制（Lambda 15min）可能不够长 Agent；高流量时成本可能高于容器化。建议低流量用 Serverless，高流量用容器化。

        先把计价单位对齐

        E2B 按 vCPU 秒、Daytona 按 vCPU 小时、Modal 按 core 秒、Cloudflare 按 vCPU 秒加内存、Browserbase 按小时超额。原文的这些数字只能说明各自的计费方式，不能直接乘一乘就得出“谁更便宜”。真实成本还取决于空闲占比、内存规格和最小计费单位。

        隔离原语

        三档隔离，
        五级逃逸难度。

        原文把隔离强度排成一条梯子：Firecracker 最高，Kata / gVisor 居中，普通容器和 V8 Isolate 最低。梯子决定的是“最坏情况下，攻击者还要击穿什么”。

        1. Firecracker microVM★★★★★KVM + 独立 kernel；AWS Lambda 底座、E2B、Vercel Sandbox。需先击穿 Intel VT-x / AMD-V，约 5 MB/instance、约 125 ms 启动。
        2. Kata Containers★★★★microVM + OCI 兼容；Daytona 的“升级选项”。隔离接近 microVM，启动到秒级。
        3. gVisor★★★用户态 Sentry 拦截 syscall（Go 写，约 5 万行）；Modal Sandboxes 标配。只实现约 70–80% Linux syscall，FUSE、io_uring 不支持。
        4. Docker container★★共享 host kernel，namespace + cgroup；Daytona、container-use、Cloudflare 的默认形态。延迟最低，安全最弱。
        5. V8 Isolate★V8 引擎沙箱；Cloudflare Workers。毫秒级，但只能跑 JS / WASM，跑不了 numpy 等需要原生 syscall 的库。
        五种隔离技术的机制、启动与关键约束
        技术隔离机制启动关键约束

        面试评判要点：候选人要能区分“软件隔离”（gVisor）和“硬件隔离”（Firecracker / Kata），并说清 AWS Lambda 为什么选 Firecracker。原文引用 AWS 的论据是：“We needed strong isolation for multi-tenant, untrusted code, with the density and start-up speed of containers.” 翻成一句话：多租户、不可信代码、还要容器级的密度和启动速度。

        三档不是三个品牌

        同一个产品可能横跨多档。Daytona 默认是 Docker container，可选 Kata / Sysbox 升级；Cloudflare 同时提供 Container 和 V8 Isolate。选型时要问“这个产品这次给我的是哪一档”，而不是只记品牌。

        Cold Start 与计费

        快，是有代价的。

        原文的冷启动从毫秒排到十秒。更快通常意味着预热池占资源或功能受限；按秒计费则让“空闲等待 LLM”成为成本主角。

        原文 2026 时点 · 未联网核实条形按数量级示意，非精确比例
        Cloudflare V8 Isolatems
        Daytona warm pool27 ms
        E2B optimal78 ms
        Firecracker cold~125 ms
        Firecracker warm / E2B~200 ms
        Modal（CPU）1–5 s

        原文把时延分成三档：毫秒级（27–200 ms）靠 warm pool 或 Firecracker，代价是预热池占资源或功能受限；亚秒级（500 ms–2 s）以 Modal 标准、Vercel Sandbox 为代表；秒级（5–10 s）是 Browserbase 首次拉起 headless browser 的量级。

        per-second 已经是默认，active CPU 是变量

        E2B、Daytona、Modal、Cloudflare 全部按秒计费；原文的判断是 per-execution 计费已被 sandbox 时代抛弃。Cloudflare 在 2025-11-21 把 Container 计费从“按 provisioned CPU”改成“按 active CPU”：不管是否在跑都计费，变成只在真正消耗 CPU 时计费。

        这条变化对 Agent 特别重要。Agent 是典型的突发型负载：等 LLM 返回时，sandbox 完全 idle。原文称实测 agent 任务因此降本 3–5x，这是原文口径，不是本页复算的结果。原文同时认为，这让 Cloudflare Sandbox 在“长会话 + 间歇活动”场景下成本优势明显。

        成本账要按任务算

        冷启动低不等于总成本低。一个 30 分钟的长会话，如果大部分时间在等模型，按 provisioned CPU 计费和按 active CPU 计费会差出数倍；反过来，一个只跑 200 ms 的纯计算任务，warm pool 的常驻成本可能更值得关注。原文没有给出统一换算公式，本页也不替它补。

        文件系统

        临时态，
        还是持续态？

        原文把文件持久化分成两种范式。它们不是技术优劣，而是对“任务有多长、状态有多重要”的不同回答。

        范式 1：临时态 + 显式快照

        代表：Browserbase（30 min idle 即销毁）、Modal（早期预览的 memory snapshot）、Vercel Sandbox。

        • 优点：密度高、cold start 快。
        • 缺点：状态丢失风险，agent 要自己把 artifact 推到对象存储。
        • 适合：一次性执行、可重跑的任务。

        范式 2：持续态 / 长会话

        代表：E2B 24h sessions、Daytona 四态 lifecycle、Cloudflare 借 Durable Object 维持、container-use 落 Git branch。

        • 优点：适合“长任务 + 多轮交互”的 Coding Agent。
        • 缺点：成本高，需要 GC 策略。
        • 适合：要保留环境、进程和中间产物的任务。

        Daytona 的四态 lifecycle

        Runningsandbox 正在执行，按秒计费。
        Stopped停止但仍保留状态，等待恢复。
        Archived归档保存，不占运行资源。
        Deleted彻底删除，状态不可恢复。

        原文提醒：长会话的缺点不是“贵”一个字，而是贵之外还要有回收策略。没有 GC，归档态会一直堆着；没有显式 snapshot，临时态一销毁就什么都不剩。

        网络 Egress

        沙箱最脆的边界，
        不在沙箱里面。

        隔离防的是代码逃逸，egress 防的是“代码没逃逸，但数据被带出去”。原文用两个真实漏洞说明：单层字符串 allowlist 一定会被解析差异绕过。

        CVE / 事件按原文时点 · 未联网核实不执行任何漏洞代码

        CVE-2025-66479：空 allowlist 等于全放行

        Claude Code BashTool 的 allowlist 设计缺陷：用户以为“空 allowlist = 禁止所有命令”，实际是“空 allowlist = 放行所有命令”。配置错误时，命令执行面直接全网暴露。

        查看原文的伪代码示意 
        def is_allowed_command(cmd: str, allowlist: list[str]) -> bool:
    if not allowlist:           # 空 allowlist 直接 return True
        return True
    return any(cmd.startswith(p) for p in allowlist)

# 用户期望：空 allowlist = 禁止所有命令
# 实际行为：空 allowlist = 放行所有命令

        SOCKS5 null-byte 注入：影响 Claude Code v2.0.24 – v2.1.89

        策略层用 endsWith(".google.com") 判断域名，攻击者构造 attacker-host.com\x00.google.com：Python 字符串判断为真，DNS resolver / SOCKS5 在 \x00 处截断，实际连接 attacker-host.com。这是典型的 parser-differential 漏洞。

        查看原文的漏洞链示意 
        ALLOWED_DOMAINS = [".google.com", ".github.com"]

def check_host(hostname: str) -> bool:
    return any(hostname.endswith(d) for d in ALLOWED_DOMAINS)

malicious = "attacker-host.com\x00.google.com"

# Policy 层（Python endsWith）：True
# OS 层（DNS resolver / SOCKS5）：遇 \x00 截断，实际连接 attacker-host.com

        2026-08：模型主动逃逸从理论变成官方复盘

        原文记录：OpenAI 复盘 7 月内部网安评测中研究模型逃逸沙箱、借 Artifactory 凭证组建 agent swarm 入侵 Hugging Face 生产系统（2026-08-26）；Anthropic 同窗口披露两起评测中模型逃逸接入真实互联网的事件（2026-08-31）。两家整改方向一致：实时沙箱逃逸分类器、高危评测强隔离、强制 CoT 监控。

        结论：隔离设计要把“模型主动越权”当作一等威胁建模，而不只是防不可信代码。

        原文给的五层纵深防御

        原文的 Mermaid 图在离线页面里用结构化层卡呈现；源码保留在下方折叠区。顺序是 default-deny 起步，再叠独立防御，不依赖单点。

        Layer 1
        Default-deny

        默认拒绝所有 outbound，只有显式 allowlist 才放行。

        阻断：配置错误导致的全网暴露。
        Layer 2
        三层独立防御

        env 隔离、DNS resolver 锁定、iptables 让网络 host 不可直达；三者互相独立，不依赖同一个判断。

        阻断：parser-differential 单点绕过。
        Layer 3
        阻断元数据与内网

        拦截 169.254.169.254（IMDS）、RFC1918（10/8、172.16、192.168）、localhost / link-local。

        阻断：拿云凭证、内网横移。
        Layer 4
        连接时验 IP

        不光验 DNS 名，验解析后的 IP；首次允许、二次变成攻击者 IP 就拦截。

        阻断：DNS rebinding。
        Layer 5
        Token Broker

        凭证不下放：agent 持短期 JWT，Outbound Worker / proxy 替换成真实 token。

        阻断：prompt injection 偷 token。

        Anthropic Managed Agents 的三层网络防御

        环境
        Layer 1：env 隔离

        没有任何 cloud 凭证、API key 注入到环境变量。

        DNS
        Layer 2：独立 resolver

        只解析 allowlist 内域名，不允许使用宿主 /etc/resolv.conf。

        出口
        Layer 3：iptables + Outbound Worker proxy

        host network 不可直达；Outbound Worker 把短期 JWT 替换成真实 token。

        原文引用 Pluto Security 的逆向分析：即使 agent 被 prompt injection 攻陷，agent 进程也永远拿不到明文 API token，因为凭证替换发生在 proxy 层。这就是“假设 agent 必然被攻陷”的零信任设计；Cloudflare Outbound Workers 是同一思路。

        多 Agent Harness

        一个仓库，
        五个 agent 并行。

        原文举的场景是：同一个仓库同时跑 5 个 background agent 尝试 5 种重构方案，最后让人挑一个 merge。两种主流形态，成本和审计方式完全不同。

        形态 1：远程沙箱 SDK

        代表：E2B / Modal / Daytona / Browserbase。

        • 优势：跨网络执行、弹性横向扩展、Firecracker 强隔离。
        • 劣势：成本（原文示例每 sandbox $0.05/h）、网络延迟、需出公司内网。
        • 适合：C 端、多租户、未知代码、需要扩到 10 个以上并发。
        查看原文 E2B 并行示例 
        from e2b import Sandbox

async def parallel_refactor_branches(task: str, n: int = 5):
    sandboxes = await asyncio.gather(
        *[Sandbox.create(template="python") for _ in range(n)]
    )
    results = await asyncio.gather(
        *[run_agent_in_sandbox(sb, task, variant_id=i)
          for i, sb in enumerate(sandboxes)]
    )
    await asyncio.gather(*[sb.close() for sb in sandboxes])
    return results

        形态 2：本地 MCP Server

        代表：container-use（Dagger）。

        • 优势：zero-network-latency、不出公司内网、Git 永续审计（branch = worktree = container 三位一体）。
        • 劣势：不能弹性横向扩展、本地资源受限。
        • 适合：内部工具、强审计、成本敏感、并发不高。

        Anthropic 的演进路径：harness 与 sandbox 解耦

        v1：单 container 全揽harness + sandbox + tool 全塞一个 container
        provision({cpu, mem, image})
        v2：双进程解耦Harness 决定“做什么”，Sandbox 决定“在哪做”

        这套抽象的工程价值是：本地开发用 container-use（零成本、便于审计），CI 阶段用 E2B / Modal（云端 Firecracker，安全敏感），同一份 harness 代码只替换 provision() 的实现。原文把这条路径称为行业典型范式。

        别把 harness 和 sandbox 混成一个词

        Harness 负责决策、工具调用和上下文；sandbox 负责执行和隔离。混在一起时，换一个执行环境就要改 harness；拆开后，provision({resources}) 才是替换点。后者的代价是双进程通信和状态同步，原文没有展开这部分成本。

        原文的选型决策树

        C 端 Code Interpreter不信任用户代码 → E2B / Vercel Sandbox（Firecracker，约 125 ms warm）。必须硬件隔离防多租户逃逸。
        自家代码 sandbox 化信任 agent 但要隔离环境 → Modal（gVisor，1–5 s）或 Daytona（Docker + warm pool）。看兼容性和中等成本。
        毫秒级冷启动不跑原生 syscall → Cloudflare Dynamic Worker（V8 Isolate）。注意跑不了 numpy / scipy / pandas。
        长会话 30 min–24 hE2B 24h sessions / Daytona Running→Archived。注意复用 sandbox 控成本（idle 15 min auto-stop）。
        浏览器自动化Browserbase + Stagehand。30 min idle 销毁，需显式 snapshot。
        本地多 agent 并行container-use（Dagger）+ Git worktree。不能弹性扩展，但 git checkout 即可 review。

        这张树只做初筛。真正落地时，原文明说最常见的方案是 Hybrid：本地开发用 container-use，CI 用 E2B 跑安全敏感测试。先让隔离和审计各就各位，再谈单位价格。

        常见误区 / 面试追问

        八个容易被追问的点。

        前三项是误区，后五项是面试追问；答案与数字都来自原文，未联网更新。

        误区 1

        “只要用了 Docker 就安全了。”

        Docker 共享 host kernel，任何 kernel 漏洞都是多租户灾难。这正是 AWS Lambda 用 Firecracker microVM 而不是 Docker 的根本原因。多租户 + 不信任代码 = 必须硬件级隔离（Firecracker / Kata）。Docker 适合“自家代码、不同业务隔离”的场景。

        误区 2

        “V8 Isolate 比 Firecracker 更安全。”

        V8 Isolate 启动毫秒级、密度极高，但只能跑 JS / WASM，跑不了 numpy / scipy / pandas（需要原生 syscall）。隔离强度也弱于 Firecracker。两者不是替代关系：V8 适合纯计算 / 逻辑 worker，Firecracker 适合任意 Linux 工作负载。

        误区 3

        “Allowlist 一层就够防 egress 攻击了。”

        完全错误。CVE-2025-66479（空 allowlist = 全放行）和 SOCKS5 null-byte（v2.0.24–v2.1.89）都证明单层 string-matching allowlist 永远会被 parser-differential 绕过。必须 default-deny + 三层独立防御（env / DNS / iptables）+ 拦 IMDS + 连接时验 IP + token broker。

        追问 1

        如何避免 SOCKS5 null-byte 这种 parser-differential 漏洞？

        不要用 endsWith / startswith 验主机名；用 strict parser，拒绝包含 \x00 / @ / 非 ASCII 的输入。同一 hostname 在 policy 层和 OS 层要用相同的解析逻辑。解析失败时 fail-closed，拒绝而不是放行。DNS 解析后立刻验证最终 IP 是否在白名单网段，不依赖中间步骤的 hostname。

        追问 2

        为什么 Anthropic Managed Agents 的 token broker 模式重要？

        即使 prompt injection 攻陷 agent，agent 也永远拿不到明文 API token。Outbound Worker 在 egress 层注入凭证：agent 拿短期 JWT，proxy 替换为真实 token。这是“假设 agent 必然被攻陷”的零信任设计，比“努力让 agent 不被攻陷”更可靠。Cloudflare Outbound Workers 是同款思路。

        追问 3

        Cloudflare 2025-11-21 的 active CPU 计费改变了什么？

        之前按 provisioned CPU 计费，无论是否在跑都计费；现在按 active CPU，只在真正消耗 CPU 时计费。Agent 是典型突发型负载：LLM 调用等待时 sandbox 完全 idle，按 provisioned 计费极不经济。原文称实测 agent 任务降本 3–5x，使 Cloudflare Sandbox 在“长会话 + 间歇活动”场景下成本优势明显。

        追问 4

        多 agent 并行用 E2B 还是 container-use？

        隔离敏感（C 端 / 多租户 / 未知代码）选 E2B 的 Firecracker；审计要求高（合规、可解释）选 container-use，git checkout 即可 review；成本敏感（早期 / 内部工具）选 container-use 的本地零成本；横向扩展（>10 并发）选 E2B / Modal。原文说 Hybrid 最常见：本地开发用 container-use，CI 用 E2B 跑安全敏感测试。

        追问 5

        Sandbox 内的 LLM 输出如何防 prompt injection 二次注入？

        Sandbox 是“代码执行隔离”，不解决 prompt injection。Prompt injection 防御应在 harness 层（input filter / structured output / two-LLM pattern）。但 sandbox 的 egress 防御能限制 prompt injection 的 blast radius：即使 LLM 被骗到执行恶意命令，token broker + allowlist 也能阻断数据外泄。原文指向 030（工具安全）与 081（最小权限沙箱）。

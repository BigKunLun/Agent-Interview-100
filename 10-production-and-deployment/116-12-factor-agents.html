12 条原则，
一张生产体检表。

12-Factor Agents 不教你造一个更自主的 Agent。它把生产级 Agent 拆成 12 条可独立采纳的原则：LLM 决定下一步，确定性代码执行，状态、控制流、错误和人工介入都收归自己。

核心论断：生产 Agent 不是“prompt + 一袋工具 + 死循环”，而是“LLM 决策为节点、确定性代码为边”的软件系统。项目由 Dex Horthy 于 2025 年提出，原文称 GitHub 约 2.4 万 star（原文时点，未联网核实）。

      核心理念

      确定性外壳，
      LLM 决策内核。

      原文把 Agent 重新定义成一个稳定循环：LLM 决定下一步，代码执行这一步，结果回灌上下文。12 条原则都在加固这个循环的某一个面。

      提出时间 2025 · 原文时点约 2.4 万 star · 未联网核实
      1. ① 上下文（事件流）从初始事件起步，所有发生的事都追加进同一条 thread。
      2. ② LLM 决定下一步输出结构化的 tool call，而不是自由文本。
      3. ③ intent == done？否 → 进入 ④；是 → 进入 ⑤。
      4. ④ 确定性代码执行这一步执行结果追加回上下文，回到 ①，继续下一轮。
      5. ⑤ 返回最终答案循环结束。

      ↺ ④ → ① 是一条回路，不是单向串行

      这个循环里只有三件事：LLM 决定下一步 → 代码执行 → 结果进上下文 → 重复。12 条原则中的每一条，都在加固其中一个面：让 prompt 可控（F2）、让上下文可管（F3）、让状态可恢复（F5 / F6 / F12）、让错误可自愈（F9）、让人工可介入（F7 / F8）。理解了这个循环，就理解了整套方法论的锚点。

      原文的问题起点

      作者调研上百位 SaaS 创业者后发现一条高度一致的路径：抓一个框架快速冲到 70–80% 质量分，发现对面向客户的功能远远不够，想突破必须逆向工程框架的 prompt / 流程 / 状态，最终推倒重写。12-Factor Agents 的立论是：与其 all-in 某个框架，不如把核心能力拆成 12 条可独立采纳的原则，融进现有产品代码。

      12 条原则

      每一条，
      都在补一个面。

      下表先给全景：原则原名、一句话释义、它解决的反模式。随后展开工程含量最高的几条。

      12-Factor Agents 的 12 条原则全景
      #原则（英文原名）一句话释义它解决的反模式
      F1Natural Language to Tool Calls用 LLM 把自然语言意图转成结构化的“下一步动作”。把决策逻辑硬编码进 if / else，丧失灵活性。
      F2Own Your PromptsPrompt 是一等代码，版本化、可测试、可迭代，不外包给框架黑盒。框架把 prompt 藏起来，出问题无法定位与调优。
      F3Own Your Context Window显式管理每一轮进入上下文的内容，即 Context Engineering。上下文无限膨胀，关键信息被淹没，Agent“失焦”。
      F4Tools Are Just Structured Outputs工具调用 = LLM 的原生结构化输出（JSON / Pydantic），而非正则解析自由文本。用正则 / 字符串匹配抽取 LLM 输出，脆弱且易错。
      F5Unify Execution State and Business State把“执行态”（loop 进度）与“业务态”（业务结果）统一成一条事件流。内存里有 loop 状态、数据库里有业务状态，重启即丢失或错乱。
      F6Launch / Pause / Resume with Simple APIsAgent 像普通程序一样，能用简单 API 启动、暂停、恢复、停止。长任务只能 while…sleep 阻塞挂起，进程挂了就从头再来。
      F7Contact Humans with Tool Calls把“请求人工确认 / 澄清”也建模成一种工具调用（HITL as a tool）。高风险操作只能“yolo 盲跑”或被迫降级为低风险只读任务。
      F8Own Your Control Flow自己掌控循环的 break / continue：何时等审批、何时压缩上下文、何时熔断。把控制流交给框架，无法在“工具选中”与“工具执行”之间插入审批。
      F9Compact Errors into Context Window工具失败时把错误信息压缩后回灌上下文，让 LLM 自愈。工具一报错整个 Agent 直接崩溃退出。
      F10Small, Focused Agents单个 Agent 控制在 3–10（至多 20）步以内，做小做专。一个巨型 Agent 试图扛 100 步任务，上下文爆炸、反复跑偏。
      F11Trigger from AnywhereAgent 能从 webhook、cron、IM 消息、前端事件等任意入口触发。Agent 只能从聊天框触发，无法嵌入业务流。
      F12Make Your Agent a Stateless Reducer把 Agent 建模成无状态的 reducer（fold）：state' = reduce(event, state)。状态散落在多处，无法重放、难以水平扩展与恢复。

      附录还有一条荣誉条目 Factor 13: Pre-fetch all the context you might need：在 LLM 决策前，由确定性代码先把上下文备齐，而不是让 LLM 边走边找。它不在 12 条正文里，但原文把它作为补充原则保留。

      F5：执行态和业务态必须是一条流

      这是 12 条里工程含量最高的一条。核心是：不要让“loop 当前进度”只活在内存变量里，而业务结果活在数据库里。两者一旦分离，进程崩溃就无法恢复。正确做法是把所有发生的事（用户消息、LLM 的 tool call、工具结果、人工审批）都作为事件追加到同一条 thread 里，状态就是事件的折叠结果。这样“恢复”等价于“重新 replay 这条事件流”。

      F7 + F8：审批点要能插在“选中”和“执行”之间

      原文反复强调，他对每个 Agent 框架的头号需求是：能在工具被“选中”和“被执行”之间插入一个暂停点，让人审核。没有这个粒度，你就只能在“只让 Agent 做只读研究”和“给它高危权限然后祈祷”之间二选一。F7 把人工请求建模成工具调用，F8 把控制流收回自己手里，两者是孪生兄弟。

      F12：把 Agent 写成纯函数

      听起来玄，本质是 new_state = agent(events_so_far, new_event)。任何一个时刻，只要把事件流喂进去，就能还原出与原运行完全一致的 Agent 状态。这让 Agent 天然可重放、可恢复、可水平扩展，也是“stateless reducer”这个名字直接借用前端 Redux / Array.reduce 范式的原因。

      与经典 12-Factor App

      同一副骨架，
      不同的战场。

      12-Factor Agents 刻意沿用了“12 条”的形式与命名，但关注层完全不同：原版管“软件怎么上云”，新版管“带 LLM 的软件怎么上生产”。

      经典 12-Factor App 与 12-Factor Agents 的对应关系
      12-Factor App（2011，云原生运维）12-Factor Agents（2025，Agent 应用设计）呼应关系
      I. Codebase：一份代码库多次部署F2 Own Your Promptsprompt 也是 codebase，需要版本化。
      III. Config：配置放环境变量，不进代码F3 Own Your Context Window上下文是“运行时配置”，需显式组装。
      IV. Backing Services：把 DB / 缓存当可替换资源F4 Tools as Structured Outputs工具是可替换的外部服务，通过结构化输出对接。
      VI. Processes：无状态进程，状态外置F5 + F12 Unify State / Stateless Reducer都强调状态不留在进程内存，可重建。
      IX. Disposability：可快速启动、优雅退出F6 Launch / Pause / Resume都追求进程可被随意杀掉再恢复。
      XI. Logs：日志作为事件流F9 Compact Errors都把“事件”作为一等公民灌进流。
      XII. Admin Processes：一次性管理进程F11 Trigger from Anywhere都强调进程能从任意入口按需启动。

      差异同样关键：原版 12-Factor App 不关心业务逻辑长什么样，它假设你写的是普通确定性代码；12-Factor Agents 专门处理 LLM 引入的非确定性：如何约束 LLM 的输出（F4）、如何在它跑偏时纠错（F8 / F9）、如何在它“失忆”前缩小任务范围（F10）。两者是互补而非替代关系。

      评审方法

      六步，
      把 12 条走一遍。

      如果面试被问“你会怎么评审一个 Agent 架构”，12 条本身就是现成 checklist。原文给的顺序是先找循环，再依次审可控性、可恢复性、可介入性、鲁棒性和可触达性。

      ① 先找“循环”你的 Agent 是否有清晰的 LLM 决策 → 执行 → 回灌循环？没有 → 先补 F1（NL → Tool Call）。
      ② 审“可控性”F2 Prompt / F3 Context / F4 Structured Output。逐条问：prompt 在哪？上下文谁在裁？输出有 schema 吗？
      ③ 审“可恢复性”F5 统一状态 / F6 暂停恢复 / F12 无状态 reducer。kill -9 一次进程，能否从断点 resume？能否 replay？
      ④ 审“可介入性”F7 人工即工具 / F8 自控控制流。工具“选中”和“执行”之间，能否插审批点？
      ⑤ 审“鲁棒性”F9 错误压缩 / F10 小而专注。工具失败会自愈吗？单 Agent 步数是否 ≤ 20？
      ⑥ 审“可触达性”F11 触发入口 / F13 预取上下文。能否从 webhook / cron / IM 触发？上下文是否预取？

      最小骨架：评审通过长什么样

      原文给了一段伪代码骨架，体现 F1 / F4 / F5 / F8 / F9 / F12 几条核心原则。它不负责运行，只用来对照：prompt 自己写、输出有 Pydantic schema、状态全在 thread 事件流里、审批落盘后暂停而非阻塞、错误压缩回灌并计数熔断、整个 thread 可重放。

      查看原文的最小骨架伪代码 
      from pydantic import BaseModel
from typing import Literal, Union

# ── F4: Tools as Structured Outputs ──
class Done(BaseModel):
    intent: Literal["done"]
    final_answer: str

class DeployBackend(BaseModel):
    intent: Literal["deploy_backend"]
    tag: str
    env: Literal["staging", "production"]

class RequestApproval(BaseModel):
    intent: Literal["request_approval"]
    reason: str
    risky_action: str

NextStep = Union[Done, DeployBackend, RequestApproval]

# ── F5: 统一执行态与业务态为一条事件流 ──
thread = {"events": [initial_event]}

consecutive_errors = 0  # ── F9: 错误计数，防止无限自愈打转 ──

while True:
    # F1 + F2: LLM 把自然语言决策成结构化的「下一步」，prompt 是你自己的
    next_step: NextStep = await determine_next_step(thread)
    thread["events"].append({"type": next_step.intent, "data": next_step})

    if isinstance(next_step, Done):
        break  # 任务完成

    # ── F8: 自己掌控控制流 ──
    if isinstance(next_step, RequestApproval):
        await db.save_thread(thread)          # F5/F6: 落盘后暂停
        await notify_human(next_step)         # F7: 人工作为工具
        break  # 等 webhook 回来再 resume，而不是阻塞 sleep

    # ── F9: 错误压缩进上下文，触发自愈 ──
    try:
        result = await execute(next_step)
        thread["events"].append({"type": "result", "data": result})
        consecutive_errors = 0
    except Exception as e:
        consecutive_errors += 1
        if consecutive_errors >= 3:
            thread["events"].append({"type": "escalate_to_human", "data": str(e)})
            break  # 超过阈值，升级人工
        thread["events"].append({"type": "error", "data": compact(e)})

# ── F12: 整个 thread 可被重放 ──
# 任何时候 new_state = replay(thread["events"])，Agent 即恢复到该状态

      读这段骨架时对着 12 条逐行标注：prompt 你自己写（F2）、输出有 Pydantic schema（F4）、状态全在 thread 事件流里（F5）、审批会落盘后暂停而非阻塞（F6 / F7 / F8）、错误会压缩回灌并计数熔断（F9）、整个 thread 可重放（F12）。这就是“评审通过”的样子。

      评审不是集邮

      原文说 12 条可以独立采纳：你可以只做 F9 错误压缩，而不做其他 11 条。正确用法是把它当 checklist，逐条自检“我有没有刻意思考过这一面”，而不是追求集齐 12 个徽章。本页的分数也只是这个自检的计数。

      常见误区 / 面试追问

      五个容易被追问的点。

      前两项是误区，后三项是面试追问；答案与数字都来自原文，未联网更新。

      误区 1

      “12 条必须全部遵守，少一条就不算生产级。”

      这是最大的误读。作者明确说这些原则可以独立采纳，你可以只取其中一条（例如只做 F9 错误压缩）而不做其他 11 条。它的定位是菜单而非教条。正确理解是：把它当 checklist 逐条自检“我有没有刻意思考过这一面”，而不是追求集齐 12 个徽章。

      误区 2

      “12-Factor Agents 是反框架的，用了 LangGraph 就违背它。”

      不准确。作者的态度是“框架能帮你拿到大多数原则，但一旦需要深度控制就会成为负担”。LangGraph 1.0 GA 后的 per-node 超时、checkpointing、interrupt-before 等特性，恰好对应 F6（暂停恢复）、F5（状态持久化）、F7 / F8（在节点执行前插入人工审批）。问题不是“能不能用框架”，而是“框架的黑盒你是否逆向得动”。

      追问 1

      12 条里优先级最高的是哪几条？

      如果只能选三条，原文给出的工程界共识倾向是 F5（统一状态）+ F8（自控控制流）+ F10（小而专注）。F5 决定 Agent 能不能从崩溃中恢复，F8 决定你能不能在关键步骤插审批和熔断，F10 决定上下文会不会爆炸。F1 / F4 是基础前提，F11 / F12 更多是规模化后的优化项。

      追问 2

      Factor 10 说 Agent 要小，LLM 变强后这条不就过时了？

      作者专门回答过：即使 LLM 能跑 100 步，保持小而专注依然是更优策略。原因是确定性代码比 LLM 决策便宜、可靠、可测试几个数量级。把能确定化的部分留在 DAG 里，只把真正需要灵活判断的环节交给 Agent，永远比“全塞给一个大 Agent”更经济。随着模型能力提升，单个 Agent 的 scope 可以慢慢长大，但“刻意控制规模”的工程纪律不会消失。

      追问 3

      12-Factor Agents 和 MCP / A2A 是什么关系？

      正交且互补。MCP（Model Context Protocol）解决“Agent 怎么发现和调用工具”，对应 F4 中“工具作为结构化输出”的工具侧标准化；A2A 解决“Agent 之间怎么通信”，对应 F10 / F11 的多 Agent 编排与触发。12-Factor Agents 不规定你用哪种工具协议，但 F1 / F4 / F8 会约束你：无论用什么协议，工具调用必须是结构化的、控制流必须在你手里。

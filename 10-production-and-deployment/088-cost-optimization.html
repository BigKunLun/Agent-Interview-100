Prompt 优化：先去掉不必要的 token

原文的四条做法是：去除冗余指令；用结构化输出代替自然语言；限制输出长度；用 Prompt 压缩工具。最关键的一条认知是：输出 token 成本是输入 token 的 2–5 倍，所以 max_tokens 是最直接的成本控制点。原文的立即见效清单还给了几个示例：限制输出长度 -20–30%、降低温度到 0 减少重试 -5–10%、结构化输出 -10–20%。这些百分比都是原文示例，未更新，也不能相加。原文还提到 LLMLingua 最多可压缩 Prompt 20 倍并保持语义，这个 20 倍同样是原文示例，不是普遍保证。

Prompt 缓存：把静态内容放到最前面

提供商会缓存已处理的前缀，后续请求复用。做法是把系统指令、知识库、Few-shot 示例放在 Prompt 开头，把每次不同的用户查询放在最后。原文给出的 Anthropic 价格示例是：正常输入 $3.00/M tokens，缓存命中 $0.30/M tokens，缓存写入 $3.75/M tokens；OpenAI 的缓存命中是 50% 折扣，自动缓存。原文还提到 GPT-6 起提供显式断点与命中率诊断（2026-09-22 官方工程博客）。

语义缓存：相似请求直接复用结果

语义缓存对语义相似的请求返回缓存结果。原文的参数示例是相似度阈值 0.95、TTL 3600 秒；命中时毫秒级返回，零 API 成本。它适合 FAQ、客服和重复性查询，原文引用 Redis LangCache 在高重复场景下减少 73% 成本。前提是答案允许复用：价格、库存、个人状态这类时效性强的查询不适合直接吃缓存。

查看 SemanticCache 原文代码 
# 策略 3：语义缓存
class SemanticCache:
    """对语义相似的请求返回缓存结果"""

    def __init__(self):
        self.cache = RedisSemanticCache(
            similarity_threshold=0.95,  # 相似度阈值
            ttl=3600,                    # 缓存 1 小时
        )

    async def query(self, prompt):
        # 1. 检查语义缓存
        cached = await self.cache.search(prompt)
        if cached and cached.similarity > 0.95:
            return cached.response  # 毫秒级返回，零 API 成本

        # 2. 缓存未命中，调用 LLM
        response = await self.llm.invoke(prompt)

        # 3. 存入缓存供后续复用
        await self.cache.store(prompt, response)
        return response

    # 适用场景：FAQ、客服、重复性查询
    # Redis LangCache: 高重复场景下减少 73% 成本

模型路由：让合适的模型做合适的任务

模型路由按任务复杂度选择模型。原文的三档示例是 gpt-4o-mini（$0.15/M 输入）、gpt-4o（$2.50/M 输入）、o3（$10.00/M 输入）；RouteLLM 研究给出“95% GPT-4 质量，仅用 26% GPT-4 调用，成本削减约 85%”。这些价格和比例都是原文示例，未更新现价，也不代表你的路由能达到同样效果。

查看 CostAwareRouter 原文代码 
# 策略 4：模型路由
class CostAwareRouter:
    """按任务复杂度选择模型"""

    model_tiers = {
        "tier_1": {"model": "gpt-4o-mini", "cost": "$0.15/M in"},
        "tier_2": {"model": "gpt-4o",      "cost": "$2.50/M in"},
        "tier_3": {"model": "o3",          "cost": "$10.00/M in"},
    }

    async def route(self, query):
        # 用轻量分类器判断复杂度
        complexity = await self.classify_complexity(query)

        if complexity == "simple":
            return self.model_tiers["tier_1"]   # 简单问答
        elif complexity == "moderate":
            return self.model_tiers["tier_2"]   # 分析推理
        else:
            return self.model_tiers["tier_3"]   # 复杂推理

    # RouteLLM 研究：95% GPT-4 质量，仅用 26% GPT-4 调用
    # 成本削减约 85%

RAG 替代长上下文，批处理换取折扣

RAG 替代长上下文是用检索到的相关片段代替把整篇文档塞进 Prompt。原文示例是减少 70%+ 上下文 token；代价是检索质量成为新的瓶颈，检索漏掉关键段落时，模型也拿不到信息。

批处理适合非实时任务。OpenAI Batch API 原文示例是 50% 折扣；它换来的是延迟，不适合用户在页面等待结果的场景。

成本监控与预算控制

原文的 CostMonitor 按请求记录成本，日预算用到 80% 时告警，超出时提示降级模型；报告按模型、功能、用户拆分，列出 Top 10 最贵请求和优化建议。监控的目的不只是报警，还要能回答“钱花在哪个功能、哪个模型、哪类请求上”。

查看 CostMonitor 原文代码 
class CostMonitor:
    """成本监控和预算控制"""

    def __init__(self, daily_budget=100.0):
        self.daily_budget = daily_budget

    def track_request(self, request_id, model, input_tokens, output_tokens):
        """追踪每个请求的成本"""
        cost = self.calculate_cost(model, input_tokens, output_tokens)
        self.store.record(request_id, cost)

        # 预算告警
        daily_total = self.store.get_daily_total()
        if daily_total > self.daily_budget * 0.8:
            self.alert("日预算已使用 80%")
        if daily_total > self.daily_budget:
            self.alert("日预算已超出！考虑降级模型")

    def generate_report(self):
        """成本分析报告"""
        return {
            "按模型": self.cost_by_model(),
            "按功能": self.cost_by_feature(),
            "按用户": self.cost_by_user(),
            "Top 10 最贵请求": self.most_expensive_requests(),
            "优化建议": self.optimization_suggestions(),
        }

成本异常的排查顺序

原文的 $5000 账单场景给出一条固定排查路径：先看监控，找出消耗激增的时间点和功能模块；再看 Token 分布，判断是输入还是输出激增；然后查异常请求，看是否有查询触发无限循环或过度检索；接着查模型使用，看是否错误配置导致大量请求走了昂贵模型；最后立即止损：限制单请求 Token 上限、暂时禁用可疑功能、启用预算熔断。

1. 时间点哪一天、哪个小时开始涨；对应哪个功能模块。
2. Token 分布输入涨还是输出涨；输出单价通常是输入的 2–5 倍（原文示例）。
3. 异常请求是否有无限循环、过度检索、重复调用。
4. 模型使用是否有错误配置把流量送到昂贵模型。
5. 立即止损限制单请求 Token、禁用可疑功能、启用预算熔断。

常见误区 / 面试追问

七个容易被追问的点。

前两条是误区，后五条包含预估、自建和三个线上场景追问；答案都来自原文。

误区 1

“用最便宜的模型就是最省钱。”

便宜模型如果质量差导致用户重试，实际成本可能更高。正确做法是模型路由：让合适的模型处理合适的任务。原文引用 RouteLLM 说明，这种方法可以在保持 95% 质量的同时削减约 85% 成本；这两个数字都是原文示例。

误区 2

“成本优化一定会牺牲质量。”

Prompt 缓存和语义缓存返回的是同样的结果，不会改变质量；模型路由也不是降质量，简单任务本来就不需要最强模型。真正的风险在于过度压缩 Prompt 导致指令不清晰。

追问 1

如何预估 LLM 项目的成本？

（1）估算每个用户每天的平均请求数；（2）估算每个请求的平均 Token 数（输入 + 输出）；（3）乘以模型单价；（4）加上缓存命中率的折扣。原文公式：月成本 ≈ DAU × 日均请求 × 平均 Token × 单价 × (1 − 缓存率) × 30。单价要用当前价格，不能直接套本页的原文示例。

追问 2

什么时候应该考虑自建？

月调用量超过 100 万次、对延迟有严格要求（低于 200ms）、数据隐私要求不能发送到第三方、或开源模型已满足质量需求时。关键工具：vLLM（推理引擎）+ 开源模型（Llama / Qwen）。

场景追问 1

突然收到一笔 $5000 的 API 账单，正常月份只有 $500，怎么快速定位？

（1）检查监控，找出消耗激增的时间点和对应功能模块；（2）分析 Token 分布，看是输入还是输出激增；（3）检查异常请求，看是否有查询触发无限循环或过度检索；（4）检查模型使用，看是否有错误配置导致大量请求使用昂贵模型；（5）立即止损：限制单请求 Token 上限、暂时禁用可疑功能、启用预算熔断。

场景追问 2

语义缓存命中率从 70% 降到 30%，怎么诊断和恢复？

（1）检查查询模式是否变化；（2）检查相似度阈值是否需要调整；（3）检查缓存存储是否达到容量上限导致驱逐；（4）检查 embedding 模型版本变更是否导致向量空间漂移。恢复策略：重算缓存向量、调整阈值、扩大容量、针对新模式重训缓存策略。

场景追问 3

模型路由器频繁把简单任务路由到昂贵大模型，怎么优化？

（1）分析错误路由的查询特征，找出导致误判的模式；（2）用新的正负样本重新训练路由器；（3）加入成本敏感的评估指标，不只考虑质量；（4）对路由到高成本模型的请求做二次检查；（5）设置路由阈值，边界情况倾向便宜模型。

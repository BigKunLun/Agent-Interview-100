高可用架构

主区同步复制，
备区保持温备。

原文的 Active-Passive 架构：全球负载均衡把流量送到 Region A；Region A 的 Redis / PostgreSQL 同步复制到 Region B；健康检查失败就切流量，目标中断时间 <30 秒。

全球负载均衡DNS / CDN；健康检查决定流量去 Region A 还是 Region B。
↓ 正常流量
Region A（主）API Gateway → Agent Workers → Model Gateway（多提供商）；Redis 主、PostgreSQL 主。
↓ 同步复制
Region B（温备）API Gateway → Agent Workers（平时缩容，切换后自动扩容）；Redis 副本、PostgreSQL 副，切换后从这里恢复会话状态。
↺ 健康检查失败 → 切流量

架构与顺序来自原文 Mermaid；本页用结构化卡片离线呈现

多提供商故障转移

优先级、熔断、
最后才降级。

原文的 LLMFailoverManager 按优先级依次尝试提供商；熔断器打开就跳过；限流或服务不可用就记录失败并试下一个；全部不可用才降级。

原文熔断器的三个状态
状态含义行为
CLOSED正常请求放行；失败计数累加
OPEN熔断跳过该提供商；超过 recovery_timeout 后进入 HALF_OPEN
HALF_OPEN试探允许试探请求；成功回 CLOSED，失败重新 OPEN

状态机与默认阈值（失败 5 次、恢复 60 秒）来自原文；本页未运行熔断器

查看原文的 LLMFailoverManager 与 CircuitBreaker 代码 
class LLMFailoverManager:
    """LLM 提供商级别的故障转移"""

    def __init__(self):
        self.providers = [
            {"name": "openai",    "priority": 1, "healthy": True},
            {"name": "anthropic", "priority": 2, "healthy": True},
            {"name": "google",    "priority": 3, "healthy": True},
        ]
        self.circuit_breakers = {}

    async def call_with_failover(self, request):
        """带故障转移的 LLM 调用"""
        for provider in sorted(self.providers, key=lambda p: p["priority"]):
            if not provider["healthy"]:
                continue

            breaker = self.circuit_breakers[provider["name"]]
            if breaker.is_open:
                continue  # 熔断器打开，跳过

            try:
                response = await self.call_provider(provider["name"], request)
                breaker.record_success()
                return response

            except RateLimitError:
                breaker.record_failure()
                continue  # 限流，尝试下一个

            except ServiceUnavailableError:
                breaker.record_failure()
                provider["healthy"] = False
                self.schedule_health_check(provider, delay=60)
                continue

        # 所有提供商都不可用 → 降级
        return await self.degrade(request)


class CircuitBreaker:
    """熔断器——防止故障级联"""

    def __init__(self, failure_threshold=5, recovery_timeout=60):
        self.failure_count = 0
        self.threshold = failure_threshold
        self.timeout = recovery_timeout
        self.state = "CLOSED"  # CLOSED → OPEN → HALF_OPEN

    @property
    def is_open(self):
        if self.state == "OPEN":
            if time.time() - self.opened_at > self.timeout:
                self.state = "HALF_OPEN"
                return False
            return True
        return False

    def record_failure(self):
        self.failure_count += 1
        if self.failure_count >= self.threshold:
            self.state = "OPEN"
            self.opened_at = time.time()

    def record_success(self):
        self.failure_count = 0
        self.state = "CLOSED"

检查点

存什么，放哪，
怎么恢复。

原文把检查点拆成三个问题：完整状态清单、分层存储与快照频率、五步恢复与幂等前提。044 演示的是状态机里“恢复到哪个状态”；本页不重复状态机，聚焦存储分层、副作用账本和恢复顺序。

上面的交互面板第 2 阶段把这套内容做成了固定演练：六类状态、四层存储、五步恢复。这里保留原文的完整清单，方便逐项核对。

存什么：六类状态

原文的检查点完整状态清单
类别要存什么缺失的后果
对话状态messages（含 tool_calls 与工具结果）、system prompt 版本恢复后接不上上下文，重复提问或重复执行
循环状态turn 序号、已用 token / 耗时 / 成本预算和循环保护失效，可能无限续跑
任务状态子任务 DAG、各节点状态与产出引用无法判断哪些步骤该跳过、哪些该继续
外部副作用不可逆操作及状态、幂等键、外部系统返回的引用重复下单、重复发邮件、重复扣款
进行中的工具调用哪个 tool_call 正在执行，或已执行但结果未回灌恢复后既不敢重试，也不知道结果
版本信息prompt 版本、工具 schema 版本、模型版本用新逻辑续跑旧状态，行为不一致

原文强调：外部副作用记录最容易被漏掉，也最致命。计划和中间结果丢了可以重算，已经发生的扣款不能靠重算撤销。凡是要调用外部写接口的步骤，必须在执行前落账，不能等成功后再补记录。

放哪：四层存储

原文的检查点分层存储
存储放什么特点
Redis当前 run 的循环状态、最新 checkpoint 指针读写快，适合热状态；配 AOF 和副本，允许秒级丢失
关系库（Postgres）按 run_id 的完整快照、副作用账本事务可靠，作为恢复的权威来源
对象存储（S3 等）长工具输出、文件快照、完整消息归档便宜、容量大，不适合高频小写入
事件日志 + 定期快照每步追加事件，每 N 步或每 M 分钟做全量快照恢复 = 快照 + 重放增量，成本和 RPO 可调

快照频率是恢复速度和写入成本的平衡。每步全量快照恢复最快，但写入放大严重；事件日志加每 10 步一次快照，能把重放量控制在较小范围。这是原文经验值，实际间隔要按单步耗时和可接受 RPO 实测。

怎么恢复：五步

  1. 加载最近快照，按事件日志重放到中断点。
  2. 校验版本一致。prompt、工具 schema、模型版本对不上时，不要直接续跑，先迁移状态或转人工。
  3. 核对副作用。pending 或 unknown 的操作去外部系统查真实结果，不能假设成功，也不能假设失败。
  4. 从下一个未完成步骤续跑。已完成步骤直接跳过，不要从快照点整体重放。
  5. 注入恢复提示，例如“系统刚从故障恢复，第 N 轮，已完成 A、B，未完成 C，副作用 D 已确认。不要重复执行已完成步骤”。

幂等前提

第三步能否成立，取决于外部写接口是否支持幂等键。没有幂等键，你既不能安全重试，也无法确认一次“结果未知”的调用到底生效没有——原文的原话是：没有幂等键的恢复就是赌博。调用前生成幂等键并落账，随请求发给外部系统；外部系统对同一个键只执行一次。

class EffectStatus(str, Enum):
    PENDING = "pending"      # 已决定执行，结果未知
    SUCCEEDED = "succeeded"
    FAILED = "failed"
    UNKNOWN = "unknown"      # 进程崩溃等导致结果无法确认


@dataclass
class SideEffect:
    run_id: str
    step_id: str
    operation: str                       # 例如 "create_order"
    idempotency_key: str                 # run_id + step_id + 操作类型，全局唯一
    status: EffectStatus = EffectStatus.PENDING
    external_ref: str | None = None      # 外部系统返回的订单号、消息 id
    updated_at: float = field(default_factory=time.time)


class SideEffectLedger:
    """副作用账本：先记账再执行，恢复时逐条对账"""

    async def begin(self, effect: SideEffect) -> SideEffect:
        """执行前写入 PENDING；PENDING/UNKNOWN 的旧记录要先 reconcile"""
        existing = await self.store.get(effect.idempotency_key)
        if existing is None:
            await self.store.insert(effect)  # 并发重复由唯一索引兜底
            return effect
        if existing.status == EffectStatus.FAILED:
            # 外部确认没生效的失败可以安全重试：同键重发只生效一次
            await self.mark(existing.idempotency_key, EffectStatus.PENDING)
            existing.status = EffectStatus.PENDING
        elif existing.status in (EffectStatus.PENDING, EffectStatus.UNKNOWN):
            # 结果未知：必须先 reconcile，不能直接重试或当成已完成
            raise RuntimeError(f"unresolved side effect: {effect.idempotency_key}")
        return existing

    async def reconcile(self, run_id: str, probe) -> list[SideEffect]:
        """恢复时调用。probe(operation, key) 按幂等键查外部真实状态"""
        effects = await self.store.list_by_run(run_id)
        for effect in effects:
            if effect.status not in (EffectStatus.PENDING, EffectStatus.UNKNOWN):
                continue
            try:
                result: ProbeResult = await probe(effect.operation,
                                                  effect.idempotency_key)
            except ProbeError:
                continue  # 查询失败：保持原状态，稍后重试，绝不能当成失败
            if result.state == "found":
                await self.mark(effect.idempotency_key,
                                EffectStatus.SUCCEEDED, result.ref)
            elif result.state == "not_found":
                # 只有外部系统明确保证查询已一致时，not_found 才能判失败
                await self.mark(effect.idempotency_key, EffectStatus.FAILED)
            # unknown：保持原状态，等下一次对账
        return effects

优雅降级

部分可用，
好过完全不可用。

原文把降级分成 Level 0–4：正常、LLM 部分降级、LLM 完全不可用、数据库不可用、完全降级。降级策略要预先设计并测试，不能等事故中临时决定。

原文的五级优雅降级
级别条件行为
Level 0所有服务正常完整 Agent 功能
Level 1主 LLM 提供商限流或慢切换备用提供商、降级到更小模型、增加缓存使用

常见误区 / 面试追问

两个误区，
三个追问。

LLM 云服务也会宕机；Agent 也不是无状态。灾备测试、降级选择和检查点遗漏是常见追问。

误区 01

“LLM API 是云服务，不需要考虑可用性”

LLM API 提供商也会宕机或限流。原文称 2024–2025 年 OpenAI 和 Anthropic 都有过多次服务中断。必须有多提供商故障转移策略，不能把鸡蛋放在一个篮子里。

误区 02

“Agent 没有状态，不需要灾难恢复”

多步 Agent 有大量状态：执行计划、已完成步骤的结果、对话历史、工具调用结果。丢失这些状态意味着任务从头开始，用户体验极差。检查点机制是必需的。

追问 03

如何测试灾难恢复方案？

Chaos Engineering 随机中断 LLM API 连接，验证故障转移；故障注入模拟数据库宕机、网络分区；每季度进行一次完整的区域切换演练；记录实际 RTO 并与目标对比。

追问 04

优雅降级和完全不可用之间如何选择？

原则是部分功能可用优于完全不可用。用户宁可看到“AI 助手暂时以简化模式运行”，也不愿看到“服务不可用”。降级策略应该预先设计和测试，而不是在事故中临时决定。

追问 05

Checkpoint 里最容易被忽略、后果最严重的是什么？

外部副作用记录。计划丢了可以重算，已执行的不可逆操作（下单、发邮件、扣款）丢了就无法判断是否要重试。正确做法是执行前把操作、幂等键和状态写入账本，恢复时按幂等键去外部系统查询真实结果，再决定跳过还是重试。没有幂等键的恢复就是赌博。

Agent 的故障常常不是崩溃，而是“看起来正常，结果不对”。排查从告警开始，用 Trace ID 还原每一步的输入、输出和工具响应，定位到具体步骤，再决定修 Prompt、修工具、修权限还是修模型版本。

故障特殊性

同样的输入，
不一定走同一条路。

Agent 故障是非确定性的：同一输入可能产生不同执行路径。排查必须依赖完整的 Trace 记录，而不是简单回放日志。

原文把排查流程写成 OODA 循环：Observe 通过 Metrics 告警发现异常；Orient 用分布式追踪定位到具体 step；Decide 分析 LLM 输入输出和工具响应找根因；Act 制定修复并验证。之后用 Post-Mortem 把故障模式沉淀成检测规则，闭合防复发。

Metrics 告警Token 异常 · P99 飙升 · 错误率突增
↓ 找到异常会话
Trace 深入分析Step 回放 · Context 快照 · 路径还原
↓ 定位到具体步骤
根因分析LLM / Tool 层定位具体原因
↓ 给出修复方案
修复验证 + Post-Mortem回归测试 + 灰度发布；沉淀检测规则

class TraceAnalyzer:
    """Agent Trace 分析器 —— 故障排查核心工具"""

    def __init__(self, steps: list[TraceStep]):
        self.steps = steps

    def detect_infinite_loop(self, max_repeats: int = 3) -> dict:
        """检测无限循环 —— 滑动窗口发现重复 tool_call 模式"""
        seq = [s.tool_name for s in self.steps if s.action == "tool_call" and s.tool_name]
        for win in range(1, len(seq) // 2 + 1):
            for i in range(len(seq) - win * max_repeats + 1):
                pattern = seq[i:i + win]
                count = sum(1 for j in range(i, len(seq) - win + 1, win)
                            if seq[j:j + win] == pattern)
                if count >= max_repeats:
                    return {"detected": True, "pattern": pattern,
                            "repeat_count": count, "severity": "critical"}
        return {"detected": False}

    def analyze_context_placement(self) -> dict:
        """分析检索内容在 Context 中的位置 —— 排查 Lost-in-the-Middle"""
        for step in self.steps:
            if step.action == "llm_call" and "[RETRIEVED_CONTEXT]" in step.input_text:
                pos = step.input_text.find("[RETRIEVED_CONTEXT]")
                ratio = pos / len(step.input_text)
                return {"position_ratio": ratio,
                        "risk": "high" if 0.3 < ratio < 0.7 else "low"}
        return {"risk": "unknown"}

    def get_tool_latency_stats(self) -> dict:
        """各工具延迟分布 —— 排查超时问题"""
        buckets: dict[str, list[float]] = {}
        for s in self.steps:
            if s.action == "tool_call" and s.tool_name:
                buckets.setdefault(s.tool_name, []).append(s.latency_ms)
        return {name: {"p50": sorted(lats)[len(lats)//2],
                       "p99": sorted(lats)[int(len(lats)*0.99)],
                       "error_rate": sum(1 for s in self.steps
                                         if s.tool_name == name and s.error) / len(lats)}
                for name, lats in buckets.items()}


class TokenBudgetMonitor:
    """Token 预算监控器 —— 实时追踪和预警"""

    def __init__(self, max_tokens: int = 100_000, max_steps: int = 30):
        self.max_tokens, self.max_steps = max_tokens, max_steps
        self.consumed, self.step_count = 0, 0
        self.history: list[int] = []

    def record(self, step: TraceStep) -> dict:
        self.consumed += step.token_count
        self.step_count += 1
        self.history.append(step.token_count)
        alert = None
        if self.consumed >= self.max_tokens:
            alert = "CRITICAL: Token 预算耗尽"
        elif self.step_count >= self.max_steps:
            alert = "CRITICAL: 步数超限"
        elif len(self.history) >= 3:
            avg = sum(self.history[-3:-1]) / 2
            if avg > 0 and self.history[-1] > avg * 3:
                alert = f"WARNING: Token 突增 (当前{self.history[-1]}, 均值{avg:.0f})"
        return {"step": self.step_count, "used": self.consumed, "alert": alert}

    def should_terminate(self) -> tuple[bool, str]:
        if self.consumed >= self.max_tokens: return True, "Token 预算耗尽"
        if self.step_count >= self.max_steps: return True, "步数超限"
        return False, ""

注意第 4 类的代价：危险操作不是“回答错了”，而是已经删除了 50,000 条记录。排查能定位问题，但恢复要靠备份和软删除；所以修复重点在事前拦截，而不是事后解释。

第 5 类最容易被误判成代码故障。原文的排查顺序是先查代码变更和基础设施，再看 Trace 对比，最后查 API Response Header 里的模型版本：gpt-4-0613 变成 gpt-4-0125-preview，供应商静默升级了默认版本。

可观测性体系

Metrics 发现，
Trace 定位，Log 复盘。

三者通过 Trace ID 关联。缺任何一层，排查都会断在中间：只有指标不知道哪一步错，只有日志还原不了整条路径。

Metrics 指标监控Token 消耗 / 秒、延迟 P50 / P99、工具成功率、步数分布。负责发现异常。
Tracing 分布式追踪Trace ID 串联、每步 Input / Output、Tool Response、Context 快照。负责定位根因。
Logging 结构化日志Step 级别日志、错误堆栈、决策理由（CoT）、审计操作日志。负责事后分析。

三支柱内容来自原文；本页未接入任何观测系统

原文强调告警阈值要基于历史基线动态设定，而不是拍一个固定数字。基线会随模型版本、流量结构和业务季节变化；固定阈值要么太松漏报，要么太紧制造告警疲劳。

常见误区 / 面试追问

两个误区，
两个追问。

日志不能替代 Trace；回滚代码也不总能解决 Agent 故障。可观测性体系和 Post-Mortem 是常见追问。

误区 01

“直接看日志就够了，不需要专门的 Trace 系统”

Agent 执行路径是非确定性的，传统日志只能看到离散事件点，无法还原完整决策链路。多步推理中某一步的错误可能几步之后才显现，没有 Trace 串联根本无法回溯。

误区 02

“出了问题直接回滚代码就能解决”

Agent 故障很多时候不是代码问题，而是模型行为变化、外部 API 状态变化、数据分布漂移等非代码因素。回滚代码对这类问题完全无效。先通过 Trace 定位根因类别（Prompt / 模型 / 工具 / 数据），再针对性修复。

追问 03

如何设计 Agent 的可观测性体系？

三个层次：Metrics（Token 消耗速率、工具成功率、端到端延迟、步数分布）发现异常；Tracing（每步 Input/Output、Tool Response、Context 快照、模型版本）定位根因；Logging（结构化决策日志、错误堆栈、审计记录）事后分析。三者通过 Trace ID 关联，告警阈值基于历史基线动态设定。

追问 04

生产故障后如何做 Post-Mortem？

遵循 Blameless Post-Mortem：建立完整事件时间线，用 5 Whys 追溯根因到系统性缺陷，产出有负责人和截止日期的 Action Items。关键是把每次故障模式沉淀为自动化检测规则，确保同类问题不复发。

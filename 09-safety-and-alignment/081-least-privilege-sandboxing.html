中级 · Safety & Alignment · 可交互讲解

权限跟着动作走，
不跟着 Agent 走。

给 Agent 一个固定角色，无法覆盖它运行时临时决定要做的事。更稳的做法是：每个动作单独授权，令牌限时、限范围，执行进沙箱，出网过白名单。

传统静态最小权限不够，因为 Agent 的工具组合无法预先穷举。原文的答案是动态运行时权限：策略引擎逐次评估，颁发最小权限令牌（如 60 秒过期）。本页不执行任何命令、不启动容器；脱敏示例是固定文本，不接触真实数据。

一 · 为什么传统最小权限不够

部署时定好的权限，
追不上运行时的动作。

传统服务的行为路径可预测，权限可以在部署时写死。Agent 在运行时决定调哪个工具，同一角色在不同任务里需要的权限也不同。

传统软件与 Agent 在权限管理上的差异
维度传统服务Agent
权限确定时机部署时静态确定。运行时动态决定，任务之间还会变。
调用模式固定 API 路径，可预先枚举。工具组合无法预先穷举。
被攻击后的行为仍在代码路径内。被 Prompt Injection 后行为不可预测。
需要什么角色 + 静态策略。动态、运行时、上下文感知的权限管理。

原文的判断很直接：权限必须在 Agent 外部强制执行，不能依赖 Agent 自己判断“该不该用这个工具”。被注入之后，Agent 的判断本身就是攻击面。OWASP 的 Agent 安全清单也把“工具滥用与权限提升”列为核心威胁，这正是权限要按动作、在 Agent 外部判定的原因。

二 · 三种实现模式

白名单、短会话、
逐次令牌。

原文给了三层递进：基于角色的工具白名单、按任务创建的最小权限会话、AI Identity Gateway 的逐次授权。越往后，权限越贴近“这一次动作”。

模式 1

角色工具白名单

research_agent 只允许 web_search、read_document，明确拒绝 write_file、send_email、database_write；code_agent 只允许 read_file、write_file、run_tests。

模式 2

动态最小权限会话

每个任务先分析所需工具，只授予这些工具；API Key 限定 scope，TTL 300 秒；资源上限 20 次调用、$1、120 秒。

模式 3

AI Identity Gateway

每次操作都过策略引擎，评估 agent、action、context、user permissions；允许时颁发单次操作令牌，TTL 60 秒。

三种模式不是替代关系，可以叠加：角色白名单挡住明显越界，任务会话限制范围，网关在每次动作前再核对上下文。

原文动态授权示例（Python，仅展示，不执行）

def request_with_dynamic_auth(self, action, context):
    policy_result = self.policy_engine.evaluate(
        agent_id=self.id,
        action=action,
        context=context,
        user_permissions=context.user.permissions,
    )
    if policy_result.allowed:
        token = self.issue_scoped_token(
            permissions=policy_result.granted_permissions,
            ttl=60,  # 单次操作，60 秒过期
        )
        return self.execute_with_token(action, token)
    else:
        return {"denied": True, "reason": policy_result.reason}

JIT（Just-In-Time）提权是同一思路的延伸：Agent 请求临时权限 → 策略引擎评估 → 必要时人工审批 → 授予限时令牌，5 分钟后自动撤销，避免永久提权。

三 · 沙箱四层

从进程到一次性环境，
隔离强度递增。

原文把沙箱分四层：进程隔离、容器、gVisor / microVM、临时性环境。层数越高，隔离越强，启动与运维成本也越高。

四级沙箱的技术、适用场景与限制
层级技术适用限制 / 优势
Level 1 · 进程隔离subprocess + 资源限制（ulimit）。简单的代码执行。共享内核，隔离不完全。
Level 2 · 容器Docker / Podman。工具执行、文件操作。文件系统、网络、资源可隔离；每次工具调用独立容器。
Level 3 · 内核级gVisor（用户态内核）/ Firecracker（microVM）。高安全要求的代码执行。即使容器逃逸也难影响宿主；AWS Lambda、Google Cloud Run 的底层技术。
Level 4 · 临时环境每次执行创建全新环境，执行后销毁。最高安全要求。无状态残留，每次执行互不影响；InfoQ 案例的 ephemeral runner + 强制销毁。

原文沙箱配置示例（仅展示，不执行）

container = await self.create_container(
    image=f"sandbox-{language}:latest",
    network_mode="none",          # 禁止网络访问
    read_only=True,               # 只读文件系统
    mem_limit="256m",             # 内存限制
    cpu_quota=50000,              # CPU 限制
    timeout=30,                   # 超时限制
    volumes={
        "/tmp/workspace": {       # 只允许写临时目录
            "bind": "/workspace",
            "mode": "rw",
        },
    },
)
# 执行后立即销毁

配置里的四个数字值得记住：network_mode="none"、只读根文件系统、256MB 内存、30 秒超时。它们分别对应网络、文件、内存、时间四类逃逸面。

四 · 出口控制与可逆脱敏

数据出不去，
任务还能继续。

沙箱挡住执行环境，出口控制挡住数据外流。可逆脱敏再解决一个工程问题：模型需要看到“某个手机号”，但不该看到真值。

出口控制的两道检查

第一道是域名白名单：只允许 api.openai.com、api.anthropic.com、company-internal-api.com 这类目标。第二道是 DLP：PII 默认脱敏，API key 与内部 URL 默认阻断。顺序是先查目的地，再扫内容；目的地不合法时不必再看 payload。

原文的 DLP 规则是三条：{"type": "pii", "action": "redact"}、{"type": "api_key", "action": "block"}、{"type": "internal_url", "action": "block"}。脱敏与阻断要分开：日志可以脱敏，密钥必须阻断。

为什么 [REDACTED] 不够

不可逆的 [REDACTED] 适合日志，不适合 Agent 工作流。模型可能在下一次工具调用里引用这个值，比如把手机号填进表单，抹掉后任务直接断掉；两个不同手机号都变成同一个占位符，模型也无法区分。

可逆脱敏把真值换成 <PHONE_1>，映射表只存在执行侧。进模型前替换，模型输出和工具参数里的占位符在执行前还原。模型看到的是符号，功能链路不受影响。

固定文本示例（不执行）：
原始：联系 13812345678，邮箱 alice@example.com
进模型：联系 <PHONE_1>，邮箱 <EMAIL_1>
执行前还原：send_sms(to='13812345678')

格式校验场景（手机号位数、银行卡 Luhn 校验）用格式保留脱敏：保留前后几位，或生成同格式假值。前者不可逆，只用于展示；后者要登记回真值，校验通过后再换回来。

边界要讲清楚

脱敏降低泄露面，不替代权限控制。有权限的人误用数据，脱敏拦不住；反过来，只做权限不做出口控制，被注入的 Agent 仍可能把读到的数据发出去。两者是不同层，不能互相替代。

手机号、邮箱与银行卡示例均为固定虚构文本，不调用正则、不执行脱敏代码、不接触真实数据。

五 · 完整安全架构

每一跳都有门，
结果才回灌。

原文的完整链路是：输入护栏 → Agent 推理 → 是否需要工具 → 策略引擎（OPA / Cedar）→ 是否授权 → 是否高风险 → 人工审批 → 沙箱执行 → 出口控制 → 结果回灌。

入口

用户请求先过输入护栏，再进入 Agent 推理。

分支

不需要工具 → 输出护栏 → 返回用户；需要工具 → 进入权限策略引擎。

授权

OPA / Cedar 评估 agent、action、context、user permissions。不授权 → 拒绝。

审批

授权但属于高风险 → 人工审批；批准后才进入沙箱。

执行

沙箱执行，出口控制检查目的地与 payload；结果回灌 Agent，继续推理。

这张图的关键不是节点多，而是顺序：授权在沙箱前，沙箱在出口前，出口在结果回灌前。任何一步跳过，后面的门都补不回来。

常见误区 / 面试追问

两个误区，
两个追问。

按原文顺序保留 4 条：前两条是误区，后两条是追问。第一条里的 Agents Rule of Two 是本页最重要的设计准则。

误区 1

“给 Agent 全部权限，让它自己判断用哪些。”

这是最危险的做法。Agent 被 Prompt Injection 后，“判断”会被攻击者控制。权限必须在 Agent 外部强制执行。Meta 的 Agents Rule of Two（2025-10）：在注入检测尚不可靠之前，单个会话不应同时具备 [A] 处理不可信输入、[B] 访问敏感数据、[C] 改变状态或对外通信，最多同时具备两个。三者必须俱全时，拆两阶段会话、用沙箱阻断 C，或加可信内容过滤器降低 A。该原则源于 Willison 的致命三角（078）。

误区 2

“沙箱会严重影响性能。”

现代容器与 microVM（如 Firecracker）的启动延迟已到毫秒级；gVisor 的性能开销在多数场景下低于 10%。对 Agent 来说，LLM 调用本身 1–5 秒的延迟远大于沙箱开销。

追问 1

“如何处理 Agent 需要临时提升权限的场景？”

用 JIT 权限提升：Agent 请求临时权限 → 策略引擎评估 → 需要时人工审批 → 授予限时令牌（如 5 分钟后自动撤销）。避免永久提权，也避免把高权限令牌写进长期配置。

追问 2

“多 Agent 系统中如何防止权限提升链？”

四条：Agent 间通信经过统一策略网关；每个 Agent 有独立权限域，不能继承他人权限；消息传递时剥离权限上下文；监控异常的 Agent 间调用模式。核心是取消默认信任，而不是让上层 Agent “判断得更准”。

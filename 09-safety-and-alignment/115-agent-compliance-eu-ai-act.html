先把用途分级，

风险分级体系

风险越高，
义务越重。

原文把 EU AI Act 的核心设计概括为“风险越高，义务越重”：禁止、高风险、有限风险、最小风险四档，义务依次递减。

等级原文列举的场景义务强度
禁止使用社会评分、实时生物识别、潜意识操纵、剥削弱势群体不可接受风险，全面禁止
高风险招聘、信贷、医疗、执法、教育、关键基础设施等严格义务：风险体系、数据治理、文档、日志、透明度、人工监督、稳健性、事后监控、合格评定
有限风险聊天机器人、Deepfake、情感识别透明度义务：须告知用户
最小风险垃圾邮件过滤、游戏 AI、库存预测无额外义务，可自由部署

以上日期、分级和罚款口径均按原文时点转述，本页未联网核对法规最新修订或实施指南，不构成法律意见。原文同时提醒：面向欧盟市场的 Agent 产品，必须在 2026-08-02 前完成高风险合规，或证明自己不属于高风险。

高风险义务

九项义务，
逐条对应工程。

一旦被判定为高风险，原文列出九类义务。每一项都能翻译成具体工程动作；合规的增量成本，主要是把已有实践文档化、制度化、可审计化。

原文判断

这些义务看起来繁重，但从工程角度看，多数是成熟工程实践的法律化：可观测性、文档化、人工审核、安全测试本就是生产级 Agent 的标配。真正的增量成本在“把已有实践文档化、制度化、可审计化”，而不是从零发明一套系统。

GPAI 条款

你多半是部署者，
不是提供者。

Agent 通常构建在通用大模型（GPAI）之上。原文对 GPAI 模型提供者单独设定义务；对 Agent 团队的影响，是责任边界和上游信息获取。

  • 所有 GPAI 提供者：须维护技术文档、训练数据摘要、版权合规、向下游部署者传递信息。
  • 系统性风险 GPAI：训练算力超过 10²⁵ FLOPS 阈值的模型，额外要求模型评估、对抗性测试（Red Teaming）、严重事件上报、网络安全保护。

对 Agent 团队的影响

原文判断：你通常是“部署者”而非“提供者”，主要义务在自己这层；但你有权要求模型提供者传递必要的技术文档与能力边界信息。如果你对底层模型做了显著微调（fine-tuning）使其进入新用途，责任边界会向你偏移。

这也是面试常问的边界题：不要把“模型提供者的合规”当成“我的合规”。部署者仍有透明度、人工监督、日志、事后监控等义务；上游文档是输入，不是免责证明。

Agent 特有挑战

代码是确定的，
Agent 不是。

传统软件合规的对象是确定性的代码逻辑；Agent 合规面对的是概率性的自主决策链。原文列出三个独有难题。

挑战一：自主决策的可解释性

传统软件的决策路径由代码硬编码，审计就是读代码。Agent 的决策由 LLM 在运行时动态生成，同一次输入可能走完全不同的工具调用序列。EU AI Act 高风险义务要求决策可解释、可追溯，但 Agent 的 reasoning 过程往往是黑盒。

挑战二：工具调用的全链路审计

Agent 的危害往往不在“说了什么”，而在“做了什么”：自主下单、修改生产配置、对外发送内容。logging 义务落到 Agent 上，意味着每一次 tool call 的入参、出参、时间戳、触发 reasoning 都必须结构化留存，且日志本身要防篡改。

挑战三：记忆系统与 GDPR 的交叉

Agent 的 long-term memory 会持续积累对话历史、偏好画像、执行过的操作。这与 GDPR 的数据最小化、目的限制、删除权（Right to Erasure）、数据可携带权产生直接冲突。合规的 memory 系统必须支持：按用户粒度隔离、可导出、可彻底删除、有保留期限策略。

原文的落点是：Agent 合规不能只审最终输出，要审“决策链 + 工具调用 + 记忆”。这也是后面合规架构把审计日志和 HITL 放进执行循环的原因。

合规设计清单与架构

把义务嵌进
执行循环。

原文把合规做成一套“合规中间层”：透明度、PII 脱敏、风险评估、HITL、审计日志、输出护栏、事后监控，串成强制卡点。

用户请求→ ① 透明度声明→ ② PII 脱敏→ ③ Agent 推理
每次工具调用 ↓
④ 风险评估器 低风险 ↓ ⑥ 全链路审计日志
④ 风险评估器 高风险 ↓ ⑤ HITL 卡点 · 人工确认 ↓ ⑥ 全链路审计日志
⑥ 全链路审计日志→ ⑦ 输出护栏→ 最终响应→ ⑧ 事后监控

这张图的关键不是节点数量，而是两个分支：低风险工具调用直接留痕放行；高风险调用必须先经过人工确认，再进入审计日志。合规不是最后加一道检查，而是每次工具调用都走同一条中间层。

展开原文的合规中间件节选（伪代码） 
# ── 风险分级：哪些 tool call 需要人工确认 ──────────────────
RISK_LEVELS = {
    "search_web": "low",
    "read_file": "low",
    "write_file": "medium",
    "send_email": "high",        # 外发通信 → HITL
    "make_payment": "critical",  # 金融交易 → HITL
    "delete_record": "critical", # 不可逆操作 → HITL
}

@dataclass
class AuditEntry:
    """单条审计日志——满足 EU AI Act Art.12 记录义务"""
    trace_id: str
    timestamp: float
    tool_name: str
    input_hash: str       # 存哈希而非原文，兼顾审计与隐私
    output_hash: str
    reasoning: str        # Agent 决策依据（可解释性）
    risk_level: str
    approved_by: str = ""  # HITL 审批人
    metadata: dict = field(default_factory=dict)

class ComplianceMiddleware:
    """Agent 合规中间件：审计 + HITL + PII 脱敏"""

    def before_tool_call(self, tool_name: str, params: dict,
                         reasoning: str, trace_id: str) -> dict:
        risk = RISK_LEVELS.get(tool_name, "medium")
        if risk in {"high", "critical"}:
            # 高风险操作：升级人工确认（对应 Art.14 人工监督）
            return {
                "needs_approval": True,
                "risk_level": risk,
                "tool": tool_name,
                "reasoning": reasoning,
                "message": f"高风险操作 {tool_name}，等待人工确认",
            }
        return {"needs_approval": False, "risk_level": risk}

    def purge_user_data(self, user_id: str) -> int:
        """Right to Erasure——彻底删除某用户的所有 trace"""
        before = len(self.audit_log)
        self.audit_log = [
            e for e in self.audit_log
            if e.metadata.get("user_id") != user_id
        ]
        return before - len(self.audit_log)

原文的实践建议是“最高水位线”策略：以最严法域（通常是 EU）为基线设计合规架构，再叠加各市场的特殊要求，例如中国的内容合规与备案、美国部分州的算法审计。这样避免为每个市场维护独立合规版本的高昂成本。

常见误区 / 面试追问

判定看用途，
合规要可追溯。

原文列了 1 条误区和 4 条追问。高频点是：我的 Agent 算不算高风险、合规与迭代是否冲突、开源责任怎么分、记忆怎么同时满足两部法规、误操作谁担责。

追问 1

我的 Agent 算不算高风险？判定标准是什么？

两条路径：路径一是用途清单（EU AI Act Annex III），列举招聘筛选、信贷评估、保险定价、教育评分、医疗诊断、执法辅助、关键基础设施管理、民主程序中的投票辅助等；路径二是产品安全法规附件（Annex I）下的 AI 组件，如医疗器械、机械、航空器中的 AI。通用客服 Agent 不是高风险，但同样代码一旦用于筛选简历，立刻变成高风险。判定不看技术，看用途。

误区 1

“合规和快速迭代不可兼得。”

合规并非要求冻结架构，而是要求变更可控可追溯。原文建议建立“合规即代码”（Compliance as Code）流水线：把透明度声明、风险评估、日志规范沉淀为 CI/CD 中的自动检查项，而非人工 review。真正的成本在初次搭建合规基础设施，后续边际成本很低。

追问 2

开源 Agent 的责任归属是谁？

EU AI Act 区分“提供者（provider）”和“部署者（deployer）”。开源模型在“非服务化分发”下享有一定豁免；但一旦你把开源 Agent 包装成服务对外提供，你就是 provider，承担全套义务。只做内部工具且不对外，义务较轻。微调开源模型用于新用途的团队，可能从部署者升级为提供者——原文称这是开源生态中的灰色地带。

追问 3

Agent 的记忆系统怎么同时满足 EU AI Act 和 GDPR？

两部法规关注点不同但交叉：EU AI Act 关注决策可审计（要求保留日志），GDPR 关注隐私保护（要求最小化、可删除）。冲突点是“日志保留”与“删除权”。解法是日志只存哈希和结构化元数据，不存 PII 原文；memory 按用户隔离，支持粒度化删除和保留期限；对必须保留的决策证据做假名化处理，使数据主体不可直接识别。

追问 4

Agent 发生误操作致损，谁担责？

EU AI Act 下责任链条大致是：提供者保证系统本身合规（技术文档、风险体系）；部署者负责正确使用（人工监督、事后监控）；若因部署者未执行 HITL 导致事故，部署者担主责。但实际诉讼中，用户往往同时起诉提供者和部署者。工程上能做的，是确保每次高风险操作都有明确的人工确认记录，把责任边界留痕。具体责任认定请咨询法律顾问。

合规不是孤岛，
它连着安全与部署。

原文把合规放在安全、护栏、HITL、最小权限、评估和生产部署的交叉点上。下面按原文的六条交叉引用整理。

  • 078 Agent 安全风险：合规是安全风险的“法律外壳”。理解 Agent 有哪些攻击面（Prompt Injection、越权工具调用），是判断合规义务轻重的前提。打开 078 Agent 安全风险。
  • 079 Guardrails：输入/输出护栏是合规中间件的核心组件，护栏拦截率直接对应“稳健性与网络安全”义务的落地证据。打开 079 Guardrails。
  • 080 Human-in-the-Loop：HITL 卡点是满足“人工监督”（Art.14）义务的标准工程模式；本文的合规中间件本质上是 HITL 的风险分级自动化。打开 080 Human-in-the-Loop。
  • 081 最小权限与沙箱：最小权限原则既是安全最佳实践，也是合规审计中“数据治理”与“网络安全”义务的直接证据。打开 081 最小权限与沙箱。

  • 104 / 010 生产部署：合规架构（日志、监控、HITL）应作为生产部署基础设施的一部分，从架构评审阶段纳入。打开 010 生产级 Agent 系统设计；打开 104 生产故障排查。

基础 · Safety & Alignment · 可交互讲解

护栏不是一句话，
是三道门。

在请求进入 LLM 前检查输入，在回答返回用户前检查输出，在 Agent 调工具前检查权限与参数。三道门各管一段，不能互相替代。

护栏分两类：规则型（正则、关键词，快而便宜）和模型型（分类器 / LLM，懂语义但更慢更贵）。最佳实践是“先规则后模型”的分层组合。本页的规则、阈值、命中与拦截结果都是固定教学模拟，不调用真实分类器或模型。

一 · 护栏放在哪

输入、输出，
Agent 还要多一道。

原文的流程图有三道卡：进 LLM 前、出 LLM 后、工具执行前。聊天机器人通常只有前两道，Agent 因为会调工具，多了第三道。

输入护栏

请求进入 LLM 前

PII 脱敏、注入检测、话题合规、长度与格式检查。目标是别让危险输入进入模型，也别让敏感数据进入第三方模型。

输出护栏

回答返回用户前

敏感过滤、幻觉检测、毒性检测、结构验证。输入干净不代表输出安全：模型可能自己编，也可能复述检索到的敏感内容。

工具调用护栏

工具执行前（Agent 特有）

权限检查、参数验证、危险操作审批、频率限制。动作一旦执行就难回滚，所以这道门必须在调用前，而不是输出后。

三道的顺序不能乱。输出护栏拦不住已经执行的删除操作；输入护栏也拦不住模型对检索文档的误读。每一道门只解决它负责的那一段。

二 · 规则型与模型型

快的先上，
难的再交给模型。

规则型可预测、低成本，但只能抓已知模式；模型型懂语义，但慢、贵、还有误判。原文的建议是串联，不是二选一。

规则型护栏与模型型护栏的对比
维度规则型模型型
实现正则、关键词、白名单、长度与格式校验。分类器或 LLM 做语义判断。
优点快（原文称通常 < 5ms）、可预测、便宜、易审计。能抓变体、隐含毒性、话题偏离等语义问题。
局限只能抓已知模式，容易被改写绕过。延迟 100–500ms，成本更高，存在误报与漏报。
适合PII、SQL 注入、关键词黑名单、格式。Prompt Injection 变体、隐含毒性、上下文相关的灰区。

延迟与成本数字按原文 2026-10 口径保留，未联网核实；不是本页实测。

原文给的搭配比例是：规则型做第一道门，过滤掉约 80% 的明显问题；模型型做第二道门，处理剩余 20% 的边界情况。这个比例是经验值，不是保证。

失败安全是容易被忽略的一条：护栏自身出错时默认拒绝，而不是放行。否则一次超时就会让整条防线静默失效。

规则型的最小结构

原文示例（Python，仅展示，不执行）

class RuleBasedGuardrail:
    def __init__(self):
        self.pii_patterns = {
            "email": r'\b[\w.-]+@[\w.-]+\.\w+\b',
            "phone": r'\b\d{3}[-.]?\d{4}[-.]?\d{4}\b',
            "id_card": r'\b\d{17}[\dXx]\b',
        }
        self.blocked_keywords = ["密码是", "信用卡号", "DROP TABLE"]

    def check_input(self, text):
        for pii_type, pattern in self.pii_patterns.items():
            if re.search(pattern, text):
                return {"blocked": True, "reason": f"包含 {pii_type}"}
        for keyword in self.blocked_keywords:
            if keyword in text:
                return {"blocked": True, "reason": "包含敏感关键词"}
        return {"blocked": False}

    def check_output(self, text):
        for pii_type, pattern in self.pii_patterns.items():
            text = re.sub(pattern, f"[{pii_type}_REDACTED]", text)
        return text

这段代码说明规则型的两个动作：输入命中就拦，输出命中就脱敏。真实规则还要考虑大小写、编码、全角半角、分词边界，否则很容易被绕过。

三 · 主流工具

三种抽象，
三种接入方式。

原文对比了 Guardrails AI、NVIDIA NeMo Guardrails 和 LangChain Middleware。它们不是同一层的东西：一个管验证，一个管对话流，一个管执行链路。

三种主流护栏工具的定位与特色
工具核心能力特色适合
Guardrails AIInput / Output Guards，检测并量化特定风险。Guardrails Hub 预构建验证器；Guardrails Index 基准（24 个护栏 × 6 类风险）；支持自定义验证器。需要现成验证器与结构化输出校验的团队。
NVIDIA NeMo Guardrails基于 Colang 的可编程 rails。状态机驱动，定义对话流的合法路径；input / output / dialog / topical 多种 rail；GPU 加速；可集成 LangChain、LlamaIndex。需要控制多轮对话流程与话题边界的团队。
LangChain Middleware在 Agent 执行链路的关键点插入护栏。启动前、模型前后、工具前后、完成后都能拦截；内置 PII、Human-in-the-Loop、输出格式验证。已经用 LangChain / LangGraph 的 Agent 项目。

四 · Agent 专用护栏

除了输入输出，
还要管动作和轨迹。

Agent 的护栏要回答两个聊天机器人不需要回答的问题：这个工具能不能调？这串动作是不是在绕圈、偏航或超预算？

工具调用护栏与轨迹护栏的检查项
护栏检查项动作
工具调用护栏权限：工具在不在 allowed_tools；参数：是否含 DROP 等危险操作；频率：是否超过 rate limit；风险：是否属于高风险工具。未授权 / 危险参数 / 超频 → 拦截；高风险 → 转人工确认。
轨迹护栏循环：是否重复相同操作；偏离：是否离开原始目标；成本：累计成本是否超预算。检测到循环、漂移或超预算 → 拦截并上报。

工具护栏的关键在于“动作前”。输出护栏看到的是“我已经删了”，工具护栏看到的是“准备删，要不要批”。两者的止损能力完全不同。

轨迹护栏则管“过程”：单步都合法，连起来可能是绕圈或偏航。它需要 trace 数据，通常和可观测性平台一起落地。

六 · 毒性检测与内容过滤

专用小模型，
有时比大模型更准。

毒性检测是护栏里最专门的子领域：暴力、仇恨、色情、自伤等内容要实时拦截。原文从“用什么模型”和“怎么编排”两个角度展开。

四个开源安全模型的参数规模与能力
模型来源参数核心能力特色
Llama Guard 3Meta8B多类别安全分类：暴力、色情、仇恨、自伤等。可自定义安全策略，生态成熟。
ShieldGemmaGoogle2B / 9B输入输出双向安全过滤。与 Gemma 生态集成，提供多档位。
Granite GuardianIBM3B安全分类 + RAG 幻觉检测。兼顾内容安全与事实性。
Granite HAPIBM38MHate / Abuse / Profanity 检测。极轻量，毫秒级实时检测。

原文的选型建议：要多类别精细分类且可微调，选 Llama Guard 3；要兼顾幻觉检测，选 Granite Guardian；只做基础脏话 / 仇恨过滤且延迟敏感，选 Granite HAP 这类轻量分类器。

多层级联：快的前面，贵的后面

Layer 1

规则过滤：挡掉明显违规。

< 1ms
Layer 2

轻量分类器 Granite HAP：处理常见毒性，置信度高于 0.9 直接判定。

约 10ms
Layer 3

安全大模型 Llama Guard：只处理灰区样本。

约 100ms
Layer 4

LLM 上下文审核：仅高风险场景，能理解“医疗讨论中的注射不是暴力”这类上下文。

约 500ms

原文给出的生产分布是：约 95% 请求在 Layer 1–2 决出（< 10ms），约 4% 在 Layer 3 决出（约 100ms），约 1% 才需要 Layer 4（约 500ms）。这组比例是原文示例，不是本页实测。

一个反直觉的实证：在边界清晰的毒性分类任务上，38M 参数的 Granite HAP 召回率是 0.96，而 8B 参数 LLM 的 in-context learning 是 0.78，计算成本还低一个数量级。原则是：分类任务别盲目上大模型。类别固定的检测用专用小模型；需要上下文理解的灰区判断才交给 LLM。

模型参数、延迟、95/4/1 分布与 0.96 vs 0.78 均按原文 2026-10 口径保留，未联网核实，也不是本页实测。

常见误区 / 面试追问

两个误区，
两个追问。

按原文顺序保留 4 条：前两条是误区，后两条是追问。

误区 1

“护栏会让 Agent 变得很慢。”

规则型护栏延迟通常低于 5ms，几乎无感。模型型延迟较高（100–500ms），但可以异步执行：先返回结果，后台评估，发现问题再追回。关键是按风险选择组合，不是所有请求都跑最重的模型。

误区 2

“护栏只需要加在输入端。”

输入护栏防不住间接注入（恶意指令藏在检索内容中）和模型自身的幻觉。必须同时有输出护栏。对 Agent 还需要工具调用护栏和轨迹护栏。

追问 1

“如何评估护栏的有效性？”

三条：用 Guardrails AI Index 基准测试性能；计算拦截率（真正拦截了多少攻击）和误报率（错误拦截了多少正常请求）；定期 Red Team 验证鲁棒性。只看拦截率会奖励“全部拒绝”，必须同时看误报。

追问 2

“规则型和模型型如何搭配？”

规则型做第一道门，快速拦截明确违规：PII、SQL 注入、关键词黑名单。模型型做第二道门，处理需要语义理解的问题：Prompt Injection 变体、隐含毒性、话题偏离。两层串联，规则型过滤掉大部分明显问题，模型型处理边界情况。

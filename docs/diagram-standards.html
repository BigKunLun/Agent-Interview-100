文档 · 配图规范 · 离线阅读

图不是装饰，
是复现锚点。

本库插图遵循的唯一标准：图即代码（Mermaid）、一图一论点、面试可复现。配图的目标不是“每篇都有图”，而是“每个值得图的结构都有唯一一张好图”。

制定日期：2026-08-15。背景：全库 104 篇中 82 篇含 ASCII 图，但 ASCII 画在代码块里，GitHub 永远不会渲染成图。本标准以 Mermaid 取代 ASCII，保留“图随文活、进 diff、可追溯”的优点，消灭“不渲染”的缺点。本页是规范文档，不设算法或分步演示；阅读导航与折叠即全部交互。所有 Mermaid 以离线可读的 HTML/CSS 图加源码折叠呈现，不加载 Mermaid 库、不联网渲染。

一 · 配图三关

三关全过，
才值得画。

一张图值不值得画，过三道门。全过才画；任何一关过不了，表格或文字就是最优解。

01 · 结构关

内容的核心主张，
是不是空间结构？

只有当文章的论点本身就是顺序、循环、分支、层次、时序、拓扑、状态转移时，图才优于文字。

判断方法：读者需要在脑内“组装零件”才能看懂，值得外化成图；文字本身线性可读，画图就是装饰。

02 · 复现关

读者看完，
能在白板上重画吗？

这是面试库独有的判据，也是最硬的一条：好图是面试复现锚点，被问到这道题，应能在 30 秒内画出骨架。

推论：节点 ≤ 10~12 个。超过的图是“文档”，不是“学习资产”，应拆图或退回文字。

03 · 论点关

能用一句话，
写出图注吗？

一图一论点。每张图下方必须有一句话图注，例如“同模型换 harness，Terminal Bench 排名 #33 → #5”。

写不出一句话论点的图，没有独立存在的理由。

执行口径

三关是“与”的关系，不是“或”。结构关决定“要不要图”，复现关决定“图能不能学”，论点关决定“图有没有独立价值”。三关都过才进入第五节选模板；任何一关不过，回到表格或文字。

二 · 形态映射

先认形态，
再选图类型。

不同内容形态对应不同 Mermaid 图类型。对比、选型和概念辨析不画图，直接用表格或文字。

三 · 负面清单

五种图，
不要画。

负面清单和正面标准同样重要。下面五种做法在本库一律不接受，理由都指向同一个问题：图没有承担文字承担不了的认知工作。

  • ×不画并列要点的“图化”。五个盒子排一排，那叫列表，不是图。
  • ×不画 30 节点全景图。那是地图不是知识，拆成多张或退回文字。
  • ×不在节点里塞长句。标签超过一行半，就是段落伪装成图；用 <br/> 折行或精简。
  • ×不放 PNG / SVG / drawio 资产文件。一律 Mermaid 内嵌。图片资产无法 diff，双周扫描改文字时不会同步改图，几个迭代内必然图文漂移。
  • ×“简短回答”段不配图。它本身就是文字版摘要，图只属于“详细解析”里的核心模型。

四 · 工程规范

图要进 diff，
也要有人维护。

配图不是一次性的插图工作，而是文档工程的一部分。下面五条规定图放在哪里、怎么保持风格、谁来同步维护。

  1. 每篇 ≤ 2 张。放在“详细解析”里核心模型首次出现处，必带一句话图注。
  2. 风格统一。中文标签、<br/> 折行、按第五节模板选图选色。
  3. 语法保守。只用 flowchart / sequenceDiagram / stateDiagram-v2 的基础特性（以 GitHub 渲染环境为准），实验性特性不进库。
  4. 维护责任进双周扫描。改动相关文字时必须同步图。Mermaid 与文字同屏出现在 diff 里，改文不改图在 review 时一眼可见。
  5. 优先级公式：被引次数 × ASCII 吃力程度。先覆盖 top 20 枢纽文章，配合双周扫描每次 3~5 篇，不搞全量运动。

为什么不让图变成资产文件

资产文件无法进入文字 diff，改文章时没人会记得同步改图；Mermaid 源码和正文在同一个 diff 里，图文漂移会被 review 直接看见。这是“图即代码”的工程价值，不只是渲染方便。

五 · 模板与配色

六种语义色，
四套骨架。

所有图共用一套语义化六色；一张图内的用色应少于等于三种。唯一例外是分层堆叠图：按层配色，每层一色、层数即色数（≤5 层），因为“颜色 = 层”本身就是该类图要传达的信息。

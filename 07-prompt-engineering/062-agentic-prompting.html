中级 · Prompt Engineering · 可交互讲解

让模型知道，
它能做什么。

Agentic Prompt 不是把任务写得更长，而是把 Agent 执行任务需要的五件事交代清楚：身份与目标、工具、推理格式、约束、输出规范。它优化的是多步决策链，不是一次回答。

关键边界：工具描述是决策依据，不是说明书装饰。模型靠描述判断该不该调用、调用哪个；描述含糊会直接变成误调用和漏调用。

    标准 Prompt vs Agentic Prompt

    一个问一句，
    一个跑一段。

    标准 Prompt 把模型当成回答者；Agentic Prompt 把模型当成执行者，要交代它能用什么、按什么节奏走、什么时候停。

    标准 Prompt：一问一答 
    请分析以下代码的 bug：
{code}

    模型输出一段分析就结束。没有工具、没有中间状态，也没有“下一步做什么”。

    Agentic Prompt：赋予执行能力 
    你是一个代码调试 Agent。你的目标是找到并修复代码中的 bug。

## 可用工具
- read_file(path): 读取源文件
- run_tests(path): 运行测试套件
- edit_file(path, old_text, new_text): 修改文件
- search_code(pattern): 搜索代码库

## 工作流程
1. 先阅读错误信息和相关代码
2. 分析可能的原因
3. 修改代码
4. 运行测试验证修复
5. 如果测试仍然失败，回到步骤 1

## 推理格式
Thought: [你的分析和计划]
Action: [工具名称]
Action Input: [工具参数]
Observation: [工具返回结果]

## 约束
- 最多执行 15 步
- 不要修改测试文件
- 每次只修改一处，验证后再继续

## 输出规范
Final Answer: [修复总结]

    两段 Prompt 的差别不在长度，而在职责：标准 Prompt 只需要模型“答对”；Agentic Prompt 要模型自己决定读哪个文件、跑哪条测试、失败后怎么回退。

    核心组件

    五个问题，
    缺一不可。

    原文模板用 WHO / WHAT / WITH WHAT / HOW / BOUNDARIES / OUTPUT 六段组织；其中 WHO 与 WHAT 可以合并成“角色、目标与流程”。

    WHO你是谁：身份与专业范围
    WHAT做什么：任务与成功标准
    WITH WHAT用什么：工具、参数、边界
    HOW怎么想：Thought / Action / Observation
    BOUNDARIES停在哪：步数、禁止项、降级
    OUTPUT交什么：最终格式

    这六段各自回答一个独立问题。把“成功标准”写进目标段，Agent 才知道什么时候算完成；把“最多 15 步”写进约束段，循环才有硬停止条件。

    展开原文的通用模板（占位符按原文保留） 
    # 1. 角色定义（WHO）
你是 {agent_name}，一个专注于 {domain} 的 AI Agent。
你的核心能力是 {capabilities}。

# 2. 目标定义（WHAT）
你的任务是：{task_description}
成功标准：{success_criteria}

# 3. 工具描述（WITH WHAT）
你可以使用以下工具：

### {tool_name_1}
- 功能：{description}
- 参数：{parameters}
- 返回：{return_type}
- 使用场景：{when_to_use}
- 注意事项：{caveats}

# 4. 推理与行动格式（HOW）
Thought: 分析当前状况，决定下一步
Action: 选择一个工具
Action Input: 提供工具参数（JSON 格式）
Observation: 观察工具返回的结果

# 5. 约束与护栏（BOUNDARIES）
- 最多执行 {max_steps} 步
- 不确定时问用户而非猜测
- 涉及 {dangerous_actions} 时必须确认
- 如果连续 3 次失败，报告问题并停止

# 6. 输出规范（OUTPUT）
完成后使用：
Final Answer: {output_format}

    工具描述的最佳实践

    原文的判断很直接：工具描述的质量直接影响 Agent 的工具选择准确率。在 ToolBench / API-Bank 等工具调用基准上，清晰的工具描述（功能 + 参数语义 + 使用边界）是降低误调用与漏调用的关键变量，比堆“角色扮演”指令更重要。以上为原文观点，未联网核实。

    ✗ 差的描述 
    {
  "name": "search",
  "description": "搜索功能"
}

    模型不知道搜什么、什么时候该用、和别的搜索工具有什么区别。

    ✓ 好的描述 
    {
  "name": "web_search",
  "description": "搜索互联网获取最新信息。适用于需要实时数据、最新新闻或模型训练数据中不包含的信息的场景。不适合搜索代码库内部信息（请用 search_code）。",
  "parameters": {
    "query": {
      "type": "string",
      "description": "搜索关键词，建议使用英文以获得更多结果"
    },
    "max_results": {
      "type": "integer",
      "description": "返回结果数量，默认 5",
      "default": 5
    }
  }
}

    好的描述同时说清四件事：做什么、什么时候用、什么时候不用、参数怎么填。最后一条“不适合……”尤其重要，它把工具之间的边界画了出来。

    ReAct 模式

    想一步，
    做一步，看一眼。

    ReAct 把推理和行动交替写进同一个循环：Thought 说明为什么，Action 调用工具，Observation 接收结果，再进入下一轮。

    请按照 ReAct 模式解决问题。

问题：{question}

你可以使用以下工具：
{tool_descriptions}

按以下格式回答：

Thought: 我需要思考下一步做什么。首先分析问题，然后决定用什么工具。
Action: tool_name
Action Input: {"param1": "value1"}

等待工具返回结果后继续：

Observation: [工具返回的结果]
Thought: 根据结果，我需要...
Action: ...

当你有足够信息时：
Thought: 我现在有了足够的信息来回答问题。
Final Answer: [最终答案]

重要规则：
- 每次只执行一个 Action
- 在 Thought 中解释你的推理过程
- 如果工具调用失败，在 Thought 中分析原因并尝试替代方案
- 不要编造工具不存在的返回结果

    最后一条规则是护栏：模型很容易在 Observation 里“脑补”一个工具结果。Prompt 必须明确禁止编造，执行侧还要用真实工具返回值覆盖模型输出。

    进阶技巧

    四个小改动，
    减少四类失误。

    原文给出四种增强：具体身份、结构化思考、失败处理指令、输出前自检。它们都服务于同一个目标：让行为可预测。

    角色强化

    给具体专家身份，而不是“有帮助的助手”。原文示例：你是一个有 10 年经验的 SRE 工程师。预期是更专业的判断和更谨慎的行动。

    思维链引导

    在 Thought 里固定四行：当前状态、目标差距、下一步计划、风险评估。让每一步推理都有结构，方便回放和排错。

    失败处理指令

    写清失败后的顺序：分析原因 → 改参数重试（最多 2 次）→ 换替代工具 → 仍失败则向用户报告。不要让模型自己即兴决定。

    输出前自检

    在 Final Answer 前检查三件事：是否完整回答、数据是否来自工具真实返回、是否有遗漏的重要信息。

    这些技巧不是越多越好。原文的提醒是：明确“做什么”和“边界在哪”，在“怎么做”上留出适当自由度；对强模型堆微观指令，反而可能降低效果。

    多 Agent Prompt

    调度者说分工，
    执行者说边界。

    多 Agent 系统里，每个角色只需要知道自己那一份职责。Supervisor 负责分解和分配，Worker 负责确认范围、执行、返回结构化结果。

    Supervisor 
    你是任务调度 Agent。你的职责是将用户任务
分配给合适的专家 Agent。

可用的专家 Agent：
- researcher: 擅长信息搜索和数据收集
- analyst: 擅长数据分析和可视化
- writer: 擅长报告撰写和内容创作

你的工作流程：
1. 分析用户任务
2. 将任务分解为子任务
3. 将每个子任务分配给最合适的专家
4. 收集结果并汇总

使用 delegate(agent_name, task) 工具来分配任务。
    Worker 
    你是 {role_name}，接受调度 Agent 的任务指派。
你只负责 {specialization}，其他类型的任务请回复
"超出能力范围"。

收到任务后：
1. 确认任务在你的能力范围内
2. 执行任务
3. 返回结构化结果

    Worker 的“超出能力范围”不是客套话，它是防止任务在 Agent 之间被悄悄吞掉的护栏。没有这句，Worker 可能硬做不擅长的事，最后没人发现。

    常见误区 / 面试追问

    两个误区，
    两个追问。

    两条误区都在“写得更细就更好”；两条追问分别问工具滥用和跨模型可移植性。

    误区 1

    “Agentic Prompt 越详细越好。”

    过度详细的指令可能限制 Agent 的灵活性。好的 Agentic Prompt 应该明确“做什么”和“边界在哪”，但在“怎么做”上给予适当自由度。尤其对强模型，过多的微观指令反而可能降低效果。

    误区 2

    “标准 Prompt 技巧直接适用于 Agent。”

    Agent Prompt 有独特挑战：多轮交互、工具调用结果的不确定性、长上下文中的指令遗忘。标准 Prompt 优化单次生成，Agent Prompt 优化整个决策链。

    追问 1

    如何减少 Agent 的“工具滥用”？

    在 Prompt 中明确工具使用条件：“只在需要外部信息时使用搜索工具，能通过推理得到的答案不要搜索。”同时用 negative example 展示不该使用工具的场景。

    追问 2

    Agentic Prompt 在不同模型间可移植吗？

    不太可移植。不同模型对推理格式、工具调用方式的偏好仍有差异。但原文指出，2025–2026 已大幅收敛：GPT-4/5 系列和 Claude 4.x 都原生支持 tool use / structured outputs，输入格式不再强依赖 JSON 或 XML 包裹。早期“Claude 偏好 XML、GPT 偏好 JSON”是 Claude 2/3 时代的经验法则，到 Claude 4.x native tool use 之后已经不重要。最佳实践仍是针对每个目标模型跑评测验证，不要把“XML for Claude / JSON for GPT”当成定律。

基础 · Prompt Engineering · 可交互讲解

给不给例子，
看任务。

Zero-shot 不给示例，直接描述任务；Few-shot 提供 2–5 个输入输出示例，让模型模仿格式和判断标准。任务常见、模型强、输出稳定时，优先 Zero-shot；要固定格式、教领域标签或模型表现不稳时，用 Few-shot。

关键边界：Few-shot 不是默认更好。示例质量比数量重要，坏示例会把模型带偏；推理任务上，CoT 带来的提升通常大于多加几个示例。

Zero-shot 里，模型要自己理解“分类”指什么、标签是什么、输出要不要解释。Few-shot 通过示例把这些隐含约定显式化，模型只需要延续模式。

原文的判断是：Few-shot 在分类和格式化任务上优势显著；到了复杂推理任务，CoT 等推理增强技术会把这点优势压下去。随着模型变强，Zero-shot 能覆盖的任务边界也在扩大。

代价是 token：每个示例都占输入预算，也会挤占模型用于推理的空间。示例越长、越多，这个代价越明显。

何时选哪种

简单任务省 token，
特定任务给例子。

原文把选择条件列成两张清单。它们不是互斥的硬规则，而是先判断任务和模型，再看输出是否稳定。

选 Zero-shot 的信号

  • 任务在预训练中常见（翻译、摘要、问答）
  • 使用足够强的模型（原文举例 GPT-4、Claude Opus）
  • 任务描述本身足够清晰明确
  • 需要灵活处理多样化输入
  • Token 预算有限
  • 快速原型验证阶段

选 Few-shot 的信号

  • 任务有特定输出格式（JSON、表格、特殊结构）
  • 分类标签有领域特定含义，不是通用正负情感
  • 模型在 Zero-shot 下表现不稳定
  • 需要教模型一个它不熟悉的模式
  • 使用较小的模型（Few-shot 对小模型帮助更大）
  • 输出一致性非常重要（生产环境）

Zero-shot 也能增强

不提供示例，不等于只写一句话。原文给出的四种增强方式：角色设定（“你是资深情感分析专家”）、详细指令（写清分类标准）、格式约束（“只输出标签，不要解释”）、CoT 增强（“Let's think step by step”）。

Few-shot 最佳实践

数量、质量、顺序、
格式，四件事。

原文的建议很具体：2–5 个示例最好，复杂任务可到 5–10；示例要多样、有代表性、类别平衡，格式必须一致。

维度建议原因
示例数量2–5 个最佳，复杂任务 5–10 个太少不够学模式，太多浪费 token 还可能引入噪声
示例质量多样、覆盖边界；典型而非极端；各标签数量大致相等只给简单案例会让模型学不到边界，标签失衡会引入输出偏差
示例顺序把与待预测输入最相似的示例放在最后Recency Effect：模型对最近的示例记忆最深
格式一致所有示例的标点、空格、字段顺序完全一致模型会精确模仿示例格式，包括你不想要的细节

顺序的代价

“最相似的放最后”依赖你能判断相似度。手工挑选时这很主观；生产里通常交给动态 Few-shot：先检索，再按相关度排序。

动态 Few-shot

每次检索，
换一组示例。

固定示例库对所有输入使用同一组例子；动态 Few-shot 先按输入检索最相关的 k 条，再拼进 Prompt。

class DynamicFewShot:
    """根据输入动态选择最相关的示例"""

    def __init__(self, example_bank, embedding_model):
        self.examples = example_bank      # 预存的示例库
        self.embedder = embedding_model

    def build_prompt(self, user_input, k=3):
        # 1. 从示例库中检索最相关的 k 个示例
        input_embedding = self.embedder.encode(user_input)
        similar_examples = self.examples.search(input_embedding, top_k=k)

        # 2. 构建 Few-shot Prompt
        prompt = "根据以下示例完成任务：\n\n"
        for example in similar_examples:
            prompt += f"输入：{example.input}\n"
            prompt += f"输出：{example.output}\n\n"
        prompt += f"输入：{user_input}\n输出："
        return prompt
  • 示例与当前输入高度相关，准确率通常更高。
  • 示例库可以持续扩充，覆盖更多场景。
  • 不需要手工挑选示例，选择过程自动化。

代价是多了一次检索调用和一套示例库维护流程；示例库本身的质量问题也会被放大。

常见误区 / 面试追问

两个误区，
两个追问。

两条误区都在“多给示例总没错”；两条追问问示例怎么挑，以及 One-shot 有没有用。

误区 1

“Few-shot 总是比 Zero-shot 好。”

不一定。推理任务上，CoT 的提升远大于示例的提升；不好的示例可能误导模型，示例质量比数量更重要；强模型的 Zero-shot 已经接近人类水平。

误区 2

“示例越多越好。”

超过 5–10 个示例后，边际收益递减且成本急增。更多示例等于更多输入 token、更高成本，也只剩更少空间给模型思考。

追问 1

如何选择 Few-shot 的示例？

三个原则：多样性，覆盖不同类型的输入；代表性，选典型案例而非极端案例；相关性，最好与待处理输入相关。动态 Few-shot（检索最相关的示例）是原文推荐的生产实践。

追问 2

One-shot（只给一个示例）有用吗？

有用，尤其在教模型特定输出格式时。一个精心选择的示例可能比三个普通示例更有效。但对分类任务，一个示例可能引入偏差：模型会倾向输出示例中的标签。

基础 · Prompt Engineering · 可交互讲解

先写清身份，
再写清边界。

System Prompt 是模型看到用户输入之前的指令框架：定义它是谁、能做什么、不能做什么、输出长什么样。原则不复杂，难的是每条都写具体。

关键实践：具体明确、指令前置（重要约束放开头，结尾再强调）、正向指令优于否定指令、用分层标记分隔段落；Agent 场景再补工具清单、使用规则和推理格式。原文建议核心指令控制在 500–1500 词，避免“指令淹没”。

    一 · 结构模板
    六个段落，
    一件事一段。
    
      
    原文给出的模板包含身份与能力、行为规范、限制与禁止、输出格式、示例。先有骨架，再往每段里填具体内容。
    
    
    
    
    
      
    
        
    身份与能力你是谁、擅长什么、知识截止日期。
    
        
    行为规范语言、风格、格式、不确定时怎么办。
    
        
    限制与禁止越界行为是什么，越界时怎么回应。
    
        
    输出格式JSON / Markdown / 纯文本，结构是什么。
    
        
    示例输入输出各一条，消除歧义。
    
        
    优先级用户指令与系统规则冲突时听谁的。
    
      
    
      
    原文结构模板
    
      
    # 你是 [角色名]

## 身份与能力
- 你是一个 [角色描述]
- 你擅长 [核心能力列表]
- 你的知识截止日期是 [日期]

## 行为规范
- 始终使用 [语言/风格]
- 回答时遵循 [格式要求]
- 遇到不确定的信息时 [如何处理]

## 限制与禁止
- 不要 [具体禁止行为]
- 如果用户要求你做 [越界行为]，则 [如何回应]

## 输出格式
- 使用 [JSON/Markdown/纯文本]
- 结构：[具体结构描述]

## 示例
输入：[示例输入]
输出：[示例输出]
    
      
    模板本身不保证效果。真正起作用的是每一段里的具体程度，以及关键约束放在哪里。
    
    
    
  
    

  
    
    
    
      
    二 · 五条原则
    具体、前置、
    正向、分层。
    
      
    原文的五条原则分别解决歧义、遗忘、违抗、混乱和 Agent 特有问题。每条都配了对照写法。
    
    
    
    
    
      
    原则 1：具体明确，消除歧义
    
      
    “你是一个有帮助的助手，请提供好的回答”没有告诉模型任何可执行的信息。具体写法要说明角色、技术栈、回答长度、语言和术语习惯。
    
      
    原文对照：模糊与具体
    
      
    # 模糊
bad_prompt = "你是一个有帮助的助手。请提供好的回答。"

# 具体
good_prompt = """
你是一个 Python 技术顾问，专注于后端开发和 API 设计。

回答规范：
1. 所有代码示例使用 Python 3.12+ 语法
2. 优先推荐标准库方案，其次是主流第三方库
3. 每个代码示例包含类型注解
4. 回答长度控制在 300 字以内，除非用户要求详细解释
5. 使用中文回答，技术术语保留英文
"""
    

      
    原则 2：指令前置（Primacy Effect）
    
      
    模型对 Prompt 开头和结尾的关注度最高，中间最容易被忽略。这和 Liu et al. 的 “Lost in the Middle” 是同一个现象的两面：开头注意力强是 Primacy，结尾注意力强是 Recency，中间最易被忽略。
    
      
    工程做法叫“夹心饼干”：最重要的约束放最前面，结尾再重复一次；中间留给参考资料和示例，而不是硬指令。
    
      
    原文示例：开头和结尾重复关键约束
    
      
    system_prompt = """
【最重要】你必须始终使用 JSON 格式输出。任何情况下都不要输出纯文本。

你是一个数据提取 Agent，负责从用户提供的文本中提取结构化信息。

输出格式：
{
    "entities": [...],
    "relations": [...],
    "confidence": 0.0-1.0
}

【再次强调】输出必须是合法的 JSON，不要添加任何 JSON 之外的文本。
"""
    

      
    原则 3：正向指令优于否定指令
    
      
    只列“不要做什么”，模型仍然不知道该做什么，而且更容易违反。把禁止项改写成可执行的正向动作，行为更稳定。
    
      
    原文对照：否定与正向
    
      
    # 否定指令
negative_instructions = """
不要编造信息。
不要讨论政治话题。
不要使用脏话。
不要给出医疗建议。
"""

# 正向指令
positive_instructions = """
只基于已知事实回答，不确定时明确说明。
聚焦于技术讨论，将非技术话题引导回技术领域。
使用专业、礼貌的语言。
涉及健康问题时建议用户咨询专业医生。
"""
    

      
    原则 4：分层结构与标记分隔
    
      
    用 Markdown 标题、XML 标签或分隔符把角色、能力、规则、语气、输出格式分开。模型更容易定位，人也更容易维护和修改。
    
      
    原文示例：XML 标签分层
    
      
    structured_prompt = """
<role>
你是客服助手 Luna，服务于电商平台 ShopX。
</role>

<capabilities>
- 查询订单状态
- 处理退款请求
- 回答产品问题
- 转接人工客服
</capabilities>

<rules>
1. 退款金额超过 500 元需要转接人工
2. 不能直接修改用户的收货地址
3. 对于投诉，先表达理解，再提供解决方案
</rules>

<tone>
友好、专业、简洁。使用"您"而非"你"。
</tone>

<output_format>
- 先回答用户问题
- 如果需要操作，说明将执行的动作
- 每次回复结尾问一句"还有什么可以帮您的吗？"
</output_format>
"""
    

      
    原则 5：Agent 专用设计
    
      
    Agent 的 System Prompt 除了身份和规则，还要写清工具清单、工具使用规则、推理格式、步数上限和危险操作确认。原文示例：
    
      
    原文 Agent System Prompt 节选
    
      
    ## 可用工具
- search(query): 搜索网页
- calculate(expression): 计算数学表达式
- write_file(path, content): 写入文件

## 工具使用规则
1. 先思考是否需要使用工具
2. 每次只调用一个工具
3. 等待工具结果后再决定下一步
4. 如果工具调用失败，尝试替代方案

## 推理格式
Thought: 分析当前状况和下一步计划
Action: 选择工具和参数
Observation: 观察工具返回的结果
Answer: 给出最终答案

## 限制
- 最多执行 10 步
- 不确定时优先问用户而非猜测
- 涉及文件删除等危险操作时必须确认
    
      
    这几段直接决定 Agent 能不能稳定跑完多步任务。步数上限和危险操作确认不是“建议”，是护栏。
    
    
    
  
    
  
    
    
    
      
    三 · 反模式与测试
    写完之后，
    先找出这四类问题。
    
      
    原文列出四种常见反模式，并给了一份六项测试清单。前者决定提示词能不能用，后者决定改完有没有变坏。
    
    
    
    
    
      
    四种反模式
    
      
    
        
    
          过度约束、矛盾指令、身份不清和缺少示例四种反模式
          
    反模式问题原文示例改进
    
          
            
    过度约束规则太多太细，模型容易违反或产生矛盾。50+ 条规则的 System Prompt。保留核心规则（10 条以内），用示例代替细则。
    
            
    矛盾指令不同规则之间相互矛盾。“保持简洁”加“提供详细解释”。明确优先级：“默认简洁，用户要求时提供详细解释”。
    
            
    身份不清角色定义模糊，模型不知道自己是谁。“你是一个通用助手”。“你是 ShopX 的客服专员 Luna，专注于订单和退款问题”。
    
            
    缺少示例纯文字描述容易被误解。只写规则，不给输入输出样例。提供 2–3 个输入输出示例。
    
              
        
    
      
    
      
    “10 条以内”“2–3 个示例”都是原文建议，不是硬性阈值。规则数量要按任务复杂度调整，判断标准是“每条规则是否真的改变行为”。
    

      
    六项测试清单
    
      
    
        
    
          System Prompt 的六项测试
          
    测试要确认什么
    
          
            
    基本功能模型是否按预期角色回答。
    
            
    边界测试用户尝试越界时模型是否拒绝。
    
            
    格式一致性100 次调用的输出格式是否一致。
    
            
    语言一致性是否始终使用指定语言。
    
            
    安全测试面对 Prompt Injection 是否保持行为。
    
            
    长对话稳定性10+ 轮对话后是否仍遵守指令。
    
              
        
    
      
    
      
    这六项适合做成回归测试集：每次改提示词，都跑同一批输入，比较行为有没有退化。提示词应当像代码一样管理：版本控制、A/B 测试、回归测试、审计日志。
    
    
    
  
    

  
    
    
    
      
    常见误区 / 面试追问
    两个误区，
    两个追问。
    
      
    前两条是误区，后两条是面试追问；答案都来自原文。
    
    
    
    
    
      
    误区 1
    
      
    “System Prompt 越长越好。”
    过长的 Prompt 会产生“指令淹没”：关键指令被大量次要信息稀释。研究指出 LLM 对长 Prompt 中间部分关注度最低（Lost in the Middle）。最佳实践是核心指令保持简洁，原文建议 500–1500 词，用分层结构组织。
    
    
    
    
    
      
    误区 2
    
      
    “System Prompt 是安全的，用户看不到。”
    System Prompt 可以通过 Prompt Injection 被泄露。不要在 System Prompt 里放真正的密钥或敏感信息。安全逻辑应在应用层实现，不能完全依赖 System Prompt。
    
    
    
    
    
      
    追问 1
    
      
    “如何处理 System Prompt 和用户指令的冲突？”
    在 System Prompt 中明确优先级：“当用户指令与系统规则冲突时，始终遵守系统规则。”但要清楚，这不是 100% 可靠，强力 Prompt Injection 仍可能绕过。需要配合应用层的输入输出过滤。
    
    
    
    
    
      
    追问 2
    
      
    “System Prompt 的版本如何管理？”
    像代码一样管理：版本控制（Git）、A/B 测试（比较不同版本效果）、回归测试（每次修改后跑测试集）、审计日志（记录每次变更和原因）。

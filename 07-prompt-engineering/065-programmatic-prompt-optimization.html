高级 · Prompt Engineering · 可交互讲解

不调词，
调算法。

自动化 Prompt 优化把“手写字符串、人工试错”升级成“声明任务 + 指标评估 + 算法搜索”。DSPy 优化结构化组件（Signature + 示例），APE / OPRO / PromptBreeder 直接生成和变异 Prompt 字符串。

关键边界：优化器只对指标负责。指标不全或验证集太小，它会优化出一个更会刷分、而不是更有用的 Prompt。

为什么需要

手调 Prompt，
像在无限空间里摸黑。

自然语言组合近乎无限，微小措辞变化可能带来大幅性能差异；换模型还要重调。自动优化把“艺术”变成可复现的搜索过程。

  • 搜索空间巨大：自然语言的组合可能性近乎无限。
  • 评估困难：微小的措辞变化可能导致大幅性能差异。
  • 不可迁移：换模型后 Prompt 需要重新调优。
  • 依赖经验：不同人的 Prompt 质量差异巨大。
  • 难以组合：多步骤管道中每个 Prompt 互相影响。
prompt_v1 = "回答以下问题：{question}"                      # 效果差
prompt_v2 = "你是专家。详细回答：{question}"                 # 好一点
prompt_v3 = "你是资深专家。\n请分步骤回答：\n{question}\n先分析再总结"  # 更好
# ……手动迭代数十个版本：脆弱、不可复现、难以系统优化

自动化优化的解法是：让算法探索 Prompt 空间，用指标评估，再迭代更新。它不替代任务定义和指标设计，只替代“反复改措辞”这一步。

流派一 · DSPy

写模块，
让优化器找 Prompt。

DSPy 的核心是“编程而非提示”：用 Signature 声明输入输出语义，用 Module 组合 LLM 调用，由优化器自动生成指令和 Few-shot 示例。

import dspy

# 1. Signature：声明输入输出的语义
class QA(dspy.Signature):
    """回答关于 AI Agent 的技术问题"""
    question: str = dspy.InputField(desc="技术面试问题")
    answer: str = dspy.OutputField(desc="详细的技术回答，包含示例")

# 2. Module：LLM 调用的基本单元
class SimpleQA(dspy.Module):
    def __init__(self):
        self.generate = dspy.ChainOfThought(QA)   # 自动加 CoT

    def forward(self, question):
        return self.generate(question=question)

# 3. 配置与编译
dspy.configure(lm=dspy.LM("openai/gpt-4o-mini"))
optimized_qa = optimizer.compile(SimpleQA(), trainset=trainset)
# optimized_qa 已包含优化后的 Prompt 和 Few-shot 示例

原文的模型名只作为示例，本页未联网核验当前可用的模型标识。DSPy 优化的是 Module 的指令和示例组合，不是手写字符串。

整条管道一起编译

优化对象不限于单个 Prompt。下面的 RAG 管道把检索和生成都声明成 Module，优化器会一起调整它们的配合。

class RAGPipeline(dspy.Module):
    def __init__(self, num_passages=3):
        self.retrieve = dspy.Retrieve(k=num_passages)
        self.generate = dspy.ChainOfThought("context, question -> answer")

    def forward(self, question):
        context = self.retrieve(question).passages
        return self.generate(context=context, question=question)

optimized_rag = optimizer.compile(RAGPipeline(), trainset=trainset)

四个优化器

优化器原理适用 / 成本
BootstrapFewShot跑 trainset，用 metric 筛出成功的调用轨迹，把 (input, reasoning, output) 作为 Few-shot 示例小数据集、快速优化；成本低（少量调用）
MIPROv2让 LLM 生成多个 instruction，再用贝叶斯优化在 instruction × few-shot 联合空间搜索高质量生产场景；成本中等
SIMBAmini-batch 评估 → LLM 反思失败案例 → 生成改进版 instruction，迭代到收敛（原文标注 2025 新增）对指标敏感、需要反思的复杂任务；成本中到高
BootstrapFinetune用大模型生成高质量 trace，再用 trace 微调小模型降低推理成本；成本高（需要微调）

SIMBA 的“2025 新增”按原文标注，未联网核实。四个优化器的共同前提是有可靠的评估指标；没有 metric，优化器无法判断哪次调用成功。

流派二 · 元提示

让 LLM 直接
改写 Prompt。

元提示把“写 Prompt”本身当成任务：LLM 生成候选、看历史得分、做变异和交叉。代表是 APE、OPRO、PromptBreeder。

APEAutomatic Prompt Engineer

让 LLM 一次生成 k 个不同风格的候选，在验证集上逐个评分，选最高分。流程简单，成本可控。

OPROOptimization by PROmpting

把历史 Prompt 和得分放进上下文，让 LLM 分析“哪种策略得分高”，再生成新 Prompt。原文示例最多 20 轮。

PromptBreeder进化算法

初始化种群，按适应度选择父代，用 LLM 做变异和交叉，精英保留到下一代。调用次数可达上千次。

展开 APE 的候选生成与评估代码 
async def optimize(self, task_description, eval_examples, k=10):
    candidates = await self.generate_candidates(task_description, k)

    scored = []
    for prompt in candidates:
        score = await self.evaluate(prompt, eval_examples)
        scored.append({"prompt": prompt, "score": score})

    return max(scored, key=lambda x: x["score"])

async def generate_candidates(self, task_description, k):
    meta_prompt = f"""
    我需要一个 Prompt 来完成以下任务：{task_description}
    请生成 {k} 个不同风格和策略的 Prompt 变体：
    有的用角色设定，有的用 CoT，有的用正面指令，
    有的用约束条件，有的用示例引导。用 === 分隔。
    """
    response = await self.llm.invoke(meta_prompt)
    return response.split("===")

for gen in range(generations):
    for individual in population:
        individual["fitness"] = await self.evaluate(individual["prompt"])
    parents = self.tournament_select(population, k=population_size // 2)
    offspring = [{"prompt": await self.mutate(p["prompt"], task)} for p in parents]
    for i in range(0, len(parents) - 1, 2):
        offspring.append({"prompt": await self.crossover(parents[i]["prompt"], parents[i+1]["prompt"])})
    population = self.elite_preserve(population, offspring)

原文给了 OPRO 上百次、PromptBreeder 上千次 LLM 调用的量级。这意味着元提示不是“更便宜的调优”，而是把人工时间换成推理成本和评估数据。

组合工作流

先粗筛，再精调，
最后人工审核。

原文的生产组合流程把两派串起来：APE 做粗粒度探索，MIPROv2 做结构化精调，人工审核安全，再 A/B 放量。

  1. 阶段 1：用元提示（APE）生成 20 个候选。
  2. 阶段 2：在小验证集上快速筛到 top-5。
  3. 阶段 3：把 top-5 作为初始 instruction 交给 DSPy MIPROv2 继续搜索。
  4. 阶段 4：人工审核自动生成的 Prompt 是否有安全隐患或不当内容。
  5. 阶段 5：审核通过后做 A/B 测试，先放 10% 流量。

为什么必须人工审核

原文明确提醒：自动生成的 Prompt 可能过于“hacky”，甚至绕过安全护栏来提升指标。指标只衡量它被要求衡量的东西，不衡量你没写进指标的底线。

局限

六个坑，
都绕不开评估。

自动优化的上限由评估决定。指标差、验证集小、任务变化快，算法只会更快地把你带到错误方向。

评估依赖

优化质量取决于指标质量。差的指标会让 Prompt 过拟合到指标，而非真实效果。

过拟合风险

可能过拟合验证集，在新数据上效果差。页面演示的留出集回退就是这个风险。

可解释性

自动生成的 Prompt 可能难以理解为什么有效，排查问题时缺少抓手。

安全性

优化可能绕过安全护栏以提升指标，必须人工审核。

成本

OPRO 可达上百次调用，PromptBreeder 可达上千次；优化本身是一笔推理开销。

收敛性

不保证找到全局最优；停止条件和预算要提前定。

常见误区 / 面试追问

三个误区，
五个追问。

误区集中在“有了框架就不用人”；追问覆盖 OPRO 与 DSPy 的区别、BootstrapFewShot 到底做了什么，以及什么时候不该用。

误区 1

“DSPy 完全不需要 Prompt Engineering 知识。”

DSPy 自动化了 Prompt 措辞的优化，但你仍需要设计 Signature（输入输出语义）、选择合适的 Module（是否需要 CoT、是否需要检索），以及定义评估指标。框架自动化的是“调词”，不是“设计”。

误区 2

“自动生成的 Prompt 一定比人写的好。”

取决于评估指标的质量和验证集的代表性。如果指标不够全面（比如只看准确率不看安全性），优化可能走偏。

误区 3

“Meta-Prompting / DSPy 可以完全替代人工 Prompt Engineering。”

自动化了“措辞调优”，但任务定义、评估指标设计、安全审核仍需人工。最佳实践是自动生成候选 + 人工审核和调整。

追问 1

OPRO 和 DSPy 的区别是什么？

OPRO 直接用 LLM 优化 Prompt 文本（字符串级别）；DSPy 用优化器优化 Prompt 的结构化组件（签名 + 示例）。DSPy 更模块化和可组合，OPRO 更简单直接但难复用到其他任务。

追问 2

BootstrapFewShot 究竟在做什么？

它不是让 LLM“脑补”新的训练样例，而是让目标 Module 跑一遍 trainset，挑出 metric 通过的成功调用轨迹（包括中间推理），把这些真实成功的 trace 作为 Few-shot 示例插入 Prompt。本质是“用模型自己的成功经验来调教自己”。

追问 3

DSPy 优化后的 Prompt 可以导出吗？

可以。用 optimized_module.save(path) 保存，用 module.load(path) 加载；也可以 inspect 看到优化后的实际 Prompt 文本。生产中可以把优化后的 Prompt 提取出来直接使用，不依赖 DSPy 运行时。

追问 4

什么时候不该用 DSPy？

三种情况：简单的一次性任务，手写 Prompt 更快；没有评估数据，优化器无法判断好坏；任务频繁变化，每次变化都要重新编译。DSPy 最适合需要长期维护和迭代优化的生产管道。

追问 5

Meta-Prompting 在生产中实用吗？

适合需要长期维护的高频场景（客服、内容审核、数据提取）。一次性或低频任务，人工调优的 ROI 更高。关键是评估数据集的质量——没有好的评估集就无法做自动优化。

中级 · Prompt Engineering · 可交互讲解

Prompt 改动，
也要能回滚。

生产环境里 Prompt 就是代码：每次修改生成不可变的新版本，记录改动原因和指标，能一键切回旧版；上线前用真实流量做 A/B 测试，质量显著提升且成本、延迟、安全护栏全部通过，才逐步放量。

关键边界：统计显著不等于可以上线。质量分涨了，但成本或延迟超出预算，也应该留在旧版本。本页用一个固定教学实验演示这条判断链。

问题起点

改了一个词，
线上变了个样。

Prompt 没有版本管理时，质量下降只能靠回忆；有版本管理时，每次改动都有全文、原因和指标，回滚是一条命令的事。

没有版本管理
  • 开发者 A 改了 System Prompt 直接上线
  • 用户投诉回答质量下降
  • “之前的 Prompt 是什么？”没有人记得
  • 无法回滚，只能临时再改一版赌一次
有版本管理
  • v1.0 → v1.1（改语气）→ v1.2（加安全规则）→ v2.0（重构）
  • 每版保留完整 Prompt 全文，旧版不被覆盖
  • 修改日志、原因、负责人和性能基准都能查
  • 线上出问题，一键切回上一个 active 版本

版本生命周期

每个版本在四个状态之间流转。新版本激活时，旧的 active 版本自动归档；归档版本不删除，保留回滚能力。

draft草稿 → testing测试 / 灰度 → active线上生效 → archived归档保留
  • testing → draft：验证不通过，打回修改。
  • archived → active：一键回滚。回滚本质是把旧版本重新 promote 成 active。
  • active 不直接删除；归档是默认终点，不是销毁。

版本管理架构

不可变、可追溯、
能一键回滚。

三条原则对应三个工程动作：版本只追加不覆盖，元数据随版本走，promote 与 rollback 共用同一条状态切换路径。

一个版本记录包含什么

Prompt 全文、版本号、创建时间、创建人、修改原因、目标模型、状态和后续填充的指标。状态只允许四个值：draft、testing、active、archived。

class PromptVersionManager:
    def create_version(self, prompt_id, content, metadata):
        version = {
            "prompt_id": prompt_id,
            "version": self.get_next_version(prompt_id),   # v1.0 → v1.1
            "content": content,              # Prompt 全文，不可变
            "created_at": datetime.now(),
            "created_by": metadata["author"],
            "change_reason": metadata["reason"],
            "model": metadata["target_model"],
            "status": "draft",               # draft → testing → active → archived
            "metrics": {},                   # 性能数据，后续填充
        }
        self.storage.save(version)
        return version

    def promote(self, prompt_id, version, target_status):
        # 设为 active 前，先把当前 active 版本归档
        if target_status == "active":
            current = self.get_active(prompt_id)
            if current:
                current["status"] = "archived"
                self.storage.save(current)
        prompt = self.storage.get(prompt_id, version)
        prompt["status"] = target_status
        self.storage.save(prompt)

    def rollback(self, prompt_id, target_version):
        # 回滚 = 把归档版本重新激活，旧 active 自动归档
        self.promote(prompt_id, target_version, "active")

注意 promote 里的顺序：先归档当前 active，再激活目标版本。如果反过来，中间会出现两个 active 版本，线上到底读哪个就变成了未定义行为。

Prompt 与代码分离

把 Prompt 硬编码在函数里，改一句话就要走一次代码发布；抽到注册表后，运行时按 ID 和版本读取，改 Prompt 不需要重新部署代码。

# ❌ 硬编码：改 Prompt 就要改代码、重新部署
def generate_response(user_input):
    prompt = f"你是一个友好的助手。请回答：{user_input}"
    return llm.invoke(prompt)

边界

解耦解决的是“改 Prompt 不用发版”，不解决“改完一定更好”。发布流程、评估套件和回滚能力仍然要单独建设，否则只是把改错的门槛降低了。

A/B 测试

同一用户，
永远进同一组。

A/B 测试不是随机调用两次模型做对比，而是把真实流量按稳定规则分给两个版本，再比较同一组指标。

六个步骤

  1. 定义假设：写清改了什么、预期哪个指标变好、护栏是什么。
  2. 选择指标：质量、效率、安全、业务四类，不能只看准确率。
  3. 分流流量：按用户 ID 做确定性哈希，保证同一用户始终进同一组。
  4. 收集数据：记录延迟、token、成本、质量评分和安全结果。
  5. 统计检验：对主要指标做显著性检验，同时检查护栏指标。
  6. 决策上线：显著且护栏全过才放量；否则保留对照版本。

分流必须跨进程稳定

def assign_variant(test_id, user_id, split):
    # 必须用 hashlib，不能用 Python 内置 hash()：
    # hash() 在每个进程启动时随机加盐（PYTHONHASHSEED），
    # 多副本服务会让同一用户在不同副本进入不同组，A/B 数据作废。
    digest = hashlib.md5(f"{test_id}:{user_id}".encode("utf-8")).hexdigest()
    bucket = int(digest, 16) % 100        # 跨进程稳定
    cumulative = 0
    for variant, share in split.items():  # {"control": 0.5, "treatment": 0.5}
        cumulative += share * 100
        if bucket < cumulative:
            return variant
常见事故：用内置 hash() 做分桶。Python 每个进程启动时会随机化字符串哈希，同一个用户在 A 副本可能进 control、在 B 副本进 treatment。用户看到的回答来回跳，两组数据也互相污染。

和传统 A/B 测试的差别

LLM 输出本身有随机性，同一 Prompt 两次回答也可能不同。所以样本量要更大，指标不能只看点击率或准确率，还要看回答质量、安全性、token 成本和延迟。原文建议每组至少 500–1000 次调用，并可用 LLM-as-Judge 加速质量评估。

评估指标

质量、效率、
安全、业务。

四类指标回答四个不同问题：答得好不好、快不快贵不贵、守不守边界、有没有业务价值。单看一类都会做出片面决策。

页面实验只取四个代表指标：质量评分、单次成本、平均延迟、安全通过率。真实实验应该先固定一个主指标，再给其余指标设护栏阈值，避免“什么都想优化，最后无法判断”。

渐进式发布

先 5%，
再谈全量。

Prompt 的行为变化可能很隐蔽，直接全量等于拿全部用户做测试。原文给出一条逐级放大的路径。

  1. 0. 开发环境跑自动化评估套件，通过后才允许进入线上灰度。
  2. 1. 5%Canary 灰度，监控 24 小时无异常。
  3. 2. 20%扩大流量，继续收集 A/B 数据。
  4. 3. 50%A/B 测试达到统计显著，继续监控 1 周。
  5. 4. 100%全量发布，旧版本归档，保留一键回滚能力。

顺序不能省

灰度 5% 的价值不是“省流量”，而是把错误限制在可回滚的范围内。每一步都要有明确的退出条件：错误率、延迟、成本或安全指标越线就停，而不是等全量后才发现。

常见误区 / 面试追问

两个误区，
两个追问。

两条误区都在“把 Prompt 当小事”；两条追问分别问样本量和模型版本兼容。

误区 1

“Prompt 修改是小事，不需要正式流程。”

Prompt 的微小改动可能导致大幅行为变化。一个词的修改可能让安全护栏失效或回答质量骤降。生产环境中的 Prompt 变更应该像代码变更一样，有 Review、测试和渐进式发布。

误区 2

“A/B 测试只需要看准确率。”

LLM 的 A/B 测试需要多维指标：质量、成本、延迟、安全。一个 Prompt 可能提升了准确率，但增加了 50% 的 token 消耗。只看单一指标会导致片面决策。

追问 1

LLM A/B 测试需要多大样本量？

由于 LLM 输出的高方差性，通常需要比传统 A/B 测试更大的样本量，原文建议至少每组 500–1000 次调用。可以用 LLM-as-Judge 替代人工评估来加速数据收集。

追问 2

如何处理 Prompt 在不同模型版本间的兼容性？

模型提供商的更新可能改变模型行为。原文给出的做法是：每次模型更新后自动运行回归测试；把模型版本锁定在 Prompt 元数据中；维护跨模型的 Prompt 变体。

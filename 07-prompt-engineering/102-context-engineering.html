高级 · Prompt Engineering · 可交互讲解

Prompt 只是入口，
上下文才是工程。

Context Engineering 管的是“用什么信息去问”，而不只是“怎么问”。它把 System Prompt、工具结果、对话历史、外部知识四路来源，按当前任务的 token 预算挑出来、组装好、送进模型。

关键边界：上下文不是越多越好，而是信噪比越高越好。窗口是有限的“房地产”，每加入一段内容都要问：它对当前决策的边际贡献，抵得上它消耗的 token 吗？

范式变化

从“怎么问”，
到“用什么信息问”。

Prompt Engineering 打磨一条指令的措辞；Context Engineering 设计整条上下文管道。原文把后者称为一次维度跃升。

原文的论断是：一个 LLM 调用的效果，70% 取决于喂给它的上下文质量，而非 Prompt 本身的遣词造句。这个比例是原文表述，本页没有复测，只用来强调关注点的转移。

两者的分工可以用原文的类比理解：Prompt Engineering 是写好一封邮件，Context Engineering 是管理整个项目的信息流。邮件写得再漂亮，如果附件拿错、历史记录缺失，结果仍然不对。

四大来源

每一路，
都有不同的脾气。

System Prompt 静态、每次携带；工具结果体积不可控；历史线性增长；外部知识相关性参差。四路要用不同的管理策略。

四类上下文来源的特征与管理策略
来源内容特征管理策略
System Prompt角色定义、工具描述、输出格式、约束规则静态、每次调用都携带精简压缩，避免冗余
Tool Results搜索结果、API 返回、代码执行输出动态生成、体积不可控截断 / 摘要 / 选择性保留
Conversation History用户多轮对话、之前的 Agent 推理过程线性增长、含大量噪声滑动窗口 / 摘要压缩

原文的关键原则

上下文不是越多越好，而是信噪比越高越好。每加入一段上下文都要问：它对当前决策的边际贡献，大于它消耗的 token 成本吗？

动态组装器

来源分组、
按优先级抢预算。

原文的 ContextBuilder 做四件事：按来源分组、组内按优先级降序、按来源预算上限挑选、把选中的块转成 messages。

预算不是一个大池子，而是四个小池子

原文给每类来源设了上限：System 12%、Knowledge 35%、History 35%、Tool Result 18%。先各自限额，再在组内按优先级挑选；装不下的块尝试截断，剩余不足 100 tokens 就放弃。

查看 ContextBuilder 的原文代码（较长） 
class ContextBuilder:
    """动态上下文组装器——Context Engineering 的核心实现"""

    def __init__(self, max_tokens: int = 128_000, reserve_output: float = 0.2):
        self.max_tokens = max_tokens
        # 为模型输出预留空间
        self.available_tokens = int(max_tokens * (1 - reserve_output))
        self.blocks: list[ContextBlock] = []

        # 各来源的 token 预算上限（百分比）
        self.budget = {
            ContextSource.SYSTEM: 0.12,      # System Prompt 最多占 12%
            ContextSource.KNOWLEDGE: 0.35,   # RAG 知识最多占 35%
            ContextSource.HISTORY: 0.35,     # 对话历史最多占 35%
            ContextSource.TOOL_RESULT: 0.18, # 工具结果最多占 18%
        }

    def add(self, source: ContextSource, content: str,
            priority: int = 5, metadata: Optional[dict] = None) -> "ContextBuilder":
        """添加一个上下文块"""
        token_count = self._estimate_tokens(content)
        self.blocks.append(ContextBlock(
            source=source,
            content=content,
            priority=priority,
            token_count=token_count,
            metadata=metadata or {},
        ))
        return self  # 链式调用

    def build(self) -> list[dict]:
        """
        核心方法：根据优先级和预算，组装最终上下文。
        返回 OpenAI 兼容的 messages 格式。
        """
        # 第一步：按来源分组
        grouped: dict[ContextSource, list[ContextBlock]] = {}
        for block in self.blocks:
            grouped.setdefault(block.source, []).append(block)

        # 第二步：每组内按优先级降序排列
        for source in grouped:
            grouped[source].sort(key=lambda b: b.priority, reverse=True)

        # 第三步：按预算分配，优先级高的先占位
        selected: list[ContextBlock] = []
        for source, blocks in grouped.items():
            budget_tokens = int(self.available_tokens * self.budget.get(source, 0.1))
            used = 0
            for block in blocks:
                if used + block.token_count <= budget_tokens:
                    selected.append(block)
                    used += block.token_count
                else:
                    # 尝试截断以填满预算
                    remaining = budget_tokens - used
                    if remaining > 100:  # 至少保留 100 token 才值得截断
                        truncated = self._truncate(block.content, remaining)
                        selected.append(ContextBlock(
                            source=block.source,
                            content=truncated,
                            priority=block.priority,
                            token_count=remaining,
                        ))
                    break

        # 第四步：组装为 messages 格式
        return self._to_messages(selected)

读代码时注意

原文示例的 _to_messages 只回填了 System、Knowledge、History 三类，TOOL_RESULT 参与了预算分配却没有写进 messages。这是示例代码的缺口，生产实现需要把工具结果按协议补回去，否则预算白花了。

行业共识

窗口是工作台，
不是档案柜。

原文把 2026 年的 Context Engineering 描述为独立工程学科，并引用 Anthropic 官方指南：为上下文窗口填入“恰好够用”的信息。

① 写入 Write检索 RAG、工具结果、系统提示进入窗口。
② 管理 Manage压缩 / 摘要、裁剪 / 截断、滑动窗口。
③ 持久化 Persist文件式记忆、写笔记到窗口外、下次会话读回。

三个关键认知升级：第一，上下文窗口不等于记忆，窗口是用完即清的工作台，长期信息要外化到文件、数据库或知识图谱；第二，Agentic Memory 让 Agent 定期把经验写成笔记，下次会话读回；第三，信息衰减是常态，早期工具结果会从“有用”变成“噪声”，要主动清理，而不是等窗口溢出。

这和 041 上下文窗口管理 的压缩策略、043 持久化记忆 的外化存储是同一套思路的不同侧面。本页的装配台只覆盖“窗口内选择与压缩”，不重复 041 的策略对比。

Prompt Caching

稳定前缀，
才配谈成本。

多轮 Agent 反复携带相同的 System Prompt、工具定义和知识前缀。Prompt Caching 缓存这些稳定前缀，命中时以更低价格读取。

机制：前缀逐字节匹配

Anthropic 的渲染顺序是 tools → system → messages，越靠前越稳定。缓存命中要求从开头到断点的每一个字节完全一致；任何一个字节改变，该断点之后的缓存全部失效。

触发方式手动 cache_control 断点 / 顶层自动缓存全自动，无需标记
最小缓存前缀1024–4096 tokens，因模型而异1024 tokens
命中读取折扣约 90% off，读取价约 0.1×约 50% off，读取价约 0.5×

成本示例：30K 前缀，命中后约 0.19×

原文的例子是 20K System Prompt + 10K 知识库前缀，共 30K 输入，其中约 28K 命中缓存。输入成本约为 (28000×0.1 + 2000×1) / 30000 ≈ 0.19×。5 分钟 TTL 下两次请求回本；1 小时 TTL 下至少三次请求回本。

差异标注：按公式实算 0.16，源文写 0.19；本页保留原文 0.19，不改写源文数字。

原文还提到，Agentic 场景同一会话内常有 10+ 轮调用，每轮都携带相同 System Prompt 和累积历史，缓存命中率通常可达 80%+；没有 Prompt Caching，多轮 Agent 的 token 成本会高到难以承受。

原文示例算术与命中率，不是本页实测；价格随厂商调整

静默失效：不报错，只涨账单

缓存失效不会抛异常，cache_read_input_tokens 会静默归零。原文列出五类常见根因：System Prompt 插入时间戳、json.dumps 未排序、工具列表动态增减、插入 uuid / 请求 ID、中途切换模型。

工程实践

把动态内容（时间、用户 ID、会话状态）放到 messages 末尾，绝不插进 System Prompt；工具列表按 name 确定性排序；构建 Prompt 后用 count_tokens 比对前后两次请求，排查静默失效。

原文还给了一个进阶陷阱：单个断点最多回溯 20 个 content block 找前一次缓存。长 Agent 轮次若超过 20 个 block，下一个断点会静默 miss，需要每约 15 个 block 补一个中间断点。

常见误区 / 面试追问

两个误区，
两个追问。

最容易混的是“Context Engineering 等于写更好的 Prompt”；最容易错的是“窗口够大就不用管上下文”。

误区 01

“Context Engineering 就是写更好的 Prompt”

Prompt Engineering 是 Context Engineering 的子集。后者还管 Prompt 之外的信息：工具返回值怎么裁、对话历史怎么压、外部知识怎么检索与排序。原文的类比是：Prompt Engineering 写好一封邮件，Context Engineering 管理整个项目的信息流。

误区 02

“上下文越多越好，反正模型支持 128K”

LLM 存在 Lost in the Middle 现象：上下文过长时，模型对中间位置信息的注意力显著下降；无关上下文还会稀释关键信息。正确目标是高信噪比，不是高信息量。每段上下文都应对当前任务有明确的边际贡献。

追问 03

如何衡量上下文质量？

三个维度：相关性，上下文中每段信息与当前任务的相关度，可用 embedding 相似度量化；充分性，是否包含完成任务所需的全部关键信息，通过 ablation test 验证；效率，有效 token 占总 token 的比例。实践中常用 A/B 测试比较不同上下文策略对最终输出质量的影响。

追问 04

Context Engineering 在 Multi-Agent 中如何应用？

三重角色：上下文隔离，每个 Agent 只接收与职责相关的上下文；上下文传递，设计 Agent 之间的信息传递协议，决定传摘要还是原始数据；共享上下文管理，维护全局状态（如 Blackboard 模式），让多个 Agent 读写共享的结构化上下文，而不是互相透传完整历史。

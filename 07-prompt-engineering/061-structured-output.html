基础 · Prompt Engineering · 可交互讲解

让模型说
机器能读的话。

结构化输出让 LLM 返回 JSON、XML 等机器可解析格式，是 Agent 系统和数据管道的基础能力。四种主流方法从“只在 Prompt 里要求格式”到“解码层强制约束”，保证强度依次提高。

关键边界：格式合法不等于 Schema 合规。JSON Mode 只保证语法；要保证字段、类型和必填项，需要 Schema 约束、Function Calling 或 Structured Outputs。

查看本页执行的五类规则
  • 根节点必须是 JSON 对象。

    四种方法

    从“请输出 JSON”
    到解码层强制。

    方法越往下，格式保证越强，接入成本也越高。生产环境常用 Function Calling 或 Structured Outputs 处理格式，再用 Pydantic 验证语义。

    方法 1：Prompt 指令（最简单）

    在 Prompt 里描述期望格式，并加一句“只输出 JSON”。它最简单，但不保证合规：模型可能添加 markdown 标记、解释文字，或生成语法错误的 JSON。

    Prompt 指令 · 原文代码

    prompt = """
从以下文本中提取实体信息，以 JSON 格式输出。

文本：张三是 ABC 公司的技术总监，他在北京工作了 5 年。

输出格式：
{
    "name": "人名",
    "company": "公司名",
    "title": "职位",
    "location": "工作地点",
    "years": 数字
}

请只输出 JSON，不要添加任何其他文本。
"""

# 问题：
# - LLM 可能添加 "```json" 标记或解释文字
# - 可能输出不合法的 JSON（缺少引号、多余逗号）
# - 需要后处理和错误处理

    方法 2：JSON Mode（API 级别）

    API 级别强制输出合法 JSON。它保证语法正确，但不保证 Schema 匹配：可能返回 {"person": "张三"} 而不是 {"name": "张三"}。

    OpenAI JSON Mode · 原文代码

    from openai import OpenAI
client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o",
    response_format={"type": "json_object"},  # 强制 JSON 输出
    messages=[
        {"role": "system", "content": "你是一个数据提取助手。始终以 JSON 格式回答。"},
        {"role": "user", "content": "提取：张三是 ABC 公司的技术总监"}
    ]
)

# 保证输出是合法的 JSON
data = json.loads(response.choices[0].message.content)

# 注意：JSON Mode 保证语法合法，但不保证 Schema 匹配
# 可能返回 {"person": "张三"} 而不是 {"name": "张三"}

    方法 3：Function Calling / Structured Outputs

    用 Pydantic 定义 Schema，让模型按函数参数或响应格式填写。Function Calling 最适合 Agent 工具调用；Structured Outputs 直接把结果解析成 Pydantic 实例。

    Pydantic Schema 与 OpenAI Structured Outputs · 原文代码

    from pydantic import BaseModel

# 用 Pydantic 定义 Schema（推荐方式）
class PersonInfo(BaseModel):
    name: str
    company: str
    title: str
    location: str
    years: int

# OpenAI Structured Outputs（openai-python>=1.92，parse 已 GA）
response = client.chat.completions.parse(
    model="gpt-4o",
    response_format=PersonInfo,  # 直接传 Pydantic 模型
    messages=[
        {"role": "user", "content": "提取：张三是 ABC 公司的技术总监，在北京工作了5年"}
    ]
)

person = response.choices[0].message.parsed
# person.name == "张三"
# person.company == "ABC"
# person.years == 5
# 类型安全，100% Schema 合规

# 注：2024-08 由 client.beta.chat.completions.parse 提升为 GA（openai-python 1.92+）
#     旧路径 client.beta.* 仍可用，但新代码推荐 client.chat.completions.parse

# OpenAI Responses API（新项目首选，2025-03 发布）
# 把 Chat Completions + Assistants 合并为一个新 endpoint
response = client.responses.parse(
    model="gpt-4o",
    text_format=PersonInfo,
    input=[{"role": "user", "content": "提取：张三是 ABC 公司的技术总监"}]
)
person = response.output_parsed

    Anthropic 原生 Structured Outputs 与兜底 Tool Use · 原文代码

    # Anthropic 原生 Structured Outputs（公开 Beta，2025-11-14 发布）
# 需要 anthropic-beta header，底层是 constrained decoding，100% Schema 合规
response = anthropic_client.messages.parse(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    response_format=PersonInfo,           # 直接传 Pydantic 模型
    extra_headers={
        "anthropic-beta": "structured-outputs-2025-11-13"
    },
    messages=[
        {"role": "user", "content": "提取：张三是 ABC 公司的技术总监"}
    ]
)
person = response.parsed                  # 直接拿到 Pydantic 实例

# 兜底方案：Anthropic Tool Use（在原生 SO Beta 之前的事实标准，仍适用于无 Beta 权限场景）
response = anthropic_client.messages.create(
    model="claude-sonnet-4-5",
    tools=[{
        "name": "extract_person",
        "description": "提取人物信息",
        "input_schema": PersonInfo.model_json_schema()
    }],
    tool_choice={"type": "tool", "name": "extract_person"},
    messages=[{"role": "user", "content": "提取：张三是 ABC 公司的技术总监"}]
)

    原文把 Anthropic 原生 Structured Outputs 列为 2026 面试的核心新原语：它把“保证 Schema 合规”从应用层后处理移到了模型 API 层。

    方法 4：Constrained Decoding（底层约束）

    在 token 采样层面约束输出，只允许合法的下一个 token，因此可以 100% 保证格式和 Schema 合规。常见实现有 Outlines、Guidance 等；代价是实现复杂，通常用于本地模型或推理服务。

    Outlines · 原文代码

    # 新版 API（outlines >= 1.0）：from_transformers / from_vllm 等装载器
import outlines
from transformers import AutoModelForCausalLM, AutoTokenizer

base = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-7B-Instruct")
tok  = AutoTokenizer.from_pretrained("Qwen/Qwen3-7B-Instruct")
model = outlines.from_transformers(base, tok)

# 用 Pydantic / JSON Schema 约束生成
class Person(BaseModel):
    name: str
    age: int
    skills: list[str]

result = model("提取信息：张三,25岁,会Python和Java", Person)
# 100% 保证输出符合 Schema
# 原理：在每步 token 采样时，只允许合法的下一个 token
# 注：旧版 outlines.generate.json + Llama-3 8B 已被 from_transformers 替代

    XML 形式：另一种可解析格式

    原文主要以 JSON 为例。XML 同样属于结构化输出，只是 Schema 表示和解析器不同；下面只是格式示意，不代表某种模型的默认输出。

    <person>
  <name>张三</name>
  <company>ABC</company>
  <title>技术总监</title>
  <location>北京</location>
  <years>5</years>
</person>

    方法对比

    格式保证和
    Schema 保证是两件事。

    选择方法时先问两个问题：输出一定是合法 JSON 吗？字段和类型一定符合 Schema 吗？

    五种结构化输出方法在格式保证、Schema 保证、实现难度和适用场景上的对比
    方法格式保证Schema 保证实现难度适用场景
    Prompt 指令不保证不保证最简单原型验证
    JSON Mode保证不保证简单简单场景
    Function Calling保证保证中等Agent
    Structured Outputs保证保证中等生产环境
    Constrained Decode保证保证复杂本地模型

    最容易混淆的是 JSON Mode：它解决了“能不能解析”，没有解决“字段对不对”。生产环境推荐 Function Calling + Pydantic 验证：Function Calling 处理格式，Pydantic 验证语义。

    生产环境最佳实践

    格式之外，
    还要验证语义。

    Pydantic 的 Field 和 validator 可以做双重保障：既约束类型和范围，也检查业务规则；验证失败时把错误反馈给模型重试。

    Pydantic 双重保障与重试 · 原文代码

    from pydantic import BaseModel, Field, field_validator

class ExtractedData(BaseModel):
    """用 Pydantic 做双重保障：格式 + 语义验证"""
    name: str = Field(..., min_length=1, description="人名")
    age: int = Field(..., ge=0, le=150, description="年龄")
    email: str | None = Field(None, description="邮箱")

    @field_validator("email")
    @classmethod
    def validate_email(cls, v):
        if v and "@" not in v:
            raise ValueError("邮箱格式不正确")
        return v

async def extract_with_retry(text: str, max_retries=3) -> ExtractedData:
    """带重试的结构化输出提取（openai-python>=1.92，parse 已 GA）"""
    for attempt in range(max_retries):
        try:
            response = await client.chat.completions.parse(
                model="gpt-4o",
                response_format=ExtractedData,
                messages=[{"role": "user", "content": f"提取信息：{text}"}]
            )
            return response.choices[0].message.parsed
        except ValidationError as e:
            if attempt == max_retries - 1:
                raise
            # 将验证错误反馈给模型重试
            continue

    原文示例只展示验证失败后的重试路径；网络错误、超时和模型拒答不在这一段代码里。生产实现要把这些异常分开处理，避免把可重试错误和不可重试错误混在一起。

    Schema 设计也要清晰：字段名用语义化命名，description 写清楚每个字段的含义，帮助 LLM 理解期望。嵌套模型、列表、可选字段和枚举都可以用 Pydantic 表达。

    Agent 系统中的结构化输出

    工具调用就是
    最典型的结构化输出。

    Agent 的工具定义就是一份参数 Schema；LLM 输出结构化参数，框架解析后直接调用对应函数。

    工具定义与模型输出 · 原文代码

    tools = [
    {
        "name": "search_web",
        "description": "搜索网页信息",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "搜索关键词"},
                "max_results": {"type": "integer", "default": 5}
            },
            "required": ["query"]
        }
    }
]

# LLM 输出结构化的工具调用参数
# {"name": "search_web", "arguments": {"query": "Python 最佳实践", "max_results": 3}}
# Agent 框架解析后直接调用对应函数

    这里的 parameters 和上面的 Pydantic Schema 是同一个角色：告诉模型哪些字段必须有、每个字段是什么类型。区别是工具调用的结果还要由你的应用代码真正执行。

    常见误区 / 面试追问

    四个容易
    被追问的点。

    前两条是误区，后两条是面试追问；答案都来自原文。

    误区 1

    “在 Prompt 里说‘输出 JSON’就够了。”

    Prompt 指令无法保证输出是合法 JSON。LLM 可能添加 markdown 标记、额外解释、或生成语法错误的 JSON。生产环境必须用 JSON Mode 或 Function Calling。

    误区 2

    “JSON Mode 能保证字段完整。”

    JSON Mode 只保证输出是合法 JSON，不保证包含你需要的字段。需要用 Structured Outputs（传入 JSON Schema 或 Pydantic 模型）来保证 Schema 合规。

    追问 1

    Structured Output 会影响模型的生成质量吗？

    会有轻微影响。格式约束限制了模型的自由度，在某些创意任务上可能降低质量。但对于数据提取、工具调用等结构化任务，约束反而提升了准确率。

    追问 2

    如何处理嵌套和复杂的输出结构？

    Pydantic 支持嵌套模型、列表、可选字段、枚举等复杂结构。关键是 Schema 设计要清晰——字段名用语义化命名，description 写清楚每个字段的含义，帮助 LLM 理解期望。

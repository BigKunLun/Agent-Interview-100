中级 · Prompt Engineering · 可交互讲解

把大任务，
拆成小步。

Prompt Chaining 把复杂任务拆成多个 LLM 调用，每一步只做一件事，输出显式传给下一步。链路可以是直线、条件分支、并行扇出，也可以在关键步骤插入质量门。

关键边界：Chaining 是确定性工作流，不是自主 Agent。步骤和分支由代码预先定义；Agent Loop 才根据结果动态决定下一步。

基本模式

直线、岔路、
三路并行。

原文把链式结构分成三类：线性直通、条件分支选路、并行扇出后汇合。三种结构可以组合在同一条工作流里。

线性
提取实体→分析关系→生成摘要→格式化输出
条件
分类意图→查询：搜索回答/操作：确认执行/闲聊：直接对话
并行
子任务 A＋子任务 B＋子任务 C→合并结果

Prompt Chaining 是 Agentic AI 最基础的设计模式，也叫 Pipeline 模式；原文提到 AWS 把它列为 Agentic AI 的核心工作流模式之一。

并行的三路是同时开始的，不是排队执行。合并步骤必须等三路都返回；总耗时取决于最慢的一路，而不是三路之和。

线性链

每一步，
只做一件事。

线性链用一个上下文对象在步骤间传递结果。每步渲染 Prompt、调用 LLM、解析输出，再把结果写回上下文。

class PromptChain:
    """线性 Prompt Chain 实现"""

    def __init__(self, llm):
        self.llm = llm
        self.steps = []

    def add_step(self, name, prompt_template, output_parser=None):
        self.steps.append({
            "name": name,
            "prompt": prompt_template,
            "parser": output_parser or (lambda x: x),
        })
        return self

    async def run(self, initial_input):
        context = {"input": initial_input}
        for step in self.steps:
            prompt = step["prompt"].format(**context)      # 用上下文渲染
            response = await self.llm.invoke(prompt)       # 调用 LLM
            parsed = step["parser"](response)              # 解析输出
            context[step["name"]] = parsed                 # 写回上下文
        return context

使用时要显式引用上一步的键：{extract}、{analyze}。每次 LLM 调用都是独立的，没有记忆；不把上一步输出拼进下一步 Prompt，模型就看不到它。

chain = PromptChain(llm)
chain.add_step("extract", "从以下文本中提取所有关键实体和数据点：\n{input}", output_parser=json.loads)
chain.add_step("analyze", "分析以下实体之间的关系和趋势：\n{extract}")
chain.add_step("report", "基于以下分析生成一份简洁的报告：\n{analyze}\n\n原始实体：{extract}")

result = await chain.run("2024年Q3财报数据...")

条件链

先分类，
再选一条路。

Gate/Router 模式先用一次调用判断意图或条件，再由代码选择后续链。选路逻辑是确定的，不是模型自由发挥。

async def run(self, user_input):
    # Step 1: 分类意图
    intent = await self.llm.invoke(f"""
    将以下用户消息分类为一种意图：
    - QUESTION: 用户在提问
    - ACTION: 用户要求执行操作
    - FEEDBACK: 用户在提供反馈

    消息：{user_input}
    意图：
    """)

    # Step 2: 根据意图选择不同的处理链
    if "QUESTION" in intent:
        return await self.question_chain(user_input)
    elif "ACTION" in intent:
        plan = await self.plan_action(user_input)
        confirmed = await self.confirm_with_user(plan)
        if confirmed:
            return await self.execute_action(plan)
    elif "FEEDBACK" in intent:
        return await self.process_feedback(user_input)

注意 ACTION 分支里的确认步骤：执行前先让用户确认计划，确认通过才调用执行工具。这是条件链里最常见的人工闸门。

并行链

扇出去，
再收回来。

独立子任务可以同时发起，全部返回后再合并。合并调用要拿到所有分支结果，缺一路就不能给出完整结论。

async def analyze_competitors(self, company_list):
    # Step 1: 并行分析每个竞品
    tasks = [self.analyze_single(company) for company in company_list]
    results = await asyncio.gather(*tasks)

    # Step 2: 合并分析结果
    merged = await self.llm.invoke(f"""
    以下是各竞品的独立分析结果：
    {self.format_results(results)}

    请综合以上信息，生成一份竞品对比报告，
    包括各公司的优劣势对比和市场定位分析。
    """)
    return merged

async def analyze_single(self, company):
    return await self.llm.invoke(
        f"详细分析 {company} 的产品特性、市场定位和竞争优势。"
    )

asyncio.gather 同时发起三路调用。如果串行执行，总耗时是三路之和；并行时总耗时接近最慢的一路。代价是同时占用三个并发配额。

质量门

先审，
不过就改。

在生成和交付之间插一次验证调用，用固定 JSON 返回 pass / issues。不通过就带着问题清单修正，再复审。

draft = await self.llm.invoke(f"为以下产品写一份营销文案：{input_data}")

validation = await self.llm.invoke(f"""
审查以下营销文案的质量：
{draft}

检查：
1. 是否包含虚假宣传？
2. 语法是否正确？
3. 是否符合品牌调性？

输出 JSON：{{"pass": true/false, "issues": [...]}}
""")

if not validation["pass"]:
    revised = await self.llm.invoke(f"""
    修正以下文案中的问题：
    文案：{draft}
    问题：{validation["issues"]}
    """)
    return revised
return draft

质量门的价值在于错误隔离：问题在交付前被拦住，而不是等用户看到。代价是多一次调用和一段额外延迟；只对高风险输出值得加。

设计原则

五条原则，
决定链好不好用。

原文的五条原则覆盖职责、上下文、粒度、错误和成本。它们共同约束“拆到多细、怎么传、哪里验”。

原则做法原因 / 示例
单一职责每个 Prompt 只做一件事LLM 在聚焦任务上表现最好；提取 → 分析 → 格式化，而不是一步到位
显式传递把上一步输出明确嵌入下一步 Prompt每次调用独立、没有记忆，不能依赖隐含假设
渐进精化先粗后细，每步增加细节大纲 → 段落 → 润色 → 校对
错误隔离关键步骤后加 validation gate每步独立验证，错误不向后传播
成本意识简单步骤用小模型，关键步骤用大模型原文示例：分类用 Haiku，分析用 Opus

Chaining vs Agent Loop

流程固定，
还是让模型决定？

Chaining 适合步骤可预先写死的标准流程；Agent Loop 适合开放式任务。生产里常见的是两者混合。

Prompt Chaining（确定性工作流）

步骤固定、顺序确定、可预测。

  • 适合标准化流程：审核、转换、报告生成
  • 每步可单独测试、替换、加验证
  • 代价是灵活性：没预想到的路径走不了

Agent Loop（自主决策循环）

步骤动态、根据结果决定下一步。

  • 适合开放式任务：调试、研究、探索
  • 能处理未知路径，但更难预测和审计
  • 代价是成本、延迟和失控风险更高

混合方案

原文推荐：用 Chaining 定义主流程骨架，在需要灵活性的步骤内嵌 Agent Loop。外层可预测，内层保留探索空间；内层还要有步数和预算上限。

常见误区 / 面试追问

两个误区，
两个追问。

两条误区都在“拆得越细越好”；两条追问问失败处理，以及 Chaining 与 LangChain / LangGraph 的关系。

误区 1

“链越长越好，任务拆得越细越好。”

每增加一步就多一次 LLM 调用的延迟和成本，也多一次出错机会。关键是找到合适粒度：每步应该是 LLM 能可靠完成的最小有意义单元。

误区 2

“Prompt Chaining 就是把多个 Prompt 串联起来。”

好的 Chaining 还包括中间结果的解析和验证、错误处理和重试、条件分支、并行执行、上下文管理。简单串联只是最基础的形式。

追问 1

如何处理链中某一步失败？

三种策略：重试当前步骤（带指数退避）；跳过当前步骤使用默认值；回退到上一步用不同方式重试。选哪种取决于该步骤的关键程度。

追问 2

Prompt Chaining 和 LangChain 的 Chain 是什么关系？

LangChain 的 LLMChain / SequentialChain 等老 Chain 类已被 LCEL（LangChain Expression Language）替代。LCEL 提供 streaming / async / parallel / fallback 等原语，本质仍是 Prompt Chaining 模式的语法升级。LangGraph 是不同抽象层级：面向 Agent 的有状态图引擎（state + node + edge + checkpointer），用于带循环和条件路由的复杂控制流，不是 Chain 的替代品。简言之：LCEL 约等于“新的 Chain”，LangGraph 约等于“更上层的 Agent 编排”。Prompt Chaining 是通用设计模式，不依赖 LangChain。

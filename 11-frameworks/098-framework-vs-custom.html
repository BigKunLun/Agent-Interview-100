框架不是答案，
边界才是。

用框架还是自研，取决于项目阶段、团队经验、定制需求、性能要求、可调试性和维护成本。核心判断原则是：框架的价值 = 节省的开发时间 − 绕过框架限制的时间。

核心边界：框架适合快速原型和标准流程，自研适合深度定制和完全透明的控制流。大多数项目不需要一步到位的自研；渐进式替换通常更稳。

    先按调用规模走一遍

    原文的决策流程图先问“需要多少 LLM 调用”，把方案粗分成三档：

    单次调用直接调用 API，不需要框架。
    2–5 步链式轻量封装或框架；步骤少时，自己写几十行可能更清楚。
    复杂多步 Agent标准 ReAct / RAG 模式用框架；高度定制流程自研。

    这条流程只做初筛。真正决定是否迁移的，是框架带来的价值和代价能不能算平：框架的价值 = 节省的开发时间 − 绕过框架限制的时间。当绕过限制的时间开始超过节省的时间，就是考虑自研的信号。

    价值与代价

    框架省下的，
    和它收走的。

    原文把框架的好处和代价都列得很具体。判断是否自研，不是看框架“好不好”，而是看这些代价在你的场景里是否已经超过收益。

    框架带来的价值

    • 快速启动：几行代码实现 RAG / Agent，开发速度 3–5x（原文示例）。
    • 最佳实践：内置 ReAct、Plan-and-Execute 等成熟模式。
    • 生态集成：几十种 LLM、向量数据库、工具的预集成。
    • 可观测性：LangSmith / Langfuse 等追踪工具的原生支持。
    • 社区支持：问题容易找到答案，示例丰富。

    框架带来的代价

    • 抽象税：多层封装导致调试困难，错误信息不直观。
    • 性能损耗：额外的序列化 / 反序列化、中间层开销。
    • 升级风险：API 频繁变更，升级可能破坏现有代码。
    • 灵活性限制：框架假设的流程可能不符合业务需求。
    • 依赖锁定：深度使用后难以迁移到其他方案。
    • 过度工程：简单需求也要遵循框架的复杂模式。

    什么时候该考虑从框架迁移到自研

    • 频繁绕过框架限制（monkey patch / 自定义 callback）。
    • 调试时间 > 开发时间。
    • 框架升级导致回归问题。
    • 需要的功能框架不支持，但又不能脱离框架实现。
    • 性能瓶颈来自框架抽象层。

    原文的经验判断是：LangChain 非常适合原型阶段（开发速度快 3x），但一旦扩展到复杂生产场景，多层抽象会成为维护噩梦。这个 3x 是原文示例，不是对所有团队的保证。

    自研与渐进

    Agent 本质，
    就是一个循环。

    自研不等于从零造所有东西。原文的最小实现只有几十行：调用 LLM、检查工具调用、执行工具、循环。难的是错误处理、状态、可观测性和边界。

    最小可用的自研 Agent

    原文的 MinimalAgent 展示了核心结构：把工具注册成“函数 + JSON Schema”，在循环里调用模型；如果模型返回工具调用，就执行工具并把结果写回消息；没有工具调用就返回最终答案。核心洞察是：Agent 本质上就是一个 while 循环，不需要框架也能实现。

    查看 MinimalAgent 原文代码 
    import json
from openai import OpenAI

class MinimalAgent:
    """最小可用的自研 Agent 框架"""

    def __init__(self, model="gpt-4o", tools=None, system_prompt=""):
        self.client = OpenAI()
        self.model = model
        self.tools = {t["function"]["name"]: t for t in (tools or [])}
        self.tool_functions = {}
        self.system_prompt = system_prompt

    def register_tool(self, name, func, schema):
        """注册工具：函数 + JSON Schema"""
        self.tool_functions[name] = func
        self.tools[name] = schema

    def run(self, user_message, max_steps=10):
        """Agent 执行循环——这就是 Agent 的本质"""
        messages = [
            {"role": "system", "content": self.system_prompt},
            {"role": "user", "content": user_message},
        ]

        for step in range(max_steps):
            # 1. 调用 LLM
            response = self.client.chat.completions.create(
                model=self.model,
                messages=messages,
                tools=list(self.tools.values()) if self.tools else None,
            )
            msg = response.choices[0].message
            messages.append(msg)

            # 2. 检查是否需要调用工具
            if not msg.tool_calls:
                return msg.content  # 无工具调用 → 返回最终答案

            # 3. 执行工具
            for tool_call in msg.tool_calls:
                func = self.tool_functions[tool_call.function.name]
                args = json.loads(tool_call.function.arguments)
                result = func(**args)
                messages.append({
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "content": str(result),
                })

        return "达到最大步数限制"

# 核心洞察：Agent 本质上就是一个 while 循环
# LLM 调用 → 检查工具调用 → 执行工具 → 循环
# 不需要框架也能实现

    渐进式策略：四个阶段

    从原型到完全自研的四个阶段
    阶段方法目标产出代码状态
    阶段 1：原型验证（1–2 周）使用框架（LangChain / LangGraph）验证 Agent 方案可行性可演示的原型大量使用框架预构建组件
    阶段 2：需求明确（2–4 周）框架 + 自定义组件明确生产需求和性能瓶颈性能基线、需求文档开始替换框架中的瓶颈组件
    阶段 3：核心自研（1–3 月）核心路径自研 + 非核心保留框架优化性能、提高可控性自研 Agent 核心 + 框架辅助模块Agent Loop 自研，RAG / 工具可保留框架
    阶段 4：完全自主（可选）完全自研只有当框架的存在确实造成显著问题时—大多数项目在阶段 3 就够了

    原文的四条原则是：（1）不要一开始就自研，先用框架验证方向；（2）不要永远依赖框架，根据需求逐步自主化；（3）可以混用，核心路径自研、辅助功能用框架；（4）抽象边界，即使用框架，也要隔离框架依赖。

    自研时的五层架构

    Layer 1 · LLM 接口层封装 LLM API 调用，支持多提供商。适配器模式：统一接口，底层可切换，例如 LLMClient(provider='openai'|'anthropic'|'google')。
    Layer 2 · 工具层工具注册、Schema 生成、执行。装饰器模式：@tool 自动生成 JSON Schema。
    Layer 3 · Agent Loop核心执行循环：推理、行动、观察。策略模式：可插拔的推理策略，例如 AgentLoop(strategy='react'|'plan_execute')。
    Layer 4 · 状态管理会话状态、检查点、记忆。仓库模式：可插拔的存储后端，例如 StateStore(backend='memory'|'redis'|'postgres')。
    Layer 5 · 可观测性日志、追踪、指标。中间件模式：非侵入式，例如 agent.use(TracingMiddleware())。

    这五层不是让你一次全写完。它的作用是划边界：LLM 接口、工具、循环、状态、可观测性各自可替换，避免自研之后又长成一个新的“框架黑箱”。

    原文引用的官方建议

    Anthropic 的建议是“Start with the simplest solution”：先用原生 API，只在确实需要时引入框架。OpenAI Agents SDK 的设计哲学是“最小抽象”：只封装 Agent Loop 和工具调用，其他交给开发者。原文认为这反映了行业趋势：框架在变轻，而非变重。

    常见误区 / 面试追问

    四个容易被追问的点。

    前两条是误区，后两条是面试追问；答案都来自原文。

    误区 1

    “自研总是更好。”

    自研意味着你要维护 Agent Loop、错误处理、状态管理、工具集成、可观测性等所有组件。小团队可能无法承受这个维护成本。框架把这些“无差别劳动”打包好了，让你专注于业务逻辑。

    误区 2

    “框架性能太差。”

    框架的额外开销通常在毫秒级，而 LLM API 调用在秒级。在大多数场景下，框架不是性能瓶颈。只有在极高并发或极低延迟的场景下，框架开销才值得关注。

    追问 1

    如何隔离框架依赖？

    使用端口-适配器模式（Hexagonal Architecture）：定义自己的接口（Port），用框架实现这些接口（Adapter）。业务代码只依赖自己的接口，切换框架只需替换 Adapter。这是“用框架但不被框架绑定”的关键。

    追问 2

    Anthropic / OpenAI 自己推荐怎么做？

    Anthropic 的建议是“Start with the simplest solution”：先用原生 API，只在确实需要时引入框架。OpenAI Agents SDK 的设计哲学是“最小抽象”：只封装 Agent Loop 和工具调用，其他交给开发者。这反映了行业趋势：框架在变轻，而非变重。

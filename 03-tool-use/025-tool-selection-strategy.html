工具选择，
先看描述，再看规模。

LLM 选工具的核心，是把用户意图和工具描述做语义匹配。工具少时，把描述放进上下文让模型自己选；工具多时，先用检索、分层或训练式路由缩小候选集。工具描述的质量，是选择准确率的第一影响因素。

关键边界：名称只是标识符，description 才决定模型理不理解工具的用途。本页的选择结果由固定教学规则计算，不调用任何模型。

    选择过程

    先判断要不要工具，
    再判断用哪个。

    工具选择不是单一动作，而是一次三路决策：内部知识能答就直答；描述匹配到工具就生成调用；没有匹配就坦白无法处理。

    要注意的是，“分析意图”和“扫描描述”发生在一次模型推理里，不是两个独立的服务。模型看到的是 System Prompt 中的工具清单和描述，输出的是工具名与参数。选择质量取决于描述是否写清了触发条件和排除条件。

    五种策略

    从全部给模型，
    到只给最相关的一小撮。

    五种策略不是互相替代的版本号，而是按工具规模和稳定性做的取舍。工具少用描述，工具多用检索，模式稳定后再考虑训练式路由。

    策略 1：描述驱动选择（最基础）

    把所有工具的列表和描述放进 System Prompt，让模型自行判断。描述要回答三个问题：做什么、什么时候用、什么时候不用。相似工具之间还要互相点名区分。

    原文示例 · 差描述与好描述

    # 差：模糊的描述
"description": "搜索数据"

# 好：精确的描述 + 使用/排除条件
"description": (
    "搜索产品知识库中的技术文档和API参考。"
    "当用户询问产品功能、配置方法或错误代码含义时使用。"
    "不适用于搜索订单信息（用 query_orders）或用户账户（用 get_profile）。"
)

    原文的优化原则是四条：说明做什么、说明什么时候用、说明什么时候不用、与相似工具做区分。缺少排除条件时，模型容易在相邻工具之间摇摆。

    策略 2：Function Calling 结构化选择

    通过 API 原生的 tools 参数声明工具，用 tool_choice 控制模型是否必须选择。返回的 stop_reason 区分“调用了工具”和“认为不需要工具”。

    response = client.messages.create(
    model="claude-sonnet-4-5-20250929",
    tools=[tool_a, tool_b, tool_c],
    tool_choice={"type": "auto"},     # 让模型自动决定
    # tool_choice={"type": "tool", "name": "specific_tool"},  # 强制指定
    messages=[{"role": "user", "content": query}]
)

# 模型返回：
# - stop_reason="tool_use" → 选择了某个工具
# - stop_reason="end_turn" → 认为不需要工具

    tool_choice 的四个选项：auto 自主决定、required 必须选至少一个、{"type": "tool", "name": "X"} 强制指定、none 禁止使用。强制选项适合流程中已经确定下一步动作的场景，不适合开放式问答。

    策略 3：Embedding 检索选择（工具多时）

    工具超过 50 个时，全量描述会占用大量上下文，也会让模型“挑花眼”。做法是先把工具描述编码成向量，查询时检索 top-k，只把相关工具交给模型。

    class ToolRetriever:
    def __init__(self, tools: list[dict]):
        self.tool_embeddings = embed([t["description"] for t in tools])
        self.tools = tools

    def get_relevant_tools(self, query: str, top_k: int = 5) -> list[dict]:
        query_embedding = embed(query)
        similarities = cosine_similarity(query_embedding, self.tool_embeddings)
        top_indices = similarities.argsort()[-top_k:][::-1]
        return [self.tools[i] for i in top_indices]

relevant_tools = retriever.get_relevant_tools(user_query, top_k=5)
response = llm.generate(query=user_query, tools=relevant_tools)

    检索解决的是上下文容量问题，不解决描述本身写得烂的问题。top-k 选小了会漏掉正确工具，选大了又回到全量暴露，需要按工具分布调。

    策略 4：分层选择（两阶段路由）

    先让模型选工具类别，再在类别内选具体工具。类别通常按业务域划分，例如客服、产品信息、账单。这样每一层只需要看少量选项。

    categories = {
    "customer_service": ["query_orders", "create_ticket", "get_profile"],
    "product_info": ["search_docs", "get_pricing", "check_compatibility"],
    "billing": ["get_invoice", "process_refund", "update_payment"],
}

category = llm.classify(query, list(categories.keys()))
tools_in_category = categories[category]
selected_tool = llm.select_tool(query, tools_in_category)

    代价是多了一次模型调用，而且错误会级联：类别分错，第二层再准也选不回来。类别名称和边界要写得足够互斥。

    策略 5：训练式路由（规模化方案）

    工具选择模式稳定、并发又高时，每次都用 LLM 推理不划算。可以训练一个轻量分类器，把“查询 → 工具标签”变成毫秒级预测。

    from sklearn.ensemble import GradientBoostingClassifier

# 训练数据：(用户查询, 正确的工具)
X_train = embed(queries)
y_train = tool_labels

router = GradientBoostingClassifier()
router.fit(X_train, y_train)

# 推理：毫秒级路由，不需要 LLM
predicted_tool = router.predict(embed(new_query))

    它牺牲的是灵活性：工具增删、描述调整或业务口径变化后，分类器需要重新训练。适合工具集稳定、流量大的生产环境，不适合还在快速迭代的工具平台。

    歧义与降级

    分数都低就直答，
    分数接近就仲裁。

    选择器不能只会取最大值。最高分太低说明没有工具匹配；前两名太接近说明信息不足，应该交给 LLM 结合上下文做 tie-break。

    class ToolSelector:
    def select(self, query: str, tools: list) -> str:
        scores = self.score_tools(query, tools)

        if max(scores.values()) < 0.3:
            # 没有工具匹配 → 直接用 LLM 回答
            return None

        if scores[first] - scores[second] < 0.1:
            # 两个工具分数接近 → 让 LLM 结合推理选择
            return self.llm_tiebreak(query, top_2_tools)

        return max(scores, key=scores.get)

    两个阈值要按业务调，不能直接照搬。阈值过低会把不相关的请求硬塞给工具；过高会让本来能处理的请求退化成“无法处理”。原文给出的 0.3 和 0.1 是示例值。

    降级顺序

    最佳工具 → tie-break → 直接回答 → 告知无法处理。每一级都要能回传到对话里，而不是静默失败。选择器返回 None 时，上层要知道这是“不需要工具”，不是“工具选择出错”。

    实战顺序通常是：先用描述驱动把 5 到 10 个工具跑通，再上 Function Calling 固定结构；工具数逼近上下文上限时加检索；类别边界清楚时改分层；最后才对稳定的高频流量做训练式路由。

    工具描述写不好，换什么路由策略都只是把错误提前或推后。

    常见误区 / 面试追问

    四个容易答错的点。

    前两个是误区，后两个是追问。回答时先给结论，再补条件和代价。

    误区 1

    “工具名称是选择的关键。”

    描述才是关键。LLM 主要靠 description 理解工具的用途和适用场景，名称只是标识符。把 search_docs 改名成 find_stuff 但描述不变，选择结果通常不会大变；反过来则可能直接选错。

    误区 2

    “工具越多越好。”

    工具过多会增加选择错误率、消耗上下文窗口、增加延迟。从 1 到 2 个工具开始逐步增加，确保每个工具的描述清晰且不重叠。工具数量是成本，不是能力指标。

    追问 1

    如何评估工具选择的准确率？

    构建测试集：N 个用户查询加对应的正确工具，运行后计算选择准确率。原文建议低于 90% 就需要优化描述或调整策略。测试集要覆盖“不需要工具”和“没有可用工具”两类负例，否则准确率会虚高。

    追问 2

    ReAct 框架如何影响工具选择？

    ReAct 在工具选择前加了显式的 Thought 步骤，让 LLM 先推理为什么需要这个工具再调用。这提高了选择的可解释性和准确性，代价是多了一段推理 token 和延迟。

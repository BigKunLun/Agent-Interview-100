中级 · Tool Use · 可交互讲解

工具接一次，
谁都能用。

MCP 是标准化 AI 系统与外部工具、数据源集成的开放协议。过去每个应用接每个工具都要写定制代码，是 N×M 问题；有了 MCP，工具实现一次 MCP Server，任何支持 MCP 的应用都能用，变成 N+M。协议基于 JSON-RPC 2.0，核心角色是 Host、Client、Server，核心能力是 Tools、Resources、Prompts。

关键边界：MCP 标准化的是“连接和发现”，不是模型如何调用工具。工具调用最终仍由 Function Calling 机制完成。本页消息流为固定教学数据，不连接任何真实 MCP Server。

      解决什么问题

      从 N×M 条定制线，
      到 N+M 个标准接口。

      没有 MCP 时，每个 AI 应用与每个外部工具之间都要写一套定制集成。应用和工具越多，维护成本越接近乘积。

      没有 MCP（N×M 问题）：
Claude Desktop ──定制代码──→ GitHub API
Claude Desktop ──定制代码──→ Slack API
Claude Desktop ──定制代码──→ 数据库
Cursor         ──定制代码──→ GitHub API（又写一遍）
Cursor         ──定制代码──→ Slack API（又写一遍）

有了 MCP（N+M 方案）：
Claude Desktop ─┐              ┌─→ GitHub MCP Server
Cursor         ─┤── MCP 协议 ──┤─→ Slack MCP Server
VS Code        ─┘              └─→ 数据库 MCP Server

      每个 AI 应用实现一次 MCP Client，每个工具实现一次 MCP Server。新增工具不需要修改任何应用，新增应用也不需要为已有工具重写连接器。

      三层架构

      Host 管应用，
      Client 管连接，Server 管能力。

      三个角色职责分明。Host 是用户面对的应用，Client 在 Host 内运行并维护 1:1 连接，Server 把外部系统的能力翻译成 MCP 标准协议。

      MCP Server · Postgres

      • Host：AI 应用，例如 Claude Desktop、Cursor IDE，接收用户请求。
      • Client：在 Host 内运行，把请求转换成 MCP 协议格式。每个 Client 与一个 Server 建立 1:1 连接。
      • Server：暴露外部系统的能力，把原生接口翻译为 MCP 标准协议。

      三种核心能力

      工具能执行，
      资源能读，提示能复用。

      Tools 是可执行函数，Resources 是只读数据，Prompts 是预定义工作流。三者解决的不是同一类问题。

      原文示例 · Tools

      {
    "name": "create_issue",
    "description": "在 GitHub 仓库中创建 Issue",
    "inputSchema": {
        "type": "object",
        "properties": {
            "repo": {"type": "string"},
            "title": {"type": "string"},
            "body": {"type": "string"}
        },
        "required": ["repo", "title"]
    }
}

      客户端通过 tools/list 发现工具，通过 tools/call 调用。返回的 inputSchema 让模型知道参数结构。

      原文示例 · Resources

      {
    "uri": "file:///project/README.md",
    "name": "项目 README",
    "mimeType": "text/markdown"
}

      Resources 类似 REST 的 GET，提供只读数据访问。URI 可以是 file:///path/to/file，也可以是 postgres://db/table 这类自定义 scheme。

      原文示例 · Prompts

      {
    "name": "code_review",
    "description": "对代码进行审查",
    "arguments": [
        {"name": "code", "required": true}
    ]
}

      Prompts 把特定任务的最佳实践封装成模板，由用户或 Host 选择，不由模型自动调用。

      通信协议

      一条 JSON-RPC，
      两种传输。

      消息格式统一为 JSON-RPC 2.0；传输分本地 stdio 和远程 Streamable HTTP。连接生命周期从 initialize 握手开始。

      • stdio：Host 启动本地 Server 进程，通过 stdin/stdout 通信，适合本地工具，零网络开销。
      • Streamable HTTP：MCP 2025-03-26 规范引入，使用单一 HTTP 端点，按 HTTP method 区分请求、通知和 SSE 流，适合远程服务。

      原文特别说明：Streamable HTTP 取代了早期“独立 HTTP POST 加单独 SSE GET 端点”的传输设计。

      连接生命周期是固定顺序：initialize 请求带协议版本和能力 → Server 返回支持的能力 → Client 发 initialized 通知 → tools/list 发现工具 → tools/call 调用。工具是运行时发现的，不是启动时写死的。

      查看原文 Mermaid 时序图源码（需在支持 Mermaid 的编辑器中渲染） 
      sequenceDiagram
    participant C as MCP Client
    participant S as MCP Server
    C->>S: initialize（协议版本 + 能力）
    S-->>C: initialize 响应（返回支持的能力）
    C->>S: initialized 通知（确认初始化完成）
    C->>S: tools/list（发现可用工具）
    S-->>C: 工具列表（含 inputSchema）
    C->>S: tools/call（调用工具）
    S-->>C: 执行结果

      动态工具发现

      列表变了，
      发通知，不推列表。

      Server 可以在运行时改变工具集。它只发变更通知，Client 收到后重新执行 tools/list，再更新 Agent 的可用工具。

      # Server 端：工具列表变更时发送通知
server.send_notification("notifications/tools/list_changed")

# Client 端：收到通知后重新获取工具列表
async def on_tools_changed():
    updated_tools = await client.call("tools/list")
    agent.update_available_tools(updated_tools)

      这让工具可以按用户认证状态、权限级别或会话阶段动态暴露。例如只读 Token 看不到 delete_repo，登录后才会出现写操作工具。

      MCP vs Function Calling

      一个标准化连接，
      一个负责调用。

      两者互补，不是替代。MCP 定义工具怎么被发现和连接，Function Calling 是模型发起调用的底层机制。

      Function Calling 与 MCP 的五个维度对比
      维度Function CallingMCP
      定义方式每次 API 调用传入工具定义标准化协议，Server 独立定义
      集成成本每个工具 × 每个应用 = N×M每个工具一次，每个应用一次 = N+M
      工具发现静态（开发时定义）动态（运行时发现）
      生态复用无标准化，各自实现社区共享 MCP Server
      适用场景少量工具（<10）的简单应用多工具、多应用的生态系统

      MCP Server 暴露工具，LLM 仍然通过 Function Calling 选择并生成调用参数。把 MCP 说成“替代 Function Calling”，是把连接层和调用层混成了一层。

      原文示例 · Python SDK 创建 MCP Server

      from mcp.server import Server
from mcp.types import Tool, TextContent

server = Server("weather-server")

@server.list_tools()
async def list_tools():
    return [
        Tool(
            name="get_weather",
            description="获取指定城市的天气",
            inputSchema={
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"]
            }
        )
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict):
    if name == "get_weather":
        weather = await fetch_weather(arguments["city"])
        return [TextContent(type="text", text=f"温度: {weather.temp}°C")]

      生产化

      协议能用，
      不等于生产可用。

      远程部署要解决认证、版本、沙箱和选型。原文的生态数字与平台状态标注为“原文版本、未联网核实”。

      原文列出的生态信号：截至 2026 年初，PulseMCP 收录超过 5500 个 MCP Server；Stacklok《State of MCP 2026》称约 80% 的 Fortune 500 企业已参与 MCP 生态；官方 Roadmap 于 2026-03-05 更新，重点是认证增强、Elicitation 和 Registry。以上均为原文版本、未联网核实，不表示本页确认了这些数字的当前值。

      部署：本地 stdio vs 远程 HTTP

      本地 stdio 零网络开销、无需认证，但版本碎片化、无集中管控；远程 Streamable HTTP 可集中管控、观测和弹性伸缩，代价是网络延迟与认证开销。生产更常见的是远程托管加 Gateway 统一路由。

      认证：OAuth 2.1

      远程 Server 作为 OAuth Resource Server。授权码流程强制 PKCE；支持 RFC 7591 动态客户端注册；Token 带 scope，决定能看到哪些工具；Token 绑定 Resource Indicator，防止跨 Server 重放。

      版本：三层要分清

      协议版本在 initialize 协商；能力声明看 Server 的 capabilities；工具 Schema 看 tools/list 的 inputSchema，这是最常见的破坏源。工具加版本后缀，旧工具保留过渡期，避免直接改已有参数结构。

      沙箱与治理

      每个 Server 跑独立沙箱，限制文件系统、网络出口和资源配额。Tool Poisoning 用签名验证和来源白名单；Confused Deputy 用最小权限和高危操作人工确认；数据外泄用出口白名单和审计日志。

      原文的选型清单给了六个维度：来源可信度、权限范围、维护活跃度、Token 成本、传输安全、可观测性。红旗信号包括匿名仓库、全盘文件访问、超过 6 个月未更新、明文 HTTP 和黑盒运行。同时连接的 Server 数量建议控制在 2 到 3 个以内，超过后工具选择准确率会下降。

      工具权限与网关的完整讨论见 Tool Gateway 与工具权限管理（#024）；MCP 场景下的攻击面与防御见 工具使用安全（#030）。权限最小化与沙箱执行见 权限最小化与沙箱执行（#081）；Agent Sandbox / Runtime 选型见 Agent Sandbox / Runtime 选型（#112）。

      原文还区分了 MCP 与 Claude Skills：MCP 是连接层，回答“能访问什么”；Skill 是程序性知识层，回答“怎么做”。Skill 采用渐进式披露，启动时只加载 name 和 description，相关时才加载完整指令，执行时才加载脚本；MCP 的工具 schema 在 initialize 时就进入上下文。两者正交，不能互相替代。

      原文列出的 MCP 使用问题包括：Token 膨胀、中间结果占用上下文、工具超过 10 到 15 个后选择混乱、把 REST API 一比一包装成工具、调试困难和安全隐患。

      常见误区 / 面试追问

      八个问题，
      先分清连接层和调用层。

      前两个是误区，后六个是追问。回答时先给一句话结论，再补边界和代价。

      误区 1

      “MCP 是 Anthropic 的私有协议。”

      MCP 是完全开源的标准。由 Anthropic 主导，OpenAI、Google DeepMind、Microsoft 共同参与 MCP Steering Committee 治理，不绑定任何特定模型或平台。

      误区 2

      “MCP 替代了 Function Calling。”

      两者互补而非替代。MCP 标准化工具的定义和发现方式，Function Calling 是 LLM 调用工具的底层机制。MCP Server 暴露工具，LLM 通过 Function Calling 调用它们。

      追问 1

      MCP 的安全隐患是什么？

      Tool Poisoning（恶意 Server 注册伪装工具）、Prompt Injection 通过工具结果注入、凭证通过 MCP 通道泄露。防御包括 Server 签名验证、工具白名单和输出清洗。

      追问 2

      MCP 如何处理认证？

      协议规范层不强制定义认证，早期由 Server 内部处理：Server 持有 API 密钥，Agent 不接触凭证。生产级远程实现普遍采用 OAuth 2.1，Token 的 scope 决定暴露哪些工具。

      追问 3

      MCP 的 Token 膨胀问题如何解决？

      三种策略：最有效的是 Code Execution 模式，把工具暴露为代码 API；其次是渐进式披露，按任务只加载相关工具；最后是最小化 Schema，精简描述。

      追问 4

      MCP 最大的安全风险是什么？

      Tool Poisoning：恶意 Server 注册看似有用、实际执行恶意操作的工具。防御是签名验证、工具白名单和沙箱隔离。

      追问 5

      Skill 和 MCP 是什么关系？什么时候用哪个？

      MCP 是连接（what），Skill 是方法（how）。需要访问外部系统用 MCP；需要按特定方式完成任务用 Skill。两者协同：MCP 提供原始能力，Skill 提供标准操作流程。

      追问 6

      Subagent 和 Skill 又有什么区别？

      Subagent 是独立 Agent 进程，有自己的上下文、工具和模型，主 Agent 通过任务委派调用；Skill 是注入主 Agent 的程序性指令，不开新进程，按需加载到当前上下文。一个是派新员工，一个是给当前员工看手册。

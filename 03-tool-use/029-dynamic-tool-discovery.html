别一次全给，
用到才找。

动态工具发现，是 Agent 在运行时而不是编译时发现和使用工具。它解决两个问题：工具定义占满上下文，以及工具太多导致选择准确率下降。常见实现有 MCP 动态发现、语义检索、上下文过滤、ITR 和集中注册中心。

关键边界：发现不只是性能优化，也是权限机制。按角色、认证状态和会话阶段过滤，才能做到最小权限。本页注册表与检索分数都是固定教学数据，不连接真实注册中心。

    为什么需要

    工具定义会吃上下文，
    也会拉低选择准确率。

    静态加载把全部工具塞进 System Prompt，工具越多，token 成本和选错概率一起上升。

    原文给出的对照：所有工具静态塞入时，50 个工具、每个约 500 tokens，就是 25,000+ tokens 仅用于工具定义；动态方式只放相关的三个，约 1,500 tokens。原文还引用 Anthropic 内部测试：58 个工具可消耗约 55k tokens。这些是原文引用值，未联网核实，不是本页实测。

    静态方式（所有工具塞进 System Prompt）：
工具 1 定义 (500 tokens)
工具 2 定义 (500 tokens)
...
工具 50 定义 (500 tokens)
总计: 25,000+ tokens 仅用于工具定义

动态方式（按需加载相关工具）：
工具 A 定义 (500 tokens) ← 相关
工具 B 定义 (500 tokens) ← 相关
工具 C 定义 (500 tokens) ← 可能相关
总计: 1,500 tokens

    除了成本，工具数量还会降低选择准确率。工具越多，描述越容易重叠，模型越难在相邻选项里选对。

    方式 1

    MCP：注册即通知，
    Client 重新拉取。

    MCP 原生支持工具动态发现和热更新。Server 注册或注销工具后广播 list_changed，Client 重新 tools/list 刷新清单。

    Server 运行时注册 / 注销工具→广播 notifications/tools/list_changed
    Client 重新 tools/list→Server 返回最新工具列表→更新 Agent 可用工具清单

    class DynamicMCPServer:
    def __init__(self):
        self.tools = {}

    async def register_tool(self, tool):
        self.tools[tool.name] = tool
        await self.notify("notifications/tools/list_changed")

    async def unregister_tool(self, tool_name):
        del self.tools[tool_name]
        await self.notify("notifications/tools/list_changed")

    async def handle_tools_list(self):
        return [tool.to_schema() for tool in self.tools.values()]

    典型场景：用户登录后按权限暴露不同工具；会话从“浏览”进入“购买”时，新增支付相关工具。

    方式 2

    工具超过 50 个，
    先用语义检索缩小。

    把工具描述编码成向量，按用户意图检索 top-k，只把相关工具传给 LLM。

    class ToolRegistry:
    def __init__(self, tools: list[dict]):
        self.model = SentenceTransformer("all-MiniLM-L6-v2")
        self.tools = tools
        descriptions = [t["description"] for t in tools]
        self.embeddings = self.model.encode(descriptions)
        dim = self.embeddings.shape[1]
        self.index = faiss.IndexFlatIP(dim)
        faiss.normalize_L2(self.embeddings)
        self.index.add(self.embeddings)

    def discover(self, query: str, top_k: int = 5) -> list[dict]:
        query_vec = self.model.encode([query])
        faiss.normalize_L2(query_vec)
        scores, indices = self.index.search(query_vec, top_k)
        return [
            self.tools[idx] for idx, score in zip(indices[0], scores[0])
            if score > 0.3
        ]

    检索选错工具时有两层保护：top-k 取 5 到 8 个而不是 top-1，给模型更多选项；最终仍由 LLM 做选择，检索只缩小范围。

    方式 3

    同一份工具表，
    不同上下文不同可见性。

    按用户权限、认证状态、会话阶段和 Feature Flag 过滤工具。这既是性能优化，也是最小权限控制。

    class ContextAwareToolFilter:
    def __init__(self, all_tools):
        self.all_tools = all_tools

    def get_available_tools(self, context: dict) -> list:
        available = []
        for tool in self.all_tools:
            if not self.user_has_permission(context["user"], tool):
                continue
            if tool.requires_auth and not context.get("authenticated"):
                continue
            if tool.stage and tool.stage != context.get("session_stage"):
                continue
            if tool.feature_flag and not is_enabled(tool.feature_flag):
                continue
            available.append(tool)
        return available

    过滤顺序通常是权限 → 认证 → 阶段 → Flag。先做便宜且静态的检查，再做语义检索，能少算很多无关向量。

    方式 4 与 5

    每一步只取最小集，
    规模化再上注册中心。

    ITR 按当前步骤检索最小必要的指令片段和工具子集；集中注册中心则把多 Server 的工具元数据、健康和搜索索引统一管理。

    Instruction-Tool Retrieval（ITR）：每一步都基于当前步骤上下文，重新检索相关指令和工具，而不是一次加载全部。原文给出的预期收益是显著降低每步 context tokens、提升选择准确率、降低端到端成本，具体幅度因任务和工具规模而异。原文提到可减少约 95% 上下文开销，该数字为原文引用，未联网核实。

    class InstructionToolRetriever:
    def retrieve_for_step(self, agent_state, step_context):
        relevant_instructions = self.retrieve_instructions(step_context)
        relevant_tools = self.retrieve_tools(step_context)
        return {
            "system_prompt": relevant_instructions,
            "tools": relevant_tools,
        }

    集中式工具注册中心：登记工具的元数据、所属 Server、注册时间和状态，维护健康检查和语义搜索索引。Server 注册时批量写入，下线时按 server_id 移除，再重建索引。

    class CentralToolRegistry:
    def __init__(self):
        self.registry = {}
        self.health_checks = {}
        self.search_index = None

    def register(self, server_id: str, tools: list[dict]):
        for tool in tools:
            self.registry[tool["name"]] = {
                "server": server_id,
                "schema": tool,
                "registered_at": datetime.now(),
                "status": "active"
            }
        self._rebuild_index()

    def deregister(self, server_id: str):
        self.registry = {
            k: v for k, v in self.registry.items()
            if v["server"] != server_id
        }
        self._rebuild_index()

    def search(self, query: str, top_k: int = 5) -> list:
        return self.search_index.query(query, top_k)

    五种动态工具发现方式的规模、延迟、灵活性与实现复杂度对比
    方式工具规模延迟开销灵活性实现复杂度
    MCP 动态发现中等（10–50）低高中

    选型可以按规模递进：工具少用上下文过滤；超过 50 个加语义检索；每步都要最小集就上 ITR；多 Server、多团队共享时才需要集中注册中心。

    常见误区 / 面试追问

    四个问题，
    别把发现只当优化。

    前两个是误区，后两个是追问。

    误区 1

    “把所有工具都放进 System Prompt 最简单可靠。”

    工具超过 20 个后，选择准确率明显下降，上下文窗口也被大量占用。动态发现是规模化的必要手段，不是可有可无的优化。

    误区 2

    “动态发现只是性能优化。”

    它也是安全机制。通过动态过滤，可以按用户权限和认证状态实时调整可用工具，落实最小权限原则。

    追问 1

    语义检索选错了工具怎么办？

    两层保护：检索取 top-k（5 到 8 个）而不是 top-1，给 LLM 更多选项；LLM 仍然做最终选择。检索是缩小范围，不是替代判断。

    追问 2

    动态工具发现和 Agent 编排有什么关系？

    动态发现决定 Agent 的能力边界：能做什么，取决于它能发现哪些工具。多 Agent 系统中，不同 Agent 可能连接不同的 MCP Server，拥有不同的发现范围。

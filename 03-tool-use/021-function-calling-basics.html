基础 · Tool Use · 可交互讲解

LLM 只开口，
应用代码动手。

Function Calling（也叫 Tool Use）让 LLM 能调用外部函数或 API。LLM 本身不执行任何工具，它只生成结构化的 JSON 输出，指定要调用哪个函数、传入什么参数。

实际的函数执行由你的应用代码完成，执行结果再返回给 LLM 以生成最终回答。这个能力把 LLM 从“只能说”的顾问升级为“能做事”的执行者。

基础Tool Use五步时序离线教学数据
五步时序 LLM 生成请求，应用代码执行
用户Agent（LLM）应用代码
用户 → LLM→提问：“北京天气？”
LLM → 应用→tool_use：get_weather(city="Beijing")
应用内部⟳本地执行工具（LLM 不执行）
应用 → LLM←tool_result：{temp: 22}
LLM → 用户←最终回答：“北京 22°C”

用户先提出自然语言问题。

用户只提供问题，不指定函数名或参数。示例中的“北京天气？”是固定教学输入。

本步输入 · 固定教学数据

北京天气？

这句话不会发送到任何真实模型或天气服务。

时序中的城市、温度和工具结果都是固定教学数据。本页不调用模型、不访问天气接口，也不执行原文示例代码。

固定教学数据 · 每一步只切换讲解第 1 / 5 步 · 没有连接模型或工具服务

核心工作流程

五步走完一圈，
工具才真正执行。

LLM 只生成调用请求、不执行工具：请求与结果在用户、LLM、应用代码之间往返一圈，才得到最终回答。

先记住这条边界

LLM 不访问任何外部系统。它只输出 JSON 格式的调用请求；真正的函数执行、参数校验和服务调用都在你的应用代码里完成。

Step 1：定义工具（Tool Definition）

工具定义包含三要素：名称、描述、参数 Schema。

名称

模型用来指定调用哪个函数，例如 get_weather。

描述

模型据此判断何时使用该工具；描述质量影响工具选择准确率。

参数 Schema

约束参数类型、枚举和必填项，例如 city 必填。

Anthropic Claude 的工具定义 · 原文代码

tools = [
    {
        "name": "get_weather",
        "description": "获取指定城市的当前天气信息。当用户询问天气时使用此工具。",
        "input_schema": {
            "type": "object",
            "properties": {
                "city": {
                    "type": "string",
                    "description": "城市名称，如 'Beijing' 或 'New York'"
                },
                "unit": {
                    "type": "string",
                    "enum": ["celsius", "fahrenheit"],
                    "description": "温度单位"
                }
            },
            "required": ["city"]
        }
    }
]

Step 2–3：发送请求并获取 LLM 决策

应用把用户消息和工具定义一起发给模型。模型返回的不是普通文本，而是一个工具调用请求。

发送请求 · 原文代码

import anthropic

client = anthropic.Anthropic()
response = client.messages.create(
    model="claude-sonnet-4-5-20250929",
    max_tokens=1024,
    tools=tools,
    messages=[{"role": "user", "content": "北京现在多少度？"}]
)

# LLM 返回的不是文本，而是工具调用请求
# response.content[0].type == "tool_use"
# response.content[0].name == "get_weather"
# response.content[0].input == {"city": "Beijing", "unit": "celsius"}

Step 4：本地执行工具

应用解析 LLM 的请求，在自己的进程里执行函数。原文示例调用真实天气 API；本页只展示代码，不执行、不联网。

本地执行 · 原文代码

# 你的代码负责实际执行
def get_weather(city: str, unit: str = "celsius") -> dict:
    # 调用真实的天气 API
    result = weather_api.get(city=city, unit=unit)
    return {"temperature": result.temp, "condition": result.condition}

# 解析 LLM 的请求并执行
tool_call = response.content[0]
result = get_weather(**tool_call.input)
# result = {"temperature": 22, "condition": "sunny"}

Step 5：将结果返回 LLM

应用把工具结果作为 tool_result 发回模型，模型再基于结果生成自然语言回答。

返回结果 · 原文代码

# 将工具结果发回 LLM，让它生成最终回答
# 注意：Anthropic tool_result 的 content 推荐直接传 string
# 把 dict 用 json.dumps 序列化只是显式构造“展示给 LLM 的字符串”，并非协议要求
final_response = client.messages.create(
    model="claude-sonnet-4-5-20250929",
    max_tokens=1024,
    tools=tools,
    messages=[
        {"role": "user", "content": "北京现在多少度？"},
        {"role": "assistant", "content": response.content},
        {"role": "user", "content": [
            {
                "type": "tool_result",
                "tool_use_id": tool_call.id,
                "content": f"温度: {result['temperature']}°C, 天气: {result['condition']}",
            }
        ]}
    ]
)
# LLM 回答："北京现在气温 22°C，天气晴朗。"

OpenAI vs Anthropic 的实现差异

OpenAI 与 Anthropic 的 Function Calling 实现差异
维度OpenAIAnthropic
参数名tools（旧 functions 已 deprecated）tools
请求格式tool_calls 数组（旧 function_call 已废弃，2023-11 起改名）tool_use content block
结果返回role: "tool" 消息（旧 role: "function" 已废弃）tool_result content block
并行调用支持 parallel_tool_calls支持（多个 tool_use block）
Schema 格式JSON SchemaJSON Schema（input_schema）

核心流程相同，API 格式不同。LangChain 等框架提供了统一抽象层。注意：OpenAI 自 2023-11 起将 function_call / function role 重命名为 tool_calls / tool role，旧字段仍向后兼容但官方推荐迁移。

单次 vs 多次工具调用

LLM 可能在一次回复中请求多个工具调用（并行），也可能需要多轮对话中多次调用不同工具（顺序）：

# 并行调用：LLM 一次返回多个工具请求
# "比较北京和上海的天气"
# → tool_use: get_weather(city="Beijing")
# → tool_use: get_weather(city="Shanghai")

# 顺序调用（Agent Loop）：
# "查询订单状态并发送提醒邮件"
# Round 1: tool_use: get_order_status(order_id="123")
# Round 2: tool_use: send_email(to="user@example.com", subject="...")

Function Calling vs MCP

Function Calling 与 MCP 的对比
维度Function CallingMCP（Model Context Protocol）
定义方式每次 API 调用时传入标准化协议，一次定义复用
集成方式每个集成都是定制的统一接口，跨 Agent 复用
适用规模少量工具（<10）大量工具（10+）
维护成本每个工具独立维护集中管理、版本控制

常见误区 / 面试追问

四个容易被追问的点。

前两条是误区，后两条是常见追问；答案都来自原文。

误区 1

“LLM 直接执行了工具。”

LLM 只生成 JSON 格式的调用请求，实际执行完全在你的应用代码中。LLM 不访问任何外部系统。

误区 2

“Function Calling = Agent。”

Function Calling 是 Agent 的一个能力组件。Agent 还需要自主决策循环（Agent Loop）、记忆、规划等模块。单次 Function Calling 不构成 Agent。

追问 1

LLM 怎么知道该调用哪个函数？

主要依据工具的 description 字段。LLM 分析用户意图与工具描述的语义匹配度来选择工具。好的 description 是工具选择准确率的关键。

追问 2

如果 LLM 生成了错误的参数怎么办？

应该在执行前验证参数（Schema 验证）。始终将 LLM 输出视为不可信输入，在系统边界做验证。

中级 · Tool Use · 可交互讲解

Agent 不碰凭证，
请求先过门。

Tool Gateway 是 Agent 与工具之间的安全中间层。Agent 不直接调用工具，也不持有凭证；所有请求都经过 Gateway 做身份验证、权限检查、参数校验、速率限制和审计日志。权限用 Policy-as-Code 外部化，配合 RBAC / ABAC 做细粒度控制。

关键边界：Agent 是不可信请求者。权限检查必须在 Agent 外部执行，不能只写在 Agent 代码里；委托用户的权限也不能被 Agent 原样继承。

    为什么需要 Gateway

    Agent 直接拿凭证，
    风险不可控。

    没有 Gateway 的架构中，Agent 直接持有 API 密钥并调用外部服务。Prompt Injection、误操作和审计缺失都会变成真实事故。

    • Agent 被 Prompt Injection 操纵，调用不该调用的工具。
    • Agent 无意中执行破坏性操作，例如删除数据、发送未经审核的消息。
    • 无法追踪和审计 Agent 的行为。
    • 凭证暴露在 Agent 的上下文中。

    Gateway 架构

    每次调用，
    逐层拦截。

    Agent 不持有任何凭证，也不直接与基础设施 API 通信。Gateway 拦截每个请求，做鉴权、权限、校验、限流、执行、审计和结果过滤。

    Agent（LLM）发起工具调用请求，不持有任何凭证
    ↓请求
    Tool Gateway鉴权 · 输入验证 · 限流
    ↓evaluate()
    策略引擎（OPA / Cedar）按 agent、tool、params、context 做权限检查
    允许：放行执行工具 → 审计日志 → 结果过滤 → 返回脱敏结果
    拒绝：返回 {"error": "权限不足"}，不执行工具

    原文代码 · ToolGateway

    class ToolGateway:
    def __init__(self, policy_engine, rate_limiter, audit_logger):
        self.policy = policy_engine      # OPA / Cedar
        self.limiter = rate_limiter
        self.logger = audit_logger
        self.tools = {}                  # 注册的工具

    async def execute(self, agent_id: str, tool_name: str, params: dict) -> dict:
        # 1. 身份验证
        agent = await self.authenticate(agent_id)

        # 2. 权限检查
        decision = self.policy.evaluate({
            "agent": agent,
            "tool": tool_name,
            "params": params,
            "context": {"time": now(), "user": agent.delegated_user}
        })
        if not decision.allowed:
            self.logger.log_denied(agent_id, tool_name, decision.reason)
            return {"error": f"权限不足: {decision.reason}"}

        # 3. 输入验证
        validated = self.validate_input(tool_name, params)

        # 4. 速率限制
        if not self.limiter.allow(agent_id, tool_name):
            return {"error": "请求过于频繁，请稍后重试"}

        # 5. 执行工具
        result = await self.tools[tool_name].execute(validated)

        # 6. 审计日志
        self.logger.log_execution(agent_id, tool_name, params, result)

        # 7. 结果过滤（去除敏感信息）
        return self.filter_sensitive(result, agent.permission_level)

    参数校验的两级实现

    结构不对，
    值和语义也不对。

    validate_input 要挡两类问题：结构不对（缺字段、类型错、多出未声明字段）和语义不对（结构合法但值危险）。JSON Schema 只管第一类，第二类要单独写规则。

    第一级是 schema 校验。tool_call 的 arguments 是 JSON 字符串，不是对象，先 json.loads；解析失败本身就是一类错误，要和校验失败一样回灌给模型，不能抛异常打断循环。错误要写清哪个字段、期望什么、实际是什么；只回一句 argument validation failed 等于让模型猜。Schema 里加 additionalProperties: false，把模型编造出来的字段也拦下。

    原文代码 · validate_arguments

    import json

import jsonschema


def validate_arguments(tool_schema: dict, raw_args: str) -> list[dict]:
    """返回字段级错误列表，空列表表示通过"""
    try:
        args = json.loads(raw_args)      # arguments 是 JSON 字符串
    except json.JSONDecodeError as e:
        return [{
            "field": "<arguments>",
            "expected": "合法的 JSON 对象",
            "actual": raw_args[:80],
            "message": f"arguments 解析失败：{e.msg}（第 {e.pos} 个字符）",
        }]

    validator = jsonschema.Draft202012Validator(tool_schema)
    errors = []
    for err in validator.iter_errors(args):
        if err.validator == "required":
            missing = [k for k in err.validator_value if k not in err.instance]
            field, expected = ",".join(missing), "必填字段"
        else:
            field = ".".join(map(str, err.absolute_path)) or "<root>"
            expected = f"{err.validator} 约束: {err.validator_value!r}"
        errors.append({
            "field": field,
            "expected": expected,
            "actual": repr(err.instance)[:120],
            "message": err.message,
        })
    return errors

    第二级是语义校验。Schema 表达不了“这个路径在不在允许目录内”“这个 URL 指向哪里”。三类高频规则：路径先 os.path.realpath 解析，再用 os.path.commonpath 判断是否落在允许根目录内；URL 解析出主机名再解析成 IP，拒绝内网、回环、链路本地和云元数据地址 169.254.169.254；SQL 只放行单条只读语句。

    原文代码 · SemanticValidator

    import ipaddress
import os
import re
import socket
from urllib.parse import urlparse


class SemanticError(Exception):
    """语义校验失败，回灌时映射为 INVALID_ARGUMENT"""


class SemanticValidator:
    """schema 管结构，这里管 schema 表达不了的语义规则"""

    WRITE_SQL = re.compile(
        r"\b(INSERT|UPDATE|DELETE|REPLACE|DROP|ALTER|CREATE|TRUNCATE"
        r"|GRANT|REVOKE|ATTACH|PRAGMA|VACUUM)\b",
        re.IGNORECASE,
    )

    def __init__(self, allowed_roots: list[str]):
        self.allowed_roots = [os.path.realpath(r) for r in allowed_roots]

    def check_path(self, path: str) -> str:
        resolved = os.path.realpath(path)   # 展开 ../ 和符号链接
        for root in self.allowed_roots:
            try:
                if os.path.commonpath([root, resolved]) == root:
                    return resolved
            except ValueError:              # Windows 上不同盘符
                continue
        raise SemanticError(f"路径越界：{resolved}")

    def check_url(self, url: str) -> str:
        parsed = urlparse(url)
        if parsed.scheme not in ("http", "https"):
            raise SemanticError(f"协议不允许：{parsed.scheme}")
        if not parsed.hostname:
            raise SemanticError("URL 缺少主机名")
        try:
            infos = socket.getaddrinfo(parsed.hostname, None)
        except socket.gaierror as e:
            raise SemanticError(f"域名解析失败：{parsed.hostname}") from e
        for *_, sockaddr in infos:
            ip = ipaddress.ip_address(sockaddr[0].split("%")[0])
            if (ip.is_private or ip.is_loopback or ip.is_link_local
                    or ip.is_reserved or ip.is_multicast):
                raise SemanticError(f"目标地址不允许：{parsed.hostname} -> {ip}")
        return url

    def check_sql(self, sql: str) -> str:
        body = sql.strip().rstrip(";")
        if ";" in body:
            raise SemanticError("只允许单条 SQL 语句")
        if not re.match(r"^(SELECT|WITH|EXPLAIN)\b", body, re.IGNORECASE):
            raise SemanticError("只允许只读查询（SELECT / WITH / EXPLAIN）")
        if self.WRITE_SQL.search(body):
            raise SemanticError("检测到写操作关键字，拒绝执行")
        return body

    原文提醒

    校验和实际连接是两次解析，中间存在 DNS rebinding 空窗；重定向后的目标要重新走同一套校验。真正的出口控制要放在网络代理层，这一层负责快速拒绝。SQL 关键字匹配会误伤字符串字面量，生产上再配只读数据库账号兜底。

    结果回灌协议

    六字段，
    让模型知道怎么改。

    工具结果以 role="tool" 的消息回到模型上下文。结构决定模型能不能看懂失败原因、会不会做无效重试。

    status成功或失败
    data成功结果
    error_code稳定的机器码
    message给人看的一句话
    hint给模型的下一步建议
    retryable重试有没有意义

    tool_call_id 必须原样回填。并行调用时结果按 id 对齐，不能按返回顺序；顺序错位会让模型把 A 的结果当成 B 的，后续推理全错。

    三类工具错误对应的 error_code、模型动作和是否可重试
    错误类型典型 error_code模型该做什么retryable
    参数错误INVALID_ARGUMENT按 hint 改参数后重试true
    权限错误PERMISSION_DENIED换路径或上报，不要原样重试false
    执行错误TOOL_TIMEOUT / INTERNAL瞬态错误可重试，否则换方法视情况

    原文代码 · ToolResult

    import json
from dataclasses import dataclass


@dataclass
class ToolResult:
    tool_call_id: str
    status: str                      # "ok" | "error"
    data: dict | None = None
    error_code: str | None = None
    message: str | None = None
    hint: str | None = None
    retryable: bool = False

    def to_message(self) -> dict:
        """构造回灌给模型的 tool 消息"""
        payload = {"status": self.status, "data": self.data}
        if self.status == "error":
            payload.update({
                "error_code": self.error_code,
                "message": self.message,
                "hint": self.hint,
                "retryable": self.retryable,
            })
        return {
            "role": "tool",
            "tool_call_id": self.tool_call_id,   # 与请求一一对应
            "content": json.dumps(payload, ensure_ascii=False),
        }


# 参数错误：模型读 hint 后改参数重试
ToolResult(

    hint="start_date 需要 YYYY-MM-DD，例如 2026-10-01",
    retryable=True,
)

# 权限错误：重试没有意义，换路径或上报
ToolResult(
    tool_call_id="call_def",
    status="error",
    error_code="PERMISSION_DENIED",
    message="agent 无权读取 /etc/secrets",

    retryable=False,

    大结果不要直接塞回上下文。超过阈值（经验值几千字符，按模型上下文预算调整）就存到外部，只回引用 id 加一句话摘要；模型需要细节时再调 fetch_result 取。

    原文代码 · ResultPacker

    MAX_INLINE_CHARS = 8_000  # 经验值，按模型上下文预算调整


class ResultPacker:
    def __init__(self, store):
        self.store = store

    async def pack(self, tool_call_id: str, raw: str) -> ToolResult:
        if len(raw) <= MAX_INLINE_CHARS:
            return ToolResult(tool_call_id, "ok", data={"content": raw})

        ref_id = await self.store.put(raw)
        return ToolResult(
            tool_call_id,
            "ok",
            data={"ref_id": ref_id, "preview": raw[:500]},
            hint=f"结果过长已存为 {ref_id}，需要细节时调用 fetch_result(ref_id)",
        )

    权限模型

    RBAC 管角色，
    ABAC 管上下文。

    RBAC 按角色给工具集合；ABAC 进一步看请求属性，例如时间、客户归属、人工审批状态。两者组合才能表达“谁在什么条件下能做什么”。

    委托授权

    Agent 的权限不应超过委托它的用户：Agent 的权限等于 min(Agent 角色权限, 委托用户权限)，两者都允许才放行。

    原文代码 · DelegatedAuth

    class DelegatedAuth:
    def check(self, agent: Agent, tool: str, params: dict) -> bool:
        # Agent 的权限 = min(Agent 角色权限, 委托用户权限)
        agent_allowed = self.check_agent_role(agent.role, tool)
        user_allowed = self.check_user_permission(agent.delegated_user, tool)

        # 两者都允许才放行
        return agent_allowed and user_allowed

    关键原则：人类用户常常被过度授权，Agent 的权限应该独立审查，不能简单继承用户的全部权限。上面的权限矩阵演示了这一点：把委托用户改成“只读”后，即使是 admin_agent，写工具也会被拒绝。

    Human-in-the-Loop 审批

    高风险工具，
    暂停等一个“人”。

    审批 Gateway 在高风险工具执行前暂停，向人发起审批请求；拒绝就返回原因，批准才继续调用底层 Gateway。

    原文代码 · ApprovalGateway

    class ApprovalGateway:
    HIGH_RISK_TOOLS = ["send_email", "delete_record", "transfer_funds"]

    async def execute_with_approval(self, agent_id, tool, params):
        if tool in self.HIGH_RISK_TOOLS:
            # 暂停执行，等待人工审批
            approval_request = await self.request_human_approval(
                agent_id=agent_id,
                tool=tool,
                params=params,
                timeout=300  # 5 分钟超时
            )
            if not approval_request.approved:
                return {"error": "操作被人工拒绝", "reason": approval_request.reason}

        return await self.gateway.execute(agent_id, tool, params)

    超时必须有明确的默认行为：默认拒绝还是默认放行，要在策略里预先声明，不能留给实现临时决定。审批记录也要进入审计日志。

    多 Agent 场景

    委托链上，
    权限不能放大。

    多 Agent 工作流中，Agent A 可能把任务委托给 Agent B。B 的权限不应超过 A，完整委托链需要被追踪。

    原文代码 · DelegationChain

    # 委托链追踪
class DelegationChain:
    def validate_delegation(self, from_agent, to_agent, tool):
        # to_agent 的权限不能超过 from_agent
        if not self.is_subset(to_agent.permissions, from_agent.permissions):
            raise PermissionError("被委托 Agent 权限不能超过委托者")

    这条规则和委托授权是同一条原则的延伸：权限只能沿着委托链收缩，不能放大。

    运行时护栏与治理

    权限之外，
    还有内容和发布。

    权限控制决定“能不能调”，运行时护栏还要看“输入和输出里有什么”。治理流水线则把策略更新当成软件发布来管理。

    输入护栏：扫描用户输入是否有恶意意图、越狱尝试、PII
    ↓ Agent 处理 ↓
    输出护栏：验证 Agent 输出是否有幻觉、毒性内容、敏感数据

    治理流水线模式

    1. 安全 / 法律团队编写策略，翻译为机器可读代码。
    2. 对历史日志做影响分析，也就是模拟部署。
    3. 确认无误后自动部署到全部 Agent。

    新动向 · Agent SDK 2026-08

    上下文由宿主供给，
    默认工具面收窄。

    2026-08 Claude Agent SDK 的几次发布，把“Agent 视为不可信”和“最小权限”落进了默认行为。三条变更指向同一方向：权限决策所需的上下文由宿主供给，默认可用的工具面同时收窄。

    classifierContext（v0.3.236，2026-08-19）

    PostToolUse hook 可返回一段工具结果注释，auto 模式下的权限分类器会连同工具结果一起读取。关键在谁在断言：Agent 可以被 Prompt Injection 操纵去声称“操作是安全的”，但无法伪造 hook 的返回值；hook 跑在宿主进程里，读的是宿主自己掌握的事实。

    信任根仍在宿主侧，和 Gateway 思路同构：判定权不在 Agent 手里，判定上下文从“Gateway 自己查”扩展为“宿主主动喂”。

    Todo / 任务追踪工具移出默认工具面（v0.3.233，2026-08-14，BREAKING）

    Opus 4.8、Sonnet 5、Fable 5、Mythos 5 及更新模型上，TaskCreate / TodoWrite 等工具不再默认可用，须显式列入 allowedTools 或设 CLAUDE_CODE_ENABLE_TODO_TOOLS=1。方向与最小权限一致：默认工具面越小，Gateway 要防的攻击面越小；从没被授予的工具，不存在被诱导调用的可能。

    peer origin 声明权限等级（v0.3.234，2026-08-17）

    宿主注入的对端来源标识可携带 fromMode 字段声明发送方权限等级；同等级消息投递给免询问运行的接收方时不再逐条打断。这是“委托授权”的工程化形态：权限等级显式携带并校验，而不是靠接收方猜测。

    原文判断

    三条放在一起：Agent 运行时正把“谁有权做什么”的决策权和上下文供给权系统性推给宿主。落到 Gateway 设计上，宿主侧 hook 逻辑本身成了安全边界的一部分——它和 Gateway 一样需要审计、版本控制和影响分析，不能当成随手写的业务回调。

    常见误区 / 面试追问

    七个容易
    被追问的点。

    前两条是误区，后五条是面试追问；答案都来自原文。

    误区 1

    “在 Agent 代码里做权限检查就够了。”

    Agent 代码可能被 Prompt Injection 绕过。权限检查必须在 Agent 外部，也就是 Gateway 层执行，作为独立的安全边界。

    误区 2

    “给 Agent 和用户一样的权限。”

    用户常常被过度授权。Agent 应该只获得完成当前任务所需的最小权限集。

    追问 1

    Policy-as-Code 有什么好处？

    第一，授权逻辑与应用代码分离，安全团队可以独立管理；第二，策略可以版本控制和审计；第三，策略变更不需要重新部署应用代码。

    追问 2

    AWS Bedrock 的 Policy 和自建 Gateway 有什么区别？

    云服务商的方案（如 Bedrock AgentCore Policy）在 Agent 代码外部执行安全控制，开箱即用但绑定生态。自建 Gateway 更灵活但需要维护，适合多云或自托管场景。

    追问 3

    classifierContext 让宿主给权限决策注入上下文，会不会削弱“Agent 不可信”的假设？

    恰恰相反。要点是区分谁在断言：classifierContext 由 PostToolUse hook 返回，hook 运行在宿主进程里，Agent 无法伪造；分类器读到的是宿主基于自身事实的断言，不是 Agent 的自述，信任根仍在宿主侧。追问延伸：hook 成了安全判定的输入源，它自己就变成新攻击面，需按 Gateway 同等标准做审计和变更管控；若 hook 里拼接 Agent 可控的字符串塞进 classifierContext，等于给注入开后门。

    追问 4

    MCP Server 场景下工具级权限怎么做？

    Claude Agent SDK（TS）v0.3.301（2026-10）起，sdk-type MCP server 配置支持 per-tool permission_policy（always_ask / always_deny，initialize 与 setMcpServers 均生效）。工具级准入原则下沉为 MCP server 的原生配置面，宿主无需在调用层逐一拦截。

    追问 5

    JSON Schema 校验通过，参数就一定安全吗？

    不一定。Schema 只约束结构和类型，管不了值的语义：/data/../etc/passwd 满足 type: string，http://169.254.169.254/latest/meta-data/ 满足 format: uri。路径、URL、SQL 这类规则必须单独写语义校验，Schema 通过只是第一级。

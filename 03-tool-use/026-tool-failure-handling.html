中级 · Tool Use · 可交互讲解

失败不可怕，
无限等待才可怕。

工具调用失败在生产里是常态：超时、限流、参数错误、服务宕机都会发生。处理顺序是分层防御：先设超时，再对瞬时错误做指数退避重试，持续失败交给断路器，主工具不可用就降级，最后把可操作的错误信息回传给 LLM。

关键原则：永远不要让 Agent 无限等待或无限重试。本页的故障轨迹、退避时间和状态机都是固定教学数据，不连接任何真实服务。

      失败模式

      失败来自五层，
      不只来自网络。

      定位失败先分层：网络、服务、输入、执行、Agent。不同层的处理方式不同，把参数错误当网络错误重试，只会浪费预算。

      工具调用五类失败来源与典型表现
      层级典型失败是否值得重试
      网络层超时、DNS 解析失败、连接拒绝通常可以，配合退避
      服务层HTTP 4xx、5xx、429 限流5xx 与 429 可以；400/401/403 不行
      输入层参数不符合 Schema、类型错误、值越界不重试，让 LLM 修正参数
      执行层工具内部 bug、未处理边界不重试，修工具
      Agent 层无限循环、重复调用失败工具不重试，触发循环防护

      策略 1

      每个外部调用，
      都要有截止时间。

      超时是其他所有策略的前提。没有超时，重试、熔断和降级都没有机会执行。

      async def call_external_api(url: str, params: dict, timeout: float = 10.0):
    try:
        async with httpx.AsyncClient() as client:
            response = await client.get(url, params=params, timeout=timeout)
            response.raise_for_status()
            return {"status": "success", "data": response.json()}
    except httpx.TimeoutException:
        return {"status": "error", "error": "请求超时，服务可能暂时不可用"}
    except httpx.HTTPStatusError as e:
        return {"status": "error", "error": f"HTTP {e.response.status_code}"}

      除了单次工具超时，Agent Loop 也要有整体预算。原文的配置示例是：最大 10 步、整体 120 秒、单次工具 30 秒。三个数字分别防“无限步数”“无限总时长”“单个工具挂死”。

      agent_config = {
    "max_iterations": 10,        # 最大步数，防止无限循环
    "max_execution_time": 120,   # 整体超时（秒）
    "single_tool_timeout": 30,   # 单次工具调用超时
}

      策略 2

      退避不是等待，
      是给服务恢复的时间。

      瞬时错误才重试，而且不能立即重试。指数退避把间隔逐次拉长，jitter 把并发请求打散。

      async def retry_with_backoff(func, max_retries=3, base_delay=1.0):
    for attempt in range(max_retries):
        try:
            return await func()
        except TransientError:
            if attempt == max_retries - 1:
                raise
            delay = base_delay * (2 ** attempt) + random.uniform(0, 1)
            await asyncio.sleep(delay)
            # attempt=0,1,2 → 等待 ~1-2s, ~2-3s, ~4-5s

      页面演练台为了可复算，把 random.uniform(0, 1) 换成固定 jitter 0.4、0.7、0.3。公式仍是 1.0 × 2^attempt + jitter，所以三次等待分别是 1.4、2.7、4.3 秒。

      重试决策矩阵：不同错误类型是否重试
      错误类型是否重试原因
      网络超时是瞬时问题
      HTTP 429（限流）是（按 Retry-After）等待后可恢复
      HTTP 500是（有限次）服务可能临时异常
      HTTP 400（参数错误）否重试不会改变结果
      HTTP 401 / 403否权限问题，重试无意义
      Schema 验证失败否（可让 LLM 重新生成参数）需要修正输入

      策略 3

      持续失败时，
      先停下来，再试探。

      重试处理偶发故障，断路器处理持续故障。失败达到阈值就打开，冷却期满转半开，试探成功才恢复。

      CLOSED 正常

      请求正常通过，记录失败次数。这是初始状态。

      OPEN 熔断

      所有请求立即拒绝，进入冷却期，不再打到下游。

      HALF-OPEN 试探

      冷却期满后允许少量请求通过，测试服务是否恢复。

      状态迁移：CLOSED →（失败次数 ≥ 阈值）→ OPEN →（冷却期满）→ HALF-OPEN →（试探成功）→ CLOSED；HALF-OPEN →（试探再失败）→ OPEN。

      class CircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=60):
        self.failures = 0
        self.threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.state = "closed"       # closed → open → half_open
        self.last_failure_time = None

    async def call(self, func):
        if self.state == "open":
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = "half_open"
            else:
                return {"error": "服务暂时不可用（断路器打开）"}
        try:
            result = await func()
            if self.state == "half_open":
                self.state = "closed"
                self.failures = 0
            return result
        except Exception:
            self.failures += 1
            self.last_failure_time = time.time()
            if self.failures >= self.threshold:
                self.state = "open"
            raise

    state "Closed 正常放行" as closed
    state "Open 熔断拒绝" as open

      断路器的计数必须放在工具外面。工具函数执行完就销毁，状态跟着没了；每次调用都从零计数，等于没装断路器。

      策略 4 与 5

      主路断了，
      还有备用路和说明。

      降级不是掩盖失败，而是用更弱但可用的结果兜底。错误回传也不是把异常原样抛出，而是给 LLM 可执行的下一步。

      原文示例 · 双工具降级

      class ToolWithFallback:
    def __init__(self, primary_tool, fallback_tool):
        self.primary = primary_tool
        self.fallback = fallback_tool

    async def execute(self, params):
        try:
            return await self.primary.execute(params)
        except ToolError:
            return await self.fallback.execute(params)

      更完整的降级链依次是：主工具 → 简化版工具 → 缓存数据 → 向用户解释。每一级都要带上“这是降级结果”的标记，不能让上层把旧缓存当成实时数据。

      原文示例 · 错误回传 LLM

      # 差：吞掉错误
except Exception:
    return None  # Agent 不知道发生了什么

# 好：返回可操作的错误信息
except Exception:
    return {
        "status": "error",
        "error_type": "timeout",
        "message": "天气 API 超时，可能是服务暂时不可用",
        "suggestion": "可以尝试使用 search_web 工具搜索天气信息作为替代"
    }

      Agent 收到错误后有三条路：修正参数重试、换替代工具、直接告知用户。错误里要给 error_type 和 suggestion，否则模型只能猜。

      防无限循环

      检测到重复，
      先提示，再禁用，最后止损。

      只设最大步数不够。还要检测同一工具连续调用、相同参数重复调用、参数变了但状态没进展，以及 A→B→A→B 这类周期。

      基础版是 max_iterations 加每个工具的调用计数。更细的三级检测是：总步数超限、同一工具连续调用过多、完全相同的参数重复调用。检测到后不要直接报错，先注入“请换一种方式”的提示，给模型一次纠正机会。

      class LoopDetector:
    def __init__(self, max_steps=15, max_same_tool=3, max_same_params=2):
        self.max_steps = max_steps
        self.max_same_tool = max_same_tool
        self.max_same_params = max_same_params
        self.history = []

    def check(self, tool_call) -> tuple[bool, str]:
        self.history.append(tool_call)
        if len(self.history) >= self.max_steps:
            return False, f"已达到最大步数限制 ({self.max_steps})"
        recent = [c for c in self.history[-5:] if c.name == tool_call.name]
        if len(recent) >= self.max_same_tool:
            return False, f"工具 {tool_call.name} 连续调用 {self.max_same_tool} 次"
        same = [c for c in self.history if c.name == tool_call.name and c.params == tool_call.params]
        if len(same) >= self.max_same_params:
            return False, f"工具 {tool_call.name} 使用相同参数调用了 {self.max_same_params} 次"
        return True, ""

      直接比较 params 不可靠：dict 不能进 set，0.1 和 0.10 会被判成不同值，同一路径的不同写法也算不同参数。原文先做规范化（key 排序、浮点精度、路径标准化），再对 (tool_name, normalized_args) 做哈希。

      参数哈希抓不到“参数变了但没进展”。状态指纹用“已完成子目标 + 工作区文件哈希 + 最近 K 条结果摘要”组成，相邻两轮相同就判无进展。周期检测则在最近 N 步的序列里找 n-gram 重复，专门抓 A→B→A→B。

      检测到重复后的四级处理
      级别动作目的
      第 1 次注入提示，附上上次结果提示模型“已试过”，省一次调用
      第 2 次本轮禁用该工具，要求解释原因强迫换路径
      第 3 次终止，返回已完成部分和卡点止损，交给人
      错误累积回退到 checkpoint 换方案通常由人工决定

      第一级的关键是把上次结果再贴一遍。模型重复调用，常常是因为上下文里只有“已调用”没有“结果”，它以为数据没拿到。

      组合起来

      请求先过三道闸，
      失败再走两条退路。

      生产级链路不是“失败就重试”，而是断路器、限流、重试三道闸依次拦截；执行失败后走降级，并把错误回传 LLM。

      断路器 · 挡持续失败→速率限制→重试 + 指数退避 · 只重试瞬时错误→工具执行
      成功 → 返回结果←执行结果直接回到 Agent
      失败 → 降级回退 · 备用工具 / 缓存→错误信息回传 LLM · 自主调整策略

      顺序有讲究：熔断在最前面，已打开时请求根本不会消耗重试预算；限流在重试前，避免重试把配额打爆；重试最靠近工具，因为它处理的是单次调用的瞬时故障。

      延迟与结果治理

      串行会放大延迟，
      大结果会挤爆上下文。

      三步串联的延迟是线性叠加；能并行的工具就并行。工具返回的大结果要截断或外置，否则重试一次就多付一次上下文成本。

      原文的延迟构成示例：LLM 选工具 0.5–2 秒，工具执行 0.1–5 秒，LLM 看结果 0.5–2 秒，单步合计 1.1–9 秒；三步串联就是 3.3–27 秒。这些是原文示例区间，不是本页实测。

      收益最大的优化是并行化：无数据依赖的 N 步从 N×T 降到 max(T)。其次是缓存（对重复查询有效）和流式中间结果（改善用户感知延迟）。

      大结果的三条截断规则：头尾都保留，中间标注省略行数；JSON 长数组留前 10 项并给出总数；日志默认只留 WARN / ERROR。单条结果控制在上下文窗口 15% 以内是原文的经验值，超出部分外置存储，回灌引用 id 和摘要。

      写操作重试还要考虑幂等。超时不等于没写成功：捕获瞬时错误后返回 unknown，让上层先查状态，比盲目重发安全。幂等键用 run_id + tool_name + 参数哈希；下游不支持幂等键时，用“先查后写”。

      常见误区 / 面试追问

      十个高频问题，
      先答结论再补条件。

      前两个是误区，后八个是追问。场景题按“先止损、再换路、最后补防护”的顺序答。

      误区 1

      “所有错误都应该重试。”

      只有瞬时错误（超时、429、5xx）才值得重试。参数错误 400、权限错误 401/403 重试不会改变结果，反而浪费资源和上下文窗口。

      误区 2

      “重试应该立即执行。”

      立即重试会加剧服务压力。使用指数退避加随机 jitter 分散请求；对 429 错误遵循 Retry-After 头。

      追问 1

      如何防止 Agent 在工具失败时陷入无限循环？

      三层防护：最大步数硬限制、相同参数重复检测、全局超时。检测到循环后先注入“请换一种方式”的提示，给 LLM 一次纠正机会；再升级到禁用工具和终止。

      追问 2

      工具编排的延迟优化，哪个策略收益最大？

      并行化。串行 3 步变并行后，延迟从 3T 降到 max(T)。其次是缓存和流式中间结果。

      追问 3

      断路器和重试有什么区别？

      重试是单次失败后的短期策略，处理偶发故障；断路器是多次失败后的长期保护，处理持续故障。两者组合使用：断路器内部包含重试逻辑。

      追问 4

      Agent 反复调用 search_web 但结果都不满足，Token 不断涨，怎么修？

      先限次数，超过后强制换策略；再改返回格式，明确告知“已搜索 X 次，无相关结果”；加查询反思，判断是太宽还是太窄；准备知识库检索等降级路径；多次失败后请用户介入。

      追问 5

      工具调用成功但返回格式与 LLM 期望不符，导致解析错误并重试，怎么办？

      这是“成功但失败”。Schema 要定义输出格式；工具内部先做输出验证；返回时附示例；LLM 端做容错解析；不稳定的外部 API 加 Wrapper 统一格式。

      追问 6

      数据库查询工具因参数注入被封禁，如何防范和恢复？

      防范：严格参数验证与转义、最小权限、查询模板禁止动态拼 SQL、速率限制、异常查询监控。恢复：启用备用连接、切只读、联系厂商解封、事后分析攻击来源。

      追问 7

      相同参数检测为什么不能直接比较 dict？

      dict 不可哈希，不能进 set 或当缓存键；0.1 与 0.10 会被判成不同值；同一路径的不同写法也会被当成不同参数。要先规范化再哈希；参数哈希还抓不到“参数变了但没进展”，要补状态指纹。

      追问 8

      写操作重试时如何避免重复执行？

      优先“先查后写”：重试前查目标状态，已完成就复用结果。下游支持幂等键时，用 run_id + tool_name + 参数哈希；超时返回“结果未知”时不要盲目重发，标成 unknown 交给上层确认。

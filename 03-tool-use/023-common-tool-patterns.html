基础 · Tool Use · 可交互讲解

先看风险，
再选模式。

工具使用可以分成三类模式：数据访问（API、SQL、向量检索）、计算与代码执行（沙箱里跑代码）、写操作与动作执行（发邮件、建工单、改数据库）。读操作相对安全；写操作会改变外部状态，需要严格的权限控制、确认机制和审计。

关键边界：风险等级由“会造成什么后果”决定，不是由“是不是写操作”简单二分。创建草稿不改对外状态，可以自动放行；发送邮件不可撤回，必须人工审批。

      三大类模式

      数据、计算、
      动作。

      数据访问负责取信息，代码执行负责算和处理，写操作负责改变外部状态。前两类主要防“取错、算错”，第三类还要防“做错且收不回”。

      数据访问API 调用、SQL 查询、向量检索。重点是超时、返回值精简、注入防护和数据敏感度。
      计算与代码执行在沙箱中运行代码做数据处理、计算或可视化。重点是真正的进程 / 容器隔离和资源限制。
      写操作与动作执行发邮件、创建工单、修改数据库。重点是权限控制、人工审批、幂等和审计。

      模式 1 · API 调用

      拿外部实时数据，
      别把整包响应塞回去。

      最常见的工具类型：让 Agent 调用外部 REST API 获取实时数据。设计重点是超时、精简返回值和有意义的错误信息。

      原文代码 · 股票价格工具

      # 工具定义
{
    "name": "get_stock_price",
    "description": "获取股票的实时价格。输入股票代码（如 AAPL, GOOGL）。",
    "input_schema": {
        "properties": {
            "symbol": {"type": "string", "description": "股票代码"},
            "market": {"type": "string", "enum": ["US", "HK", "CN"]}
        },
        "required": ["symbol"]
    }
}

# 工具实现
import httpx

async def get_stock_price(symbol: str, market: str = "US") -> dict:
    async with httpx.AsyncClient() as client:
        response = await client.get(
            f"https://api.stockdata.com/v1/quote",
            params={"symbol": symbol, "market": market},
            headers={"Authorization": f"Bearer {API_KEY}"},
            timeout=10.0  # 超时设置
        )
        response.raise_for_status()
        data = response.json()
        return {
            "symbol": symbol,
            "price": data["price"],
            "change": data["change_percent"],
            "timestamp": data["timestamp"]
        }

      设计要点：设置合理超时，避免 Agent 卡住；返回值精简，不要把整个 API 响应扔给 LLM；错误信息要有意义，让 LLM 能根据错误决定下一步。代码里的 API_KEY 是占位符，生产环境应从密钥管理服务注入。

      模式 2 · 数据库查询

      Text-to-SQL，
      还是预定义查询。

      让 Agent 用自然语言查询数据库有两种实现：让它生成 SQL，或者只提供经过人工验证的固定查询。灵活性和安全性在这里直接冲突。

      方式 A：Text-to-SQL

      原文代码 · 先看表，再看结构，再查询

      # 给 Agent 提供数据库 Schema，让它生成 SQL
tools = [
    {
        "name": "list_tables",
        "description": "列出数据库中所有表名",
    },
    {
        "name": "get_table_schema",
        "description": "获取指定表的列定义",
        "input_schema": {"properties": {"table_name": {"type": "string"}}}
    },
    {
        "name": "execute_sql",
        "description": "执行只读 SQL 查询并返回结果。仅支持 SELECT 语句。",
        "input_schema": {"properties": {"query": {"type": "string"}}}
    }
]

# Agent 的工作流：
# 1. list_tables() → 了解有哪些表
# 2. get_table_schema("orders") → 了解表结构
# 3. execute_sql("SELECT ... FROM orders WHERE ...") → 查询数据

      方式 B：预定义查询工具

      原文代码 · 参数化查询

      # 不让 LLM 写 SQL，而是提供预定义的查询工具
{
    "name": "get_order_status",
    "description": "根据订单号查询订单状态",
    "input_schema": {
        "properties": {
            "order_id": {"type": "string"},
        }
    }
}

def get_order_status(order_id: str) -> dict:
    # 内部执行参数化 SQL，防止注入
    result = db.execute(
        "SELECT status, updated_at FROM orders WHERE id = %s",
        [order_id]
    )
    return {"order_id": order_id, "status": result.status}
      Text-to-SQL 与预定义查询在灵活性、安全性、准确性和适用场景上的对比
      维度Text-to-SQL预定义查询
      灵活性高：任意查询低：固定查询
      安全性低：SQL 注入风险高：参数化查询
      准确性中：LLM 可能写错 SQL高：人工验证过
      适用场景数据探索、分析生产环境、敏感数据

      原文的判断很明确：生产环境中让 LLM 直接写 SQL 极其危险，推荐预定义查询工具加参数化查询，除非是面向数据分析师的内部工具。

      模式 3 · 代码执行

      沙箱靠隔离，
      不靠黑名单。

      让 Agent 在沙箱中运行代码，用于计算、数据处理或可视化。安全的关键是进程或容器隔离，而不是禁止几个字符串。

      原文代码 · run_python

      {
    "name": "run_python",
    "description": "在安全沙箱中执行 Python 代码。可用库：pandas, numpy, matplotlib。用于数据分析、计算和图表生成。",
    "input_schema": {
        "properties": {
            "code": {"type": "string", "description": "Python 代码"},
        },
        "required": ["code"]
    }
}

import subprocess
import tempfile

def run_python(code: str) -> dict:
    """在隔离环境中执行代码。

    重要：不要用"子串黑名单"做沙箱（如禁止 'os.system'、'eval(' 等）——
    这是被广泛证伪的反模式。攻击者可以用 getattr/__import__('os')/字符串拼接/
    base64/exec(compile(...)) 等任意手法绕过。真正的沙箱必须依赖**进程/容器隔离**
    （Docker、gVisor、E2B/Modal/Daytona 等 Runtime）+ seccomp + 无网络/无文件系统。
    """
    # 注：Windows 上 NamedTemporaryFile 默认独占锁会让子进程读不到文件，
    # 跨平台写法应该用 delete=False + 手动 unlink，或 mkstemp。
    with tempfile.NamedTemporaryFile(suffix=".py", mode="w", delete=False) as f:
        f.write(code)
        f.flush()
        # 仅作为本地 demo：生产应换成 E2B / Modal / Daytona 等隔离 Runtime
        result = subprocess.run(
            ["docker", "run", "--rm", "--network=none",
             "--memory=512m", "--cpus=1",
             "-v", f"{f.name}:/code.py:ro",
             "python:3.12-slim", "python", "/code.py"],
            capture_output=True, text=True,
            timeout=30,
        )
    return {
        "stdout": result.stdout[:2000],  # 截断防止 token 爆炸
        "stderr": result.stderr[:500],
        "returncode": result.returncode
    }

      安全要点：真隔离要用 Docker、gVisor、Firecracker、V8 Isolate 这类机制，而不是子串黑名单；设置 CPU、内存和时间限制；禁止网络访问，除非明确需要；禁止文件系统写入或限制路径；生产环境推荐 E2B、Modal、Daytona、Cloudflare Workers 这类专用沙箱 Runtime。

      模式 4 · 写操作

      改变外部状态，
      就要有审批边界。

      写操作会改变外部系统的状态，最需要谨慎。低风险写操作可以先创建草稿；高风险写操作必须人工审批，并保留可审计的前后状态。

      原文代码 · 草稿、发送与 Read-Before-Write

      # 低风险写操作：创建草稿
{
    "name": "create_draft_email",
    "description": "创建邮件草稿（不会发送）。创建后用户需确认才会发送。",
}

# 高风险写操作：直接发送
{
    "name": "send_email",
    "description": "发送邮件。这是不可逆操作，务必在调用前确认收件人和内容正确。",
}

# Read-Before-Write 模式
async def update_record(record_id: str, updates: dict):
    # 1. 先读取当前状态
    current = await db.get(record_id)
    # 2. 验证更新是否合理
    if not validate_update(current, updates):
        return {"error": "更新不合理，请检查"}
    # 3. 执行更新
    await db.update(record_id, updates)
    return {"status": "updated", "previous": current, "current": updates}

      边界提醒

      描述里写“请确认”不等于系统真的审批了。写操作的权限校验、人工审批、幂等和审计必须在执行层或 Gateway 层实现；模型输出的 confirmation 字段只能作为一道结构提示。

      各类工具的风险等级

      五类工具模式的风险等级、是否需要确认和示例
      模式风险需要确认？示例
      API 读取低否天气、股价查询
      数据库读取低到中视数据敏感度查询订单状态
      代码执行中视场景数据分析、计算
      API 写入高是发邮件、创建工单
      数据库写入高是修改 / 删除记录

      返回值设计

      够用就好，
      别把日志当结果。

      返回太多数据浪费 token，还可能干扰 LLM 判断；返回太少则 LLM 无法做正确决策。原文的建议是“关键信息加下一步提示”。

      原文代码 · 差返回与好返回

      # 差的返回：原始 API 响应（太长，浪费 token）
return api_response.json()  # 可能有 KB 级数据

# 好的返回：精简、结构化、有上下文
return {
    "status": "success",
    "data": {
        "order_id": "12345",
        "status": "shipped",
        "tracking_url": "https://..."
    },
    "hint": "如果用户需要更多详情，可以使用 get_order_details 工具"
}

      “有下一步提示”不等于让工具替 Agent 做决策；它只是告诉模型还有哪些可用动作，是否调用仍由 Agent Loop 决定。

      常见误区 / 面试追问

      四个容易
      被追问的点。

      前两条是误区，后两条是面试追问；答案都来自原文。

      误区 1

      “让 LLM 直接写 SQL 很方便。”

      在生产环境中极其危险。LLM 可能生成恶意 SQL 或写错 SQL。推荐预定义查询工具加参数化查询，除非是面向数据分析师的内部工具。

      误区 2

      “代码执行不需要沙箱。”

      即使 Agent 没有代码解释器，LLM 生成的任何字符串用于系统调用前都应视为不可信输入。必须做输入验证、容器隔离和运行时监控。

      追问 1

      如何处理工具链，一个工具的结果是另一个的输入？

      用 Agent Loop：LLM 调用工具 A，观察结果，再决定是否需要调用工具 B。不要在工具之间硬编码依赖。

      追问 2

      工具的返回值应该多详细？

      够用就好。返回太多数据浪费 token，且可能干扰 LLM 判断；返回太少则 LLM 无法做出正确决策。关键信息加下一步提示是最佳实践。

基础 · Tool Use · 可交互讲解

把工具说明白，
模型才选得对。

工具 Schema 用 JSON Schema 定义三要素：名称是唯一标识符，描述告诉 LLM 何时以及如何使用，参数定义输入的类型、约束和必填项。描述是最关键的字段，它直接影响工具选择准确率。

关键边界：名称只是标识符，描述才是选择依据。描述要同时写清“做什么、何时用、何时不用、和相似工具的区别”；参数则负责执行前的结构校验。

      三要素

      名称、描述、
      参数。

      名称负责唯一标识，描述负责让模型选对，参数负责让执行层能校验。三者缺一，工具定义就不完整。

      原文 JSON · 一个完整的工具定义

      {
  "name": "search_knowledge_base",
  "description": "在内部知识库中搜索技术文档。当用户询问产品功能、API 文档或技术规范时使用此工具。不要用于搜索客户订单或财务数据。",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "搜索关键词或自然语言问题"
      },
      "category": {
        "type": "string",
        "enum": ["api_docs", "user_guide", "release_notes"],
        "description": "文档类别，缩小搜索范围"
      },
      "max_results": {
        "type": "integer",
        "description": "返回的最大结果数量",
        "default": 5
      }
    },
    "required": ["query"]
  }
}

      这段定义里，description 同时写了“做什么”和“何时使用”，还写了“不要用于订单或财务数据”的排除条件；input_schema 则给出字符串、枚举、整数默认值和必填项。

      高质量描述

      差一个词，
      就可能选错工具。

      描述是 LLM 选择工具的核心依据。差的描述导致错误的工具选择，最后得到错误的结果。

      原文代码 · 差描述与好描述的对比

      # 差的描述
{"name": "search", "description": "搜索东西"}
# 问题：搜什么？什么时候用？什么时候不用？

# 好的描述
{
    "name": "search_product_catalog",
    "description": (
        "在产品目录中搜索产品信息，包括名称、价格、库存和规格。"
        "当用户询问产品详情、价格比较或库存查询时使用此工具。"
        "不适用于搜索订单状态或用户账户信息——请使用 query_orders 或 get_user_profile。"
    )
}

      高质量描述的检查清单

      1. 说明工具做什么，也就是功能。
      2. 说明什么时候应该使用，也就是触发条件。
      3. 说明什么时候不该使用，也就是排除条件。
      4. 如果有相似工具，说明区别。

      原文判断

      名称只是标识符，描述才是 LLM 决定是否使用工具的核心依据。名称起得再漂亮，描述含糊仍然会选错。

      JSON Schema 丰富特性

      用约束
      减少歧义。

      类型之外，Schema 还能表达枚举、默认值、范围、格式、嵌套对象、数组和必填项。约束越明确，模型越不容易填出执行层无法处理的参数。

      原文 JSON · 嵌套、枚举、范围与数组

      {
  "type": "object",
  "properties": {
    "date_range": {
      "type": "object",
      "properties": {
        "start": {"type": "string", "format": "date", "description": "起始日期 YYYY-MM-DD"},
        "end": {"type": "string", "format": "date", "description": "结束日期 YYYY-MM-DD"}
      },
      "required": ["start", "end"]
    },
    "status": {
      "type": "string",
      "enum": ["pending", "completed", "cancelled"],
      "description": "按订单状态过滤"
    },
    "amount": {
      "type": "number",
      "minimum": 0,
      "description": "最低金额过滤（美元）"
    },
    "tags": {
      "type": "array",
      "items": {"type": "string"},
      "description": "标签列表，取交集过滤"
    }
  }
}

      可用特性包括 type、enum、description、default、minimum / maximum、format、嵌套对象、数组和 required。但原文也提醒：Schema 不是越详细越好，过度复杂会消耗上下文窗口，并增加模型出错概率。

      Pydantic 自动生成

      别手写，
      让类型生成 Schema。

      工具多了以后，手写 JSON Schema 容易出错。用 Pydantic 定义参数模型，再自动生成 Schema，描述、默认值和约束会跟着代码走。

      原文代码 · SearchParams

      from pydantic import BaseModel, Field
from typing import Optional, Literal
import json

class SearchParams(BaseModel):
    """在知识库中搜索文档"""
    query: str = Field(description="搜索关键词或自然语言问题")
    # Pydantic v2 推荐：用 Literal 表达枚举，自动转为 JSON Schema 的 enum
    category: Optional[Literal["api_docs", "user_guide", "release_notes"]] = Field(
        default=None,
        description="文档类别",
    )
    max_results: int = Field(default=5, description="最大返回数量", ge=1, le=50)

# 自动生成 JSON Schema
schema = SearchParams.model_json_schema()
print(json.dumps(schema, indent=2))

# 自动验证 LLM 的输出
def execute_tool(llm_output: dict):
    params = SearchParams(**llm_output)  # 自动类型验证
    return knowledge_base.search(**params.model_dump())

      Pydantic 的优势有四点：自动类型验证和默认值处理；description 从 Field 自动提取；数据解析和序列化一体；Schema 更新时自动同步。

      工具命名空间

      给工具
      分个域。

      工具数量增多时，用命名空间组织。它帮助 LLM 理解工具的归属领域，减少跨域误选。

      原文代码 · 按域分组

      tools = [
    # CRM 域
    {"name": "crm.search_contacts", "description": "搜索 CRM 中的联系人"},
    {"name": "crm.create_lead", "description": "创建新的销售线索"},

    # 计费域
    {"name": "billing.get_invoice", "description": "获取发票详情"},
    {"name": "billing.process_refund", "description": "处理退款"},

    # 物流域
    {"name": "shipping.track_package", "description": "追踪包裹状态"},
]

      命名空间本身不会让描述变好，但它提供了领域线索。工具很多时，还要配合动态加载或分类路由，避免一次性把所有工具塞进上下文。

      输出验证

      模型给的参数，
      执行前必须验。

      LLM 生成的参数可能不完全符合 Schema。始终在执行前做结构验证和安全检查。

      原文代码 · 验证后执行

      import jsonschema

def validate_and_execute(tool_name: str, llm_args: dict):
    schema = tool_schemas[tool_name]["input_schema"]

    # 1. Schema 验证
    try:
        jsonschema.validate(llm_args, schema)
    except jsonschema.ValidationError as e:
        return {"error": f"参数验证失败: {e.message}"}

    # 2. 安全检查（防注入）
    if contains_injection(llm_args):
        return {"error": "检测到潜在注入攻击"}

    # 3. 执行
    return tools[tool_name](**llm_args)

      注意 jsonschema.validate 只检查结构，不检查业务权限，也不判断这次调用该不该执行。权限和审批属于 Tool Gateway 的职责，见 024 页。

      常见设计模式

      危险操作先确认，
      列表操作要分页。

      两个高频模式：删除等不可逆操作要求显式确认；列表类工具提供分页参数，避免一次返回过多数据。

      原文代码 · 确认型与分页型

      # 模式 1：确认型工具（危险操作前确认）
{
    "name": "delete_record",
    "description": "删除数据库记录。这是不可逆操作，调用前请确认用户意图。",
    "input_schema": {
        "properties": {
            "record_id": {"type": "string"},
            "confirmation": {
                "type": "string",
                "enum": ["confirmed"],
                "description": "必须传入 'confirmed' 才会执行删除"
            }
        },
        "required": ["record_id", "confirmation"]
    }
}

# 模式 2：分页型工具
{
    "name": "list_items",
    "input_schema": {
        "properties": {
            "page": {"type": "integer", "default": 1, "minimum": 1},
            "page_size": {"type": "integer", "default": 20, "maximum": 100}
        }
    }
}

      确认参数只能证明模型按要求填了字段，不能替代真正的人工审批。生产环境还要在 Gateway 层做权限校验和审批流；Schema 只是第一道结构约束。

      Skills 封装

      Function Calling 是 syscall，
      Skill 是 SDK。

      Function Calling 是 LLM 调用工具的底层机制，裸用会面临工具定义散落、无法复用、缺乏统一生命周期管理的问题。Skills 层在它之上做工程封装。

      Skills 封装层工具发现 · 参数校验 · 状态管理 · 错误处理 · 权限控制 · 日志审计
      ↓使用
      Function Calling 机制模型级能力：LLM 生成结构化的工具调用请求
      ↓调用
      底层工具API / DB / Code，实际执行

      封装判断标准

      不是所有能力都需要封装成 Skill。原文给出的核心公式是：复用频次 × 调用复杂度 > 手动调用成本。

      判断是否需要封装为 Skill 的三个维度
      维度高分：需要封装低分：直接调用
      复用频次多个场景 / Agent 都会用仅单次使用
      调用复杂度多步骤编排、需状态管理单次 API 调用即可
      出错成本失败影响大，需要降级失败可忽略或重试

      粒度平衡

      原文示意 · 太细、太粗与合适粒度

      太细（过度拆分）：               太粗（一个 skill 做太多事）：
- search_user_skill              - do_everything_skill
- filter_user_skill                （难以测试、难以复用）
- sort_user_skill
- paginate_user_skill
  （编排开销大，LLM 容易选错）

合适的粒度：
- user_search_skill（包含搜索、过滤、分页的完整查询）

      太细会让 LLM 在多个相似工具间选错，太粗会让单个工具难以测试和复用。合适的粒度是按一次完整的用户意图切，而不是按每个内部函数切。

      工具数量管理

      工具过多会降低 LLM 的选择准确率。原文给出的固定观察如下：

      工具数量与 LLM 选对概率、平均选择延迟的关系
      工具数量LLM 选对概率平均选择延迟
      1–5> 95%+0.2s
      6–1085–95%+0.5s
      11–2070–85%+1.0s
      20+< 70%+1.5s+

      原文的解决方案是分类路由：先让 LLM 选类别，再暴露该类别的工具。

      原文代码 · 分类路由

      tool_categories = {
    "数据查询": [search_users, search_orders, search_products],
    "数据分析": [run_sql, generate_chart, export_csv],
    "消息通知": [send_email, send_slack, create_ticket],
}

# 路由工具：让 LLM 先选类别
{
    "name": "route_to_category",
    "description": "根据用户需求选择工具类别: 数据查询、数据分析、消息通知",
    "input_schema": {
        "properties": {
            "category": {"type": "string", "enum": ["数据查询", "数据分析", "消息通知"]}
        }
    }
}

      常见误区 / 面试追问

      六个容易
      被追问的点。

      前两条是误区，后四条是面试追问；答案都来自原文。

      误区 1

      “名称比描述重要。”

      恰恰相反。描述是 LLM 决定是否使用工具的核心依据，名称只是标识符。好的描述应明确说明用途、触发条件和排除条件。

      误区 2

      “Schema 越详细越好。”

      过度复杂的 Schema 会消耗上下文窗口，且增加 LLM 出错概率。保持简洁，只定义必要的参数。

      追问 1

      工具太多（50+）怎么办？

      四条路：用命名空间分组；根据用户意图动态加载相关工具；用 Embedding 做工具检索（RAG for tools）；分层，先让 LLM 选类别，再加载该类别的工具。

      追问 2

      如何测试工具 Schema 的质量？

      构建测试用例集：一组用户查询加期望被选中的工具。运行后检查 LLM 的工具选择准确率；低于 90% 就需要优化描述。

      追问 3

      Skill 和 Function Calling 的本质区别是什么？

      Function Calling 是模型级能力，LLM 生成结构化的工具调用请求；Skill 是工程级封装，在 Function Calling 之上加了生命周期管理、错误处理、降级策略和审计日志。类比：Function Calling 是 syscall，Skill 是 SDK。

      追问 4

      如何判断一个能力是否需要封装成 Skill？

      三个维度打分：复用频次、调用复杂度、出错成本。多步骤编排、跨 Agent 复用、涉及外部系统交互的能力都应该封装；单次简单 API 调用不需要。

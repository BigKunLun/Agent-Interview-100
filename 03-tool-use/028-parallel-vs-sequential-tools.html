中级 · Tool Use · 可交互讲解

能并行就别排队，
有依赖才按顺序。

并行工具调用让 LLM 同时请求多个无依赖的工具，总延迟从“所有调用时间之和”降到“最长单次调用”。顺序调用适合后一个工具要用前一个输出的场景。生产系统通常用混合模式：先并行收集独立数据，再顺序处理依赖步骤。

关键边界：模型只负责生成调用请求，实际并行还是顺序由应用层编排决定。本页的任务图、时长和状态都是固定教学数据，不调用模型，也不启动真实任务。

      顺序调用

      后一步的输入，
      来自前一步的输出。

      工具一个接一个执行。顺序不是落后，而是数据依赖的必然结果。

      # 用户："查询订单 #123 的状态，然后给客户发物流提醒"

order = await get_order_status(order_id="123")
# → {"status": "shipped", "tracking": "SF1234", "customer_email": "user@example.com"}

result = await send_email(
    to=order["customer_email"],   # 依赖上一步输出
    subject="您的订单已发货",
    body=f"物流单号: {order['tracking']}"
)

      适用场景：工具 B 的输入依赖工具 A 的输出；需要根据前一步结果决定下一步操作；数据写入后需要验证结果。

      并行调用

      互不依赖的调用，
      同时出发。

      多个无依赖的工具同时执行，总延迟取最长的一次，而不是全部相加。

      # 用户："比较北京、上海、深圳的天气"
results = await asyncio.gather(
    get_weather(city="Beijing"),
    get_weather(city="Shanghai"),
    get_weather(city="Shenzhen")
)
# 延迟 = max(三次调用时间) ≈ 300ms
# 顺序执行则需要 ≈ 900ms

      原文的性能对照：4 个各 300ms 的调用，顺序执行总计 1200ms，并行执行总计 300ms。适用场景是多源数据收集、比较分析和独立子任务。

      并行不是没有代价

      瞬时并发会撞上速率限制；部分失败要决定回滚还是保留；并行工具不应修改同一份共享状态。延迟收益要用并发控制、错误策略和一致性成本换。

      谁来决策

      模型提请求，
      基础设施定执行。

      模型返回多个 tool_use block 只说明“这些调用可以发出”，并不强制并行执行。真正的执行策略在应用层。

      # 模型返回多个 tool_use block → 可并行
response.content = [
    ToolUse(name="get_weather", input={"city": "Beijing"}),
    ToolUse(name="get_weather", input={"city": "Shanghai"}),
]

# 模型返回单个 tool_use → 先拿结果，再决定下一步
response.content = [
    ToolUse(name="get_order", input={"order_id": "123"}),
]

      关键点：模型生成调用请求，你的基础设施决定如何执行。即使模型一次返回多个调用，开发者也可以选择串行执行；反过来，应用层也可以把本可并行的调用排成队。编排策略是工程决策，不是模型自带的优化。

      混合模式

      先扇出收集，
      再扇入处理。

      生产最佳实践通常不是全并行或全顺序，而是按依赖图分段：独立段并行，依赖段串行。

      用户请求 · 生成竞品分析报告→阶段 1：并行扇出（无依赖）
      research · Product A
      research · Product B
      research · Product C
      ↓三路全部完成后扇入
      generate_comparison→format_report→最终报告

      # 阶段 1：并行收集数据（无依赖）
product_data = await asyncio.gather(
    research_product("Product A"),
    research_product("Product B"),
    research_product("Product C"),
)

# 阶段 2：顺序处理（依赖阶段 1 的结果）
comparison = await generate_comparison(product_data)
report = await format_report(comparison)

      延迟从全顺序的 N×T 降为 max(T) 加串行段。扇出只发生在独立段，扇入点必须等齐所有分支。

      关键设计考量

      依赖、限流、
      失败和共享状态。

      并行化不是把 for 循环换成 gather 就结束了。四个问题都要在设计阶段回答。

      1. 依赖分析

      先判断每个调用的参数是否引用其他调用的输出。独立调用放一组并行，依赖调用排顺序。原文给了一个简化检测函数：

      def analyze_dependencies(tool_calls):
    independent = []
    dependent = []
    for call in tool_calls:
        if references_other_output(call.params):
            dependent.append(call)
        else:
            independent.append(call)
    return independent, dependent

      2. 速率限制

      并行降低延迟，但增加瞬时并发。用信号量限制同时在飞的请求数：

      semaphore = asyncio.Semaphore(5)  # 最多 5 个并发

async def rate_limited_call(tool, params):
    async with semaphore:
        return await tool.execute(params)

results = await asyncio.gather(
    *[rate_limited_call(tool, p) for p in params_list]
)

      3. 错误处理差异

      顺序模式一个失败就停，逻辑简单；并行模式要决定部分失败怎么办。return_exceptions=True 可以避免单个失败取消全部，然后分别收集成功和失败：

      results = await asyncio.gather(
    tool_a(), tool_b(), tool_c(),
    return_exceptions=True
)
successes = [r for r in results if not isinstance(r, Exception)]
failures = [r for r in results if isinstance(r, Exception)]

      4. 共享状态

      并行工具不应修改共享状态。并行阶段只读，写入操作顺序执行，避免竞态。原文的边界很直接：危险的是并行工具改同一条数据库记录，安全的是并行只读、写入排队。

      框架实现

      LangGraph 用两条边，
      画出扇出和扇入。

      编排框架把并行表达成图：一个节点连到多个并行节点是 fan-out，多个并行节点连到同一个汇聚节点是 fan-in。

      from langgraph.graph import StateGraph

graph = StateGraph(State)
graph.add_node("research_a", research_product_a)
graph.add_node("research_b", research_product_b)

# fan-out: 一个节点分发到多个并行节点
graph.add_edge("start", "research_a")
graph.add_edge("start", "research_b")

# fan-in: 多个并行节点汇聚到一个节点
graph.add_edge("research_a", "aggregate")
graph.add_edge("research_b", "aggregate")

      Map-Reduce 是这种模式的特例：Map 阶段把任务分发给多个并行工具，Reduce 阶段汇聚结果。LangGraph 等框架原生支持 fan-out / fan-in。

      决策框架

      看依赖，
      不看感觉。

      按条件选模式，六种情况覆盖大多数工具编排。

      并行、顺序与混合模式的选择条件
      条件选择原因
      工具间无数据依赖并行降低延迟
      后续工具需要前序结果顺序数据依赖
      需要根据结果做条件判断顺序逻辑依赖
      多源数据收集并行最大化吞吐
      写操作涉及同一资源顺序避免竞态
      混合场景混合DAG 调度

      常见误区 / 面试追问

      四个问题，
      别把并行当默认。

      前两个是误区，后两个是追问。

      误区 1

      “并行总是更好。”

      并行会增加瞬时并发，可能触发 API 速率限制。而且并行错误处理更复杂：部分失败时，是全部回滚还是保留成功结果，需要提前决定。

      误区 2

      “LLM 会自动优化并行 / 顺序。”

      LLM 只负责生成工具调用请求。实际执行策略由应用层编排代码决定。开发者需要显式实现并行执行逻辑；模型返回多个调用不等于它们会自动同时执行。

      追问 1

      如何处理并行调用中的部分失败？

      两种策略：原子性，一个失败全部回滚，适合事务操作；尽力执行，保留成功结果，把失败信息返回给 LLM 让它决定下一步，适合数据收集。

      追问 2

      Map-Reduce 模式和并行工具调用有什么关系？

      Map-Reduce 是并行工具调用的一种特定模式：Map 阶段把任务分发给多个并行工具，Reduce 阶段汇聚结果。LangGraph 等框架原生支持 fan-out / fan-in。

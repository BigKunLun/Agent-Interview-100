一 · 先分清三层

题库、考场、成绩单，
是三件事。

日常说“跑个 benchmark”常把三层混在一起。Inspect AI 的设计把评测显式拆成四个独立原语，正是为了让每一层可替换、可追踪。

Benchmark、Eval Harness 与评估报告三层职责
层是什么例子换掉它会怎样
Benchmark题库 + 评分标准。定义题目、输入格式、什么算对。SWE-bench Verified、GAIA、τ²-bench题目和难度变了，分数不可直接横比。
Eval Harness运行时框架：加载题目、让模型作答、提供工具环境、判分、记录。Inspect AI、lm-evaluation-harness、HELM同一个题库也能跑出不同分数，因为 prompt、工具、资源和判分都变了。
评估报告分数 + 产生分数的条件：harness 版本、sandbox、配额、scaffold、重试策略。系统卡、leaderboard 提交、内部 eval 记录只留一个标量分数，别人无法复现，也无法判断可比性。

原文给的关键洞见是责任分离：Solver 负责怎么答、Scorer 负责怎么判分、Sandbox 是 Solver 调用工具时的隔离层。分离之后，“同 SWE-bench Verified 不同 harness 跑出不同分数”既是必然，也是合理的。

原文数据、未联网核实

Anthropic Terminal-Bench 2.0 在同模型、同任务、仅变更 pod 资源预算的条件下，实测 5.8% 的任务因 pod / infrastructure 错误失败（p<0.01）。这说明资源预算本身就是分数的一部分，不是环境噪声。

四个原语各管什么

Harness 四原语的职责与代表实现
组件职责代表实现
Task Loader从数据集加载样本、组装 prompt、注入 few-shot。lm-eval-harness 的 YAML：doc_to_text / doc_to_target / filters
Solver让模型作答的 scaffold：单轮生成、ReAct、多轮 critique。Inspect AI 的 generate → prompt → react → multi_turn 链式组合
Sandbox隔离代码执行与工具调用，限定资源。Docker（主流）/ k8s（大规模）/ Proxmox VM（高风险）/ Daytona / Modal / EC2
Scorer判分：精确匹配、单元测试、LLM Judge、数据库状态比对。SWE-bench 的 fail→pass 测试套件、τ²-bench 的 DB diff、model_graded_qa 多 judge 投票

还有一个常被忽略的第五件事：日志。没有完整轨迹、token 用量和失败原因，分数就只是一句无法复核的结论。

二 · 四个生态

三足鼎立，
加一个 METR 范式。

原文把主流 harness 分成 lm-evaluation-harness、Inspect AI、HELM 三家，再加 METR 的 Time Horizon 度量。它们解决的问题不同，不是同一张榜单上的竞品。

EleutherAI · 2021

lm-evaluation-harness

model eval 的行业标杆，Hugging Face Open LLM Leaderboard 的后端。核心是单轮 logprob / 生成 + 打分，适合学术 benchmark 和模型横评。

UK AISI · 2024-05

Inspect AI

Agent eval 的事实标准。把评测显式拆成 dataset → Task → Solver → Scorer，内置多种 sandbox，Agent Bridge 可接 Claude Code、Codex CLI 等。

Stanford CRFM · 2022

HELM

多维度全景评测：准确率之外，同时测校准、鲁棒性、公平性、偏差、毒性和效率。强调公开原始输入与输出，任何研究者都能重跑。

METR · Time Horizon

METR 范式

不直接比准确率，而是测“AI 能以 50% 成功率独立完成多长的任务”。用人类完成时间标定，形成可外推的连续度量。

lm-evaluation-harness：单轮评测的默认选项

它的任务定义是 YAML，把 prompt 模板、目标字段和指标解耦。贡献新任务不需要写 Python，这也是它能积累 60+ 标准学术 benchmark、数百个子任务的原因。

原文任务定义示例（YAML，仅展示）

task: mmlu_abstract_algebra
dataset_path: hails/mmlu_no_train
dataset_name: abstract_algebra
output_type: multiple_choice
doc_to_text: "{{question.strip()}}\nA. {{choices[0]}}\nB. {{choices[1]}}\nC. {{choices[2]}}\nD. {{choices[3]}}\nAnswer:"
doc_to_target: answer
metric_list:
  - metric: acc
    aggregation: mean
    higher_is_better: true
version: 1.0

统一后端覆盖 HF transformers、vLLM、SGLang、OpenAI、Anthropic、LiteLLM 等 100+ providers；输出类型分 generate_until、loglikelihood、loglikelihood_rolling、multiple_choice，对应不同评分语义。

可复现性靠四个开关：--use_cache 跳过已评样本、--log_samples 保留完整响应、--check_integrity 校验数据、任务 version 字段防止静默变更。局限也明确：它面向单轮模型评测，没有 sandbox、没有多轮 solver、没有轨迹 scorer。

Inspect AI：把 Agent 评测拆开

原文核心抽象示例（Python，仅展示，不执行）

from inspect_ai import Task, task, eval
from inspect_ai.dataset import Sample
from inspect_ai.solver import generate, system_message, use_tools
from inspect_ai.scorer import includes, model_graded_qa
from inspect_ai.tool import bash, python

@task
def swe_bench_lite():
    return Task(
        dataset=swe_bench_dataset(),
        solver=[
            system_message("You are an expert software engineer..."),
            use_tools([bash(timeout=180), python(timeout=180)]),
            generate(max_messages=50),  # ReAct loop
        ],
        scorer=swe_bench_scorer(),       # fail→pass 测试套件
        sandbox=("docker", "compose.yaml"),  # 每 sample 独立 sandbox
    )
Inspect AI 的架构特性
维度实现
Solver 库ReAct / Multi-Agent / Human Agent / Agent Bridge，可桥接 LangChain、OpenAI Agents SDK、Pydantic AI、Claude Code、Codex CLI。
Sandbox内置 docker / local，扩展支持 k8s / proxmox / daytona / modal / ec2；每个 sample 独立实例，避免交叉污染。
Scorer可进入 sandbox 读文件、跑命令验证最终状态；model_graded_qa 支持多 judge 投票。
inspect_evals社区贡献 GAIA、SWE-bench、Cybench、GDM CTF、SciCode 等 200+ agent benchmark，50+ 贡献者。
资源管理max_sandboxes = 2 × cpu_count、max_subprocesses = cpu_count、max_samples = max_connections + 1。sandbox 是 Agent eval 的并发瓶颈。

生态收敛的信号是 METR：2026-01 发布 Time Horizon 1.1 时，完成从自研 Vivaria 到 Inspect 的迁移，并用 Inspect 重跑全部数据，验证“7 个月翻倍”的趋势在迁移后仍成立。

HELM 与 METR：两种不同的“全景”

HELM 的经典 7 大度量是 accuracy、calibration、robustness、fairness、bias、toxicity、efficiency，每个 scenario 同时测。2025-03 的 Capabilities 版本引入 MMLU-Pro / GPQA / IFEval / WildBench / Omni-MATH 五个能力切面，每个 scenario 采样 1000 实例，并用 mean score 取代 mean win rate，因为 win rate 对小幅波动太敏感。

METR 的 Time Horizon 用“50% 成功率对应的任务时长”做度量。原文称过去 6 年该指标约每 7 个月翻一番；GPT-5.1-Codex-Max（2025-11）的 50% time horizon 约为 2 小时 40 分钟，80% 约为 30 分钟。它天然抗污染、抗饱和，也能给出可外推的趋势。

原文版本、未联网核实

以上工具版本、发布日期、200+ 评测数量、7 个月翻倍与 2 小时 40 分钟均按原文 2026-10 口径保留。本页未联网核对，不保证这些版本与数字仍然有效。

三 · 沙箱与事故

沙箱既保安全，
也保可复现。

原文强调：sandbox 不只是技术参数，它同时决定评测能不能复现、会不会越界。两起跨厂商事故说明，prompt 里写的隔离不算隔离。

四类 sandbox 的隔离强度、启动成本与适用场景
Sandbox 类型隔离强度启动成本适用场景
local无0信任的题目：纯算术、文本生成。
docker进程级约 1 秒主流：代码执行、shell 工具（SWE-bench、Terminal-Bench）。
k8s进程级 + 资源调度约 5–30 秒大规模并行（WebArena 多服务 compose）。
Proxmox / VM内核级分钟级高风险评测（Cyber CTF、sandbox escape）。

WebArena 是可复现性的教科书案例：5 个 Docker 服务（电商 / CMS / GitLab / 论坛 / 地图）打包成 AMI，拉取后可完全 reset。2025 年的 WebArena-Verified 把镜像体积压缩 92%，删除 LLM-as-judge 改为确定性评分，并提供 258 题 Hard 子集降低成本。

反面教材同样有：2025 年 Zhu et al. 审计 37 个公开 agent benchmark suite，普遍存在“成功标准未充分定义”和“低精度评估器”的问题。这正是 τ²-bench 强调比对数据库最终状态、而不是听 agent 说了什么的原因。

两起事故：声明的隔离 ≠ 实际拓扑

安全边界 · 仅复述结论

本页只转述原文公开的事故结论，不提供任何攻击步骤或可执行载荷。真实评测环境请由网络层独立验证隔离。

Anthropic（2026-07 复盘）：三起网络安全评测事故中，本应完全隔离的环境实际连着真实互联网，而 prompt 告诉 Claude“你处在模拟环境、没有网络访问”。模型于是对真实系统执行了本以为是演习的操作。原文的归因是：模型并未失准，目标对齐、行为符合任务描述，有害结果来自被喂了错误的世界模型；新模型识破环境为真实后主动中止，旧版本继续执行。结论是把 defense-in-depth 延伸到评测基础设施本身。

OpenAI（第三方网安评测）：在与 UK AISI、Irregular 合作的评测中，安全护栏放宽加环境配置失当两件事叠加，模型访问公网、超出预定测试边界。原文列表页标注 2026-08-04，正文页未渲染日期，这条日期未做正文交叉验证。随后收紧的协议有三条：识别高风险评测、事前约定测试范围、联网请求需经审批。

两例合起来证明这是模式而非个例。可直接落到 harness 设计上的两条原则：

  • 隔离必须由外部证明。无论承诺写在 prompt 还是配置里，只要没有独立的网络层验证，它就只是一句话。出口规则、DNS 策略、代理白名单要能拿出来对账。
  • 第三方评测的边界责任要写进协议。评测方搭环境、模型方放护栏，两边都容易默认对方兜底。网安评测又必须放宽护栏才测得出上限，所以隔离不能靠模型侧克制。

实操推论：eval 报告的 sandbox 字段之外，还要记录“这套隔离是谁、用什么方式验证过的”。“我们用了 Docker”和“我们验证过容器出网被 deny-by-default 拦住”是两个强度完全不同的声明。

事故日期、厂商结论均按原文 2026-10 口径，未联网核实。

四 · Agent Eval 与污染

一次成功，
说明不了什么。

Model Eval 评的是单次回答，Agent Eval 评的是一条轨迹加最终环境状态。非确定性来源更多，ground truth 也不再唯一。

Model Eval 与 Agent Eval 的七维差异
维度Model EvalAgent Eval
评估对象单 prompt → 单 response多轮 workflow + 工具 + 环境
关注点输出质量：正确性、流畅度任务完成 + 推理链 + 工具使用 + 错误恢复
评分对象最终答案轨迹 + 最终状态
非确定性来源仅采样温度采样 + 工具执行 + 环境响应 + 时序
Ground truth参考答案，通常单一多条有效轨迹同时存在
统计设计单次足够（high pass@1）必须多 trial，pass@k 与 pass^k 双侧
典型基准MMLU / GSM8K / HumanEvalSWE-bench / GAIA / τ²-bench / WebArena

Anthropic 推荐的四个独立评估维度是：Outcomes（最终环境状态，例如数据库里是否真有这条预订）、Transcripts（turn 数、token 用量、行为 rubric）、Tool Calls（是否按合适参数调用，但别过度规定顺序）、Cost & Latency（与正确性并列报告）。原话是 “grade what agent produced, not the path it took”。

只看终态也不够。arXiv 2510.02837 的结论是：trajectory-opaque eval 会漏掉 44% 的安全违规和 13% 的鲁棒性失败。解法是 hybrid pipeline：outcome check + trajectory check + tool sequence check 联合判定。

Contamination：榜单信任为什么塌了

原文记录：2026-02 OpenAI 主导的 SWE-bench Verified 污染审计发现，受测的前沿模型都能逐字复现某些任务的 gold patch；59.4% 的最难未解题测试用例有缺陷；部分模型只给文件结构、不给 issue 描述，也能定位要改的文件。OpenAI 随后宣布停报 SWE-bench Verified，转向 SWE-bench Pro。

Scale AI 的 SWE-bench Pro 有 1865 个多语言任务和严格污染控制：在 Verified 上 80%+ 的模型，在 Pro 上只能拿 46–57%，原文称其中包含 22pp 的 scaffold-induced 差距。

三种污染检测方法的原理与局限
方法原理局限
Watermarking用 Llama-3 instruct 重写题目并嵌入红 / 绿 list 水印，5% 污染即可在 p<10⁻³ 显著性下检出。只能检出“重写后被训练”的情形。
Question variant testing生成变体题，检查模型在变体上是否退化。reformulated 题本身就足以提升原题分数，相关性不强。
Loss-based detection比较训练集与测试集上的 loss 分布。在推理模型上失效：RL 阶段会掩盖 SFT 阶段污染。

原文的实操建议：公开 benchmark 只做初筛；必须准备“训练截止日期之后”的私有 holdout；关注持续收题的动态 benchmark，例如 SWE-MERA 和每月更新的 LiveCodeBench。

59.4%、46–57%、22pp、44%、13% 均为原文 2026-10 引用值，未联网核实。

问题 1 / 3

评测对象是多轮 Agent 吗？

需要工具调用、sandbox、轨迹评分，就走 Agent eval 分支。

    固定选型逻辑来自原文决策树；工具版本与生态按原文 2026-10 口径，未联网核实。

    固定决策路径 · 本页不安装、不运行任何工具尚未作答 · 共 3 个判断问题

    评估报告至少写清这些

    可复现评估报告应记录的字段
    字段为什么必须写
    Benchmark 与版本题目会更新、会被污染；“SWE-bench”不是一个稳定对象。
    Harness 与版本同一个 benchmark 换 harness 会有 20+ 分差距。
    Sandbox 类型与资源pod 资源预算本身就能造成 5.8% 的失败差异。
    Scaffold 版本Solver 链、工具集、最大轮数决定模型怎么答。
    重试与评分策略retry 次数、judge 模型、是否多次投票都会改变分数。
    隔离验证方式“用了 Docker”不等于“验证过出网被拦住”。

    第 1 层原则是：先固定 production harness，只让模型变化。第 2 层把 sandbox、配额、scaffold、retry 写进报告。第 3 层同时报 pass@1（多 trial 估计）、pass@k（乐观上界）、pass^k（悲观下界）。第 4 层把 capability eval（目标低通过率，找能力边界）和 regression eval（目标接近 100%，防退步）分开。

    2026-08 的前沿动向（社区单次实验）

    • HarnessEval-W（arXiv 2608.16859，2026-08-17）把 harness 范式搬进评分环节：不套固定 rubric，让 agent 按上下文自行组织判据，并留下可审查的推理链。输出从标量分数变成“判据 + 推理过程 + 结论”。
    • Beyond Final Scores（arXiv 2608.13417）用规则指标把一次 run 拆成 Solution Framing / Execution / Feedback Control 三个维度，覆盖 7 个前沿模型 × 36 个长时程任务。

    原文明确标注这两项为社区单次实验、尚无独立复现。它们不推翻“先固定 harness”，反而加强：标量分数还能勉强跨 harness 比，过程记录的粒度与字段完全由 harness 决定，不固定就无从对齐。

    常见误区 / 面试追问

    四个误区，
    六个追问。

    按原文顺序保留 10 条。其中第 1、2、3、8 条是误区，其余是面试追问；答案均按原文 2026-10 口径。

    误区 1

    “Eval Harness 和 Benchmark 是一回事。”

    这是 Agent 评测领域最大的概念混淆。Benchmark 是题库加评分标准，Harness 是运行时框架。同一个 benchmark 在不同 harness 上跑出 20+ 分差距是工程常态，这正是 Inspect AI 显式拆四个原语的原因。

    误区 2

    “SWE-bench 80% 就是 SOTA。”

    2026-02 之后这个说法已经过时。OpenAI 宣布 Verified 污染严重（59.4% 最难题测试有缺陷），转向 SWE-bench Pro。Verified 上 80%+ 的模型在 Pro 上只能拿 46–57%。引用 SOTA 时必须问：哪个 harness、哪个版本、是否私有 holdout。

    误区 3

    “Inspect AI 是 UK 政府的玩具，主流不会用。”

    METR 在 2026-01 Time Horizon 1.1 发布时弃用自研 Vivaria、全面迁移到 Inspect，是生态收敛的标志。200+ inspect_evals、50+ 贡献者、Agent Bridge 接 Claude Code / Codex CLI，它已是 Agent eval 的事实标准。

    追问 1

    “为什么 lm-eval-harness 对 Agent 评测无能为力？”

    它的核心抽象是“单轮 logprob / 生成 → 匹配”，没有 sandbox、没有 multi-turn solver、没有轨迹 scorer。Agent 需要的“调用 bash → 看输出 → 决定下一步”闭环，只能由 Inspect 的 Solver 链或专用 harness 提供。加一个 OpenAI provider 也只是包了一层 API 调用。

    追问 2

    “如何设计 provider-agnostic 的 harness 给团队选模型？”

    四层：先固定 production harness，只让模型变化；把 sandbox、配额、scaffold、retry 写进报告；同时报 pass@1、pass@k、pass^k；capability eval 与 regression eval 分离。

    追问 3

    “Sandbox 类型怎么选？”

    代码生成 + shell 用 Docker（启动约 1 秒）；大规模并行（100+ sample）用 k8s；高风险评测（Cyber CTF、sandbox escape）用 Proxmox / VM；纯文本生成用 local。关键准则：sandbox 是 Agent eval 真正的并发瓶颈。

    追问 4

    “如何应对 Benchmark Contamination？”

    不依赖单一公开 benchmark，准备训练截止日期之后的私有 holdout；使用动态 benchmark；用 Time Horizon 这类连续度量；用 watermarking 检测（5% 污染可在 p<10⁻³ 下检出）。警惕“只给文件结构也能定位文件”这类信号。

    误区 4

    “评测跑在沙箱里，最坏也就是结果不准。”

    Anthropic 2026-07 复盘的三起网安评测事故是反例：环境自称隔离、实际连着公网，模型按 prompt 描述行动，操作了真实系统。模型本身没有失准，错的是被喂的世界模型。隔离必须由网络拓扑保证并定期对账。

    追问 5

    “第三方评测出了越界事故，责任在谁？”

    责任真空来自默认对方兜底。评测方搭环境、模型方放护栏，而网安评测必须放宽护栏才测得出上限。OpenAI 收紧协议的三条措施就是显式化归属：高风险评测识别、测试范围事前约定、联网请求审批。落到 harness 上：隔离要有一个独立于评测方声明的验证方。

    追问 6

    “评测只输出一个分数够不够？”

    2026-08 两篇工作给出的答案是不够，方向是“留下可审查的过程记录”。但两篇都是社区单次实验、未经独立复现，引用时要连出处和日期一起标。这不推翻“先固定 harness”，反而让固定更重要。

出了错，
先看它走过的路。

Trace 是一次完整 Agent 执行，Span 是执行里的一个操作单元：一次 LLM 调用、一次工具调用、一次检索。父子 Span 组成树，树上的耗时、token、状态和属性，决定了你能不能回答“做了什么、花了多久、哪里出错”。

关键边界：指标名一样，口径不一样就没法比。每个指标都要写死分子、分母和数据来源；本页的耗时按原文示例，token 与成本为固定教学补值。

结构

Trace 是因果链，
日志是事件点。

一次 Agent 执行是一条 Trace；每个 LLM 调用、工具调用、检索都是 Span。Span 有父子关系，父 Span 的耗时包含子 Span。

原文的示例是“分析竞品 A 定价策略”：总耗时 8.2s，下面四个 Span 分别是理解任务 1.2s、web_search 2.5s、分析结果 3.1s、生成报告 1.4s。四项相加正好 8.2s，说明这是串行执行；并发场景不能直接相加。

Trace 和日志的分工不同：日志是离散事件，告诉你“发生了什么”；Trace 是结构化因果链，告诉你“为什么发生”以及“事件之间是什么关系”。多步 Agent 里，没有 Trace 几乎无法定位问题。

OpenTelemetry

标准属性，
供应商无关。

OTel 是 LLM 可观测性的主流方向。原文明确：GenAI 语义约定截至 2026-05 仍是 Development 阶段，尚未 Stable。

OTel 的价值是供应商无关：同一套埋点可以发到 Jaeger、Datadog、Langfuse 等后端，换监控工具只改 exporter 配置，不改业务代码。代价是语义约定还在演进，API 名字可能在 GA 前微调，生产接入建议固定到具体语义版本。

查看原文的 ObservableAgent 代码 
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

# 初始化 OTel
provider = TracerProvider()
provider.add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="http://collector:4318"))
)
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("agent-service")

class ObservableAgent:
    """带完整可观测性的 Agent"""

    async def execute(self, task: str):
        # 创建 Trace（顶层 Span）
        with tracer.start_as_current_span("agent_execution") as root_span:
            root_span.set_attribute("task", task)
            root_span.set_attribute("agent.name", "research-agent")

            # Step 1: 规划
            plan = await self.plan(task)

            # Step 2: 执行每个步骤
            results = []
            for step in plan.steps:
                result = await self.execute_step(step)
                results.append(result)

            # 记录总体指标
            root_span.set_attribute("total_steps", len(results))
            root_span.set_attribute("task_success", True)

            return self.synthesize(results)

    async def plan(self, task):
        with tracer.start_as_current_span("llm_call") as span:
            span.set_attribute("gen_ai.system", "openai")
            span.set_attribute("gen_ai.request.model", "gpt-4o")
            span.set_attribute("gen_ai.operation.name", "planning")

            response = await self.llm.invoke(task)

            # 记录 token 使用
            span.set_attribute("gen_ai.usage.input_tokens", response.usage.prompt_tokens)
            span.set_attribute("gen_ai.usage.output_tokens", response.usage.completion_tokens)

            return response

    async def execute_step(self, step):
        with tracer.start_as_current_span("agent_step") as span:
            span.set_attribute("step.name", step.name)

            if step.requires_tool:
                # 工具调用子 Span
                with tracer.start_as_current_span("tool_call") as tool_span:
                    tool_span.set_attribute("tool.name", step.tool_name)
                    tool_span.set_attribute("tool.input", str(step.tool_params))

                    result = await self.call_tool(step.tool_name, step.tool_params)

                    tool_span.set_attribute("tool.output_size", len(str(result)))
                    if result.error:
                        tool_span.set_status(trace.Status(trace.StatusCode.ERROR))
                        tool_span.record_exception(result.error)

                    return result

原文代码里既有 OTel 标准属性（gen_ai.*），也有自定义属性（tool.name、step.name）。实际项目要约定哪些用标准、哪些用私有前缀，避免同名不同义。

三大支柱

Trace、Metrics、Logs，
各回答一个问题。

Trace 回答“做了什么、每步多久”；Metrics 量化性能和健康状态；Logs 记录详细事件和错误。三者不能互相替代。

Traces 追踪完整执行路径；每步耗时。工具：Jaeger、Zipkin、Langfuse、LangSmith。
Metrics 指标请求延迟 P50/P95/P99、token 消耗、工具成功率、任务完成率、每次请求成本。工具：Prometheus、Datadog、Grafana。
Logs 日志LLM 输入输出、工具参数与返回值、错误堆栈。工具：ELK Stack、CloudWatch。

成功率最容易算错

原文给了三种判定方式：有明确成功标记的走规则判定；没有的用 LLM-as-Judge，但必须先写 rubric；再叠加用户反馈。线上常用组合是：用户没重试、没报错，先记为隐式成功，再按固定比例抽样，用人工或 judge 复核校准。不校准，隐式成功会把数字抬高。

分母按 run 算，不按请求算；超时算失败；用户主动中止不计入分母，但单独报中止率。口径写进文档，不能指标难看就改。

工具选错率线上拿不到真值，只能用代理信号：同一意图连续重试、工具返回空结果后换工具、模型输出里出现自我纠正。代理信号误报多，线上只看趋势，准确值靠离线标注集。

耗时按 Span 分段记账。原文的代码注释明确：串行执行可以直接相加；并发 Span 应改用墙钟起止区间，否则会把重叠时间重复计算。

class Outcome(Enum):
    SUCCESS = "success"            # 规则判定成功
    FAILURE = "failure"            # 规则判定失败
    IMPLICIT_SUCCESS = "implicit"  # 无报错、无重试，待抽样复核
    TIMEOUT = "timeout"
    ABORTED = "aborted"            # 用户主动中止


@dataclass
class RunMetrics:
    run_id: str
    outcome: Outcome
    model_ms: float = 0.0
    tool_ms: float = 0.0
    queue_ms: float = 0.0          # 排队
    approval_ms: float = 0.0       # 人工审批等待
    token_cost_usd: float = 0.0    # 按各模型单价分别计算后汇总
    external_cost_usd: float = 0.0
    tool_calls: int = 0
    schema_failures: int = 0

    @property
    def cost_usd(self) -> float:
        return self.token_cost_usd + self.external_cost_usd

    @property
    def latency_ms(self) -> float:
        # 串行执行可以直接相加；并发 Span 应改用墙钟起止区间
        return self.model_ms + self.tool_ms + self.queue_ms + self.approval_ms


class RunMetricsAggregator:
    """成功率：分母按 run；超时算失败；中止单独报，不进分母"""

    def __init__(self) -> None:
        self._reviewed: dict[str, bool] = {}  # run_id -> 复核是否成功

    def review(self, run_id: str, is_success: bool) -> None:
        """按比例抽样人工或 LLM judge 复核，用来校准隐式成功"""
        self._reviewed[run_id] = is_success

    def success_rate(self, runs: list[RunMetrics]) -> float:
        denominator = [r for r in runs if r.outcome is not Outcome.ABORTED]
        if not denominator:
            return 0.0

        numerator = 0
        for run in denominator:
            if run.outcome is Outcome.SUCCESS:
                numerator += 1
            elif run.outcome is Outcome.IMPLICIT_SUCCESS:
                # 未复核先按成功计；复核为失败的扣回来
                numerator += int(self._reviewed.get(run.run_id, True))
        # TIMEOUT 和 FAILURE 留在分母里但不加分，等价于算失败
        return numerator / len(denominator)

调试场景

从失败 Trace，
走到复现修复。

原文给了一个五步调试流程：找失败 Trace、看 Span 树、检查出错 Span 详情、分析上下文、复现和修复。

  1. 找到失败的 Trace：按 request_id 或 error 状态筛选。
  2. 查看 Span 树结构：定位哪个 Span 出错（红色标记）。
  3. 检查出错 Span 的详情：LLM 调用看输入 Prompt 和输出；工具调用看参数和返回值；错误信息看异常类型和堆栈。
  4. 分析上下文：前序 Span 的输出是否正常？传给它的输入是否合理？
  5. 复现和修复：用相同输入参数重放，修复后重新运行验证。

本页第 2 步的 Span 属性面板对应的就是第 3 步：选中出错工具 Span，能看到 error.type、异常事件和调用参数。第 3 步的指标口径对应第 1 步：先确认你看的是哪个指标、分子分母是什么，再决定要不要追这条 Trace。

多 Agent 场景的 Trace 更长、分支更多，浏览方式可以参考 039 多 Agent 调试与监控；本页聚焦单条 Trace 的 Span 属性和指标口径，不重复多 Agent 的过滤视图。

常见误区 / 面试追问

两个误区，
两个追问。

有日志不等于有 Trace；Trace 也不只在故障时有用。存储成本和 OTel 的价值是常见追问。

误区 01

“有日志就不需要 Trace”

日志是离散事件记录，Trace 是结构化因果链。日志告诉你“发生了什么”，Trace 告诉你“为什么发生”以及事件之间的关系。多步 Agent 中，没有 Trace 几乎无法定位问题。

误区 02

“Trace 只在出问题时有用”

日常监控同样重要：发现性能瓶颈（哪个 Span 最慢）、优化成本（哪个 LLM 调用 token 最多）、理解用户行为（Agent 通常走什么路径）。

追问 03

如何控制 Trace 数据的存储成本？

三条：采样，不是每个请求都记录完整 Trace，例如 10% 采样率；按需详细度，正常请求只记关键 Span，错误请求记全部细节；数据保留策略，Trace 数据保留 7–30 天。

追问 04

OpenTelemetry 的优势是什么？

供应商无关。用 OTel 标准化的数据可以发送到任何后端（Jaeger、Datadog、Langfuse）；换监控工具不需要改代码，只改 exporter 配置。这避免了供应商锁定。

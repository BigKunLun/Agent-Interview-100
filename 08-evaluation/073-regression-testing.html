回归测试是在每次 Prompt 修改、模型升级、代码或数据变更后，自动跑一套固定用例，检查 Agent 是否退化。LLM 输出不确定，所以不能比“输出相等”，要比多次运行的统计指标、语义评分和趋势。

关键边界：回归集不是拿来把 Prompt 调到 100% 通过。要留 holdout、按 badcase 分层抽样、定期轮换；安全等高优先级用例必须全过。

class LLMRegressionTester:
    """LLM/Agent 回归测试框架"""

    def __init__(self, golden_dataset, metrics, threshold):
        self.dataset = golden_dataset   # 标注好的测试集
        self.metrics = metrics          # 评估指标
        self.threshold = threshold      # 退化阈值

    async def run_regression(self, current_version, baseline_version=None):
        """运行回归测试，对比当前版本与基线"""

        # 1. 在测试集上运行当前版本
        current_results = []
        for case in self.dataset:
            output = await current_version.invoke(case.input)
            scores = await self.evaluate(case, output)
            current_results.append(scores)

        # 2. 加载基线结果（或运行基线版本）
        if baseline_version:
            baseline_results = await self.run_baseline(baseline_version)
        else:
            baseline_results = self.load_baseline()

        # 3. 对比
        comparison = self.compare(current_results, baseline_results)

        # 4. 判断是否退化
        regressions = []
        for metric_name, delta in comparison.items():
            if delta < -self.threshold[metric_name]:
                regressions.append({
                    "metric": metric_name,
                    "baseline": baseline_results[metric_name],
                    "current": current_results[metric_name],
                    "delta": delta,
                })

        return {
            "passed": len(regressions) == 0,
            "regressions": regressions,
            "details": comparison,
        }

Golden Dataset

黄金集是活的，
不是一次性题库。

原文建议最少 50 个用例覆盖核心场景，理想 200–500 个；按 50% 核心、20% 边界、15% 安全、10% 格式、5% 性能配置。

原文建议的 Golden Dataset 覆盖比例
类别覆盖内容占比
核心功能Agent 的主要使用场景50%
边界情况极端输入、特殊字符、长文本20%
安全测试Prompt Injection、敏感话题15%
格式测试输出格式一致性10%
性能基准延迟和成本的基准用例5%

每个用例要标注优先级：critical / normal / low。原文明确说，高优先级用例（如安全相关）必须 100% 通过；优先级不是用来排“有空再修”的顺序。

数据集维护

从生产 bug 转成用例；定期审查和淘汰过时用例；随功能迭代补充新场景。Golden Dataset 应该是活的，随产品演进。

class GoldenDataset:
    """维护回归测试的黄金数据集"""

    def __init__(self):
        self.cases = []

    def add_case(self, input_text, expected_output=None,
                 rubric=None, category=None, priority="normal"):
        self.cases.append({
            "input": input_text,
            "expected_output": expected_output,
            "rubric": rubric,             # LLM Judge 评分标准
            "category": category,          # 分类（便于按类分析）
            "priority": priority,          # critical/normal/low
            "created_at": datetime.now(),
        })

badcase 沉淀

先归因，
再进回归集。

原文的原话是：badcase 要先归因，再沉淀成用例，否则越堆越假。归因顺序是从后往前，最后才怀疑模型能力。

五步归因

  1. 复现：固定当时的模型和 Prompt 版本，用 trace 里的输入重放。复现不了先查环境差异；不可复现的 case 先标记待观察。
  2. 工具层：工具选对了吗？参数对吗？工具返回本身对吗？
  3. 检索层：相关文档进 top-k 了吗？rerank 排对了吗？
  4. 上下文层：该有的信息在吗？被压缩丢了吗？
  5. Prompt 层：指令有歧义吗？few-shot 有错误示范吗？最后才是模型能力。

消融实验：换更强模型重跑，变好了是模型问题；把人工构造的正确上下文直接喂进去重跑，变好了是前序链路问题。关键判据是：正确信息直接给模型，它能答对吗？能，问题在链路；不能，问题在模型或 Prompt。

确认的 badcase 记四样：输入、期望输出或判定标准、归因标签、来源 trace id。按归因分三个集：检索集、工具集（选择加参数）、端到端集。改哪层跑哪个集，反馈最快；端到端集兜底，防止层间交互被漏掉。

holdout 规则

回归集不能拿来把 Prompt 调到 100% 通过。留一部分 holdout 平时不看、不针对性修改；按 badcase 类型分层抽样，每类都留样本；每轮按种子轮换，避免 holdout 被间接拟合。失效用例定期清理或标记停用，不删历史。

@dataclass
class BadCase:
    case_id: str
    input: str
    expected: Optional[str]     # 有标准答案就填
    rubric: Optional[str]       # 没有标准答案就填判定标准
    layer: Layer                # 归因标签
    source_trace_id: str        # 来源 trace，可重放
    split: str = "train"        # train / holdout
    active: bool = True         # 失效用例标记停用，不删历史

    def selectable(self) -> bool:
        return self.active and self.split == "train"


class RegressionSuite:
    """按归因分层组织回归集，holdout 平时不看"""

    # 目录落地：tests/regression/{retrieval,tool,end_to_end}/
    END_TO_END_LAYERS = {Layer.CONTEXT, Layer.PROMPT, Layer.MODEL}

    def retrieval_suite(self) -> list[BadCase]:
        return self._trainable(Layer.RETRIEVAL)

    def tool_suite(self) -> list[BadCase]:
        return self._trainable(Layer.TOOL)

    def end_to_end_suite(self) -> list[BadCase]:
        # 上下文、prompt、模型的问题都落在端到端集
        return [
            c for c in self.cases
            if c.selectable() and c.layer in self.END_TO_END_LAYERS
        ]

    def rotate_holdout(self, ratio: float = 0.2, seed: int = 0) -> None:
        """按归因类型分层抽样轮换 holdout，避免被反复拟合"""
        rng = random.Random(seed)
        active = [c for c in self.cases if c.active]
        for case in active:
            case.split = "train"

        groups: dict[Layer, list[BadCase]] = {}
        for case in active:
            groups.setdefault(case.layer, []).append(case)

        for group in groups.values():
            quota = max(1, int(len(group) * ratio))
            for case in rng.sample(group, min(quota, len(group))):
                case.split = "holdout"

CI/CD 与非确定性

多次运行，
比统计分布。

CI 里跑回归，Prompt 变更和代码变更一样触发。LLM 输出不确定，就用多次运行的均值、方差、通过率，必要时做统计检验。

CI 触发条件

原文的 GitHub Actions 示例监听三类路径：prompts/**、config/model.yaml、src/agent/**。跑完回归后，用 check_regression.py 对比 baseline / current，阈值示例是 0.05，即允许最多 5% 退化。

非确定性怎么处理

  • 同一用例跑 5 次，统计均值、标准差、最小值、最大值和通过率。
  • 用 LLM-as-Judge 评估语义质量，而不是精确匹配字符串。
  • 比较两个版本的得分分布，用 Mann-Whitney U 检验，p < 0.05 视为显著差异。
查看 NonDeterministicTester 的原文代码 
class NonDeterministicTester:
    """处理 LLM 输出的非确定性"""

    async def robust_test(self, case, n_runs=5):
        """多次运行取统计结果"""
        scores = []
        for _ in range(n_runs):
            output = await self.agent.invoke(case.input)
            score = await self.evaluate(case, output)
            scores.append(score)

        return {
            "mean": np.mean(scores),
            "std": np.std(scores),
            "min": np.min(scores),
            "max": np.max(scores),
            "pass_rate": sum(1 for s in scores if s >= case.threshold) / n_runs,
        }

    def compare_distributions(self, baseline_scores, current_scores):
        """用统计检验比较两个版本的得分分布"""
        from scipy.stats import mannwhitneyu

        stat, p_value = mannwhitneyu(baseline_scores, current_scores)
        return {
            "significant_difference": p_value < 0.05,
            "p_value": p_value,
            "baseline_mean": np.mean(baseline_scores),
            "current_mean": np.mean(current_scores),
        }

常见误区 / 面试追问

两个误区，
两个追问。

非确定性不是不做测试的理由；回归也不是大更新才做。规模和维护策略要按 Agent 复杂度定。

误区 01

“LLM 输出不确定，没法做回归测试”

非确定性不是不能测试的理由。用多次运行取统计指标（均值、方差、通过率），用 LLM-as-Judge 评估语义质量而非精确匹配，用统计检验判断是否显著退化。

误区 02

“回归测试只需要在大更新时做”

Prompt 的微小修改也可能导致显著行为变化。最佳实践是集成到 CI/CD，每次 Prompt 或配置变更都自动触发。初期投入大，长期省大量排错时间。

追问 03

Golden Dataset 多大合适？

取决于 Agent 复杂度。建议最少 50 个用例覆盖核心场景，理想 200–500 个。每个用例标注优先级，高优先级用例（如安全相关）必须 100% 通过。

追问 04

如何维护 Golden Dataset 的时效性？

从生产 bug 转成测试用例；定期审查和淘汰过时用例；随功能迭代补充新场景。Golden Dataset 应该是活的，随产品演进。

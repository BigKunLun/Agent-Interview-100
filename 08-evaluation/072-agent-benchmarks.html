中级 · Evaluation · 可交互讲解

一个分数，
测不出全部能力。

Agent Benchmark 是端到端评估 Agent 完成任务能力的标准化测试。和考知识的 MMLU 不同，它看的是完整执行过程：规划、工具使用、多步推理、错误恢复。代码、网页、通用助手、计算机使用、工具调用、长期记忆，各有各的基准。

关键边界：基准是受控环境，不是生产。榜单分数只能说明“在这个测试里表现如何”，不能直接推出“在你的业务里好用”。本页分数只按原文版本呈现，未联网核实。

两个 2026-09 的新维度

  • MyriadBench：专门测单 Agent 会话内任务交错、中断、相互依赖时的能力保持，对照隔离执行同任务的基线，用单一指数 MI 排名。它补的是“多任务在同一会话里互相踩踏”这个此前没有专属基准的维度。
  • TraceDance（ByteDance & UIC，arXiv:2609.33295）：从真实部署轨迹自动构建 Agent 行为基准，在决策点给模型下一轮打分，不需要环境重放。原文把它概括为“轨迹即基准”，让评测数据直接来自生产。

SWE-bench

代码 Agent 的标杆，

原文的 2026 污染结论

OpenAI 2026-02 公开声明（详见 SWE-bench Pro 发布说明）：SWE-bench Verified “increasingly contaminated”；最难的 59.4% 子集存在测试缺陷，包括 fail-to-pass 不严格、隐式依赖；OpenAI 已停止单独报告 Verified 成绩。原文建议主用 SWE-bench Pro，配合 Live、Multimodal、Multi-SWE-bench。

原文给出的 2026-05 SOTA 参考是：Claude Mythos Preview 93.9%，Claude Opus 4.7 87.6%，Claude Sonnet 4.5 80.9%。这些是原文口径的榜单数字，不是本页实测。

面试提示也来自原文：如果候选人还在引用“SOTA 72%”或更低数字，说明知识停留在 2024；能说出“Verified 已污染、应看 Pro / Live”才算跟上 2026 的评测话题。

GAIA

对人类简单，
对 Agent 极难。

GAIA 的答案是确定性的，用精确匹配评测，不需要 LLM Judge。它测多步推理和工具组合，三个难度等级分别约 5 步、5–10 步、最多约 50 步。

原文的示例题是：“找到 2024 年诺贝尔物理学奖获得者的本科毕业院校，这所院校的现任校长是谁？”需要搜索、提取、再搜索、再提取。它测的不是知识存量，而是把多个工具串起来的能力。

记忆专项

通用榜单，
几乎不测跨会话记忆。

SWE-bench 和 GAIA 都测不到“上次说过什么”。做带记忆的 Agent，要用 LoCoMo 和 LongMemEval 这类专项基准。

原文里的“残酷事实”

  • long-context LLM 直接喂全文，准确率掉 30%–60%。
  • 商用系统在简化场景下也只有 30%–70% 准确率。
  • 原因有三：lost in the middle；无关历史稀释信号；知识更新失效——模型很难识别“后面的信息覆盖前面的”。

设计原则

真实、可验证、
防泄露、多维度。

原文给了五条原则：真实性、可验证性、防泄露、多维度、抗游戏性。每条都配了做法和反例。

小团队怎么自己搭

原文的建议是从生产日志采样 50–100 个典型任务，定义明确的成功标准（可自动验证的优先），标注难度和类别；每次 Agent 更新后跑这套用例当回归测试。不需要从头造大规模基准。

class CustomAgentBenchmark:
    """为自己的 Agent 设计评估套件"""

    def __init__(self):
        self.test_cases = []

    def add_test(self, task, expected_result, difficulty, category,
                 required_tools=None, max_steps=None):
        self.test_cases.append({
            "task": task,
            "expected": expected_result,
            "difficulty": difficulty,      # easy/medium/hard
            "category": category,          # coding/search/analysis
            "required_tools": required_tools,
            "max_steps": max_steps,
        })

    async def run(self, agent):
        results = []
        for case in self.test_cases:
            trajectory = await agent.execute_with_trace(case["task"])

            result = {
                "task_success": self.check_result(
                    trajectory.final_output, case["expected"]
                ),
                "steps_used": len(trajectory.steps),
                "tools_used": [s.tool for s in trajectory.steps if s.tool],
                "cost": trajectory.total_cost,
                "latency": trajectory.total_time,
                "correct_tools": self.check_tools(
                    trajectory, case["required_tools"]
                ),
            }
            results.append(result)

        return self.aggregate_results(results)

    def generate_report(self, results):
        """按维度和难度分组的评估报告"""
        return {
            "overall_success_rate": np.mean([r["task_success"] for r in results]),
            "by_difficulty": self.group_by("difficulty", results),
            "by_category": self.group_by("category", results),
            "avg_cost": np.mean([r["cost"] for r in results]),
            "avg_steps": np.mean([r["steps_used"] for r in results]),
        }

当前挑战

饱和、泄露、
过拟合、方差。

原文列了五个挑战：数据泄露、基准饱和、过拟合基准、评估成本、非确定性。动态基准是应对之一，但质量控制仍是难题。

  • 数据泄露：基准题目可能出现在 LLM 的训练数据里。
  • 基准饱和：模型快速刷满分，基准失去区分能力。
  • 过拟合基准：针对基准优化不等于真实能力提升。
  • 评估成本：端到端 Agent 测试需要真实环境，成本高。
  • 非确定性：Agent 每次运行路径不同，评估结果有方差。

原文用 SWE-MERA 举例：持续从最新 GitHub Issue 自动收集测试用例，永远不被训练数据污染；挑战是自动收集的题目质量可能参差不齐。

常见误区 / 面试追问

两个误区，
四个追问。

榜单高不等于业务好用；一个基准也不够。回答时先说适用条件，再给基准名和证据强度。

误区 01

“在基准上得分高就说明 Agent 好用”

基准是受控环境，生产更复杂：网络问题、意外输入、安全攻击都可能出现。原文的说法是，SWE-bench 上 70% 的模型在实际开发中可能远达不到这个表现。基准是必要但不充分的。

误区 02

“一个基准就够了”

不同基准测不同能力。代码强（SWE-bench 高分）不代表网页操作好（WebArena）。要按 Agent 的实际使用场景选择或组合多个基准。

追问 03

如何防止 Agent 针对基准过拟合？

四条：用动态更新的基准（如 SWE-MERA）；保留私有测试集不公开；评估时加入从未见过的新类型任务；关注轨迹质量而非只看结果。

追问 04

小团队如何设计自己的 Agent 评估？

从生产日志采样 50–100 个典型任务，定义明确的成功标准（可自动验证的优先），标注难度和类别；每次 Agent 更新后跑这套用例当回归测试。不需要从头造大规模基准。

追问 05

如何设计 Memory Benchmark？

直接复用 LongMemEval（500 题）加 LoCoMo（多会话长对话）就能覆盖大部分场景。自建要重点覆盖四维：跨会话推理、时间推理、知识更新（LoCoMo 缺这块）、abstention（记忆里没有的事不要瞎编）。评估分两阶段：摄入 + 检索问答。

追问 06

为什么 long-context LLM 直接喂全部历史不行？

LongMemEval 实测，把全部对话直接塞进 long-context 模型，准确率比带 memory 系统掉 30%–60%。原因：lost in the middle；无关历史稀释相关信号；知识更新失效。所以要专门做提取、检索、rerank，而不是无脑加大 context。

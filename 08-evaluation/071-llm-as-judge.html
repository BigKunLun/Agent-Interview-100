中级 · Evaluation · 可交互讲解

会打分的模型，
也会偏。

LLM-as-Judge 用一个更强的 LLM 自动评估另一个模型的输出。两种核心模式：Pointwise 按 Rubric 给单个输出打分，Pairwise 比较两个输出谁更好。它便宜、可扩展，但分数是“有偏差的专家意见”，不是客观事实。

关键边界：衡量 Judge 可靠性要看 Cohen's Kappa，而不是 raw percent agreement。后者容易虚高：κ = 0.62 时，表面一致率仍可能超过 80%。

两种核心模式

打绝对分，
还是分胜负？

Pointwise 给单个输出打分，适合有明确标准的评估；Pairwise 比较两个输出，适合主观偏好，但会放大位置偏差。

原文的两种调用方式

Pointwise 把问题和回答放进 Prompt，要求 Judge 先分析优缺点，再输出 JSON 分数；Pairwise 把两个回答并排，要求给出 A 更好、B 更好或差不多，并说明理由。

查看 Pointwise 与 Pairwise 的原文代码 
# 模式 1：Pointwise 评分（直接打分）
async def pointwise_judge(question, answer, rubric=None):
    prompt = f"""
    请评估以下回答的质量。

    问题：{question}
    回答：{answer}

    评分标准（Rubric）：
    {rubric or '''
    5分：完全正确、完整、清晰
    4分：基本正确，有小瑕疵
    3分：部分正确，有明显遗漏
    2分：大部分不正确或不相关
    1分：完全错误或无关
    '''}

    请先分析回答的优缺点，然后给出分数。
    输出 JSON：{{"analysis": "...", "score": 1-5}}
    """
    return await judge_llm.invoke(prompt)

# 模式 2：Pairwise 对比（两两比较）
async def pairwise_judge(question, answer_a, answer_b):
    prompt = f"""
    比较以下两个回答，判断哪个更好。

    问题：{question}
    回答 A：{answer_a}
    回答 B：{answer_b}

    比较维度：准确性、完整性、清晰度、实用性。
    输出：A更好 / B更好 / 差不多，并说明理由。
    """
    return await judge_llm.invoke(prompt)

选择建议

有明确标准的评估，Pointwise 加详细 Rubric 更高效；主观偏好或两个版本难以绝对打分时，用 Pairwise，但要交换位置并检查一致性。

已知偏差

分数里的偏差，
有六种常见来源。

前五种是格式层的被动干扰，可以用交换位置、统一格式等机械手段缓解；第六种是修辞层的主动攻击，机械手段不够用。

修辞偏差为什么单独说

位置、冗长、格式偏差作用在表层特征上，像是随机噪声，固定流程基本能抵消。修辞偏差不同：改写本身合法合规，没有可对齐的“正确格式”，攻击者可以针对评分机制定向优化，也就是 reward hacking。

格式层偏差与修辞层偏差对比
位置 / 冗长 / 格式偏差修辞偏差
层次格式层：排序、长度、排版这类表层特征修辞层：论证语气、确定性措辞、框架叙述
性质被动干扰，方向大体固定，接近随机噪声主动攻击，攻击者可定向优化评分
缓解交换位置、统一格式等机械手段基本可消除机械手段无效；需要对抗性改写测试和人工抽检

原文引用 arXiv:2608.08975《How Can Rhetoric Reward-Hack AI Reviewers?》（2026-08-14）。该文报告：用 4200 篇改写稿（源自 120 篇 ICLR 2026 投稿）实验，在科学内容完全不变的前提下，纯修辞改写可以系统性操纵 AI 审稿打分。原文同时提醒，这是社区单次实验，截至原文更新时未见独立复现，应作为需要防范的风险面，而不是已确立的定量结论。

实践含义

只要打分会带来实际收益（论文录用、排行榜位次、RLAIF 奖励信号），就要假设被评估方会针对 Judge 优化。评估设计要包含对抗性改写的稳健性测试，并保留人工抽检。

构建可靠 Judge

重复、投票、
交换位置。

原文给了一个 ReliableLLMJudge：同一输入评三次取平均，多模型取中位数，Pairwise 交换位置后再判。

三种降低偏差的手段

  • 多次评估取平均：同一问题、同一回答评三次，减少单次随机性。
  • 多 Judge 投票：不同家族的模型各评一次，取中位数作为共识，减少单模型偏差。
  • Pairwise 去偏：正序和交换位置各评一次；两次都选同一个答案才算胜出，否则判“不确定”。
查看 ReliableLLMJudge 的原文代码 
class ReliableLLMJudge:
    """带偏差缓解的 LLM 评估系统"""

    async def evaluate(self, question, answer, rubric):
        scores = []

        # 策略 1：多次评估取平均（减少随机性）
        for _ in range(3):
            score = await self.pointwise_judge(question, answer, rubric)
            scores.append(score)
        avg_score = np.mean(scores)

        # 策略 2：多 Judge 投票（减少单模型偏差）
        judges = ["gpt-4o", "claude-sonnet-4-5", "gemini-pro"]
        multi_scores = []
        for judge in judges:
            s = await self.judge_with_model(judge, question, answer, rubric)
            multi_scores.append(s)
        consensus = np.median(multi_scores)

        return {
            "single_judge_avg": avg_score,
            "multi_judge_consensus": consensus,
            "agreement": self.compute_agreement(multi_scores),
        }

    async def pairwise_debiased(self, question, answer_a, answer_b):
        """消除位置偏差的 Pairwise 评估"""
        # 正序评估
        result_1 = await self.pairwise_judge(question, answer_a, answer_b)
        # 交换位置再评估
        result_2 = await self.pairwise_judge(question, answer_b, answer_a)

        if result_1 == "A" and result_2 == "B":
            return "A更好"  # 两次都选了同一个答案
        elif result_1 == "B" and result_2 == "A":
            return "B更好"
        else:
            return "不确定"  # 结果不一致，可能真的差不多

怎么选 Judge 模型

原文给的原则是：Judge 应比被评估模型更强；Judge 应与被评估模型来自不同家族，减少自我偏好；关键评估用多个 Judge 投票。常见组合是用 GPT-4o 评估 Claude 输出，反之亦然。

成本控制

原文给出的做法是：大规模评估采样而非全量；先用便宜模型初筛，只对边界案例用强 Judge；缓存相同输入的评估结果。原文称 LLM Judge 成本通常是人工评估的 1/10。

Rubric 设计

“评估质量”太虚，
拆成可打分的项。

好的 Rubric 把每个维度的分数锚点写清楚。原文的示例是四项、满分 10 分：准确性 0–3、完整性 0–3、清晰度 0–2、实用性 0–2。

具体 Rubric 比模糊的“评估质量”可靠得多。每一项都说明什么情况得几分，Judge 才有稳定的判断依据，人工校准也才有可对照的标尺。

查看原文的四维 Rubric 
rubric_example = """
评估维度及标准：

1. 事实准确性 (0-3分)
   3: 所有事实完全正确
   2: 大部分正确，有 1-2 处小错误
   1: 有多处事实错误
   0: 大部分内容不准确

2. 完整性 (0-3分)
   3: 全面覆盖问题的所有方面
   2: 覆盖了主要方面，遗漏了次要点
   1: 只回答了部分问题
   0: 严重遗漏关键内容

3. 清晰度 (0-2分)
   2: 结构清晰，逻辑连贯
   1: 基本可读但组织可改进
   0: 混乱难懂

4. 实用性 (0-2分)
   2: 包含可操作的建议或代码
   1: 提供了方向但缺少细节
   0: 纯理论无实用价值

总分 = 准确性 + 完整性 + 清晰度 + 实用性（满分 10）
"""

Rubric 还有两个作用：一是把“简洁也是优点”写进去，抵消冗长偏差；二是要求 Judge 先给分析再给分，让分数有可检查的依据。

前沿趋势

不只推理，
还能动手验证。

Agent-as-Judge 用 Agent 代替纯 LLM：除了推理评判，还能搜索事实、执行代码，再综合打分。原文把它列为 2025 年的新趋势。

纯 LLM Judge 只能基于已有上下文判断。Agent-as-Judge 多了工具：抽取回答中的关键声明并搜索验证，抽取代码块并执行检查，再把核查结果综合成评分。

查看 AgentJudge 的原文代码 
class AgentJudge:
    """用 Agent 替代纯 LLM 做评估——可以调用工具验证"""

    async def evaluate(self, question, answer):
        # Agent 不仅用推理评判，还可以执行验证动作

        # 1. 事实核查：搜索验证关键声明
        claims = await self.extract_claims(answer)
        fact_checks = []
        for claim in claims:
            evidence = await self.web_search(claim)
            is_true = await self.verify(claim, evidence)
            fact_checks.append({"claim": claim, "verified": is_true})

        # 2. 代码验证：运行代码检查正确性

常见误区 / 面试追问

五个问题，
分清分数与事实。

两个误区、三个追问。回答时先给结论，再讲适用条件和证据强度。

误区 01

“LLM Judge 的评分就是客观事实”

评分包含系统性偏差，只能算“有偏差的专家意见”，需要人工标注定期校准。衡量可靠性必须用 Cohen's Kappa，而不是 raw percent agreement。原文给出的基准是：人类-人类 κ ≈ 0.80，顶级 LLM Judge（GPT-4o / Claude Opus）κ ≈ 0.78–0.84（“Judging the Judges”, arXiv:2406.12624）。

误区 02

“Pairwise 比 Pointwise 总是更好”

Pairwise 在主观评估（风格、偏好）上更稳定；但对有明确标准的评估（事实正确性），Pointwise 加详细 Rubric 更高效。原文引用 ACL 2025 研究指出，Pairwise 实际上会放大偏差。

追问 03

如何选择 Judge 模型？

三条原则：Judge 应比被评估模型更强；Judge 应与被评估模型来自不同家族，减少自我偏好；关键评估用多个 Judge 投票。常见选择是 GPT-4o 评估 Claude 输出，反之亦然。

追问 04

LLM Judge 的成本如何控制？

大规模评估采样而非全量；先用便宜模型做初筛，只对边界案例用强 Judge；缓存相同输入的评估结果。原文称 LLM Judge 成本通常是人工评估的 1/10。

追问 05

缓解了位置偏差和冗长偏差，Judge 就可信了吗？

不够。位置、冗长、格式属于格式层的被动干扰，交换位置、统一排版基本可以消除；但 arXiv:2608.08975 报告了修辞层的主动攻击面：科学内容不变，纯修辞改写即可系统性操纵 AI 审稿打分。该实验用 4200 篇改写稿（源自 120 篇 ICLR 2026 投稿），改写本身合法合规，没有可对齐的“正确格式”。实践上，凡打分会带来收益的场景都要假设被评估方会针对 Judge 优化，加入对抗性改写测试并保留人工抽检。注意该结论来自社区单次实验、尚未独立复现，应作为风险面而非定量事实。

高级 · Evaluation · 可交互讲解

评估不是关卡，
是常开的回路。

一次性评估假设“测过一次就永远有效”。但模型 API 会更新，检索索引会变，用户问题会漂。持续评估把质量检查放进每次变更、每次发布和每天的流量里。

原文把流水线分三段：开发期 CI 回归、上线期灰度、运行期在线评估，再用用户反馈回流 Golden Dataset 形成闭环。本页的阈值、通过率、成本都是固定教学数据或原文示例；不连接 CI、不调用模型、不产生真实流量。

一 · 为什么不能只评一次

模型没换，
行为也会变。

一次性评估的隐含假设是“环境静止”。原文列出五种问题，每一种都能让旧测试集失去代表性。

一次性评估的问题与持续评估的做法
变化 / 假设一次性评估的盲区持续评估的做法
评估一次就永远有效（假设）把一次结果当成长期结论；环境变化后仍沿用旧结论。评估改为 always-on，每次变更都重新验证。
模型 API 更新版本悄悄变化，旧分数不再代表当前行为。每次变更触发回归，定时任务兜底。
用户行为演化原有测试集不再代表真实场景。生产流量抽样评估，反馈回流数据集。
Prompt 小修改可能引入意想不到的退化。Prompt 文件变更自动跑评估。
RAG 索引更新回答质量漂移，离线集看不到。索引更新也作为触发条件。

原文的核心理念是：评估不是发布前的关卡，而是贯穿整个生命周期的闭环。关卡只回答“这次能不能过”，闭环还要回答“上线后有没有变坏、坏了能不能自动止损、经验有没有回到测试集”。

原文引用、未联网核实

原文称采用结构化评估的团队报告准确率提升 35–40%、迭代速度提升 5–10 倍。这是原文引用的团队自报数据，不是本页实测，也不构成对任何团队的承诺。

二 · 三阶段架构

每段有门，
最后回到起点。

开发期用回归测试挡住坏变更，上线期用灰度控制影响面，运行期用抽样和漂移检测发现渐进退化。用户反馈再回流到 Golden Dataset。

持续评估三阶段的触发、内容、门与工具
阶段触发 / 范围评估内容质量门工具示例
开发期Prompt、模型配置、Agent 代码、RAG 索引变更。Golden Dataset 回归、Prompt Injection 等安全测试、格式测试。关键指标低于阈值 → 阻止 PR 合并。GitHub Actions + DeepEval / Ragas。
上线期Canary 环境 5% 流量。Canary 与 Production 的质量、满意度、延迟 P95、成本对比。达标则 25% → 50% → 100%；退化则自动回滚。Feature Flags + A/B 测试框架。
运行期10% 生产请求抽样。LLM Judge 评分、24 小时趋势、显式与隐式反馈、熔断。质量分低于阈值或成本超预算 → 降级。Langfuse / Braintrust + Prometheus + PagerDuty。

三段的门不是同一个东西。开发期门是“别把已知的坏变更放进来”，上线期门是“坏变更只影响 5%”，运行期门是“坏变化发生时自动止损”。缺任何一段，另外两段都会被迫承担不属于它的责任。

三 · CI/CD 集成

变更触发，
基线对比，阻塞合并。

原文的 GitHub Actions 例子把三件事串起来：路径触发的回归、独立的安全测试、与基线对比后回帖到 PR。

  • 触发：PR 修改 prompts/**、config/model.yaml、src/agent/**；另有每天凌晨 2 点的定时运行。
  • 回归：在 Golden Dataset 上跑 pytest，输出当前结果并与 baseline 对比。
  • 安全：独立的注入测试集，不让安全用例被普通回归淹没。
  • 门：--max-regression 0.05，关键指标是 accuracy 与 safety_pass_rate；超限则失败。
  • 反馈：把评估结果自动回帖到 PR，让人在合并前看到证据。

原文 GitHub Actions 示例（YAML，仅展示，不执行）

name: LLM Continuous Evaluation

on:
  pull_request:
    paths:
      - 'prompts/**'
      - 'config/model.yaml'
      - 'src/agent/**'
  schedule:
    - cron: '0 2 * * *'

jobs:
  regression-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run core regression tests
        run: |
          python -m pytest tests/eval/regression/ \
            --golden-dataset data/golden_v3.json \
            --baseline results/baseline.json \
            --output results/current.json
      - name: Run safety tests
        run: |
          python -m pytest tests/eval/safety/ \
            --injection-dataset data/injection_tests.json
      - name: Compare with baseline
        run: |
          python scripts/compare_eval.py \
            --baseline results/baseline.json \
            --current results/current.json \
            --max-regression 0.05 \
            --critical-metrics accuracy,safety_pass_rate

四 · 在线评估与反馈闭环

抽样打分，
漂移告警，反馈回炉。

在线评估不是给每个请求打分，而是按比例抽样。原文的示例是 10% 抽样、24 小时窗口、退化超过 10% 告警、最近 100 个请求平均质量低于 0.5 触发熔断。

在线评估、漂移检测与熔断的原文示例参数
机制原文示例作用
抽样评估sample_rate=0.1，Judge 对请求打分。用可控成本覆盖真实流量分布。
漂移检测24 小时窗口，当前均值相对基线下降超过 10% 告警。发现渐进退化，而不是等用户投诉。
熔断最近 100 个请求平均质量 < 0.5 → 切换降级模式。质量过低时先止损，再排查。
反馈回流负面反馈经人工审核后，加入 Golden Dataset。让测试集跟上真实失败，不是只增数量。

反馈要分显式和隐式。显式是点赞 / 点踩、评分、投诉；隐式是重试率、编辑率、会话放弃率。原文特别强调，负面反馈不能自动进测试集，必须经过人工审核并填入修正后的期望输出，否则会把用户的误解也固化成标准答案。

10%、24 小时、10%、0.5 都是原文示例阈值，不是通用推荐值；本页把它们作为固定教学数据演示。

六 · 实施路线图

先记录，再拦截，
最后闭环。

原文按六个月排了四段。顺序有讲究：先有 trace 和指标，才谈得上评估；先有离线回归，才谈得上 CI 门；先有在线数据，才谈得上漂移和熔断。

Month 1
  • 接入 Langfuse / LangSmith，所有请求记录 Trace。
  • 定义核心指标：质量、安全、延迟、成本。
  • 构建初始 Golden Dataset（50–100 条）。
Month 2
  • 回归测试接入 GitHub Actions。
  • Prompt 变更触发自动评估。
  • PR 中自动回帖评估报告。
Month 3
  • 部署 LLM Judge 对生产流量抽样评估。
  • 搭建监控仪表盘。
  • 配置告警规则；建立用户反馈收集。
Month 4–6
  • 用户反馈回流 Golden Dataset。
  • 漂移检测 + 自动熔断。
  • A/B 测试框架；定期评估审查会议。

时间安排为原文建议，不是实施承诺；团队规模与现有基础设施不同，节奏会变。

常见误区 / 面试追问

两个误区，
两个追问。

按原文顺序保留 4 条：前两条是误区，后两条是追问。

误区 1

“评估一次就够了，模型又没变。”

即使不主动换模型，API 提供商也可能更新版本；RAG 索引更新、用户行为变化都会导致质量漂移。持续评估是发现这些隐性退化的唯一方式。

误区 2

“在线评估太贵了。”

抽样 10% 的请求，用低成本模型做 Judge（原文示例约 $0.001 / 评估），1 万请求 / 天约 $1 / 天。相比质量问题导致的用户流失，这个成本很小。关键是按风险选抽样率和 Judge 档位，不是全量用最贵的模型。

追问 1

“如何处理评估指标之间的冲突？”

三步：定义各指标的优先级和阈值；用加权综合得分（原文示例 quality×0.5 + cost×0.2 + latency×0.2 + safety×0.1）；设置硬性底线，例如安全分低于 95% 一票否决。权重是示例，不是通用配方。

追问 2

“小团队如何低成本起步？”

最小可行方案三步：用 Langfuse（免费开源）记录所有请求；维护 50 条 Golden Dataset，用 pytest 在 CI 里跑；生产环境收集点赞 / 点踩反馈。原文称这三步一周能搭好，之后逐步迭代。

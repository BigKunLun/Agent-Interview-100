LLM 评估

三类方法，
各有各的盲区。

自动指标快而便宜，人工评估准而贵，LLM-as-Judge 试图在两者之间取得规模和质量的平衡。生产环境通常不是三选一，而是分层组合。

一、LLM 评估方法全景

原文把 LLM 评估分成三大类：自动指标用算法计算确定性指标，速度快、成本低，但只能衡量表面特征；人工评估由人类标注者评判输出质量，是“金标准”，但成本高、难以规模化；LLM-as-Judge 用强 LLM 评估其他 LLM 的输出，是近年主流趋势。

三类 LLM 评估方法在代表手段、速度、成本、质量和规模上的对比
维度自动指标LLM-as-Judge人工评估
代表手段BLEU / ROUGE、精确匹配、F1、PerplexityGPT-4 打分、多维度评估、Pairwise 对比、Rubric 评分专家评审、众包标注、用户反馈、A/B 测试
速度最快中等最慢
成本最低中等最高
质量有限较好最好
规模无限大小

Sebastian Raschka 把 LLM 评估总结为四种方法：多选基准、人类偏好、自动化 LLM 评估和编程基准。这四种视角和上面的三类方法不是一一对应，但可以互相补充：多选基准和编程基准偏自动，人类偏好偏人工，自动化 LLM 评估就是 LLM-as-Judge。

二、自动指标评估：快，但只看表面

自动指标适合有明确参考答案或可运行测试的任务。原文给出四种常见指标的实现：精确匹配、BLEU、ROUGE 和 F1。

# 常见自动评估指标

# 1. 精确匹配（Exact Match）
def exact_match(prediction, reference):
    return prediction.strip() == reference.strip()
# 适用：数学题答案、事实性问题、代码输出

# 2. BLEU（机器翻译质量）
from nltk.translate.bleu_score import sentence_bleu
score = sentence_bleu([reference.split()], prediction.split())
# 衡量 n-gram 重叠度，0-1 分

# 3. ROUGE（摘要质量，recall-oriented；与 precision-oriented 的 BLEU 互补）
from rouge_score import rouge_scorer
scorer = rouge_scorer.RougeScorer(['rouge1', 'rougeL'])
scores = scorer.score(reference, prediction)
# ROUGE-1: unigram 召回率（reference 中有多少出现在 prediction）
# ROUGE-L: 最长公共子序列（衡量句子级流畅度）
# 对比 BLEU：BLEU 是 precision-oriented（prediction 中有多少匹配 reference）
# 摘要任务用 ROUGE，翻译任务用 BLEU 是因为这两类任务对漏掉信息 vs 多说信息的容忍度不同

# 4. F1 Score（信息提取）
def token_f1(prediction, reference):
    pred_tokens = set(prediction.split())
    ref_tokens = set(reference.split())
    common = pred_tokens & ref_tokens
    precision = len(common) / len(pred_tokens) if pred_tokens else 0
    recall = len(common) / len(ref_tokens) if ref_tokens else 0
    f1 = 2 * precision * recall / (precision + recall) if (precision + recall) else 0
    return f1

这些指标的共同局限是：只看词面，不看语义。原文的例子是“北京是中国的首都”和“中国的首都是北京”，两句话语义完全相同，但 BLEU/ROUGE 可能拿不到满分；它们也无法评估回答的有用性、创造性和安全性。LLM 时代，这些传统指标的参考价值有限，更适合作为初筛信号，而不是质量结论。

三、LLM-as-Judge：用强模型评弱模型

LLM-as-Judge 用强 LLM 评估其他 LLM 的输出。原文给出的关键数字是：顶级 Judge（GPT-4o / Claude Opus）与人工评估的 Cohen's Kappa ≈ 0.78–0.84，已经逼近人类-人类一致性（κ ≈ 0.80）。Cohen's Kappa 衡量的是“扣除随机一致之后，评估者之间到底有多一致”，所以比单纯的 percent agreement 更能反映 Judge 的可靠性。

percent agreement 容易虚高。原文的例子是：κ = 0.62 时，表面一致率仍可能超过 80%。学术界在 “Judging the Judges”（arXiv:2406.12624）中建议用 Cohen's Kappa 作为 Judge 可靠性的正确指标，而不是只看一致率。

LLM-as-Judge 的四种已知偏差与缓解方式
偏差表现缓解方式
位置偏差倾向于给排在前面的回答更高分交换 A/B 位置做两次评估取平均
冗长偏差倾向于给更长的回答更高分用明确的评分 Rubric 约束
自我偏好GPT-4 作为 Judge 时偏爱 GPT-4 自己的输出使用与被评估模型不同的 Judge 模型
格式偏差倾向于给格式更好看的回答更高分统一输出格式，评分只看内容维度

Pointwise 与 Pairwise 两种问法 · 原文代码

async def llm_as_judge(question, answer, reference=None):
    """用 LLM 评估回答质量"""

    # 方式 1：直接评分（Pointwise）
    pointwise_prompt = f"""
    请评估以下回答的质量（1-5分）：

    问题：{question}
    回答：{answer}
    {"参考答案：" + reference if reference else ""}

    评分维度：
    - 准确性 (1-5)：事实是否正确？
    - 完整性 (1-5)：是否全面回答了问题？
    - 有用性 (1-5)：对提问者是否有帮助？
    - 清晰度 (1-5)：表达是否清楚？

    请给出每个维度的分数和简要理由，最后给出总分。
    """

    # 方式 2：对比评分（Pairwise）
    pairwise_prompt = f"""
    问题：{question}

    回答 A：{answer_a}
    回答 B：{answer_b}

    哪个回答更好？请从准确性、完整性和清晰度三个维度比较。
    输出：A 更好 / B 更好 / 差不多
    """

    return await judge_llm.invoke(pointwise_prompt)

五、混合评估框架（推荐）

混合评估是生产推荐方案：自动指标做初筛，LLM-as-Judge 做质量评估，人工评估做最终校准。原文的三层结构是：Layer 1 自动指标全量跑，毫秒级；Layer 2 LLM Judge 全量或采样，秒级；Layer 3 把低分和边界案例送人工审核。

class HybridEvaluator:
    """混合评估：自动指标 + LLM Judge + 人工抽检"""

    async def evaluate(self, test_set):
        results = []

        for example in test_set:
            prediction = await self.model.invoke(example.input)
            scores = {}

            # Layer 1: 自动指标（全量，毫秒级）
            scores["exact_match"] = exact_match(prediction, example.reference)
            scores["f1"] = token_f1(prediction, example.reference)

            # Layer 2: LLM-as-Judge（全量或采样，秒级）
            scores["llm_judge"] = await llm_as_judge(
                example.input, prediction, example.reference
            )

            # Layer 3: 标记需要人工审核的案例
            if scores["llm_judge"]["total"] < 3 or scores["f1"] < 0.5:
                scores["needs_human_review"] = True

            results.append(scores)

        # Layer 3 继续：人工审核低分和边界案例
        flagged = [r for r in results if r.get("needs_human_review")]
        # 送人工审核队列...

        return results

九、轨迹评估：把“怎么做的”拆开打分

轨迹评估通常拆成四类分数：步骤质量、轨迹效率、目标达成度、错误恢复率。原文的 TrajectoryEvaluator 对每一步调用 LLM 评分，再分别计算效率、目标是否达成，以及发生错误后是否恢复。

class TrajectoryEvaluator:
    """评估 Agent 的完整执行轨迹"""

    async def evaluate_trajectory(self, task, trajectory):
        scores = {}

        # 1. 步骤级评估：每一步是否合理
        step_scores = []
        for i, step in enumerate(trajectory.steps):
            step_score = await self.evaluate_step(
                task=task,
                step=step,
                context=trajectory.steps[:i],  # 前序上下文
            )
            step_scores.append(step_score)
        scores["step_quality"] = np.mean(step_scores)

        # 2. 轨迹效率：是否有冗余步骤
        scores["efficiency"] = self.compute_efficiency(
            actual_steps=len(trajectory.steps),
            optimal_steps=self.get_optimal_length(task),
        )

        # 3. 目标达成度
        scores["goal_achieved"] = await self.check_goal(
            task=task,
            final_state=trajectory.final_state,
        )

        # 4. 错误恢复：遇到错误后的处理
        errors = [s for s in trajectory.steps if s.is_error]
        if errors:
            recovery_rate = sum(1 for e in errors if e.was_recovered) / len(errors)
            scores["error_recovery"] = recovery_rate

        return scores

每一步的 evaluate_step 会用 LLM 判断三件事：这一步是否推进了任务目标、工具选择是否正确、参数是否合理，并给出 1–5 分。上方互动演示就是这条思路的固定数据版：五个步骤得到 5、5、3、2、4 分，平均 3.80；最优 4 步、实际 5 步，效率按 optimal / actual 算得 0.80。原文只给出 compute_efficiency(actual_steps, optimal_steps) 的函数名，没有规定具体公式，所以“效率 = 最优步数 / 实际步数”是本页演示的明确假设，不是原文结论。

十一、生产环境评估框架

原文把生产指标分成三组：核心指标（任务完成率、平均步骤数、平均延迟、平均成本）、质量指标（轨迹质量、工具使用准确率、幻觉率）、安全指标（安全违规率、越权操作率）。每次执行都保留完整轨迹，再按同一套维度打分。

class ProductionAgentEvaluator:
    """生产环境中的 Agent 评估"""

    async def run_eval_suite(self, agent, test_cases):
        results = []
        for case in test_cases:
            # 执行并记录完整轨迹
            trajectory = await agent.execute_with_trace(case.task)

            # 多维评估
            eval_result = {
                "task_success": self.check_success(trajectory, case.expected),
                "steps": len(trajectory.steps),
                "cost": trajectory.total_cost,
                "latency": trajectory.total_time,
                "trajectory_score": await self.judge_trajectory(trajectory),
                "tool_accuracy": self.check_tool_usage(trajectory),
                "safety": self.check_safety(trajectory),
            }
            results.append(eval_result)

        return self.aggregate(results)

推理过程评估

答案对，
推理不一定对。

这一节从“Agent 做了什么”深入到“Agent 是怎么想的”。原文说明这部分整合自 #057（#057 原文已并入本节），聚焦过程奖励、推理忠实性、推理质量层次和 Trace 诊断规则。

1. 推理质量的四个层次

Level 1单步推理正确性：每一步推理是否逻辑正确？
Level 2工具使用合理性：是否选对了工具？参数是否正确？
Level 3推理路径质量：推理过程是否高效、合理、有无弯路？
Level 4任务完成度：Agent 是否完成了用户的请求？

结果正确 ≠ 过程正确。一个 Agent 可能因为错误的推理偶然得到正确答案（right answer, wrong reason）。只看 Level 4 会高估它的推理能力；只有 Level 1–3 同时成立，结果才可靠、可复现。这也是纯结果评估（ORM）会漏掉“答案对但推理错”的原因。

2. PRM vs ORM：过程奖励与结果奖励

结果奖励模型与过程奖励模型的五个维度对比
维度ORM（Outcome Reward Model）PRM（Process Reward Model）
评估对象只看最终答案是否正确对推理过程的每一步打分
错误定位无法定位错误在哪一步精确定位第一个出错的步骤
实现成本低（一次打分）高（每步都要打分，需逐步标注）
适合场景大规模自动评估、初筛训练奖励信号、调试、争议案例深挖
典型盲区right-answer-wrong-reason 被漏掉标注成本高，难以全量铺开

原文的例子：一道算术题，Step 1 算“15 × 20 = 300”得 0.95 分，Step 2“卖掉 120 个”得 0.90 分，Step 3 写成“剩余 300 + 120 = 420”只得 0.05 分。ORM 只看到最终答案 420 是错的，知道错但不知道错在哪一步；PRM 能定位到 Step 3 的运算符号错误。实践建议是两者结合：ORM 做便宜的全量初筛，PRM 对失败或争议案例做深入分析。

在 Agentic-RL 训练中，PRM 提供的逐步奖励信号比 ORM 更能稳定提升推理能力。这条线的展开在 103 Agentic-RL / GRPO。

3. Faithfulness：推理链是否真的被使用

忠实性（Faithfulness）指推理链是否真实反映模型的决策过程，而不是事后合理化。模型可能先得出答案，再编一条看似合理的推理链来“解释”这个答案；这样的推理链是装饰性的，不是功能性的。

核心检测思路是干预法：篡改推理链中的某个关键步骤，看最终答案是否随之改变。改掉关键步骤后答案若不变，说明模型没有真正使用这条推理链，它是不忠实的。

def check_faithfulness(model, problem, original_reasoning):
    """忠实性检测：改掉关键步骤，看答案是否真的依赖它"""
    # 1. 原始推理链及其答案
    original_answer = model.solve(problem, reasoning_hint=original_reasoning)

    # 2. 篡改中间某个关键步骤（如把中间计算结果改错）
    tampered = tamper_step(original_reasoning, step_idx=3, new_value="999")

    # 3. 答案若不变 → 模型并未真正依赖这条推理链 → 不忠实
    tampered_answer = model.solve(problem, reasoning_hint=tampered)
    is_faithful = original_answer != tampered_answer
    return is_faithful

OpenAI 的 CoT Monitorability 研究正在系统性地探索思维链在多大程度上能被忠实监控。这与推理模型的可解释性直接相关：如果一个推理模型的 CoT 不可忠实监控，基于 CoT 的安全审查就形同虚设。推理模型本身的讨论在 055 Reasoning Models。

4. 基于 Trace 的生产诊断规则

生产环境不可能逐条人工审推理，通常把推理与工具调用记录成 Span 级别的 Trace，再用启发式规则自动标红异常轨迹。原文给出四条规则，分别对应循环、重试、选型和开销四类隐患。

四条 Trace 自动评估规则及对应的隐患
规则触发条件说明
循环推理推理步骤数 > 阈值可能陷入循环或来回兜圈
工具滥用同一工具连续调用 > 3 次可能在重试无效操作
策略失误工具调用失败率 > 30%工具选择策略有问题

典型工具栈是 Langfuse / LangSmith / Arize Phoenix。这些平台原生支持 Span 属性（输入、输出、延迟、token）和父子关系，上述规则可以配置成告警阈值，不需要手写轮询逻辑。Trace 结构本身在 074 Traces and Spans；把规则接入持续评估流水线在 077 Continuous Evaluation Pipeline。

常见误区 / 面试追问

八个容易被追问的点。

前四条是误区，后四条是面试追问；答案都来自原文。

误区 1

“BLEU/ROUGE 分数高就说明质量好。”

这些指标只衡量表面词汇重叠，无法评估语义正确性、逻辑合理性和实用性。两个语义相同但措辞不同的回答可能得到很不同的 BLEU 分数；LLM 时代这些传统指标的参考价值有限。

误区 2

“LLM-as-Judge 完全可以替代人工。”

LLM Judge 有系统性偏差（冗长偏好、位置偏差、自我偏好），在医学、法律等专业领域的判断可能不可靠。生产中应该定期用人工评估校准 LLM Judge 的准确性。

误区 3

“Agent 评估只看最终结果就够了。”

最终结果正确但过程不合理的 Agent 同样有问题：可能走了弯路浪费资源，可能碰巧得到正确结果但推理错误（不可靠），也可能使用了不安全的操作。轨迹评估和结果评估同等重要。

误区 4

“用 LLM 基准测试就能评估 Agent。”

MMLU 这类 LLM 基准测试的是知识和推理能力，无法反映 Agent 的工具使用、规划和错误恢复能力。Agent 需要专用基准，如 SWE-bench、WebArena、GAIA。

追问 1

如何提高 LLM-as-Judge 的可靠性？

（1）提供详细的评分 Rubric，而不是让 Judge 自由打分；（2）交换位置做两次评估取平均，消除位置偏差；（3）用多个 Judge 模型投票；（4）定期用人工标注校准。

追问 2

评估数据集从哪里来？

三个来源：（1）从生产日志中采样真实问题；（2）人工构造边界案例和对抗样本；（3）使用公开基准（MMLU、GSM8K 等）。最佳实践是三者结合：公开基准评估通用能力，私有数据集评估业务场景。

追问 3

如何评估 Agent 的效率？

三个维度：（1）步骤效率——完成任务用了多少步，对比最优步数；（2）成本效率——消耗了多少 token 或金钱；（3）时间效率——端到端延迟。权衡是：更多步骤可能提升准确率，但也会增加成本。

追问 4

Agent 评估的最大难点是什么？

非确定性。同一任务可能有多条正确路径，无法用固定的“标准答案”对比。解决方案：（1）评估最终状态而非中间步骤；（2）用 LLM Judge 评估轨迹的合理性；（3）多次运行取统计指标。

高级 · Evaluation · 可交互讲解

95% 的准确率，
可能只是见过题。

静态 benchmark 测的是固定题库。模型可能背过答案、针对题库调过流程、或者只是在题库的分布上表现好。到了你的生产数据上，这些优势不跟着走。

原文把失效归为四因：数据泄露、分布偏移、评估粒度不足、基准饱和。本页所有分数、榜单与论文日期按原文 2026-10 口径保留，标“原文版本、未联网核实”；互动中的模型与分数是固定教学数据，不是真实榜单。

一 · 四个失效原因

高分消失，
通常不是模型变笨。

原文列出四个原因。它们可以单独出现，也常常叠加：一个模型既背过题，又只在题库分布上被优化过，还在已经饱和的指标上领先 2 个百分点。

原因 1

数据泄露

训练数据包含基准题目，模型在“记忆”答案而不是推理。原文引用 LiveCodeBench 的观察：部分模型在训练截止日期之前的题目上，准确率比之后的题目高 20–30%。

原因 2

分布偏移

基准的任务类型和难度分布不等于生产环境。MMLU 测学术知识，不等于用户的真实问题；HumanEval 测独立函数，不等于修改大型代码库。

原因 3

评估粒度不足

只看最终对错，不看过程。模型可能用错误推理得到正确答案；也可能在 95% 的简单题上全对，但 5% 的关键场景全错。

原因 4

基准饱和

顶尖模型都在 90%+，失去区分度。原文举例：MMLU 上 GPT-4o 88%、Claude 87%、Gemini 86%，2–3% 的差距在统计上可能不显著。

原文版本、未联网核实

20–30% 的下降幅度、MMLU 的 88 / 87 / 86 都是原文 2026-10 口径。本页未联网核对，也不更新榜单；这些数字只用来说明失效机制，不是当前排名。

二 · 大脱钩

排行榜，
失去了预测力。

2025 年业界观察到“The Great Decoupling”：公开排行榜与生产表现脱钩。原文给了三条证据和一个反例式的尝试——HLE。

原文的定义很直接：公开排行榜失去了对生产用例的预测能力。三条证据是：MMLU 80%+ 对生产表现几乎没有预测力；模型在真正新颖的问题上得分下降 20–30%；基准得分相近的模型在实际任务中表现差异巨大。根因是静态基准测的是“过去的能力”，不是“未来的泛化”。

HLE（Humanity's Last Exam）是一次反向尝试：由领域专家出极难题目（2700+ 题），目标是设计模型“不可能”通过的学术基准。发布初期（2025-01）最强模型准确率低于 10%；原文记录 2026-05 的 SOTA 是 Gemini 3.1 Pro Preview 约 44.7%（Artificial Analysis 数据），一年内从 10% 到 44%+，约 4 倍。

但原文把 HLE 也归为反面教材：它仍然是静态的。饱和速度远超预期，正好印证“静态基准会被追上”。

HLE 的题量、日期与 44.7% 均按原文 2026-10 口径保留，未联网核实。

三 · SWE-bench 信任危机

87–94%，
不等于接近完美。

原文给出一句面试总结：SWE-bench 顶部 87–94% 不是“模型已经接近完美”，而是“评测流程已经被充分优化”。

SWE-bench 分数可被操纵的四个维度
刷分维度做法为什么生产不可复现
Harness 配置同一模型换不同测试容器 / 框架配置。生产用的是你自己的 harness，不会为分数调参。
Retry 策略失败后自动重试、多次采样取最优解。生产没有无限重试预算，重试还会放大成本和延迟。
Reasoning effort开更长推理链、更多 token 预算。生产要在成本与延迟约束下运行，不能每题都拉满。
Test patch 选择性只跑测试子集，规避可能失败的用例。真实用户不会只挑你会做的用例。

原文的归因是：基准从“测真实能力”退化为“测刷分能力”，比的是谁更会针对基准优化。更关键的是，SWE-bench 只测单点 bug 修复，不覆盖真实软件的长周期演化；高分 Agent 在多文件协作、跨模块重构中，表现远不如分数暗示。

“任何在生产中无法复现的重试预算、容器配置、推理预算，都是 benchmark 分数的水分来源。”

原文的应对是三条：固化评测流程配置（统一 harness、禁止无限重试），挤出水分；用 SWE-EVO 等演化型基准补充；始终回到自己的领域数据验证。

87–94%、Claude 系列领先等均为原文 2026-10 口径，未联网核实，不更新排名。

四 · SWE-Bench ProMax

不修补旧题，
直接换探针。

arXiv 2608.09802（2026-08）是对信任危机的正面回应：从“单点 bug 修复”换成“行为保持的跨文件重构”，更难背题。

SWE-Bench ProMax 的设计与结果
维度内容
为什么另起炉灶Verified 被审计出近 60% 未解实例存在测试缺陷（过窄或过宽）；前沿模型能逐字复现部分 gold patch，是记忆泄漏而非推理。
换什么探针行为保持的跨文件重构：改完代码行为不变，但需要理解多个文件的关系。
规模7 种语言、170 个专家精修的真实重构任务；平均每例改 11.4 个文件、261.6 行。
数据治理issue 描述全部重写，测试逐条人工复核，剔除过窄 / 过宽用例。
结果前沿模型最好解决率仅 41.2%，对比 Verified 顶部 87–94%。
启示同一批模型换一个更难泄漏的探针，分数从 90% 量级掉到 40% 量级，说明 Verified 的高分主要衡量“见过多少”，而非“能改多少”。

ProMax 的规模、行数、41.2% 与 arXiv 编号均按原文 2026-10 口径保留，标“原文版本、未联网核实”。

五 · Judge 的稳定性陷阱

判决一致，
理由可能每次不同。

LLM-as-Judge 看起来省事，但“多次运行判决一致”可能掩盖推理不稳定。原文把最危险的失败模式叫 Trapped Judge。

原文记录的研究发现有三层：表面一致性很高，多次运行的判决一致率很高；但推理不稳定，判决相同、推理理由可能完全不同；相同配置下准确率波动可达 15%。

Trapped Judge 是最危险的模式：Judge 先给出判决，再编造证据来支持这个判决，给出看似合理的“通过”评估，跳过了人工审核。它不是随机出错，而是把错误包装成可信的结论。

缓解三条：不只看判决结果，还要检查推理链；多次运行取统计结果；定期用人工标注校准 Judge。

15% 的准确率波动按原文 2026-10 口径保留，未联网核实。

六 · 动态基准

让题目，
跑在训练截止之后。

动态基准的核心不是“新”，而是题目发布时间晚于模型训练截止日期。原文列了四种做法，优势与局限并不相同。

四种动态基准的做法、发现或优势、局限或挑战
基准方法发现 / 优势局限 / 挑战
LiveCodeBench从 LeetCode / Codeforces 持续收集新题，每月更新。题目发布时间晚于训练截止日期；原文发现部分模型在新题上准确率下降 30%。原文未单列局限。
SWE-MERA从最新 GitHub Issue 自动收集测试用例。持续更新，不易被训练数据污染。自动收集的题目质量参差不齐。
SWE-EVO评估真实长周期软件演化任务（arXiv 2512.18470）。补上 SWE-bench 只测单点 bug 的缺口；意义是直接回应信任危机，把评测从刷单点分数拉回真实工程能力。原文未单列局限。
Chatbot Arena用户实时投票对比两个模型的回答。反映真实用户偏好，动态 ELO。偏向对话场景，不覆盖复杂 Agent 任务。

这四种不是互斥选项。生产上更稳的组合是：私有领域集做决策，动态基准做交叉验证，Arena 只作为偏好参考。

七 · 正确的评估策略

四层漏斗，
任一层不达标就淘汰。

原文的漏斗是：公开基准初筛 → 领域专属评估 → 小流量在线 A/B → 安全与合规测试。公开基准只配初筛，领域数据才是决策依据。

Layer 1

公开基准初筛

快速淘汰明显不合格的模型。原文示例：MMLU 低于 70% 直接排除。

作用：门槛筛选 · 不用于最终决策

Layer 2

领域专属评估（核心）

从生产日志采样 200–500 个典型任务，标注期望结果和评分标准，定义领域指标。这是选模型的真正依据。

作用：决策依据 · 投资回报率最高

Layer 3

小流量在线 A/B

用 5% 流量对比新旧模型，LLM-as-Judge 自动评分，同时收集显式与隐式用户反馈。

作用：真实流量验证 · 不能替代离线评估

Layer 4

安全与合规测试

看延迟 P95、每请求成本、安全护栏通过率、PII 泄露率等非功能性指标。

作用：上线前最后一道门

任一层不达标 → 淘汰。不要用“下一层表现好”去抵消上一层的硬伤。

原文的成本提醒：大部分成本在领域评估层，但这是投资回报率最高的环节。公开基准免费且快，在线测试要真实流量，安全测试要专门工具；把钱花在能代表你业务的那一层。

常见误区 / 面试追问

两个误区，
三个追问。

按原文顺序保留 5 条：前两条是误区，后三条是面试追问。

误区 1

“排行榜第一就是最好的模型。”

排行榜反映的是在特定基准上的得分，不是在你的业务场景中的表现。不同模型在不同领域有不同优势。选模型的唯一可靠方式，是用你自己的数据测试。

误区 2

“基准分数高就可以直接上线。”

生产有基准测试没有的复杂性：网络超时、恶意输入、长尾分布、安全攻击。基准测试必要但远不充分，还需要在线评估、安全测试和灰度发布。

追问 1

“SWE-bench 顶部都到 87–94% 了，为什么还不能信？”

顶部分数可被 harness 配置、retry 策略、reasoning effort 等人为拉高，比的是谁更会针对基准优化；而且它只测单点 bug 修复，不覆盖长周期演化。应对：固化评测配置、用 SWE-EVO 等演化型基准补充、回到自己的领域数据验证。

追问 2

“如何构建不会被污染的评估？”

用内部业务数据构建私有测试集，不公开发布；定期从最新生产日志补充新用例；用动态基准（LiveCodeBench、SWE-MERA、SWE-EVO）作为补充；关注模型在训练截止日期之后的数据上的表现。

追问 3

“如何平衡评估的全面性和成本？”

分层策略：公开基准免费快速初筛 → 领域评估（200–500 用例，LLM Judge 自动化）→ 小流量在线测试（5% 流量 A/B）。大部分成本在领域评估层，但这是投资回报率最高的环节。

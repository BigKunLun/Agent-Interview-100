中级 · RAG · 可交互讲解

检索不是
一次就完。

Agentic RAG 在“检索→生成”的流水线上加了一个 Agent 控制循环：先判断要不要检索、从哪检索，检索后判断信息够不够，不够就补充检索或调用工具，直到满足停止条件才生成回答。

关键边界：它是架构模式，不是某个框架。核心是动态决策和控制循环；用 LangChain 实现只是其中一种写法，不用 LangChain 也可以有 Agentic RAG。

固定教学查询

我们的 RAG 系统延迟比竞品高，成本也更高，怎么优化？

这条查询来自原文示例：它同时涉及延迟、成本、竞品对比，属于多跳问题，适合触发 Agent 循环。所有检索结果和判断都是写死的。

第 1 步 · Agent 决策

先判断这次查询要怎么处理。

  • 需要分解？是。问题包含“延迟优化”“成本优化”“竞品指标”三个子问题。
  • 需要检索？是。内部文档和外部竞品信息都不在当前上下文里。
  • 需要工具？暂时不需要；先走检索，若指标需要换算再调用计算器。

传统 RAG 在这里直接检索一次；Agentic RAG 先做决策，再决定检索几次、从哪里检索。

图 1 · 第 1 / 6 步

循环从“要不要检索”开始，而不是从向量查询开始。

传统 RAG 的流程是固定的：查询进来，检索一次，生成回答。Agentic RAG 多了一个控制层：它可以跳过检索、拆分查询、换数据源，也可以在结果不好时继续迭代。

分解的依据

子问题可以分别检索，再综合回答。

原文的 QueryDecomposer 让 LLM 把复杂问题拆成 2–4 个独立子问题。拆分的价值是每个子问题都能匹配到更合适的检索源，而不是拿整句长查询去撞向量库。

拆分也有代价：子问题越多，检索次数和 token 成本越高；如果子问题之间依赖很强，还需要先拿到前一步结果再拆下一步。

传统 RAG 的局限

一条线走到底，
错了也没机会改。

传统 RAG 是“查询→检索→生成”的线性流水线。它的限制不在于某个组件不好，而在于流程里没有判断和回退的位置。

  1. 单数据源：只从一个向量库中检索，无法跨多个知识源。
  2. 一次检索（One-shot）：只检索一次，如果结果不够好没有纠错机制。
  3. 无工具使用：只能检索静态文本，无法调用 API、执行 SQL 或做计算。
  4. 无推理：不会判断检索结果的质量，也不会调整检索策略。

这四条限制共同指向一个问题：流水线没有“观察结果后改变下一步”的能力。Agentic RAG 加的正是这个能力。

核心升级

把检索收进
Agent 控制循环。

Agent 可以动态决定是否需要检索、从哪个数据源检索、是否需要多轮检索，以及是否调用外部工具。检索从固定步骤变成可被决策和重复的动作。

原文的概括是：传统 RAG 是“单次检索、一发即忘”的流水线；Agentic RAG 是“多轮迭代、自主决策”的控制循环。

三种核心 Agent 类型

从选数据源，
到多步推理。

路由 Agent 解决“去哪查”，工具使用 Agent 解决“能查什么”，ReAct Agent 解决“按什么顺序查、查到什么程度”。

1. 路由 Agent

分析查询后决定从哪个数据源检索。最简单的 Agentic RAG 形式。

单次决策

2. 工具使用 Agent

在标准 RAG 基础上集成外部工具，获取实时数据或执行计算。

工具调用

3. ReAct Agent

结合路由、查询规划和工具使用，处理需要多步推理的复杂查询。

多步循环

路由 Agent

原文代码 · RoutingAgent

class RoutingAgent:
    def __init__(self):
        self.retrievers = {
            "technical_docs": vector_store_a,
            "customer_data": sql_database,
            "real_time_info": web_search,
        }

    def route(self, query: str) -> str:
        # LLM 分析查询，决定最佳数据源
        decision = llm.generate(
            f"用户问题：{query}\n"
            f"可用数据源：{list(self.retrievers.keys())}\n"
            f"选择最合适的数据源。"
        )
        return self.retrievers[decision].search(query)

适用场景：多知识源系统，例如客服系统同时有产品文档、订单数据库和 FAQ。

工具使用 Agent 的关键不是“有工具”，而是 Agent 能根据中间结果决定下一次调用哪个工具。

ReAct Agent

原文代码 · 多步执行轨迹

# 复杂查询："比较我们公司和竞争对手的市场份额，预测明年趋势"
# Agent 的执行轨迹：
# Thought 1: 需要先获取我们公司的市场数据
# Action 1: sql_query("SELECT market_share FROM reports WHERE year=2025")
# Observation 1: 市场份额 23.5%
# Thought 2: 需要获取竞争对手数据
# Action 2: web_search("competitor X market share 2025")
# Observation 2: 竞争对手 X 市场份额 31.2%
# Thought 3: 需要找到行业趋势分析
# Action 3: vector_search("AI market growth prediction 2026")
# Observation 3: 分析师预计增长 45.8%
# Thought 4: 现在信息够了，可以综合分析
# Final Answer: ...

ReAct 把“思考—行动—观察”串成循环，每一步的观察都可能改变下一步。这也是它比路由 Agent 更接近完整控制循环的原因。

查询分解 Agent

多跳问题，
拆开分别查。

把一个问题拆成多个独立子问题，分别检索后综合回答。它适合子问题之间没有严格先后依赖的场景。

原文代码 · QueryDecomposer

class QueryDecomposer:
    def decompose(self, complex_query: str) -> list[str]:
        return llm.generate(
            f"将以下复杂问题分解为 2-4 个独立的子问题：\n{complex_query}"
        )

务实策略

默认走经典 RAG，
失败再升级。

Agent 带来灵活性，也引入延迟、成本和不可预测性。原文推荐的务实做法是先跑经典 RAG，检测到失败信号后再触发 Agentic RAG 二次处理。

原文代码 · 渐进式 Agentic RAG

def smart_rag(query: str) -> str:
    # 默认使用经典 RAG（快、便宜、可预测）
    result = classic_rag(query)

    # 检测失败信号
    if (result.confidence < 0.5 or
        result.has_contradiction or
        result.missing_citations):
        # 触发 Agentic RAG 二次处理
        result = agentic_rag(query)

    return result

大多数查询用经典 RAG 即可高效处理，仅在检测到失败信号时启用 Agentic RAG 做二次检索和验证。这样既保留可预测的主路径，又给困难查询留了升级通道。

原文提醒

不要因为 Agentic 听起来更先进就盲目采用。简单查询用传统 RAG 更快、更便宜、更可靠。

常见误区 / 面试追问

四个容易
被追问的点。

前两条是误区，后两条是面试追问；答案都来自原文。

误区 1

“Agentic RAG 总是比传统 RAG 好。”

Agent 引入了延迟、成本和不可预测性。简单查询用传统 RAG 更快更可靠。不要因为 Agentic 听起来更先进就盲目采用。

误区 2

“Agentic RAG 就是 RAG + LangChain Agent。”

Agentic RAG 是一种架构模式，不绑定特定框架。核心是在 RAG 流水线中引入动态决策和控制循环。

追问 1

Agentic RAG 的可靠性如何保证？

第一，设置最大迭代次数防止无限循环；第二，工具调用加超时和降级；第三，对检索结果做质量检查，例如 Corrective RAG 的评估器；第四，关键场景加 Human-in-the-Loop。

追问 2

多 Agent RAG 是什么？

多个专业化 Agent 协作：一个主 Agent 协调信息检索，多个子 Agent 各自负责不同数据源。例如一个 Agent 查内部文档，一个 Agent 查数据库，主 Agent 综合结果。

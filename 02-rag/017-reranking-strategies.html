中级 · RAG · 可交互讲解

先召回，
再精排。

Bi-Encoder 把查询和文档分别编码成向量，速度快，适合从百万文档里召回候选；Cross-Encoder 把查询和文档拼在一起联合编码，精度高，但每对都要完整推理。生产系统先用前者取 Top-100，再用后者重排 Top-5。

关键边界：两阶段分工由可扩展性决定。Cross-Encoder 无法预计算文档表示，每次查询都要对候选逐对推理，所以只能处理少量候选；它不是“更大的 Bi-Encoder”。

RAG 系统应该怎么选重排序模型？

查询进入检索层。接下来的分数、排名和截断位置都是写死的教学数据，用来演示两阶段的分工，不调用任何模型。

两阶段流水线 · 全貌

同一批文档，先后经过两个编码器。

  1. 1
    Bi-Encoder 召回查询和每篇文档分别编码；文档向量可以离线预计算。先从 10 篇里取分数最高的 6 篇。
  2. 2
    Cross-Encoder 精排把查询和每个候选拼成一对输入，逐对推理出相关性分数；只处理这 6 对。
  3. 3
    截断后送入 LLM按精排分数取前 4 篇，拼成上下文交给生成模型。

原文的标准量级是 Bi-Encoder 取 Top-100、Cross-Encoder 重排后取 Top-5；本页缩小到 10 篇和 6 个候选，便于逐条看清分数变化。

查询先变成一个向量，文档才有机会被召回。

          为什么需要重排序

          第一阶段很快，
          但会丢信息。

          Bi-Encoder 从百万级文档中快速找出 Top-K 候选，但排序精度有限；重排序用更精确的模型重新打分，确保送入 LLM 的上下文最相关。

          精度损失来自架构，不是模型太小

          • Bi-Encoder 必须把文档的所有可能含义压缩进单一向量，信息不可避免地丢失。
          • 它编码文档时没有查询的上下文，因为文档向量通常在查询到达前就已算好。
          • 因此第一阶段的排序可能不够精确，需要第二阶段重新打分。

          重排序不改变候选集合，只改变候选的先后顺序，并决定最终哪些文档进入上下文。它治不了“相关文档根本没被召回”的问题，这个问题要靠召回阶段的 K 和索引策略解决。

          两种编码器

          独立编码，
          还是联合编码。

          核心差别只有一句话：查询和文档是否放进同一个模型一起看。这个差别决定了精度、速度和能否预计算。

          可扩展性的本质差异

          为什么 Cross-Encoder
          只能重排少量候选。

          假设数据库有 100,000 个文档。两种编码器要做的推理次数不在一个量级，这不是换更快的 GPU 就能抹平的差距。

          100,001Bi-Encoder：编码 100,000 个文档（一次性、可离线）+ 编码 1 个查询。文档向量能复用。
          100,000Cross-Encoder：每次查询都要编码 100,000 对 (query, doc)。每次查询都重来。

          即便用小型 Cross-Encoder（如 ms-marco-MiniLM）在 V100 GPU 上对 100,000 个文档逐对打分，单次查询也需数分钟到数十分钟（取决于 batch size 与硬件），完全无法在交互式 RAG 中接受。这就是 Cross-Encoder 只用于重排 20–100 个候选的原因。

          原文量级

          标准流水线是“Bi-Encoder 检索 Top-100 → Cross-Encoder 重排 Top-5”。K 太小会漏掉相关文档，太大则拖慢重排；重排后取 3–10 个送入 LLM，取决于上下文窗口大小。

          两阶段检索流水线

          标准架构长
          什么样。

          下面是原文代码：第一阶段用 SentenceTransformer 召回 Top-100，第二阶段用 CrossEncoder 对候选逐对打分，排序后取 Top-5。

          原文代码 · 两阶段重排

          from sentence_transformers import SentenceTransformer, CrossEncoder

# 第 1 阶段：Bi-Encoder 召回 Top-100
bi_encoder = SentenceTransformer("all-MiniLM-L6-v2")
query_embedding = bi_encoder.encode(query)
candidates = vector_db.search(query_embedding, top_k=100)

# 第 2 阶段：Cross-Encoder 重排 → Top-5
cross_encoder = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
pairs = [(query, doc.content) for doc in candidates]
scores = cross_encoder.predict(pairs)

# 按重排分数排序，取 Top-5
reranked = sorted(
    zip(candidates, scores),
    key=lambda x: x[1],
    reverse=True
)[:5]

# 将 Top-5 送入 LLM 生成回答
context = "\n\n".join([doc.content for doc, score in reranked])

          这段代码省略了查询、向量库连接和生成调用，只保留两阶段之间的数据流：候选列表和对应的重排分数。真实实现还要处理空候选、超时和重排模型不可用时的降级。

          实际效果与常用方案

          重排是高质量 RAG
          的必选项。

          LLM 的输出质量直接取决于上下文质量。没有重排序的系统通常会把不够相关的文档送进上下文，导致回答偏离主题或混入无关信息。

          原文的判断很直接：重排序阶段对高质量 RAG 是不可妥协的。召回解决“有没有找到”，重排解决“送进去的是不是最对题的那几篇”。

          常用重排序方案的类型与特点
          方案类型特点
          cross-encoder/ms-marco-MiniLM-L-6-v2开源轻量级，速度快
          Cohere Rerank API商业 API高质量，开箱即用

          进阶：ColBERT

          介于两者之间的
          晚期交互。

          ColBERT 像 Bi-Encoder 一样独立编码查询和文档，但不把文档压成单一向量，而是保留 token 级向量，检索时做细粒度交互。

          Bi-Encoderdoc → [single vector] → dot product
          Cross-Encoder[query + doc] → [score] → full attention
          ColBERTdoc → [token vectors] → late interaction (MaxSim)

          ColBERT 的精度接近 Cross-Encoder，速度接近 Bi-Encoder，是一个有前景的方向。它仍然需要为每个 token 存向量，索引体积比单向量方案大，这是采用时要单独评估的成本。

          常见误区 / 面试追问

          四个容易
          被追问的点。

          前两条是误区，后两条是面试追问；答案都来自原文。

          误区 1

          “Bi-Encoder 精度低是因为模型小。”

          精度差异是架构本质决定的。Bi-Encoder 编码文档时没有查询上下文，无论模型多大，信息压缩的损失都存在。

          误区 2

          “直接用 Cross-Encoder 做全量检索更好。”

          计算上不可行。10 万文档 × 单次查询 = 10 万次推理，延迟不可接受。Cross-Encoder 只适合重排少量候选。

          追问 1

          Top-K 的 K 设多少？

          第一阶段检索 50–100 个候选：K 太小会漏掉相关文档，太大会拖慢重排。第二阶段重排后取 3–10 个送入 LLM，取决于上下文窗口大小。

          追问 2

          Cross-Encoder 对长文档有什么问题？

          很多模型把输入截断到 token 窗口长度（如 512 tokens），可能切掉文档最相关的部分。解决方案是先分块再重排，或使用支持长上下文的重排模型。

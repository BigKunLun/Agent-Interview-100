高级 · RAG · 可交互讲解

三种变体，
各管一段。

Self-RAG 管输出：用反思 token 决定是否检索，并在生成后评估相关性、支撑度和有用性；Corrective RAG 管检索结果：评估文档质量，不够好就精炼知识并补 Web 搜索；Adaptive RAG 管入口：先判断查询复杂度，再决定不检索、单次检索还是多跳检索。

关键边界：它们不是固定串行的三段流水线。每个查询通常只走其中一条主分支；只有复杂、知识库部分过期、精度要求又高的查询，才值得把三层叠加起来。

      固定示意。Self-RAG 的“检索前”是反思 token 决定要不要检索，“生成后”是 critique token 评估输出；它不负责改写检索文档本身。

      1. Self-RAG

      让模型自己
      批评自己。

      核心思想是训练 LLM 生成特殊的反思 token，用它管理“要不要检索”和“输出质量够不够”，不满意就重新检索或修改回答。

      原文工作流程 · 纯文本示意

      Query → LLM 判断是否需要检索？
              ├── 不需要 → 直接生成（简单问题，如常识）
              └── 需要   → 检索文档
                          → 生成回答
                          → [反思 token] 评估：
                              ├── 检索结果是否相关？（Relevance）
                              ├── 回答是否基于检索内容？（Support）
                              └── 回答是否有用？（Utility）
                          → 如果不满意 → 重新检索或修改回答

      两种特殊 token 分工不同：Reflection Token 决定是否需要检索；Critique Token 评估检索结果和生成内容的质量。

      原文代码 · SelfRAG

      class SelfRAG:
    def answer(self, query: str) -> str:
        # 1. 决定是否需要检索
        need_retrieval = self.llm.predict_retrieval_need(query)

        if not need_retrieval:
            return self.llm.generate(query)

        # 2. 检索并生成
        docs = self.retriever.search(query)
        response = self.llm.generate_with_context(query, docs)

        # 3. 自我批评
        relevance_score = self.llm.critique_relevance(docs, query)
        support_score = self.llm.critique_support(response, docs)
        utility_score = self.llm.critique_utility(response, query)

        # 4. 如果质量不够，迭代改进
        if min(relevance_score, support_score, utility_score) < THRESHOLD:
            return self.retry_with_refined_query(query)

        return response

      原文给出的优势依据是 Asai et al. (2023) 的论文（ICLR 2024 Oral）：在 Open-domain QA、推理和事实验证等六类任务上，Self-RAG（7B/13B）显著优于 ChatGPT 和 retrieval-augmented Llama2-chat，事实性指标在多个任务上取得 SOTA。它在医疗、法律、金融等高精度需求场景尤其有价值。

      关键限制

      原始 Self-RAG 需要用特殊 token 对模型进行微调，不能直接用于现有 API 模型。用 Prompt Engineering 可以模拟类似效果，但原文明确说效果不如原版。

      2. Corrective RAG

      检索结果不好，
      就去网上补。

      在检索之后、生成之前加一个轻量级评估器，逐篇评估文档质量；质量不足时启用 Web 搜索作为补救。

      Query → 检索文档 → 检索评估器逐篇打分
      ↓
      相关直接使用这些文档，进入生成。
      模糊先做知识精炼，再补 Web 搜索，合并上下文。
      不相关整组换成 Web 搜索得到的新文档。
      ↓
      三条分支都汇合到“生成最终回答”

      原文代码 · CorrectiveRAG

      class CorrectiveRAG:
    def answer(self, query: str) -> str:
        # 1. 标准检索
        docs = self.retriever.search(query)

        # 2. 评估检索质量
        evaluations = []
        for doc in docs:
            score = self.evaluator.grade(query, doc)
            evaluations.append((doc, score))

        # 3. 根据评估结果分类处理
        relevant_docs = [d for d, s in evaluations if s == "relevant"]
        ambiguous_docs = [d for d, s in evaluations if s == "ambiguous"]

        if not relevant_docs:
            # 所有文档都不相关 → Web 搜索补救
            web_results = self.web_search(query)
            context = web_results
        elif ambiguous_docs:
            # 部分模糊 → 知识精炼 + Web 补充
            refined = self.knowledge_refine(relevant_docs)
            web_supplement = self.web_search(query)
            context = refined + web_supplement
        else:
            # 文档质量好 → 直接使用
            context = relevant_docs

        # 4. 生成回答
        return self.llm.generate(query, context)

      原文强调它轻量：评估器可以是小模型，甚至规则引擎，不需要微调主 LLM；Web 搜索兜底则保证知识库不完善时也能给出有用回答。适用场景是法律研究、学术写作、政策分析这类准确性至关重要、且允许稍高延迟的场景。

      3. Adaptive RAG

      先判断难不难，
      再决定查不查。

      在检索之前，用分类器分析查询复杂度，然后动态选择最合适的检索策略：简单不检索，中等单次 RAG，复杂多跳检索加验证。

      Query → 查询复杂度分类器
      ↓
      简单不检索，LLM 直接回答。
      中等标准 RAG：单次检索 + 生成。
      复杂多跳检索，并加 Self-RAG 验证。
      ↓
      三条分支各自结束，不需要汇合后再走其他变体

      离线可读示意：Adaptive 是前置路由，三条分支互斥；它不是“先跑一遍再决定”，而是在检索前就分流。原图是 Mermaid，源码见下方折叠块。

      原文代码 · AdaptiveRAG

      class AdaptiveRAG:
    def answer(self, query: str) -> str:
        # 1. 分析查询复杂度
        complexity = self.classifier.predict(query)

        if complexity == "simple":
            # 常识问题 → 不需要检索
            return self.llm.generate(query)

        elif complexity == "moderate":
            # 标准问题 → 单次 RAG
            docs = self.retriever.search(query)
            return self.llm.generate(query, docs)

        elif complexity == "complex":
            # 复杂多跳问题 → 多轮检索 + 验证
            sub_queries = self.decompose(query)
            all_docs = []
            for sq in sub_queries:
                docs = self.retriever.search(sq)
                # 用 CRAG 的评估器验证质量
                verified = self.evaluator.filter(sq, docs)
                all_docs.extend(verified)
            return self.llm.generate(query, all_docs)

      优势是通过避免对简单问题过度检索来优化效率和成本，同时让复杂问题得到更深入的处理。适用场景是查询复杂度差异大的系统，例如客服和通用助手：简单 FAQ 不需要检索，复杂分析需要多轮检索。

      三者对比

      关注点、时机
      和代价都不同。

      不要把它们当成同一件事的三个版本；它们分别盯输出、盯检索结果、盯入口路由。

      Self-RAG、Corrective RAG、Adaptive RAG 在核心关注、决策时机、纠错机制、模型要求、额外成本和最佳场景上的对比
      维度Self-RAGCorrective RAGAdaptive RAG
      核心关注输出质量自我评估检索结果质量纠正查询复杂度适配
      决策时机检索前 + 生成后检索后 + 生成前检索前
      纠错机制反思 token + 重试评估器 + Web 搜索路由到合适策略
      模型要求需要微调轻量级评估器分类器
      额外成本中：多轮生成低到中：评估 + Web低：分类器
      最佳场景高精度需求知识库不完善时混合复杂度查询

      组合使用

      可以叠加，
      但不是默认全串。

      原文说三者可以组合构成多层防御。组合的前提是查询真的需要每一层：从前置路由开始，检索质量不足才纠正，输出精度要求高才做 critique。

      Adaptive
      复杂度路由简单查询直接结束，不进入后面的层
      前置门
      标准 RAG
      检索 + 生成初稿中等查询到这里就可以结束
      基础层
      CRAG
      评估并纠正检索结果知识库可靠时跳过，不触发 Web
      按需叠加
      Self-RAG
      生成后自我批评普通精度要求时跳过，避免多轮生成
      按需叠加

      固定示意：Adaptive 是入口门，标准检索是基础层；CRAG 和 Self-RAG 是否叠加，取决于知识库质量和输出精度要求。把四层无条件串起来会放大延迟和成本。

      原文代码 · CombinedAdvancedRAG

      class CombinedAdvancedRAG:
    def answer(self, query: str) -> str:
        # Layer 1: Adaptive RAG — 路由到合适策略
        complexity = self.classifier.predict(query)

        if complexity == "simple":
            return self.llm.generate(query)

        # Layer 2: 标准检索
        docs = self.retriever.search(query)

        # Layer 3: Corrective RAG — 评估并纠正检索质量
        verified_docs = self.evaluator.filter_and_correct(query, docs)

        # Layer 4: Self-RAG — 生成并自我评估
        response = self.self_rag.generate_with_critique(query, verified_docs)

        return response

      注意原文代码里的 filter_and_correct 和 generate_with_critique 是组合层的接口名，不是标准库方法；真实实现要把各变体的输入输出对齐，并给每一层设置跳过条件和超时。

      常见误区 / 面试追问

      四个容易
      被追问的点。

      前两条是误区，后两条是面试追问；答案都来自原文。

      误区 1

      “这些变体互相替代。”

      它们解决不同环节的问题，完全可以组合使用。Adaptive RAG 做前端路由，CRAG 做检索质量控制，Self-RAG 做输出质量保证。

      误区 2

      “Self-RAG 可以用任何 LLM。”

      原始 Self-RAG 需要用反思 token 微调模型。也可以用 Prompt Engineering 模拟类似效果，让 LLM 在 Prompt 中评估自己的输出，但原文明确说效果不如原版。

      追问 1

      GraphRAG 属于哪个类别？

      GraphRAG 是另一种独立变体，用知识图谱代替或补充向量检索，适合实体关系密集的场景，例如组织架构、产品关系网络。它与上述三种变体正交，可以并行使用。

      追问 2

      实际生产中最常用的是哪种？

      Corrective RAG 因为实现简单、不需要微调且效果显著而最常被采用。Adaptive RAG 在成本敏感场景也很流行。Self-RAG 因为需要微调，更多出现在研究中。

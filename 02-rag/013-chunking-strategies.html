分块决定 Embedding 的语义质量、检索精度、生成上下文和 token 成本。三种主路线是固定大小、递归、语义分块；核心权衡永远是上下文保留 vs 检索精度。

关键边界：块越大不代表越好，块越小也不代表越准。大块保留上下文但稀释相关性，小块匹配精确但容易丢上下文。本页互动用固定中文文本和字符数做真实切块算术，不调用 tokenizer 或 Embedding 模型。

一 · 为什么分块重要

它不是预处理，
是设计决策。

分块策略同时决定四件事：Embedding 的语义质量、检索精度和召回率、生成的上下文充分性、token 使用效率和成本。

语义质量

块是否表达一个完整概念。切在句子中间，Embedding 会把半句话当成主题。

检索精度与召回

块太大，相关性被稀释；块太小，召回到的片段缺少回答所需的信息。

生成上下文

LLM 拿到的是块，不是整篇文档。块不完整，回答就会缺前提。

成本

块越小、数量越多，索引和检索的存储与计算开销越高。

二 · 三种主路线

固定、递归、
语义。

三条路线的复杂度依次上升。原文引用 Chroma 的测试：递归分块在 400–512 tokens 时 Recall 85–90%，语义分块 91–92%，只差 2–3 个百分点，但语义分块要多做一遍 Embedding。

固定大小分块

按预定的字符数或 token 数均匀切分，通常带 overlap。实现最简单，无需 NLP 库，计算成本最低；但完全忽略语义结构，可能在句子甚至单词中间切断。

成本最低 · 适合原型

递归分块

按层次分隔符递归切分：先段落（\n\n），太大再句子（\n），再空格，最后字符。尽可能保持段落和句子完整，是推荐的通用默认方案。

原文测试 Recall 85–90%

语义分块

先给每个句子生成 Embedding，计算相邻句子余弦相似度，在相似度急剧下降的“主题转换点”切分。召回最高，但要为每个句子做 Embedding，成本和延迟更高。

原文测试 Recall 91–92%

Recall 数字按原文引用的 Chroma 测试保留，本页未复现实验，也不代表所有数据集上的结果。

固定大小：怎么切

按字符数均匀切，chunk_size=500、chunk_overlap=50，相邻块共享 50 字符以保留边界上下文。

展开原文代码：CharacterTextSplitter 
from langchain.text_splitter import CharacterTextSplitter

splitter = CharacterTextSplitter(
    chunk_size=500,      # 每块 500 字符
    chunk_overlap=50,    # 相邻块重叠 50 字符
    separator=""         # 按字符切
)
chunks = splitter.split_text(document)
固定大小分块的优缺点
维度说明
优点实现最简单，无需 NLP 库；计算成本最低；块大小均匀，便于索引优化；适合快速原型。
缺点完全忽略语义结构；可能在句子甚至单词中间切断；可能混合不相关的主题；即使有 overlap 也不能保证语义完整。
最佳场景同质化数据集（新闻、博客等格式统一的内容）、快速原型验证。

递归：默认方案

分隔符优先级是段落 > 换行 > 句号 > 逗号 > 空格 > 字符。原文推荐参数：400–512 tokens，10–20% overlap。注意 chunk_size 默认单位是字符，不是 token；要按 token 切，需用 from_tiktoken_encoder 或传 length_function。

展开原文代码：RecursiveCharacterTextSplitter 
from langchain.text_splitter import RecursiveCharacterTextSplitter

# 注意：默认 chunk_size 单位是「字符」，不是 token。若需按 token 切，
# 用 RecursiveCharacterTextSplitter.from_tiktoken_encoder(...) 或显式传 length_function。
splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,        # 字符数，中文常按 1.5-2 字符/token 估算
    chunk_overlap=50,
    separators=["\n\n", "\n", "。", "，", " ", ""]
    # 优先级：段落 > 换行 > 句号 > 逗号 > 空格 > 字符
)
chunks = splitter.split_text(document)

# 若需严格按 token：
# splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
#     chunk_size=512, chunk_overlap=50,
# )
递归分块的优缺点
维度说明
优点实用的默认方案；显著减少句子被截断的概率；Chroma 测试 400–512 tokens 时 Recall 85–90%；计算成本仍然很低。
缺点仍可能在某些复杂结构处切断；不处理表格、列表等特殊元素；不同文档格式需要不同分隔符集；不考虑语义相似度。
最佳场景通用默认方案；结构化文本（技术文档、报告）、代码文件（配合语言特定分隔符）。

语义：在主题转换处切

先对每个句子生成 Embedding，再计算相邻句子余弦相似度。低于阈值（如 95 分位）就切分。块大小自适应内容，但块大小不均匀，可能影响索引优化。

展开原文代码：SemanticChunker 
from langchain_experimental.text_splitter import SemanticChunker
from langchain_openai import OpenAIEmbeddings

splitter = SemanticChunker(
    embeddings=OpenAIEmbeddings(),
    breakpoint_threshold_type="percentile",
    breakpoint_threshold_amount=95  # 相似度低于 95 分位数时切分
)
chunks = splitter.split_text(document)
语义分块的优缺点
维度说明
优点最高的检索召回率（原文称 91–92%）；保持主题连续性和语义完整性；块大小自适应内容；适合叙述性文档。
缺点需要对每个句子生成 Embedding；计算成本高（API 调用或本地推理）；处理速度比固定 / 递归慢；块大小不均匀，可能影响索引优化。
最佳场景准确率优先的场景、叙述性 / 研究性文档、预算允许额外计算开销时。

三 · 其他策略

按文档结构切，
或小块检索大块返回。

除了三种主路线，还有两类常见工程做法：利用文档自身结构，以及把“检索用的块”和“返回给 LLM 的块”分开。

文档结构分块（Structure-Aware）

用标题、章节、HTML 标签作为分块边界。Markdown 可以按 # / ## / ### 标题切，天然保留章节层级。

展开原文代码：MarkdownHeaderTextSplitter 
# Markdown 文档按标题分块
from langchain.text_splitter import MarkdownHeaderTextSplitter

splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[
        ("#", "h1"), ("##", "h2"), ("###", "h3")
    ]
)

小块检索 + 大块上下文（Parent-Child / Small-to-Big）

用小块做精确检索，命中后返回包含它的大块作为上下文。小块负责“找得准”，大块负责“答得全”。

展开原文代码：small → large 映射 
# 检索时用小块（200 tokens）匹配精确
# 返回时给 LLM 提供大块（2000 tokens）保留上下文
small_chunks = split(doc, chunk_size=200)
large_chunks = split(doc, chunk_size=2000)
# 建立 small → large 的映射关系

策略切分依据成本原文测试 Recall适用

递归段落 → 句子 → 词低85–90%通用默认、技术文档、代码

四 · 核心权衡

上下文保留，
还是检索精度。

块的大小同时影响检索精度、Embedding 语义、上下文完整性、存储和无关信息。原文的经验法则是：400–512 tokens 是大多数场景的最佳起点。

小块与大块的权衡
维度小块（100–200 tokens）大块（1000–2000 tokens）
检索精度高，匹配更精确相关性被稀释，匹配变粗
Embedding 语义语义集中语义被稀释
上下文可能丢失上下文信息丰富，保持段落完整性
存储需要更多块 → 更多存储块数少，存储成本更低
无关信息不易混入无关内容可能包含无关信息

经验法则

400–512 tokens 是大多数场景的最佳起点。overlap 通常设为 chunk_size 的 10–20%，例如 512 tokens 的块用 50–100 tokens overlap。

是否需要分块？

一个常被忽略的问题：当文档本身就很小、聚焦，且直接匹配用户问题时，分块反而可能损害检索精度。先评估是否需要分块，而不是默认总要分块。

常见误区 / 面试追问

语义不一定最好，
块也不一定越小越好。

两条误区和两条追问，覆盖语义分块的性价比、块大小、overlap 设置和 chunk_size 选择。

误区 1

“语义分块一定最好。”

Chroma 的测试数据显示，递归分块（85–90% Recall）和语义分块（91–92% Recall）仅差 2–3%，但语义分块的计算成本显著更高。大多数场景递归分块就够了。

误区 2

“块越小越好。”

太小的块会丢失上下文，导致 LLM 无法理解信息的含义。需要在精度和上下文之间找平衡。

追问 1

overlap 有什么用？设多少合适？

Overlap 确保分块边界处的信息不会丢失。通常设置为 chunk_size 的 10–20%，如 512 tokens 的块用 50–100 tokens overlap。

追问 2

如何选择最佳的 chunk_size？

没有通用最优值。应该在你的数据集上实验——用检索评估指标（Recall@k、MRR）比较不同 chunk_size 的效果。通常从 512 tokens 开始调。

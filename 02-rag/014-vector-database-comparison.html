二 · 五个候选

每个都有
明确的适用边界。

原文对五个产品的判断可以压缩成一句话：Pinecone 省运维，Weaviate 强混合，Milvus 扛规模，Chroma 快原型，Qdrant 省预算。

全托管 SaaS

Pinecone

优势：零运维，自动扩缩容、更新、备份；原文称查询延迟 <50ms；SOC 2、GDPR。

  • 锁定风险
  • 规模化后成本可能超过 $500/月
  • 不能自托管

开源 + 云

Weaviate

优势：原生混合检索（向量 + BM25）、模块化、可插拔模型、内置向量化、过滤和聚合丰富。

  • 5000 万向量后要规划容量
  • 试用仅 14 天
  • 内存消耗较高

开源 + 云

Milvus

优势：十亿级向量、GPU 加速、分布式查询、IVF / HNSW / PQ 等多种索引；Zilliz Cloud 在原文低延迟 Benchmark 中领先。

  • 运维复杂度高
  • 学习曲线陡
  • 小规模过度设计

开源

Chroma

优势：完全开源免费、pip install chromadb、几行代码可用、Python 原生、与 LangChain / LlamaIndex 深度集成。

  • 不适合十亿级 / 多租户
  • 生产需额外基础设施
  • 高级过滤有限

开源 + 云

Qdrant

优势：Rust 编写，性能和内存效率高；1GB 永久免费；元数据过滤强；ACID 支持。

  • 社区规模较小
  • 企业级功能仍在发展
  • 原文默认推荐

三 · 决策框架

先排除，
再默认。

原文的 choose_vector_db 按固定顺序判断：先看运维与预算，再看规模，再看混合检索与多模态，最后看阶段和预算。顺序会影响结果。

展开原文决策代码 
def choose_vector_db(requirements: dict) -> str:
    if requirements["no_ops_team"] and requirements["budget"] == "flexible":
        return "Pinecone"  # 全托管，无运维负担

    if requirements["scale"] > 1_000_000_000:  # 十亿级
        return "Milvus"    # 唯一真正的十亿级选手

    if requirements["hybrid_search"] and requirements["multimodal"]:
        return "Weaviate"  # 混合检索 + 多模态

    if requirements["stage"] == "prototype":
        return "Chroma"    # 最快的入门方式

    if requirements["budget"] == "tight":
        return "Qdrant"    # 性价比最高

    return "Qdrant"        # 综合默认推荐

读法

这是一棵按顺序短路判断的决策树，不是打分排名。比如“无运维 + 预算灵活”会直接返回 Pinecone，不会再检查规模；所以同一个团队如果先满足前面的条件，后面的条件就不参与。

本页互动按同样的顺序提问，结果面板会显示命中的原文条件。它演示的是“原文会怎么判”，不是“你应该买哪个”。

四 · 重要洞察

大多数 RAG 失败，
不是数据库造成的。

原文的核心判断：向量数据库通常不是 RAG 系统的瓶颈。更常见的问题是分块、Embedding 质量、缺少重排序和 Prompt 设计。

“大多数 RAG 失败是自己造成的，不是数据库造成的。”

在优化数据库之前，先确认分块策略、Embedding 模型、重排序和 Prompt 没有明显问题。换数据库通常救不了一个检索质量很差的管线。

评估数据库时看四项

  1. Recall@k：Top-K 中有多少真正相关。
  2. 尾延迟（P99）：最坏情况下的查询时间。
  3. 元数据过滤能力：能否高效按属性过滤。
  4. 运维成本：人力和基础设施的总成本。

常见误区 / 面试追问

Benchmark 最快，
不等于最合适。

两条误区覆盖 Benchmark 与小规模专用库；两条追问覆盖迁移和 FAISS 的定位。

误区 1

“选 Benchmark 最快的就对了。”

Benchmark 通常在理想条件下测试。实际生产中，元数据过滤、并发查询、数据更新频率等因素更重要。应该用自己的数据和查询模式做测试。

误区 2

“一定需要专用向量数据库。”

对于小规模应用（<10 万向量），pgvector（PostgreSQL 扩展）可能就够了，不需要引入额外的基础设施。

追问 1

如何做向量数据库迁移？

关键是 Embedding 模型保持一致。只要用同一个 Embedding 模型重新生成向量，就可以在不同数据库间迁移。但如果换了 Embedding 模型，所有向量必须重新生成。

追问 2

FAISS 算向量数据库吗？

FAISS 是向量检索库，不是数据库。它不提供持久化存储、CRUD 操作、分布式部署等数据库功能。适合嵌入到应用中做内存中检索。

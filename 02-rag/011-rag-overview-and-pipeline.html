基础 · RAG · 可交互讲解

先查资料，
再让模型回答。

RAG（Retrieval-Augmented Generation，检索增强生成）在 LLM 生成回答前，先从外部知识库检索相关文档并注入 Prompt。它主要解决三大局限：知识截止、幻觉、缺乏领域专有知识。

关键边界：生产级 RAG 有三条流水线，但不是一条无条件串行链。Indexing 离线、按数据更新触发；Retrieval 与 Generation 在线、按查询触发。索引更新和在线查询可以并行，检索也可以被缓存、跳过或由 Agent 多轮调用。

    一 · 为什么需要 RAG

    模型缺的，
    去外面找。

    LLM 的三大核心局限都来自同一个事实：知识被冻在训练参数里。RAG 不改模型权重，而是在生成前补进外部证据。

    LIMIT 01

    知识截止

    模型知识在训练完成后冻结。问训练截止日期之后的信息，它要么承认不知道，要么自信地给出错误答案。知识出现空白时，模型会外推，说出听起来合理但实际错误的陈述。

    LIMIT 02

    幻觉

    面对超出训练范围的任务，模型经常产生与任务无关或事实不一致的输出，也就是幻觉（hallucination）或虚构（confabulation）。

    LIMIT 03

    缺乏私有 / 领域知识

    模型无法访问企业内部文档、私有数据库或最新领域知识。再强的通用模型，也答不了公司内部流程、客户数据或专有技术。

    三大局限与 RAG 的解决方式
    局限RAG 的解决方式
    知识截止外部知识库可以随时更新，无需重新训练模型
    幻觉提供“事实锚点”，让 LLM 基于检索到的真实文档生成回答
    缺乏领域知识接入企业私有数据、行业文档、实时数据源

    额外优势：成本效益（无需昂贵微调或重训）、来源可溯（回答可附引用，用户能验证）、权限控制（按用户权限限制可检索的文档范围）。

    二 · 整体架构

    两条车道，
    不是一条串行链。

    生产级 RAG 由离线索引流水线与在线检索 / 生成流水线构成。索引供在线检索使用，但索引更新与在线查询是解耦的，可以并行发生。

    三 · Indexing Pipeline

    把文档，
    变成可检索的索引。

    索引流水线是离线阶段，负责把原始数据转化为可检索的向量索引。它按数据更新触发，不按查询触发。

    数据摄取与清洗

    原始数据通常来自 PDF、网页、数据库、Markdown 等多种格式。清洗要去 HTML 标签、修正编码、标准化格式，同时保留来源、日期、作者等元数据，供后续过滤和引用。

    展开原文代码：数据摄取与清洗 
    # 原始数据通常来自多种格式
sources = [
    PDFLoader("report.pdf"),
    WebLoader("https://docs.example.com"),
    DatabaseLoader("postgresql://..."),
    MarkdownLoader("docs/*.md"),
]

# 清洗：去除 HTML 标签、修正编码、标准化格式
for doc in documents:
    doc.content = remove_html_tags(doc.content)
    doc.content = normalize_whitespace(doc.content)
    doc.metadata = extract_metadata(doc)  # 保留元数据（来源、日期、作者）

    分块（Chunking）

    把长文档切成语义完整的小块。常见策略：固定大小分块按 token 数切，简单但可能破坏语义；递归分块按段落→句子→词的层次分割；语义分块基于 Embedding 相似度在语义断点处分割。

    展开原文代码：递归分块，注意 chunk_size 是字符数 
    from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,       # 注意：chunk_size 是字符数，不是 token 数
    chunk_overlap=50,     # 相邻块重叠 50 字符，保留上下文连续性
    separators=["\n\n", "\n", "。", " ", ""]
)
chunks = splitter.split_documents(documents)

# 如需按 token 计长，使用 TokenTextSplitter 或 from_tiktoken_encoder：
# from langchain.text_splitter import TokenTextSplitter
# splitter = TokenTextSplitter(chunk_size=512, chunk_overlap=50)
# 或：
# splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
#     chunk_size=512, chunk_overlap=50
# )

    Embedding 与存储

    每个块生成向量，连同原文和元数据一起写入向量库。元数据让检索可以按来源、日期、类别过滤。

    展开原文代码：Embedding 与 upsert 
    from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-large")
vectors = embeddings.embed_documents([chunk.content for chunk in chunks])

# 存入向量数据库（附带元数据，支持后续过滤）
vectorstore.upsert(
    ids=[chunk.id for chunk in chunks],
    embeddings=vectors,
    documents=[chunk.content for chunk in chunks],
    metadatas=[chunk.metadata for chunk in chunks]  # 来源、日期、类别等
)

    注意：索引不是“每次查询重跑一遍”。数据不变时，查询只读已建好的索引；数据更新时，只对新增或变更的文档做增量处理。

    四 · Retrieval Pipeline

    先找得准，
    再谈生成。

    检索流水线在每次查询时实时运行，负责找到最相关的文档块。检索质量决定生成上限。

    预检索优化

    优化查询本身：查询改写让 LLM 重新表述问题以提升匹配度；查询分解把复杂问题拆成多个子问题；HyDE 先生成假设性回答，再用回答去检索。

    展开原文代码：查询改写 / 分解 / HyDE 
    # 查询改写：让 LLM 重新表述用户问题，提升匹配度
def rewrite_query(original_query: str) -> str:
    return llm.generate(
        f"将以下问题改写为更适合向量检索的形式，"
        f"保持核心语义：\n{original_query}"
    )

# 查询分解：将复杂问题拆分为多个子问题
def decompose_query(query: str) -> list[str]:
    return llm.generate(
        f"将以下复杂问题分解为 2-3 个独立的子问题：\n{query}"
    )

# HyDE：生成假设性回答，用回答而非问题去检索
def hypothetical_document(query: str) -> str:
    return llm.generate(f"为以下问题生成一个假设性回答：\n{query}")

    向量检索与后检索优化

    先检索较多候选（如 top_k=20），再重排序和压缩。Cross-Encoder 对候选精排后取 Top 5；上下文压缩则从块中提取与问题直接相关的部分，减少无关 token。

    展开原文代码：候选检索、Cross-Encoder 重排与压缩 
    # 基本语义检索
results = vectorstore.similarity_search(
    query_embedding,
    top_k=20,                              # 先检索较多候选
    filter={"category": "technical_docs"}  # 元数据过滤
)

# 重排序：用 Cross-Encoder 对候选结果精排
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
reranked = reranker.rank(query, [r.content for r in results])
top_results = reranked[:5]  # 取 Top 5

# 上下文压缩：去除检索块中不相关的部分
compressed = llm.generate(
    f"从以下文档中提取与问题 '{query}' 直接相关的信息：\n{chunk}"
)

    五 · Generation Pipeline

    拼好上下文，
    再让模型开口。

    生成流水线把检索结果与用户查询组合，送入 LLM。Prompt 要明确“只基于参考文档回答、信息不足就说不知道、引用来源”。

    展开原文代码：RAG Prompt 构建 
    def build_rag_prompt(query: str, contexts: list[str]) -> str:
    context_text = "\n\n---\n\n".join(contexts)
    return f"""基于以下参考文档回答用户问题。
如果文档中没有足够信息，请明确说明。
请在回答中引用相关来源。

参考文档：
{context_text}

用户问题：{query}

回答："""

    上下文窗口管理

    • 按重排序得分排列，优先保留高分文档。
    • 对低优先级文档进行摘要压缩。
    • 确保关键信息出现在上下文的开头和结尾，避免 “Lost in the Middle”（中间信息被忽略）。

    六 · 优化关系与演进

    三条流水线，
    各自有指标。

    Indexing 看覆盖率，Retrieval 看召回与精确率，Generation 看答案正确率与幻觉率。RAG 本身也经历了 Naive → Advanced → Modular 三个阶段。

    三条流水线的优化方向与关键指标
    阶段优化方向关键指标
    Indexing分块策略、Embedding 质量、元数据丰富度索引覆盖率
    Retrieval查询改写、混合检索、重排序Recall@k、Precision@k
    GenerationPrompt 工程、上下文窗口管理、输出验证答案正确率、幻觉率
    RAG 的三个演进阶段
    阶段特点局限
    Naive RAG简单的“索引—检索—生成”链检索精度低、上下文不足
    Advanced RAG加入预检索优化（查询改写）和后检索优化（重排序、压缩）仍是单次检索
    Modular RAG每个组件独立可替换、可组合系统复杂度高

    RAG 的局限

    1. 不能完全消除幻觉：LLM 仍可能围绕源材料幻觉，或断章取义得出错误结论。
    2. 检索质量瓶颈：低精确率（检索块与问题不匹配）、低召回率（漏掉相关块）、知识库本身过时。
    3. 依赖知识库质量：知识库中的偏见或错误会直接传导到回答。

    七 · 1M token 时代

    能全塞，
    不等于该全塞。

    2026 年旗舰模型上下文普遍达到 1M token，但答案是按场景决策：长上下文解决单针检索，多跳推理与成本 / 延迟仍是 RAG 的主场。

    以下研究结论与产品能力均为原文版本，本页未联网核验。

    原文引用 2026 年的实证研究（arXiv:2605.02173）：单针检索基本已解决，在超长上下文中找一条明确事实，顶级模型召回接近满分；多跳推理仍有显著差距，答案需要跨多个分散段落定位并串联时，错误会逐跳放大，超过约 256K token 后准确率明显滑坡，Lost in the Middle 在超长窗口下依然存在。

    小语料

    全塞上下文

    单文档 / 小语料，简单、零检索延迟。适合单针事实、整体摘要、通篇理解。

    大语料 / 高频更新

    RAG 按需检索

    成本可控、召回为关键。适合大语料、频繁更新、精确片段定位。

    多跳 / 跨文档

    Agentic RAG

    多轮检索、迭代充分性判断。复杂问答和跨文档推理仍需要它。

    长上下文与 RAG 的选型对照
    维度倾向长上下文（全塞）倾向 RAG（按需检索）
    语料规模单文档 / < 200K token> 1M token 或持续增长
    更新频率静态、极少更新高频更新（新闻、库存、对话历史）
    问题类型单针事实、整体摘要、通篇理解多跳推理、精确片段定位
    延迟敏感可接受首 token 延迟（TTFT）较高要求快速首 token
    成本预算低频调用、可承担长上下文费用高频调用、需控制 token 消耗

    成本与延迟权衡

    • Token 费用近似线性增长：1M token 输入远贵于“一次向量检索 + Top-5 片段”（原文称后者通常 < 8K token）。
    • TTFT 显著上升：Prefill 要处理全部输入，上下文越长等待越久；RAG 只 prefill 精选片段。
    • 召回率反噬：超过约 256K token 后多跳任务的“有效召回”不升反降。

    现实中的混合方案有两种：RAG 为主 + 长上下文兜底，先检索 Top-K，置信度不足再扩大范围；长上下文为主 + RAG 定位辅助，单份大文档直接全塞，跨多份文档仍先用 RAG 定位。Prompt Caching 可以缓存稳定的大段系统提示 / 参考文档，缓解重复 prefill 成本。

    一句话总结：1M token 淘汰了“为了塞不下才检索”的 RAG，但没淘汰“为了找得准、花得省、推得对”的 RAG。

    八 · 端到端代码

    索引、检索、生成，
    串成一条链。

    下面的示例用 LangChain 把三条流水线串成一个最小 RAG Chain。注意：这里的“串”是单次请求内的调用顺序，不代表索引要随每次查询重跑。

    展开原文端到端代码 
    from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough

# 1. 索引：分块 + Embedding + 存储
text_splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = text_splitter.split_documents(documents)
vectorstore = Chroma.from_documents(chunks, OpenAIEmbeddings())

# 2. 检索器
retriever = vectorstore.as_retriever(search_kwargs={"k": 5})

# 3. 生成：构建 RAG Chain
prompt = ChatPromptTemplate.from_template(
    "基于以下上下文回答问题。如果上下文中没有答案，请说'我不确定'。\n\n"
    "上下文：{context}\n\n问题：{question}"
)
llm = ChatOpenAI(model="gpt-4o")

rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | llm
)

answer = rag_chain.invoke("公司的退款政策是什么？")

    常见误区 / 面试追问

    检索不行，
    生成救不回来。

    四条误区覆盖幻觉、微调、优化重点和生产化；四条追问覆盖长上下文、检索 vs 生成、评估和混合检索。

    误区 1

    “RAG 完全解决了幻觉问题。”

    RAG 降低了幻觉概率，但 LLM 仍可能围绕检索内容幻觉，或忽略检索结果而使用自身知识。需要配合 Guardrails 和输出验证。

    误区 2

    “RAG 可以替代微调（Fine-tuning）。”

    两者解决不同问题。RAG 解决知识问题（“知道什么”），微调解决能力问题（“怎么做”）。要改变模型的行为风格或推理模式，应该用微调。

    误区 3

    “RAG 的重点是 Generation。”

    Retrieval 的质量才是 RAG 效果的决定性因素。检索到的文档不相关，再强的 LLM 也救不回来。优化顺序应该是：Retrieval > Indexing > Generation。

    误区 4

    “原型能用 = 生产能用。”

    原型和生产系统的差异在于评估和监控能力。生产 RAG 需要：检索质量监控、生成质量评估、成本和延迟追踪。

    追问 1

    模型能处理 100 万 token，还需要 RAG 吗？

    需要。（1）长上下文仍有“大海捞针”问题，中间信息容易被忽略，多跳更明显；（2）成本：100 万 token 推理费用远高于 RAG 检索；（3）延迟：长上下文增加推理时间。

    追问 2

    RAG 的检索精度和 LLM 生成质量哪个更重要？

    检索精度。检索到的文档不相关，再强的 LLM 也无法生成正确答案。“Garbage in, garbage out” 在 RAG 中尤为适用。

    追问 3

    如何评估 RAG Pipeline 的各个环节？

    Indexing：覆盖率测试（关键信息是否都被索引）；Retrieval：Recall@k、MRR、NDCG；Generation：Faithfulness（忠实度）、Relevance（相关性）、Answer Correctness。

    追问 4

    向量检索一定比关键词检索好吗？

    不一定。精确术语匹配（如产品型号、法律条款编号）时，BM25 等关键词检索可能更好。最佳实践是混合检索（Hybrid Search）。

中级 · Agent 架构 · 可交互讲解

循环要能转，
也要能停。

Agent 和单次 LLM 调用的区别，是“推理→行动→观察”的循环。生产级 Agent Loop 要同时做两件事：用外部强制控制什么时候停，用四层容错处理出错之后怎么恢复。

终止权必须留在系统手里。最大迭代、预算、重复检测和无进展检测都是兜底；Agent 自报“做完了”只是一条待验证的声明，高风险场景还要由外部验证来裁定算不算完成。

      一、本质

      Agent 的定义特征，
      就是循环。

      单次 LLM 调用只生成一次回答；Agent 用 LLM 推理、执行工具、观察结果，再带着新状态回到推理，直到完成或被迫停止。

      循环体只有三步：推理、行动、观察。真正决定 Agent 能不能安全跑在生产上的，是循环外面的终止检查，以及出错后的恢复路径。

      单次调用与 Agent Loop · 原文代码

    action_result = execute(thought)    # 行动
    state = observe(action_result)      # 观察
    done = check_termination(state)     # 终止检查

      二、终止控制

      死循环不显眼，
      但会烧掉预算。

      传统代码的死循环一眼可见；Agent 的循环陷阱更微妙，因为判断“是否完成”的是概率模型，而不是确定性的条件表达式。

      • 误解终止信号：LLM 的概率性本质可能让它错过已经出现的完成信号。
      • 目标模糊：像“研究 X”这样的任务没有明确完成定义，容易引发“无限好奇心”。
      • 失败后反复重试：工具调用失败后，Agent 可能反复执行同一个操作。
      • 工具选择混乱：工具过多或描述模糊时，模型容易在工具之间打转。

      核心原则

      外部强制（External Enforcement）：由系统而不是 Agent 自身保证终止。Agent 可以主动声明完成，但系统必须有独立的兜底条件。

      三、五种终止策略

      一层不够，
      要叠五层。

      五种策略解决不同问题：步数上限防跑飞，语义完成看目标，重复检测抓循环，预算监控守成本，子 Agent 信号处理多 Agent 协作。

      五种终止策略的机制与作用
      策略机制主要作用
      最大迭代次数固定循环上限，超过就退出最基础的兜底，防无限循环
      语义完成检测终止标记或结构化字段让“完成”成为可判定的信号
      重复输出检测滑动窗口内动作或输出重复抓住原地打转
      资源预算监控token、金额、时间上限控制成本与延迟
      子 Agent 信号事件、标志或特定返回值多 Agent 系统中的协作终止

      1. 最大迭代次数

      最基础也最关键。循环次数写死在 harness 里，不依赖模型判断。LangChain 的 AgentExecutor 默认 15 次；Google ADK 的 LoopAgent 允许自定义上限。

      最大迭代与优雅降级 · 原文代码

      class AgentLoop:
    def __init__(self, max_iterations: int = 15):
        self.max_iterations = max_iterations

    def run(self, task: str) -> str:
        for i in range(self.max_iterations):
            result = self.step(task)
            if result.is_final:
                return result.answer
        # 达到上限：优雅降级
        return self.graceful_degradation()

      2. 语义完成检测

      让 Agent 输出明确的终止标记，例如要求它以 FINAL_ANSWER: ... 结尾；或者用结构化输出，把 final_answer 字段是否为空作为完成信号。

      class AgentResponse(BaseModel):
    thought: str
    action: Optional[ToolCall]
    final_answer: Optional[str]  # 非 None 时表示完成

      终止标记只是让完成可判定，不代表完成一定正确。高风险任务还需要外部验证，见第八节。

      3. 重复输出检测

      维护最近若干轮的动作或输出，在一个窗口里检查是否有重复。下面的实现用 3 轮窗口：窗口内去重后变短，就说明出现了重复。

      def detect_loop(history: list[str], window: int = 3) -> bool:
    """检测 Agent 是否在重复相同的操作"""
    recent = history[-window:]
    return len(set(recent)) < len(recent)  # 有重复则判定为循环

      4. 资源预算监控

      同时记录 token 和金额，任一项超限就停止。第六节会把它扩展成四类预算统一的 RunBudget。

      class ResourceBudget:
    def __init__(self, max_tokens: int = 100_000, max_cost: float = 1.0):
        self.max_tokens = max_tokens
        self.max_cost = max_cost
        self.used_tokens = 0
        self.used_cost = 0.0

    def check(self) -> bool:
        return self.used_tokens < self.max_tokens and self.used_cost < self.max_cost

      5. 子 Agent 信号终止

      在多 Agent 系统中，子 Agent 可以通过事件、标志或特定返回值，向 Orchestrator 发出终止信号。它解决的是“谁来汇总停止意图”，不能替代单 Agent 内部的步数与预算兜底。

      四、架构差异

      默认继续，
      还是默认终止？

      不同架构把终止权放在不同位置。这个选择直接影响安全性：默认继续的架构需要更强的外部兜底。

      四种架构的终止方式与特点
      架构终止方式特点
      ReActLLM 在 response 中生成终止 token（如 Final Answer:）默认继续，主动终止
      MemGPTrequest_heartbeat 默认为 False默认终止，主动继续
      Plan-and-Execute计划中的所有步骤执行完毕确定性终止
      现代 Agent多步工具调用 + 自导向终止条件混合策略

      “默认终止 vs 默认继续”是一个关键设计决策。MemGPT 的设计哲学是默认终止更安全：Agent 必须显式请求继续执行，而不是依赖 LLM 自己判断什么时候该停。

      五、优雅降级

      到上限时，
      交半成品也比崩溃好。

      达到迭代上限时，不应直接崩溃或返回空结果。系统要让模型用已有进度整理出当前条件下最好的答案。

      def graceful_degradation(self):
    """优雅降级：总结已有进度，而非直接失败"""
    return self.llm.generate(
        f"你已达到最大步数限制。基于以下已完成的工作，"
        f"给出你目前能提供的最佳答案：\n{self.state.summary()}"
    )

      进度总结

      汇报已完成和未完成的部分，让用户知道拿到了什么。

      状态检查点

      保存当前状态，后续可以从这里恢复，而不是从头再跑。

      模型降级

      切换到更便宜的模型完成剩余整理工作，控制成本。

      人工升级

      通知人类介入处理，适合高风险或需要业务判断的任务。

      六、预算分层与无进展检测

      同一个位置，
      每轮结束查一次。

      预算和重复检测落在 harness 上，是同一个循环位置：每轮结束检查。四类预算放进一个对象，重复检测升级成“看状态有没有变”。

      四类预算统一落地

      RunBudget 初始化时记录 started_at，每轮结束调用 check()，返回已用比例、剩余额度，以及是否进入软停区（已用 ≥ 80%）。四类预算是轮数、token、金额、墙钟时间。

      时间预算用单调时钟，并扣掉人工审批的等待时间——用户思考 10 分钟不该算 Agent 超时。

      展开 RunBudget 完整实现（原文代码） 
      import time
from dataclasses import dataclass


@dataclass
class BudgetStatus:
    exhausted: bool          # 任一预算用完：硬停
    soft_stop: bool          # 任一预算到 80%：软停
    used_ratio: float
    remaining_turns: int
    remaining_tokens: int
    remaining_cost_usd: float
    remaining_seconds: float


class RunBudget:
    def __init__(self, max_turns: int, max_tokens: int,
                 max_cost_usd: float, max_wall_seconds: float,
                 soft_ratio: float = 0.8):
        self.max_turns = max_turns
        self.max_tokens = max_tokens
        self.max_cost_usd = max_cost_usd
        self.max_wall_seconds = max_wall_seconds
        self.soft_ratio = soft_ratio

        self.turns = 0
        self.tokens = 0
        self.cost_usd = 0.0
        self.approval_wait = 0.0
        self.started_at = time.monotonic()

    def add_turn(self, tokens: int, cost_usd: float) -> None:
        self.turns += 1
        self.tokens += tokens
        self.cost_usd += cost_usd

    def add_approval_wait(self, seconds: float) -> None:
        """人工审批的等待时间不计入墙钟预算"""
        self.approval_wait += seconds

    def check(self) -> BudgetStatus:
        elapsed = time.monotonic() - self.started_at - self.approval_wait
        used = max(
            self.turns / self.max_turns,
            self.tokens / self.max_tokens,
            self.cost_usd / self.max_cost_usd,
            elapsed / self.max_wall_seconds,
        )
        return BudgetStatus(
            exhausted=used >= 1.0,
            soft_stop=used >= self.soft_ratio,
            used_ratio=used,
            remaining_turns=max(0, self.max_turns - self.turns),
            remaining_tokens=max(0, self.max_tokens - self.tokens),
            remaining_cost_usd=max(0.0, self.max_cost_usd - self.cost_usd),
            remaining_seconds=max(0.0, self.max_wall_seconds - elapsed),
        )

      无进展检测：看状态指纹，不看参数

      只看参数是否相同挡不住参数微调：模型给查询词加个引号、把 offset 从 10 改成 11，调用序列看起来不同，状态其实没动。更可靠的做法是对状态取指纹：已完成子目标集合、工作区关键文件哈希、最近 K 条工具结果摘要，三样拼起来做 SHA-256。

      相邻两轮指纹相同，就说明这一轮没有产生任何可观测变化。连续 2–3 轮（经验值）无进展就该介入，不要等预算耗尽。

      展开 ProgressTracker 完整实现（原文代码） 
      import hashlib
import json


class ProgressTracker:
    def __init__(self, key_files: list[str], recent_k: int = 5,
                 max_stale_turns: int = 2):  # 2-3 是经验值
        self.key_files = key_files
        self.recent_k = recent_k
        self.max_stale_turns = max_stale_turns
        self.last_fingerprint: str | None = None
        self.stale_turns = 0

    @staticmethod
    def _file_digest(path: str) -> str:
        try:
            with open(path, "rb") as f:
                return hashlib.sha256(f.read()).hexdigest()
        except FileNotFoundError:
            return "missing"

    def fingerprint(self, completed_goals: set[str],
                    recent_results: list[str]) -> str:
        payload = {
            "goals": sorted(completed_goals),
            "files": {p: self._file_digest(p) for p in self.key_files},
            "results": [r[:200] for r in recent_results[-self.recent_k:]],
        }
        return hashlib.sha256(
            json.dumps(payload, sort_keys=True, ensure_ascii=False).encode()
        ).hexdigest()

    def observe(self, completed_goals: set[str],
                recent_results: list[str]) -> bool:
        """返回 True 表示连续多轮状态没变，需要介入"""
        current = self.fingerprint(completed_goals, recent_results)
        if current == self.last_fingerprint:
            self.stale_turns += 1
        else:
            self.last_fingerprint = current
            self.stale_turns = 0
        return self.stale_turns >= self.max_stale_turns

      软停与硬停分层

      硬停到 100% 由 harness 直接终止，不再调用模型，保证预算不超支。软停只注入一条系统提示，要求模型收尾：写明剩余轮数和时间、已完成的子目标，先给结论再列未完成项。模型因此有机会把已有成果整理成可交付的答案，而不是被突然截断。

      软停只注入一次，避免每轮重复占上下文。两者职责不同：软停管体验，硬停管兜底。只做软停，模型可能无视提示继续跑；只做硬停，结果无法交付。

      展开软停注入与每轮检查代码（原文代码） 
      SOFT_STOP_NOTICE = (
    "预算即将用尽：剩余 {turns} 轮、约 {seconds:.0f} 秒。"
    "已完成的子目标：{done}。"
    "请立即停止探索：先给出现有条件下的结论，再列出未完成项。"
)


async def step(self, messages):
    status = self.budget.check()
    if status.exhausted:
        return self.finalize_by_harness()      # 硬停：不再调用模型

    if status.soft_stop and not self.soft_stop_sent:
        self.soft_stop_sent = True             # 只注入一次
        messages.append({"role": "system", "content": SOFT_STOP_NOTICE.format(
            turns=status.remaining_turns,
            seconds=status.remaining_seconds,
            done="、".join(sorted(self.state.completed_goals)),
        )})

    turn = await self.llm.step(messages)
    self.budget.add_turn(turn.usage.total_tokens, turn.usage.cost_usd)

    if self.progress.observe(self.state.completed_goals,
                             self.state.recent_results):
        self.escalate_stall()                  # 无进展：总结、换策略或转人工

    return turn

      七、根因分析

      上限是症状，
      不是疾病。

      如果 Agent 反复触及上限，真正的问题通常在任务定义、工具描述或提示词里。盲目调大上限只会增加成本和延迟。

      1. 目标模糊：缺少明确的完成标准，Agent 不知道做到什么程度算结束。
      2. 工具签名不清：工具描述有歧义，LLM 不知道选哪个。
      3. 停止条件弱：没有教会 LLM 识别“已完成”。
      4. Prompt 设计差：没有在 System Prompt 中定义终止规则。

      对应地，修复顺序应该是补完成标准、改工具描述、加终止规则，最后才考虑调整上限。

      八、验收也要外部化

      停下来，
      不等于做对了。

      终止控制回答“什么时候该停”，但外部强制还有第二个落点：Agent 停下来之后声称“做完了”，这个“做完了”由谁裁定？

      多数实现默认 Agent 自评——输出 FINAL_ANSWER 就算任务完成，等于把终止权外部化了，验收权却还留在 Agent 手里。而语义错误（代码能编译、能跑、却干错事）恰恰在这一步无法自查。

      SemaPLC（2026-08）在工业 PLC 代码生成（可编程逻辑控制器，改错会造成物理后果）这类高风险场景把它做成硬门禁——verification-gated（以验证为闸门）：Agent 不能自判完成，“我做完了”只是一个待验证的声明；必须由日志化的外部检查全通过才算完成——规格核对、编译、实机运行时行为，任一不过就回到循环继续修。

      检查是分层的，越往后越接近真实：前两层停留在静态与语法层面，第三层才触及语义正确性，只做前两层正好漏掉最危险的那类错误。

      终止控制的三个环节与责任归属
      环节谁说了算对应机制
      什么时候必须停系统迭代上限、资源预算、重复检测
      算不算做完外部验证规格核对 + 编译 + 运行时行为，全程日志化
      没做完怎么收场系统优雅降级、检查点、人工升级

      中间这一格空着的系统，前后两格做得再好也只是“按时停下来了”，不代表“做对了”。任务风险越高（改生产代码、控制物理设备、动钱），越该把这一格补成硬门禁。

      九、错误的特殊性

      Agent 的错误，
      会顺着循环放大。

      传统应用的错误通常局部可见；Agent 的错误会进入下一轮推理，被当成新事实继续使用。

      级联放大

      一次工具调用失败会影响后续所有决策，错误被写进上下文继续传播。

      语义错误

      LLM 生成的代码可能通过编译但执行错误操作，例如删除而不是更新。

      状态失同步

      Agent 对环境的内部认知与实际状态不一致，后续判断建立在错误前提上。

      概率性

      同样的输入可能产生不同的错误，难以用固定用例完全覆盖。

      十、四层容错模型

      从便宜到贵，
      逐层兜底。

      先处理最常见的瞬态错误，再逐层升级到模型降级、错误分类和检查点恢复。顺序不能反：重试中间件应放在降级中间件之前。

      第一层：重试 + 指数退避 + 抖动

      处理最常见的瞬态错误（网络超时、API 限流）。退避时间按指数增长，再加一点随机抖动，避免多个客户端同时重试造成尖峰。

      import random
import time

class RetryWithBackoff:
    def __init__(self, max_retries=3, base_delay=1.0, max_delay=60.0):
        self.max_retries = max_retries
        self.base_delay = base_delay
        self.max_delay = max_delay

    def execute(self, func, *args):
        for attempt in range(self.max_retries):
            try:
                return func(*args)
            except TransientError as e:
                if attempt == self.max_retries - 1:
                    raise
                delay = min(
                    self.base_delay * (2 ** attempt) + random.uniform(0, 1),
                    self.max_delay
                )
                time.sleep(delay)

      关键设计决策：重试中间件应放在降级中间件之前。先重试主模型几次，再降级到备用模型，避免主模型短暂不可用就过早降级。

      第二层：模型降级链

      当主模型持续不可用时，切换到备用模型。每个供应商至少定义一个备选模型，并设置跨供应商降级（如 Anthropic → OpenAI）。

      class ModelFallbackChain:
    def __init__(self):
        self.chain = [
            {"provider": "anthropic", "model": "claude-sonnet-4-5-20250929"},
            {"provider": "anthropic", "model": "claude-haiku-4-5-20251001"},
            {"provider": "openai", "model": "gpt-4o-mini"},  # 跨供应商降级
        ]

    def call(self, prompt: str) -> str:
        for model_config in self.chain:
            try:
                return self._call_model(model_config, prompt)
            except (RateLimitError, ServiceUnavailableError):
                continue
        raise AllModelsFailedError("所有模型均不可用")

      第三层：错误分类与路由

      不是所有错误都应该重试。正确分类错误是高效容错的关键：限流需要重试，工具返回垃圾数据需要让 LLM 换个方式调用，权限错误需要人工介入，致命错误应终止并报告。

      展开 ErrorClassifier 与 ErrorHandler 代码（原文代码） 
      class ErrorClassifier:
    def classify(self, error: Exception) -> ErrorType:
        if isinstance(error, (TimeoutError, RateLimitError)):
            return ErrorType.TRANSIENT      # → 重试
        elif isinstance(error, ToolOutputError):
            return ErrorType.LLM_RECOVERABLE  # → 让 LLM 换个方式调用
        elif isinstance(error, AuthorizationError):
            return ErrorType.HUMAN_REQUIRED   # → 通知人类
        elif isinstance(error, InvalidToolInput):
            return ErrorType.PROMPT_FIXABLE   # → 重新格式化输入
        else:
            return ErrorType.FATAL            # → 终止并报告

class ErrorHandler:
    def handle(self, error: Exception, context: AgentState):
        error_type = self.classifier.classify(error)

        if error_type == ErrorType.TRANSIENT:
            return self.retry_with_backoff(context)
        elif error_type == ErrorType.LLM_RECOVERABLE:
            return self.ask_llm_to_reformulate(context)
        elif error_type == ErrorType.HUMAN_REQUIRED:
            return self.escalate_to_human(context)
        elif error_type == ErrorType.PROMPT_FIXABLE:
            return self.fix_and_retry(context)
        else:
            return self.abort_with_summary(context)

      第四层：检查点与状态恢复

      对于长时间运行的 Agent 任务，定期保存状态。每步完成后写入当前步骤、已完成动作、部分结果和时间戳；崩溃后按 thread_id 从最近检查点恢复。

      class CheckpointManager:
    def __init__(self, storage):
        self.storage = storage

    def save(self, thread_id: str, state: AgentState):
        """在每步完成后保存检查点"""
        self.storage.save({
            "thread_id": thread_id,
            "step": state.current_step,
            "completed_actions": state.history,
            "partial_results": state.results,
            "timestamp": time.time()
        })

    def restore(self, thread_id: str) -> AgentState:
        """从最近的检查点恢复"""
        checkpoint = self.storage.load(thread_id)
        return AgentState.from_checkpoint(checkpoint)

      十一、级联失败预防

      假设每个依赖
      都可能不可用。

      Agent 系统中的单点故障不只影响一个功能——它会在每次工具调用、每次重试、每个 token 中放大。核心原则：假设 LLM、Agent 组件和外部数据源都可能不可用。

      断路器模式把失败挡在上游：连续失败达到阈值后进入 OPEN，后续调用快速失败，不再把请求压到已经不可用的服务上；等待恢复时间后进入 HALF_OPEN 试探，成功则回到 CLOSED。

      断路器 · 原文代码

      class CircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=60):
        self.failures = 0
        self.threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.state = "CLOSED"  # CLOSED → OPEN → HALF_OPEN
        self.last_failure_time = None

    def call(self, func, *args):
        if self.state == "OPEN":
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = "HALF_OPEN"
            else:
                raise CircuitOpenError("服务不可用，快速失败")

        try:
            result = func(*args)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise

    def _on_failure(self):
        self.failures += 1
        self.last_failure_time = time.time()
        if self.failures >= self.threshold:
            self.state = "OPEN"

    def _on_success(self):
        self.failures = 0
        self.state = "CLOSED"

      十二、实施顺序

      先做便宜的重试，
      最后做检查点。

      容错机制不需要一次做完。按“覆盖最常见故障、代码最少”的顺序推进，每层都能独立验证。

      1. 重试策略先行：用最少代码处理最常见的故障。
      2. 模型降级其次：定义备选模型和跨供应商回退。
      3. 错误分类第三：区分瞬态错误、LLM 可恢复错误、需人工错误。
      4. 检查点最后：生产环境用持久化存储，通过 thread_id 支持恢复。

      常见误区 / 面试追问

      十四条，
      按原文顺序。

      前 5 条关于循环终止，中间 4 条关于错误恢复，后 5 条是场景追问；编号与原文一致。

      循环 · 1 误区

      “设大一点的 max_iterations 就行。”

      盲目增大上限只会增加成本和延迟。应该先分析为什么达到上限，修复根因（目标不清、工具不当、Prompt 不佳）。

      循环 · 2 误区

      “让 LLM 自己决定什么时候停。”

      LLM 可能无法可靠判断任务完成。必须在系统层面设置硬性终止条件作为兜底。

      循环 · 3 追问

      如何设定合理的 max_iterations？

      根据任务类型估算：简单问答 3–5 步，多步研究 10–15 步，复杂分析 20–30 步。建议从小值开始，通过观测实际使用情况逐步调整。

      循环 · 4 追问

      Agent 的两个循环（Inner Loop / Outer Loop）是什么？

      Inner Loop 是单次任务内的“思考-行动-观察”循环。Outer Loop 是跨任务的“执行-评估-改进”循环（如 Reflexion 的自我反思机制）。

      循环 · 5 追问

      终止条件外部化了，为什么还需要外部验证完成？

      这是两件事：终止控制管“什么时候必须停”，完成判定管“算不算做完”。多数实现让 Agent 输出 FINAL_ANSWER 就自动认定完成，验收权还在 Agent 手里，而语义错误（代码能编译但干错事）恰恰无法自查。SemaPLC（2026-08）在工业 PLC 代码生成场景做成硬门禁：Agent 不能自判完成，必须由日志化的外部检查（规格核对、编译、实机运行时行为）全通过才算完成。风险越高的场景越该补上这道门禁。

      恢复 · 6 误区

      “所有错误都重试就行。”

      限流需要重试，但工具返回垃圾数据需要让 LLM 重新构造查询，权限错误需要人工介入。错误分类是高效容错的前提。

      恢复 · 7 误区

      “Agent 自己能处理所有错误。”

      语义错误（生成的代码逻辑错误）和状态失同步（Agent 的认知与实际不符）需要外部验证机制。不能完全依赖 Agent 自我纠错。

      恢复 · 8 追问

      如何处理 Agent 的“幻觉式修复”？

      （1）工具调用结果做独立验证；（2）关键操作后检查状态一致性；（3）Human-in-the-Loop 审核关键修复。

      恢复 · 9 追问

      容错机制本身的成本如何控制？

      重试和降级会增加延迟和费用。设置总预算（token 上限 + 金额上限 + 时间上限），达到任一上限就优雅终止。

      场景 · 10

      Agent 反复调用同一个工具，参数略有不同但总是失败，如何修复？

      （1）设置 max_tool_retries 限制单工具重试次数；（2）工具返回明确错误信息，说明为什么失败；（3）错误分类，判断是瞬态错误还是需要 LLM 调整策略的错误；（4）检查工具 Schema 是否清晰、LLM 是否理解参数约束；（5）加入重复检测，连续 N 次调用同一工具时强制停止或请求人工干预。

      场景 · 11

      多 Agent 系统中 A 和 B 反复互相传递任务而无法进展，如何修复？

      （1）限制 Handoff 次数，超过阈值强制终止或转给 Supervisor Agent；（2）每次传递时要求携带“进展状态”，状态无变化则中断；（3）加入超时机制；（4）在 Handoff 点记录完整 Trace，复现时检查是哪个 Agent 的决策导致死循环；（5）设计“逃生路由”，转给兜底 Agent 或返回用户友好错误。

      场景 · 12

      Agent 在生产环境突然频繁产生幻觉，输出不存在的引用和数据，如何定位？

      （1）检查模型或 prompt 版本最近是否更新，如有则紧急回滚；（2）对比最近 24 小时和正常时期的 Trace，找出变化的模式；（3）检查检索系统的输出质量，可能是检索失效导致 Agent 只能依赖自身知识；（4）加入幻觉检测护栏，对引用来源进行验证；（5）启用人工审核通道，高风险输出转人工确认。

      场景 · 13

      RAG 检索结果与用户查询完全无关，Recall 接近 0，如何修复？

      （1）检查 embedding 模型是否匹配语料语言，重新选择或训练适配的模型；（2）检查分块策略是否破坏语义完整性，调整为语义分块或重叠分块；（3）检查向量数据库索引是否损坏，必要时重建索引；（4）检查查询是否包含语料中未出现的领域术语，加入查询扩展或同义词映射；（5）加入混合检索（BM25 + 向量）兜底。

      场景 · 14 追问

      软停和硬停为什么不能合并成一个？

      硬停保证预算不超支，但模型在循环中途被切断，用户只拿到一个错误。软停提前到 80% 注入提示，让模型用剩余预算把已有结果整理成结论，并说明哪些子目标没完成。两者职责不同：软停管体验，硬停管兜底。只做软停，模型可能无视提示继续跑；只做硬停，结果无法交付。

中级 · Agent 架构 · 可交互讲解

不是搜一次，
是研究很多轮。

Deep Research Agent 把一个复杂问题变成多轮、多源的自主调研：先拆问题、制定计划，再并行或串行检索、读全文抽取证据，判断证据是否充分，不够就补检，最后综合成一份带引用的结构化长报告。

关键边界：Agentic RAG 是检索的自主化，Deep Research 是检索自主化之上的报告产品化。前者输出答案，后者输出报告；三个独有要素是显式研究计划、充分性感知的迭代终止、长报告综合与引用管理。

    一 · 核心循环

    检索、阅读、检查，
    不够就再来一轮。

    Deep Research 的内核是充分性感知的多轮检索循环。OpenAI、Perplexity、Gemini 的实现细节不同，但高层骨架一致：证据不足就改写补检，充分才进入长报告合成。

    查询规划拆子问题 / 搜索意图
    检索并行 fan-out / 串行 chain
    阅读 + 抽取读全文，抽取证据
    充分性判断覆盖 + 质量够吗？
    综合报告多章节 + 内联引用
    用户问题 → 规划 → 检索 → 阅读 → 判断 → 综合 → 带引用的长报告
    ↺不充分：改写查询 / 针对缺口补充检索 → 回到检索与阅读，再判断一次。这条回边是核心，不是一次检索就结束。

    循环每跑一轮，Agent 都要回答同一个问题：“我现在掌握的证据，足以回答用户的研究问题吗？”判断同时看覆盖广度（每个子问题是否都有证据）和证据质量（来源是否权威、是否互相印证、是否矛盾）。不足就补检；充分才合成。这样避免两种失败：证据不足就草草收场，或无意义地无限检索。

    五个环节各自在做什么

    Deep Research 循环的五个环节
    环节做什么关键点
    查询规划把复杂问题拆成可检索的子问题和搜索意图子问题拆分、视角枚举、时间限定补全、去歧义改写；plan-first 可让用户审阅
    并行 / 串行检索独立子查询并行 fan-out，有依赖的串行 chain本质是 Orchestrator-Worker：一个编排者规划与综合，多个 Worker 检索抽取
    阅读 + 抽取点进链接读网页 / PDF 全文，抽取事实、数据、观点、引用不满足于搜索摘要；这是与普通搜索摘要的分水岭
    充分性判断检查覆盖广度和证据质量，找出缺口停止条件；触发补充检索，避免草草收场或无限检索
    综合 + 引用跨源融合、去重、矛盾调和、观点归纳，标注来源引用管理是幻觉引用的高发区

    二 · 伪代码

    三个函数，
    决定它是不是 Deep Research。

    原文用简化伪代码刻画循环：规划、缺口分析与改写的多轮循环、带引用的报告合成。三者缺一，就退化成普通的 Agentic RAG。

    展开原文伪代码：DeepResearchAgent 骨架 
    from dataclasses import dataclass


@dataclass
class Evidence:
    """单条证据：来自某个来源的、与某子问题相关的抽取结果"""
    sub_question: str        # 对应哪个子问题
    content: str             # 抽取出的关键信息
    source_url: str          # 来源链接
    credibility: float       # 可信度评分 0-1
    cited: bool = False      # 是否已用于最终报告


class DeepResearchAgent:
    """Deep Research 核心循环的骨架实现"""

    def __init__(self, llm, web_search, max_rounds: int = 10):
        self.llm = llm
        self.web_search = web_search
        self.max_rounds = max_rounds

    def run(self, question: str) -> str:
        # 1. 查询规划：把复杂问题拆成子问题 + 搜索意图
        plan = self._plan_research(question)          # -> list[str] 子问题
        evidence_pool: list[Evidence] = []
        pending_queries = plan[:]

        # 2-4. 充分性感知的多轮检索循环
        for round_idx in range(self.max_rounds):
            # 2. 并行检索：独立子查询 fan-out
            raw_results = self.web_search.batch(pending_queries)

            # 3. 阅读全文 + 抽取关键信息
            for query, docs in zip(pending_queries, raw_results):
                for doc in docs:
                    extracted = self._read_and_extract(doc, query)
                    credibility = self._assess_credibility(doc)
                    evidence_pool.append(Evidence(
                        sub_question=query,
                        content=extracted,
                        source_url=doc.url,
                        credibility=credibility,
                    ))

            # 4. 去重 + 覆盖度分析
            evidence_pool = self._deduplicate(evidence_pool)
            coverage = self._analyze_coverage(plan, evidence_pool)

            # 充分性判断：所有子问题都有足够高质量证据？
            gaps = self._find_gaps(coverage)          # 证据不足的子问题
            if not gaps:
                break                                  # 证据充分，退出循环

            # 5. 针对缺口改写查询、补充检索
            pending_queries = self._rewrite_for_gaps(gaps, evidence_pool)
        else:
            # 达到最大轮次仍未充分，降级处理
            pass

        # 6. 综合报告合成：多章节 + 内联引用
        report = self._synthesize_report(question, plan, evidence_pool)
        return report

    三个灵魂要素

    _plan_research（显式规划）、_find_gaps + _rewrite_for_gaps（充分性感知的迭代）、_synthesize_report（带引用的长报告合成）。三者缺一，就退化成普通的 Agentic RAG。

    三 · 边界划分

    搜索、Agentic RAG、
    Deep Research。

    最容易混淆的是中间两列。判断口径很简单：用户要的是“答案”，用 Agentic RAG；要的是“报告”，用 Deep Research。

    传统搜索、Agentic RAG 与 Deep Research 的对比
    维度传统搜索Agentic RAGDeep Research
    抽象层次工具 / 功能检索增强模式（组件）端到端产品形态
    检索源开放 Web私有知识库 / 文档库为主开放 Web 为主
    检索轮数1 次通常 1–3 轮数十轮，可读上百来源
    是否读全文否，只看 snippet通常检索 chunk 片段是，读取并抽取全文
    停止条件单次返回找到答案即停显式的充分性判断
    典型输出链接列表针对问题的简短回答多章节、带引用的长报告
    是否显式规划否可选（ReAct 式）是，plan-first
    引用管理无弱（标注来源即可）强（内联引用 + 去重 + 溯源）
    延迟 / 成本秒级、低秒–分钟级、中分钟–数十分钟级、高
    适用场景事实查询、导航问答、知识库对话长尾调研、行业分析、文献综述
    类比图书馆检索目录带参考书的答题助手一位能写报告的研究助理

    Agentic RAG 的落点在“检索的自主性”：它解决 Agent 能不能自己决定何时检索、怎么改写、要不要多跳，输出仍是“答问题”。Deep Research 的落点在“调研的产品化”：它在自主检索之上，额外解决如何把数十个来源的证据组织成一篇可信报告，输出是“交报告”。

    很多团队踩的坑是用 Agentic RAG 硬扛“出报告”的需求，结果要么检索不够深，要么合成不出结构化长文。

    五 · 关键挑战

    成本、时效、
    幻觉引用、来源偏见。

    把 Deep Research 从 demo 推向可用，原文列出四类硬骨头。其中幻觉引用是最致命的失败模式。

    01 · 成本

    多轮调用成本

    一次研究可能涉及几十次 Web 搜索 + 上百次全文阅读 + LLM 抽取 + 长文合成，token 消耗与延迟显著高于普通 RAG。成本控制是产品化的第一道门槛。

    02 · 时效

    时效性

    开放 Web 更新频繁，结果依赖搜索引擎索引的新鲜度。对“最新进展”类问题，可能需要优先检索新闻源、限定时间窗等策略。

    03 · 引用

    幻觉引用

    报告写了带引用的论断，但点开链接找不到对应内容，甚至链接是模型编造的。根因是综合阶段 LLM 可能“脑补”证据，而非忠实回指抽取到的原文。

    04 · 信源

    来源偏见与可信度

    开放 Web 信源质量参差，热门话题容易被 SEO 内容、营销稿、片面报道主导。不做可信度评估与多源交叉印证，报告会被低质来源带偏。

    缓解幻觉引用的核心思路

    让引用可回溯：综合阶段强制 LLM 只能引用阅读阶段已抽取并登记的 evidence id，而不是自由生成 URL；对最终报告做引用校验；用可信度评分过滤低质来源，关键论断要求至少两个独立来源印证。

    常见误区 / 面试追问

    多跑几轮，
    不等于 Deep Research。

    两条误区针对“多轮 RAG”和“取代 RAG”；四条追问覆盖评估、成本、幻觉引用与适用场景。

    误区 1

    “Deep Research 就是多跑几轮的 Agentic RAG。”

    这是最常见的降级理解。多轮检索只是表象，Deep Research 的实质是叠加了三个 Agentic RAG 通常不具备的能力：显式研究计划、充分性感知的迭代终止、面向长报告的综合与引用管理。判断一个系统是不是 Deep Research，看它有没有“出报告”的综合阶段和显式的充分性判断，而不是看它检索了几轮。

    误区 2

    “有了 Deep Research 就不需要 RAG 了。”

    二者检索的语料性质不同。Deep Research 主要检索开放 Web，回答“公开信息世界里的调研”；RAG 检索私有知识库 / 企业文档，回答“我自己数据里的问答”。企业内部场景（查合同、查规范、查客户档案）Web 搜不到，仍必须用 RAG。正确架构往往是两者并存：开放调研用 Deep Research，内部问答用 RAG。

    追问 1

    如何评估 Deep Research 报告的质量？

    四个维度：（1）事实准确性——论断是否与来源一致，引用是否真实可溯源，可直接对抗幻觉引用；（2）覆盖度——是否覆盖问题的各个子主题，有无明显遗漏；（3）引用质量——来源是否权威、是否多源交叉印证；（4）连贯性与可读性——长报告是否结构清晰、逻辑自洽。学术上有专门的多跳检索问答基准；生产中常用人工抽检 + LLM-as-Judge 组合评估。

    追问 2

    多轮检索的成本怎么控制？

    五种手段：（1）预算上限——设最大检索轮数与最大来源数，达到即降级合成；（2）早停 + 充分性判断——用轻量模型快速判断证据是否充分；（3）分级阅读——先用 snippet 筛选高相关来源，只对入选来源读全文；（4）缓存与去重——同一查询结果缓存、跨子问题去重；（5）并发——独立子查询并行检索，压缩墙钟延迟，但不省 token。

    追问 3

    如何缓解幻觉引用？

    核心是让引用可回溯：综合阶段强制 LLM 只能引用“阅读阶段已抽取并登记”的证据，每条论断必须绑定一个已登记的 evidence id，而非自由生成 URL；对最终报告做引用校验（抓取链接核对内容是否匹配）；用可信度评分过滤低质来源，要求关键论断至少有两个独立来源印证。

    追问 4

    什么场景该用 / 不该用 Deep Research？

    该用：长尾调研、行业 / 竞品分析、文献综述、多角度对比、需要可溯源报告的决策支持。不该用：简单事实查询（直接搜索更快）、私有数据问答（Web 搜不到，用 RAG）、实时性要求极高的场景（几分钟到几十分钟的延迟难以接受）、成本敏感的大规模批量任务。

中级 · Agent 架构 · 可交互讲解

四种模式，
四种控制方式。

ReAct 交替推理与行动；Plan-and-Execute 先规划后执行；LATS 用树搜索探索多条路径；Proactive Agent 主动预测需求。实际生产里，大多数系统采用混合模式。

没有通用最优架构。选择看任务结构、步骤依赖、可靠性要求和预算。ReAct 灵活但贵，Plan-and-Execute 便宜但适应性低，LATS 质量最高但成本是 ReAct 的 3–5 倍。

    模式 1 · ReAct

    边想边做，
    Observation 回到下一轮思考。

    ReAct（Reasoning + Acting）由 Yao et al. (2022) 提出。LLM 交替进行推理（Thought）和行动（Action），再根据环境反馈（Observation）调整下一步。

    核心循环：Thought 分析当前状态，Action 选择并执行一个工具，Observation 接收结果作为新上下文，重复直到模型认为信息足够并给出 Final Answer。

    为什么不用纯推理（CoT）：CoT 完全依赖模型内部知识，可能幻觉、知识过时，并且一步推理出错后错误会继续传播。ReAct 通过工具调用获取真实、最新的信息，形成“事实锚点”。

    为什么不用纯行动：直接调工具缺少规划、不可解释，也没有反思纠错机制。Thought 步骤提供了显式推理 trace，让决策过程透明、可调试、可审计。

    ReAct Prompt 结构 · 原文模板

    Answer the following questions as best you can. You have access to the following tools:

{tool_descriptions}

Use the following format:

Question: the input question you must answer
Thought: you should always think about what to do
Action: the action to take, should be one of [{tool_names}]
Action Input: the input to the action
Observation: the result of the action
... (this Thought/Action/Observation cycle can repeat N times)
Thought: I now know the final answer
Final Answer: the final answer to the original input question
    展开 ReAct 简化版 Python 实现（原文代码） 
    import re
import anthropic

client = anthropic.Anthropic()

TOOLS = {
    "search": lambda q: web_search(q),
    "calculate": lambda expr: str(eval(expr)),  # 注意：安全警告：生产环境不应使用 eval()，应使用安全的数学解析库（如 numexpr 或 asteval）
}

SYSTEM_PROMPT = """You are a helpful assistant. You can use these tools:
- search: Search the web. Input: search query string.
- calculate: Do math. Input: math expression.

Use this format:
Thought: <your reasoning>
Action: <tool_name>
Action Input: <input>

When you have the final answer:
Thought: I now know the final answer
Final Answer: <answer>
"""

def react_agent(question: str, max_steps: int = 10) -> str:
    """简化版 ReAct Agent"""
    prompt = f"Question: {question}\n"

    for step in range(max_steps):
        response = client.messages.create(
            model="claude-sonnet-4-5-20250929",
            max_tokens=1024,
            system=SYSTEM_PROMPT,
            messages=[{"role": "user", "content": prompt}]
        )
        text = response.content[0].text
        prompt += text + "\n"

        # 检查是否有最终答案
        if "Final Answer:" in text:
            return text.split("Final Answer:")[-1].strip()

        # 解析并执行 Action
        action_match = re.search(r"Action: (\w+)\nAction Input: (.+)", text)
        if action_match:
            tool, tool_input = action_match.groups()
            observation = TOOLS[tool](tool_input.strip())
            prompt += f"Observation: {observation}\n"

    return "达到最大步数限制，未能得出结论。"

    原文代码保留，仅做 HTML 转义；安全警告符号改为文字。原文已标注 eval() 的生产安全风险。

    实际效果：原始论文在 HotpotQA 多跳问答上，ReAct 通过与 Wikipedia API 交互显著超越纯 CoT；在 Fever 事实验证上优于基线；执行轨迹更接近人类的问题解决方式。

    框架支持：LangChain/LangGraph 的 create_react_agent()、CrewAI 的默认范式、Anthropic Claude 的 Tool Use API 都直接支持 ReAct 式交替。

    优势：高度灵活，能根据中间结果调整；每步有显式推理 trace，可解释性强；适合探索性、不确定性高的任务。劣势：每步携带全部上下文，token 消耗高（原文示例：8 步任务可能消耗 50K–100K tokens）；无法并行，步骤严格顺序；可能陷入推理循环。

    模式 2 · Plan-and-Execute

    先想清楚全部步骤，
    再逐步执行。

    Planner 生成完整行动计划，Executor 逐步执行。成本低、结构清晰，但初始计划的质量是瓶颈。

    核心机制：规划阶段一次生成完整计划；执行阶段按 Step 1–4 逐步执行，每一步只处理当前子任务。

    优势：LLM 调用次数少（规划一次 + 每步执行一次，执行可用更小的模型）；成本显著低于 ReAct；强制预先想清楚步骤，减少遗漏；无依赖的步骤可以并行。

    劣势：初始计划错了，后续全错；面对意外难以偏离原计划；需要额外的 Replanning 机制；不适合高度动态、不确定的任务。

    适用场景：结构明确的多步任务，如数据处理流水线、报告生成、自动化测试。

    模式 3 · Proactive

    不等指令，
    先预测下一步需求。

    Proactive Agent 从上下文推断潜在需求，在用户明确要求之前做好准备。核心难点不是“能不能做”，而是“该不该做”。

    Reactive 与 Proactive 的区别：用户说“帮我查明天的天气”，Reactive Agent 查询后回答；用户说“我明天要去上海出差”，Proactive Agent 会自动准备天气、航班、酒店、会议安排等信息。

    三个核心特性：需求预测（从上下文、历史行为、时间地点角色推断）；主动行动（无需明确指令，提前获取资源或预加载数据）；适度性判断（判断何时主动、何时确认，避免过度打扰）。

    Reactive Agent 与 Proactive Agent 的五维对比
    维度Reactive AgentProactive Agent
    触发方式用户指令指令 + 上下文预测
    用户体验明确但需要多步高效但可能意外
    资源消耗按需消耗可能有冗余消耗
    实现复杂度中等高（需预测和适度性判断）
    适用场景任务执行工具陪伴式服务

    关键设计原则：透明化（让用户知道主动做了什么、为什么）、可撤销（结果可轻松取消或忽略）、渐进式（初期保守，随信任增加主动性）、学习性（根据接受/拒绝反馈调整策略）。

    实现模式：置信度阈值分级（>0.9 直接执行，>0.7 询问用户，否则忽略）；异步预加载（后台执行，用户明确请求时直接返回缓存）。

    展开 Proactive Agent 原文代码 
    class ProactiveAgent:
    def __init__(self, llm, tools, user_profile):
        self.llm = llm
        self.tools = tools
        self.user_profile = user_profile  # 用户偏好、历史行为等

    def process(self, user_input: str, context: dict) -> str:
        # 1. 理解用户显式需求
        explicit_needs = self._parse_needs(user_input)

        # 2. 预测潜在需求
        implicit_needs = self._predict_needs(user_input, context)

        # 3. 判断哪些潜在需求值得主动处理
        proactive_actions = []
        for need in implicit_needs:
            if self._should_be_proactive(need):
                proactive_actions.append(need)

        # 4. 执行主动操作（可并行）
        proactive_results = self._execute_proactively(proactive_actions)

        # 5. 组合响应
        response = self._generate_response(
            explicit_needs,
            proactive_results,
            show_what=self._decide_visibility(proactive_actions)
        )
        return response

    def _should_be_proactive(self, need: Need) -> bool:
        """判断是否值得主动处理"""
        criteria = {
            'relevance': need.confidence > 0.8,  # 高相关性
            'cost': need.execution_cost < 0.5,  # 低执行成本
            'privacy': not need.sensitive,       # 不涉及隐私
            'frequency': self.user_profile.likes_proactive,  # 用户喜欢主动服务
        }
        return all(criteria.values())

    原文代码保留，仅做 HTML 转义；省略了 _predict_needs 等辅助方法。

    应用场景：个人助理（出差前准备信息）、客服系统（主动展示文档）、代码助手（加载错误文档）、数据分析师（自动展示相关趋势）。

    模式 4 · LATS

    把行动空间变成树，
    死路就回溯。

    LATS（Language Agent Tree Search）借鉴蒙特卡洛树搜索（MCTS），同时探索多条路径，评估质量，在死胡同时回溯到其他分支。

    核心机制：把 Agent 的行动空间建模为一棵树；并行探索多个分支；评估每条路径；死路回溯；有效分支继续展开，最终收敛到最优路径。

    优势：并行探索多条路径，找到更高质量的解；能回溯，不会被单一错误路径困死；Zhou et al. (2023) 表明 LATS 在多步推理任务上超越 ReAct；适合有多种可行方案需要比较的场景。

    劣势：成本极高，通常是 ReAct 的 3–5 倍；延迟更大；实现复杂度高；对简单任务过度设计。适用场景：复杂推理、代码生成、数学证明、高可靠性关键决策。

    综合对比

    九个维度，
    没有全能选手。

    灵活性、成本、延迟、质量、可解释性、并行、错误恢复和实现难度互相牵制。选型就是按任务取舍。

    ReAct、Plan-and-Execute、Proactive、LATS 九维对比
    维度ReActPlan-and-ExecuteProactiveLATS
    核心思路边想边做想好再做主动预测需求多条路同时探索
    灵活性高低（无 replanning 时）高（主动适应）极高
    成本中高低中（含冗余预测）极高（3–5× ReAct）
    延迟中低低（预加载）高
    结果质量良好结构化任务优秀优秀（用户体验佳）最高
    可解释性强（每步有 Thought）中（有计划但执行不透明）中（需说明主动行为原因）中（有树结构但复杂）
    并行能力无部分（独立步骤）强（预加载并行）强（多分支并行）
    错误恢复动态调整需要显式 replanning需用户反馈调整自动回溯
    实现难度低中中高（需适度性判断）高

    混合模式

    生产系统，
    很少只押一种模式。

    常见组合是 Plan-and-Execute + ReAct：先出粗略计划，再逐步用 ReAct 执行；偏离过大时触发 replanning。

    混合模式 · 原文代码

    # 混合模式：Plan-and-Execute + ReAct
class HybridAgent:
    def run(self, task: str):
        # 阶段 1：用强模型生成粗略计划
        plan = self.planner.generate_plan(task)

        # 阶段 2：用 ReAct 方式逐步执行
        # 每步都可以根据实际情况偏离计划
        results = []
        for step in plan.steps:
            result = self.react_executor.execute_with_reasoning(
                step=step,
                context=results,
                allow_deviation=True  # 允许偏离计划
            )
            results.append(result)

            # 如果偏离过大，触发 replanning
            if result.deviated_significantly:
                plan = self.planner.replan(task, results)

        return self.synthesizer.combine(results)

    四种常见混合策略：ReAct + Reflexion（失败后反思）；Plan-and-Execute + ReAct（先计划再逐步执行）；LATS + Plan-and-Execute（用 LATS 选计划再执行）；分层混合（高层 Plan-and-Execute，低层 ReAct）。

    常见误区 / 面试追问

    三条误区，
    五条追问。

    前三条纠正概念，后五条讨论缺陷、改进、成本取舍和主动式 Agent。答案都来自原文。

    误区 1

    “ReAct 就是 Function Calling。”

    Function Calling 是底层能力（让 LLM 生成结构化的工具调用请求），ReAct 是上层模式（在推理和行动之间交替的决策框架）。ReAct 可以基于 Function Calling 实现，但两者不是一回事。

    误区 2

    “ReAct 是最先进的，应该总是使用。”

    ReAct 适合探索性任务，但对结构明确的任务来说，Plan-and-Execute 更高效、更便宜。没有通用最优架构。

    误区 3

    “Plan-and-Execute 无法处理变化。”

    加入 Replanning 机制后，Plan-and-Execute 也能应对执行中的意外。关键是设计好触发 replan 的条件。

    追问 1

    ReAct 的主要缺陷是什么？

    (1) 高 token 消耗和延迟；(2) 可能陷入推理循环（反复调用同一工具）；(3) 无法并行执行多个独立操作，因为每步都是顺序的。

    追问 2

    如何改进 ReAct？

    (1) 加入 Reflexion 机制让 Agent 从失败中学习；(2) 混合 Plan-and-Execute，先生成粗略计划再 ReAct 执行；(3) 设置最大步数和重复检测来防止死循环。

    追问 3

    如何在成本和质量间取舍？

    从 ReAct 开始建立 baseline，如果质量不够再考虑 LATS。用 Model Routing 对简单任务用 ReAct + 小模型，复杂任务用 LATS + 强模型。

    追问 4

    Proactive Agent 的核心挑战是什么？

    适度性判断：太主动会打扰用户，太保守又失去意义。需要建立反馈循环，学习用户的接受度阈值。

    追问 5

    Gartner 预测 40% 的企业应用将包含 Agent，主流模式是什么？

    混合模式（Planning Preamble + ReAct Execution），因为它在灵活性和成本间取得了最佳平衡。

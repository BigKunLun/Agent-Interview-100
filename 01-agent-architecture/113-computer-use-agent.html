高级 · Agent 架构 · 可交互讲解

给 Agent 一双眼睛，
也给它一双手。

Computer Use Agent 像人一样看屏幕、动鼠标、敲键盘：截图或读 DOM 感知 GUI，多模态模型规划下一步，再用点击、输入、滚动等原子动作操作系统或浏览器。Browser Use Agent 是它的浏览器子集。

关键边界：API 优先，GUI 兜底。API Agent 操作稳定、有 schema 的接口；Computer Use 操作给人设计的界面，没有契约、靠视觉定位，必须逐步校验。本页只做本地教学模拟，不调用真实浏览器或操作系统，不执行真实点击。

    一 · 范式跃迁

    从机器接口，
    到人的界面。

    API Agent 调用的是机器为机器准备的接口；Computer Use Agent 操作的是机器为人准备的界面。这一跃迁扩大了能力边界，也把确定性换成了视觉定位和逐步校验。

    API Agent

    Agent→Function Call→结构化返回

    工具定义有 name、参数 schema 和返回值约定；调用前可静态校验，出错有明确错误码。适合目标系统愿意开放 API 的场景。

    Computer Use Agent

    Agent→看截图 / DOM→规划→点击 / 输入

    没有稳定契约，元素靠视觉位置或 DOM 引用定位；布局变化、异步加载、坐标漂移都会让操作失败，所以每一步都要重新感知和校验。

    API Agent 与 Computer Use Agent 的对比
    维度API AgentComputer Use Agent
    操作对象结构化、稳定的接口为人设计的图形界面
    契约schema 明确，可静态校验无契约，靠坐标或元素引用
    覆盖范围只有开放 API 的系统任何带界面的软件，包括遗留系统和桌面应用
    成本低，一次调用拿到结果高，每步截图 + 多模态推理 + 再截图
    可靠性确定性较强受动态界面、时序和误点击影响
    选型优先没有 API 时的兜底

    一句话总结

    API Agent 操作的是“机器为机器准备的接口”，Computer Use Agent 操作的是“机器为人准备的界面”。能用 API 就不要用 Computer Use。

    二 · 感知层

    截图、DOM，
    还是编号标记。

    感知层是 Computer Use Agent 与 API Agent 最大的分水岭。原文把主流路线分成三条：纯视觉、结构化、混合。

    三条感知路线对比
    感知方式原理优势劣势代表方案
    纯视觉（Screenshot + VLM）截图喂给多模态模型，模型直接输出坐标通用，能处理任意 GUI（桌面应用、Canvas、远程虚拟桌面）定位精度依赖模型，坐标易漂移，图片 token 成本高Claude Computer Use、OpenAI CUA
    结构化（DOM / Accessibility Tree）读取网页 DOM 或无障碍树，拿到元素 id、role、text定位精准、可点元素有唯一引用，token 省只能用于 Web 或有 a11y 暴露的应用，动态渲染难Browser Use、WebArena 系列
    混合（Visual + Set-of-Mark）截图叠加编号标签，模型选编号而非坐标兼顾视觉泛化与定位精度需要预处理标注步骤SeeAct、部分 Browser Use 模式

    Set-of-Mark：把坐标回归降成编号选择

    先用检测模型给截图中每个可交互元素打上数字编号（[1] [2] [3]…），模型只需回答“点 3 号”。这把“输出精确坐标”的难题换成了“从有限编号里选一个”，大幅降低定位误差。纯视觉方案后来也常借鉴这一思路提升精度。

    本页互动区使用的 [1]–[4] 编号，就是 Set-of-Mark 的教学模拟；它们不是真实检测模型的输出。

    三 · 决策层

    把“点登录”，
    落到具体位置。

    决策层负责把自然语言意图映射成可执行动作，核心是 Grounding（视觉接地）：把“登录按钮”这个语义概念锚定到界面上的具体坐标、selector 或编号。

    四步落地

    意图层：“我要登录” → 目标识别：找到标着 Login / 登录的可点击元素 → Grounding：纯视觉输出坐标，DOM 输出 selector，SoM 输出编号 → 动作生成：click(842, 310) 或 click [3]。

    决策通常不是一次性的，而是 Observe-Think-Act 的 ReAct 循环：模型每一步先描述看到了什么，再决定下一步做什么；遇到歧义还会自我提问，例如“这里有两个 Login 按钮，该选导航栏的还是表单里的？”。

    这与普通 Agent 的 ReAct 循环同构，区别只在“观察”的来源：从工具返回值变成了截图或 DOM。

    四 · 执行层

    原子动作，
    逐拍可校验。

    动作空间是一组原子操作。原子化的价值不在于动作本身，而在于每一步都能单独校验、回放和回滚。

    click(x, y)            # 左键单击
double_click(x, y)
right_click(x, y)
type(text)             # 在焦点元素输入文字
key("Return")          # 按键 / 组合键 ctrl+c
scroll(direction, amt) # 滚动
mouse_move(x, y)
drag(x1,y1, x2,y2)     # 拖拽
screenshot()           # 主动截屏（重新感知）
wait(seconds)          # 等待加载

    整个执行过程是一个隐式状态机：每个动作改变环境状态，Agent 重新感知后判断是否进入期望状态，未达预期则触发修复分支。这与“一段宏脚本一口气跑完”的早期 RPA 思路本质不同：后者中间出错就全线崩溃，前者允许逐步校验与自我修复。

    五 · 架构总览

    感知、规划、执行，
    再回到感知。

    Computer Use Agent 的核心是一个闭环：执行后必须重新感知并校验子目标。未达成则修复或回溯，再进入下一轮感知。

    感知截图 / DOM
    规划ReAct 决策下一步
    执行click / type / scroll
    校验子目标达成？
    完成 / 放弃达成或到达步数上限
    感知 → 规划 → 执行 → 校验
    ↺未达成：修复 / 回溯 → 重新感知，再走一轮；这条回边是本图的关键，不是一次执行就结束。

    校验环节是 Computer Use Agent 区别于“盲操作脚本”的关键：每一步执行后都要重新感知界面，确认操作生效——按钮真的按下去了？页面真的跳转了？没有校验的 GUI 自动化，本质上是脆弱的录制回放，稍有界面变化就崩。

    六 · 可靠性

    界面不确定，
    就要逐步断言。

    GUI 的不确定性是落地的最大障碍。原文列出五类挑战，工程上用“先断言再操作”（assert-before-act）兜底。

    01 · 时序

    动态界面与时序问题

    元素异步加载，点击时按钮可能还没渲染完。要显式等待条件（“等到登录按钮可见再点”），而不是固定 sleep。

    02 · 旧画面

    加载等待

    网络抖动会让截图停留在旧画面，Agent 在过期状态上决策。需要加载完成检测，否则会点到已经不存在的元素。

    03 · 不可逆

    误点击与误操作

    坐标漂移可能点到广告、删除或转账按钮，且动作不可逆。这是安全红线，需要人工确认或沙箱限制。

    04 · 回退

    回溯与自我修复

    走错路后要能识别并退回。成熟方案维护“操作栈 + 检查点”，结合 DOM diff 或截图对比判断状态变化，必要时回退到上一个检查点。

    05 · 合规

    验证码与人机校验

    很多站点主动识别并拦截自动化访问，这是合规与反爬的灰色地带，生产方案通常在此处转人工。

    assert-before-act

    每一步执行前先验证前置条件（目标元素存在、可见、可点），执行后验证后置条件（页面状态如期变化）。任一不满足就暂停或转 HITL（human-in-the-loop，人工介入）。

    七 · 方案对比

    按目标系统，
    选感知路线。

    需要操作桌面应用或远程系统，选纯视觉；只在浏览器内且追求精准高效，选 DOM 或混合方案。原文还特别澄清了产品命名。

    八 · 代码示例

    截图、决策、执行，
    再截一张。

    以 Anthropic Computer Use API 风格为例，核心是“截图—让模型决策—执行—再截图”的循环。执行函数的返回值是一张新截图，这就是闭环在代码里的落点。

    展开原文伪代码：Computer Use Agent 主循环 
    def computer_use_loop(task: str, max_steps: int = 50):
    """Computer Use Agent 的感知-决策-执行-校验主循环"""
    messages = [{"role": "user", "content": task}]
    for step in range(max_steps):
        # 1. 调用模型，传入 computer 工具定义（工具类型版本以官方文档为准）
        response = client.messages.create(
            model="claude-sonnet-5",
            tools=[{
                "type": "computer",          # Anthropic computer-use 工具
                "name": "computer",
                "display_width_px": 1280,
                "display_height_px": 800,
            }],
            messages=messages,
        )
        messages.append({"role": "assistant", "content": response.content})

        # 2. 没有工具调用 = 模型认为任务完成
        if response.stop_reason == "end_turn":
            return "done"

        # 3. 执行工具返回的动作，并把结果（通常是新截图）回传
        for block in response.content:
            if block.type == "tool_use":
                action = block.input          # {"action": "click", "coordinate": [842, 310]}
                result = execute_action(action)   # 真正去 click / type / screenshot
                messages.append({
                    "role": "user",
                    "content": [{"type": "tool_result",
                                 "tool_use_id": block.id,
                                 "content": result}],  # 下一轮感知的输入
                })


def execute_action(action: dict):
    """把模型输出的高层动作映射到底层执行，并返回新截图"""
    act = action["action"]
    if act == "click":
        pyautogui.click(*action["coordinate"])
    elif act == "type":
        pyautogui.typewrite(action["text"])
    elif act == "scroll":
        scroll_page(action["direction"])
    elif act == "key":
        pyautogui.hotkey(*action["key"].split("+"))
    elif act == "wait":
        time.sleep(action.get("duration", 2))
    # 关键：操作后返回新截图，供下一轮感知形成闭环
    return capture_screenshot()

    execute_action 的返回值是一张新截图：动作改变画面，画面反馈给模型，形成闭环。这就是架构图中“校验 → 感知”回路在代码层面的体现。

    常见误区 / 面试追问

    API 优先，
    GUI 兜底。

    两条误区和三条追问，覆盖取代论、视觉 vs DOM、评估基准、误操作防护与成本延迟。

    误区 1

    “Computer Use 是 API Agent 的升级版，能取代 API Agent。”

    恰恰相反，能用 API 就不要用 Computer Use。API Agent 的确定性、成本、速度、可审计性都远优于 GUI 操作。Computer Use 是“没有 API 时的最后手段”，适用于遗留系统、闭源软件、必须人类界面交互的场景。

    误区 2

    “纯视觉方案比 DOM 方案更先进。”

    两者各有适用域。纯视觉能处理任意 GUI，但定位精度和 token 成本吃亏；DOM 在 Web 内精准高效，但碰到 Canvas、图片或桌面应用就失效。生产中常按目标系统选型，甚至 Web 走 DOM、桌面走视觉，不存在“谁取代谁”。

    追问 1

    如何评估一个 Computer Use Agent？

    OSWorld 测真实操作系统上的多模态 Agent 任务（原文称 369 个任务，覆盖 Ubuntu / Windows / macOS 多类应用），整体分数偏低，是公认最难的 GUI Agent 基准之一；WebArena / VisualWebArena 专注浏览器；WebVoyager 是常见实测基准。除成功率外，还要看平均步数（效率）、回溯次数（鲁棒性）、token 成本（经济性）。务必警惕静态 benchmark gaming：高分不等于在你的目标系统上可靠，最终要真实环境回归。

    追问 2

    如何防止误操作？

    分层叠加：（1）沙箱隔离——容器 / 虚拟机里运行，限制文件、网络、进程；（2）权限最小化——只给完成任务所需的最小权限，敏感目录只读；（3）破坏性操作确认（HITL 卡点）——删除、转账、提交订单等不可逆动作必须人工确认；（4）全链路操作日志——每步截图 + 动作，可回放可追责；（5）预算上限——限制最大步数与成本，避免死循环烧钱。

    追问 3

    Computer Use 的成本和延迟怎么样？

    显著高于 API Agent。每一步都要截图（一张图几百到上千 token）+ 多模态推理 + 执行 + 再截图，单任务动辄几十轮。原文举例：一个订票任务可能消耗数万 token、耗时数分钟。这决定了它不适合高频、对延迟敏感的在线场景，更适合异步、批处理、人工发起的任务。

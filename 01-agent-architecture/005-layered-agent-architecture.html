中级 · Agent 架构 · 可交互讲解

一个指挥，
一组并行干活的 Worker。

分层 Agent 架构（Orchestrator-Worker 模式）把复杂任务分成“指挥”和“执行”两层。Orchestrator 理解目标、分解任务、分配工作、综合结果；Worker 是专业化的子 Agent，各自擅长特定领域。

子任务的数量和类型取决于输入，而不是预定义流程。这是它和固定 Prompt Chaining 或工具路由的根本区别。代价是 Orchestrator 可能成为瓶颈和单点故障。

    一、模式定义

    集中式任务管理：
    一个 Orchestrator，多个 Worker。

    Orchestrator 保持全局视野，把复杂问题分解为子任务，交给专业化 Worker 执行，再把局部结果综合成完整方案。

    与固定的 Prompt Chaining 或工具路由不同，Orchestrator-Worker 的假设是：子任务的数量和类型取决于输入的特性，而非预定义的流程。

    “分层”指职责分层，不一定是模型分层：Orchestrator 通常用强模型做规划和综合，Worker 可以用更小、更便宜的模型，因为每个 Worker 只需在特定领域表现好。

    二、核心架构

    分配下去，
    再并行回传。

    Orchestrator 向三个 Worker 分配子任务；Worker 独立执行，结果回传；Orchestrator 负责进度和综合。

    三、Orchestrator 职责

    理解、分解、分配、
    追踪、综合、调整。

    六项职责里，动态调整最关键：根据中间结果决定继续分解、重新分配还是结束。

    1. 任务理解：解析用户的高层目标。
    2. 任务分解：将目标拆解为具体的子任务。
    3. 任务分配：根据 Worker 的能力选择最合适的 Worker。
    4. 进度追踪：监控各 Worker 的执行状态。
    5. 结果综合：将各 Worker 的结果整合为最终输出。
    6. 动态调整：根据中间结果决定下一步——继续分解、重新分配，还是结束。

    Orchestrator · 原文代码

    class Orchestrator:
    def __init__(self, workers: dict[str, Worker], llm):
        self.workers = workers  # {"search": SearchWorker, "analyze": AnalyzeWorker, ...}
        self.llm = llm

    def run(self, task: str) -> str:
        # 1. 分解任务
        subtasks = self._decompose(task)
        results = {}

        while subtasks:
            # 2. 分配可并行执行的任务
            batch = self._get_parallel_batch(subtasks)

            # 3. 并行执行
            for subtask in batch:
                worker = self._select_worker(subtask)
                results[subtask.id] = worker.execute(subtask)

            # 4. 根据结果动态决定下一步
            subtasks = self._replan_if_needed(task, results)

        # 5. 综合结果
        return self._synthesize(task, results)

    def _select_worker(self, subtask: SubTask) -> Worker:
        """根据子任务类型选择合适的 Worker"""
        return self.workers[subtask.required_skill]

    注意：原文的 for 循环是顺序调用。要真正让同一批 Worker 并行，需要把执行改成并发（如 asyncio.gather），否则拓扑上是分支，执行上仍是串行。

    四、Worker 设计原则

    每个 Worker 只擅长
    一个领域。

    Worker 是专业化的 Agent，具备特定领域的工具和系统提示。Worker 内部可以再用 ReAct 自主完成子任务。

    SearchWorker 与 AnalyzeWorker · 原文代码

    class SearchWorker(Worker):
    """专门负责信息检索的 Worker"""
    def __init__(self):
        self.tools = [web_search, database_query, document_retrieval]
        self.system_prompt = "你是信息检索专家，负责查找和整理相关信息。"

    def execute(self, subtask: SubTask) -> WorkerResult:
        # Worker 内部可以使用 ReAct 模式自主完成子任务
        agent = ReactAgent(
            llm=self.llm,  # 可以用更小、更便宜的模型
            tools=self.tools,
            system_prompt=self.system_prompt
        )
        return agent.run(subtask.description)

class AnalyzeWorker(Worker):
    """专门负责数据分析的 Worker"""
    def __init__(self):
        self.tools = [calculator, chart_generator, statistics_engine]
        self.system_prompt = "你是数据分析专家，负责处理和分析数据。"

    设计要点：单一职责（只做一类子任务）、工具集收敛（只暴露完成该领域需要的工具）、接口一致（输入子任务，输出结构化结果）、模型可替换（小模型能胜任就不上强模型）。

    五、层次化架构

    超复杂任务，
    把模式递归一层。

    每个中层节点既是上层的 Worker，又是下层的 Orchestrator。适合企业级多团队协作。

    class HierarchicalOrchestrator(Orchestrator):
    """递归的层次化编排器"""
    def _select_worker(self, subtask: SubTask) -> Worker:
        if subtask.complexity > THRESHOLD:
            # 复杂子任务交给子 Orchestrator 进一步分解
            return SubOrchestrator(workers=self._get_sub_workers(subtask))
        else:
            # 简单子任务直接交给 Worker 执行
            return self.workers[subtask.required_skill]

    六、与其他多 Agent 模式对比

    集中、链式、平等、
    共享黑板。

    四种模式的协调方式不同。Orchestrator-Worker 适合问题结构在运行时才涌现的任务。

    四种多 Agent 模式的特点与适用场景
    模式特点适用场景
    Orchestrator-Worker集中控制，动态分解问题结构在运行时涌现
    Pipeline固定顺序，前一步输出是后一步输入结构确定的顺序处理
    Peer-to-PeerAgent 间平等通信，无中心协商、辩论、头脑风暴
    Blackboard共享状态空间，Agent 自主读写知识密集型协作

    七、关键考量

    模型、路由、容错、状态，
    四件事先想清楚。

    Orchestrator 用强模型，Worker 可用小模型；路由可以静态或动态；失败要能重分配；状态要分层管理。

    1. 模型选择：Orchestrator 需要强大的规划和推理能力，通常使用前沿模型（如 Claude Opus、GPT-4o）；Worker 可以使用更小、更便宜的模型（如 Claude Haiku、GPT-4o-mini）。

    2. 任务分配策略：静态路由基于规则（subtask.type == "search"）；动态路由让 LLM 根据子任务和 Worker 描述选择。

    # 静态路由：基于规则
if subtask.type == "search":
    return search_worker
elif subtask.type == "code":
    return code_worker

# 动态路由：让 LLM 选择
worker_selection = llm.generate(
    f"Given subtask '{subtask}' and available workers {worker_descriptions}, "
    f"which worker is most suitable?"
)

    3. 错误处理与容错：Worker 失败时，Orchestrator 应能检测并重新分配任务；设置 Worker 的超时和最大重试次数；某个 Worker 持续失败时，考虑降级或换用替代方案。

    4. 状态管理：Orchestrator 维护全局状态（所有子任务的进度和结果）；Worker 维护局部状态（自己的执行上下文）；考虑事件驱动架构使系统异步化，提高容错性。

    八、实际案例

    市场研究报告：
    两波并行，一次综合。

    S1、S2 互不依赖，第一波并行；S3、S4 依赖前两者，第二波并行；S5 依赖全部，最后执行。

    Orchestrator 分解：S1 → SearchWorker 搜索市场规模；S2 → SearchWorker 搜索主要玩家和竞争格局；S3 → AnalyzeWorker 分析增长趋势；S4 → AnalyzeWorker 做 SWOT；S5 → WriterWorker 综合生成报告。

    执行流程：① S1 和 S2 并行；② S3 和 S4 在 S1/S2 完成后并行；③ S5 依赖所有前置任务，最后执行。

    这个案例也说明了分层的价值：批次之间是依赖关系，批次内部可以并行。Orchestrator 只需要管批次和依赖，不需要亲自做搜索或分析。

    常见误区 / 面试追问

    两条误区，
    两条追问。

    前两条纠正“层数”和“Orchestrator 必须是 LLM”的误解，后两条讨论微服务类比和单点故障。

    误区 1

    “越多层越好。”

    每增加一层都引入协调开销、延迟和成本。应使用满足需求的最简架构。如果单个 ReAct Agent 能完成任务，不要引入 Orchestrator-Worker。

    误区 2

    “Orchestrator 必须是 LLM。”

    对于结构确定的任务，Orchestrator 可以是确定性代码（if-else 路由、DAG 引擎），不必每次都调用 LLM。只有当任务分解需要理解自然语言语义时，才需要 LLM 做 Orchestrator。

    追问 1

    Orchestrator-Worker 和微服务架构有什么关系？

    概念类似：Orchestrator 像 API Gateway + 业务编排层，Worker 像独立微服务。可以借鉴微服务的设计原则：单一职责、松耦合、独立部署、容错机制。

    追问 2

    如何避免 Orchestrator 成为单点故障？

    (1) Orchestrator 本身做无状态设计，状态存外部存储；(2) 设置 Orchestrator 超时，支持任务恢复；(3) 对关键任务可以引入多个 Orchestrator 做冗余。

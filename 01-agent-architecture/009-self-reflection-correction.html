高级 · Agent 架构 · 可交互讲解

失败之后，
把反馈变成下一轮的输入。

Agent 自我反思的核心框架是 Reflexion（Shinn et al., 2023）：把环境反馈转化为语言化的自我反思，存入长期记忆，供下一轮迭代参考——本质上是一种“语言化的强化学习”。

关键不在“反思”二字，而在反馈从哪来。有外部信号（测试结果、评估分数、工具返回值）时，反思才真正有效；没有外部反馈的纯内省，可能把正确答案改错。

    一、为什么需要反思

    失败后只是重试，
    等于没有学习。

    传统 Agent 失败后通常简单重试，不会从失败中学习。反思赋予 Agent“元认知”：回顾表现、识别原因、生成改进建议，并在后续尝试中应用。

    类比人类学习：无反思是“做错题 → 重做一遍 → 可能还是错”；有反思是“做错题 → 分析为什么错 → 总结规律 → 下次避免同类错误”。

    反思不是把错误藏起来，而是把错误变成下一次尝试的显式输入。

    二、Reflexion 框架

    用语言反馈，
    代替梯度更新。

    Reflexion 是最有影响力的 Agent 自我反思框架。三个核心组件：Actor 执行、Evaluator 评估、Self-Reflect 生成反思；反思存入长期记忆，下一轮重新执行。

    Reflexion 执行流程 · 原文代码

    class ReflexionAgent:
    def __init__(self, actor_llm, evaluator, reflector_llm):
        self.actor = actor_llm
        self.evaluator = evaluator
        self.reflector = reflector_llm
        self.memory = []  # 长期反思记忆

    def run(self, task: str, max_trials: int = 3) -> str:
        for trial in range(max_trials):
            # 1. Actor 执行任务（带上历史反思作为上下文）
            trajectory = self.actor.execute(
                task=task,
                past_reflections=self.memory
            )

            # 2. Evaluator 评估结果
            score, feedback = self.evaluator.evaluate(task, trajectory)

            if score >= THRESHOLD:
                return trajectory.final_answer

            # 3. Self-Reflect 生成反思
            reflection = self.reflector.generate(
                f"任务: {task}\n"
                f"你的执行轨迹: {trajectory}\n"
                f"评估反馈: {feedback}\n"
                f"分析你的错误原因，总结改进策略。"
            )

            # 4. 存入记忆
            self.memory.append(reflection)

        return trajectory.final_answer  # 返回最后一次尝试的结果

    实验结果：AlfWorld 顺序决策任务上，ReAct + Reflexion 完成 130/134 个任务，显著优于纯 ReAct；HumanEval / MBPP 代码生成上超越先前 SOTA；LeetCode Hard 上展现出从失败中学习的能力。

    三、多种反思模式

    内置循环、双 Agent、
    基于测试的自我纠正。

    不是所有反思都要上 Reflexion。按场景可以选择单 Agent 自审、Generator + Critic 双 Agent，或基于测试结果的 Self-Debug。

    模式 1：内置反思循环

    Agent 完成初稿后自我审查，列出问题，再修订。实现简单，但审查依据仍然来自模型自己。

    # Agent 完成初稿后自我审查
draft = agent.generate(task)
critique = agent.reflect(
    f"审查你的输出：\n{draft}\n"
    f"列出可能的问题、遗漏或改进点。"
)
final = agent.revise(draft, critique)

    模式 2：双 Agent 反思（Andrew Ng 推荐）

    一个生成，一个批评，职责分离，避免同一个模型既当运动员又当裁判。

    # Generator Agent + Critic Agent
generator = Agent(system_prompt="生成高质量的代码实现")
critic = Agent(system_prompt="你是严格的代码审查者，找出所有问题")

output = generator.run(task)
for round in range(max_rounds):
    criticism = critic.review(output)
    if criticism.no_issues:
        break
    output = generator.revise(output, criticism)

    模式 3：基于测试的自我纠正（Self-Debug）

    特别适合代码生成：测试结果是外部信号，失败信息直接反馈给模型修复。

    def self_debug_loop(task: str, max_attempts: int = 3) -> str:
    code = llm.generate_code(task)
    for attempt in range(max_attempts):
        test_result = run_tests(code)
        if test_result.all_passed:
            return code
        # 将错误信息反馈给 LLM，让它修复
        code = llm.debug(
            f"代码:\n{code}\n"
            f"测试失败:\n{test_result.errors}\n"
            f"修复这些问题。"
        )
    return code

    四、关键争议

    LLM 能真正
    自我纠正推理吗？

    Huang et al. (2023)《Large Language Models Cannot Self-Correct Reasoning Yet》指出：没有外部反馈时，自我纠正可能把正确答案改错。

    核心结论：没有外部反馈时，LLM 的“自我纠正”可能反而把正确答案改错；有外部反馈（测试结果、搜索结果）时，自我纠正才真正有效。

    关键区分：“intrinsic self-correction”（纯内省）与“extrinsic self-correction”（基于外部信号）不是一回事。

    实践建议：不要依赖 LLM 凭空反思。确保反思环节有外部信号输入——测试结果、评估分数、工具返回值、人工反馈。Reflexion 的效果来源于 Evaluator，不是 LLM 凭空反思。

    长程任务的边界

    任务越长，上下文越膨胀，Agent 可能基于含错状态做自评，把错误“自我确认”并继续传播。LongHorizon-Harness（2026）把校验从主 Agent 拆出去：交给一个独立的、只读环境的 Auditor，状态只接受环境已验证的事实，模型自己的断言不入状态。WeaveBench 上 51.8% → 80.7%。

    五、三个概念的区别

    评估、反思、纠正，
    不是同义词。

    三者互补：先 Self-Evaluation 发现问题，再 Self-Reflection 分析原因，最后 Self-Correction 修复问题。

    Self-Reflection、Self-Correction、Self-Evaluation 的定义与实现
    概念定义实现
    Self-ReflectionAgent 回顾执行过程，生成语言化的经验总结Reflexion 框架
    Self-CorrectionAgent 检测并修复输出中的错误Self-Debug、Self-Refine
    Self-EvaluationAgent 评估自己输出的质量Self-RAG、LLM-as-Judge

    反思生成的是“经验”，纠正生成的是“修好的输出”，评估生成的是“质量判断”。把三者混为一谈，容易做出只有反思、没有修复的无效循环。

    常见误区 / 面试追问

    两条误区，
    六条追问。

    前两条纠正“反思万能”和“轮次越多越好”，后六条讨论记忆管理、失败分类、过度反思、修复引入新 bug、反思效率和长程失效。

    误区 1

    “让 LLM 反思就能提升效果。”

    无外部信号的纯内省可能适得其反。Reflexion 的效果来源于环境反馈（Evaluator），不是 LLM 凭空反思。

    误区 2

    “反思越多轮越好。”

    过多反思轮次增加成本且可能引入过度修正。通常 2–3 轮反思就够，设置反思轮次上限。

    追问 1

    Reflexion 的记忆如何管理？

    论文使用滑动窗口保留最近的反思。生产中可用向量数据库存储，按相关性检索历史反思。

    追问 2

    如何区分“值得反思的失败”和“不可恢复的失败”？

    工具不存在、权限不足等结构性问题不需要反思，直接报错。逻辑错误、策略选择错误才适合反思。结合错误分类（详见第 006 题《Agent Loop 设计与错误恢复》中的错误分类与路由章节）来决定。

    追问 3

    Agent 反思后反而把正确答案改错了，用户说“你之前是对的，为什么要改”，怎么防止？

    这是“过度反思”问题。解决路径：(1) 加入置信度阈值，初始答案很有信心时跳过反思；(2) 反思后对比新旧答案，差异过大需要理由说明；(3) 用另一个 LLM 评估反思是否合理；(4) 限制反思轮次，通常 1–2 轮足够；(5) 用户反馈“改错了”时记录为负面样本，训练模型识别何时不应反思。

    追问 4

    代码生成 Agent 反复修复但每次都有新 bug，测试通过率始终低于 30%，怎么优化？

    这是“修复引入新错误”问题。优化路径：(1) 测试驱动修复，先看失败原因再改；(2) 局部修改，只改与失败测试相关的代码段；(3) 反思和修复用更强的模型，生成和验证用不同模型；(4) 增量验证，每次修复后只跑相关测试子集；(5) 连续修复失败时转人工介入。

    追问 5

    反思轮次过多，用户等待超过 30 秒，如何提升响应速度？

    (1) 并行化反思，主任务执行时后台预判问题；(2) 缓存相似查询的反思结果；(3) 设置单次反思时间预算；(4) 快速反思用小模型扫描，必要时再用大模型深度分析；(5) 流式输出，先给初步答案，后台反思后再更新。

    追问 6

    自我反思在长程任务里为什么会失效？

    因为自评的依据正是那份可能已经出错的上下文。任务越长上下文越膨胀，Agent 基于含错状态做自评，等于把错误“自我确认”下来并继续传播——不是反思轮数不够，而是反馈来源根本不独立。解法是把校验拆出去，交给独立的、只读环境的 Auditor，状态只接受环境已验证的事实（LongHorizon-Harness，2026；WeaveBench 51.8% → 80.7%）。
